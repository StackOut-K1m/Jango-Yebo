## 표본

**직접 수집(촬영)은 하지 않는다.** 공개 데이터 + 합성으로만 구성하고, 그로 인해 잃는 것(실제 폰 촬영
분포, 실제 POS 벤더 레이아웃)은 결과 보고에 한계로 명시한다.

| 폴더 | 내용 | 출처 | 용도 |
| --- | --- | --- | --- |
| `datasets/receipts/korie/train/` | 한국 소매 영수증 | **KORIE** (아래 참고) | 컨버터 디버깅 |

KORIE 와 합성판 성능을 **섞어서 평균내지 않는다** — 벤치마크(KORIE test) / 강건성(열화 합성) / POS(합성) 를
따로 보고한다. **시연에는 KORIE 이미지를 쓰지 않는다** — 라이선스가 표기되지 않은 데이터라 내부 평가용으로만
두고, 화면에 띄우는 것은 우리가 만든 합성 이미지로 한다.

### 라벨 형식 (고정)

이미지와 같은 이름의 `.json`. 스키마는 [`labels.py`](./labels.py) `LabelRecord` —
`extraction` 은 계약 스키마(`EvidenceExtraction`)와 같은 필드, `meta.unlabeledFields` 는
원천에 정답이 없는 필드(평가에서 "틀림"이 아니라 "판정 불가"). 라벨 형식을 바꾸면 이전 측정이 무효가 된다.

```json
{
  "image": "korie-test-IMG00632.png",
  "evidenceType": "RECEIPT",
  "extraction": { "supplierName": "...", "issuedDate": "2023-05-04", "totalAmount": 7400, "items": [ ... ] },
  "meta": { "source": "korie", "sourceId": "IMG00632", "split": "test",
            "unlabeledFields": ["supplierBusinessNo", "items.unit"], "notes": [] }
}
```

### KORIE 변환

KORIE(*Mathematics* 2026, 14(1):187 — 한국 소매 영수증 748장(공개판 774장), 탐지·OCR·IE 라벨)는
[GitHub README](https://github.com/MahmoudSalah/KORIE)의 Google Drive 링크로만 배포된다.
**라이선스가 표기되어 있지 않다** — 평가용으로만 쓰고 레포에 올리지 않으며(`datasets/` 는 .gitignore),
문서에 출처를 적는다.

**세 트랙을 영수증 ID 로 합쳐야 라벨이 완성된다** (2026-09-07 실측):

| 트랙 | 파일 | 내용 | 우리가 쓰는 것 |
| --- | --- | --- | --- |
| IE | `items_{train,val,test}.csv` | **품목 행만** — `image_name, Item_Name, Number of units, Price, Total Price …`. `Item_Name` 은 영수증 한 줄 전체(`005 청피망 1봉, 23000476, 4,990, 1, 4,990 #`) | 레코드·분할의 기준. 상품명은 `clean_item_name` 으로 정제 |
| OCR | `<IMG>_<Entity>.jpg` + `.txt` | 영수증 단위 필드 **텍스트 전사** — `Total`·`TotalTax`·`Subtotal`·`TransactionDate`·`PaymentDate`·`MerchantName` 등 (엔티티당 crop 1개) | 상호명·날짜·합계·부가세 정답. 분할 무관하게 병합 |
| Detection | `{train,val,test}/images/*.png` + YOLO `labels/*.txt` | 원본 이미지 774장 + 17 클래스 박스(텍스트 없음) | 이미지. 클래스 순서는 README 의 17개 순서와 일치 |

세 트랙의 분할은 **서로 다른 분할**이다 — IE val 360장 중 Detection val.zip 에 이미지가 있는 것은 72장뿐이라
Detection 세 zip 을 모두 받아야 IE val 전체(360장)에 이미지가 붙는다. 병합 결과(val): 이미지 360/360,
날짜 358, 총액 350, 부가세 300, 상호명 332, 품목 360. **사업자등록번호는 어느 트랙에도 없다.**

**품목 라벨은 부분 라벨이다.** IE CSV 는 영수증당 평균 1.6 행(val 577행/360장)만 담고 있고, 실제 영수증에는
그보다 많은 행이 있다(예: `IMG00001` 은 메뉴 3줄 중 1줄만 라벨). 그래서 KORIE 에서는 품목 **재현율**만 보고,
정밀도·환각률은 라벨이 완전한 합성 POS·CORD 에서 잰다 — 컨버터가 `meta.extra.itemsComplete = false` 로 표시하고
채점기가 그 영수증의 "예측에만 있는 행"을 환각으로 세지 않는다.

**Drive 파일명 함정** — Detection·OCR 의 val 파일이 둘 다 `val.zip` 이다. `-O` 로 이름을 명시하지 않으면
덮어쓴다.

test 분할을 평가할 때만 `items_test.csv`(IE test, [107ckPQ5…](https://drive.google.com/file/d/107ckPQ59gda7172Ls_iiEg5JomWhLtVA/view))를 받는다.

**분할 규칙 — 가장 중요하다.** 모델을 학습시키지 않아도 프롬프트·스키마·검산·후처리를 계속 고치므로
시스템이 데이터에 맞춰진다. 그래서 `train` = 컨버터 디버깅, `val` = 개발(빠른 반복은 val 안의 고정
50장 dev subset), **`test` = 모든 설정을 freeze 한 뒤 최종 측정 1회.** test 의 실패 케이스를 들여다보는
것도 오염이다. 공개판의 분할을 그대로 쓴다 — **공개판 test 는 359장**(val 360, train 55. 논문의 60/20/20
과 다르다. 2026-09-08 `items_test.csv` 변환 실측: 날짜 357·총액 349·부가세 310·품목 359). 샘플링하지
않는다. 장당 ≈ $0.04 이므로 최종 1회에 약 $14 가 든다.

```powershell
# 1) Drive 에서 IE 분할(items_train/val/test.csv)과 이미지를 내려받아 datasets/korie/raw/ 에 푼다
# 2) 형식 감지·필드 커버리지 확인 (CSV 헤더가 그대로 출력된다 — 매핑 확인용)
uv run --frozen python -X utf8 -m experiments.convert_korie datasets/korie/raw --split val --dry-run
# 3) 변환 → datasets/receipts/korie/val/ (+ manifest.json)
uv run --frozen python -X utf8 -m experiments.convert_korie datasets/korie/raw --split val --source-commit <sha>
# 4) freeze 후 최종 1회
uv run --frozen python -X utf8 -m experiments.convert_korie datasets/korie/raw --split test --source-commit <sha>
```

변환 규칙: `MerchantName→supplierName`, `TransactionDate→issuedDate`, `Total→totalAmount`,
`TotalTax→vatAmount`(기본 매핑, manifest 에 가정으로 기록), `Item/Quantity/Price/TotalPrice→items[]`.
**`Subtotal→supplyAmount` 는 기본 미매핑**이다 — 한국 영수증은 과세/면세·"공급가액"·"과세물품" 표기가
상점마다 달라 변환 가정이 정답을 오염시킬 수 있다. 샘플 30~50장을 눈으로 확인한 뒤 `--map-subtotal`
을 켠다(그때도 `Subtotal + TotalTax == Total` 인 경우에만 매핑). **사업자등록번호·품목 단위는 KORIE 에
없다** → `unlabeledFields`. 형식을 인식하지 못하면 첫 레코드의 키(CSV 는 헤더)를 출력하고 종료 코드 2.

`manifest.json` 에 소스 커밋·변환 일시·분할·라벨 파일 sha256·장수·변환 가정이 남는다. 결과 보고에는
"KORIE 150장"이 아니라 이 manifest(커밋·분할·장수)를 인용한다 — 논문 748장과 README 774장이 다르듯
공개판이 바뀔 수 있다.

**사업자번호 추가 라벨(50장)** 은 사업자번호가 보이는 영수증만 골라 만들지 않는다. present / absent /
unreadable 을 자연 분포로 두고(`meta.unreadableFields`), 평가는 **exact match 가 주 지표**, 체크섬
통과율은 후처리 검증 지표로 따로 본다 — 틀리게 읽은 번호도 체크섬을 통과할 수 있다.

## 실행 흐름

```powershell
# 1) KORIE val 변환 (test 는 freeze 후)
uv run --frozen python -X utf8 -m experiments.convert_korie datasets/korie/raw --split val --source-commit <sha>
# 2) 키 없이 흐름 확인 → 실제 평가 (예측은 artifacts/eval/<run>/predictions/ 에 저장·재개)
#    유료 실행은 한 번에 하나씩, 먼저 --limit 20 소표본으로. 실행당 예산 상한은 --budget-usd (기본 $3, 닿으면 멈춤)
#    토큰 0 개발 경로: --pipeline local (사용자 PC 의 Ollama). 정확도 낮음, 최종 수치는 --pipeline vlm(Claude)
uv run --frozen python -X utf8 -m experiments.evaluate_evidence datasets/receipts/korie/val --out artifacts/eval/local-001 --limit 20 --pipeline local
uv run --frozen python -X utf8 -m experiments.evaluate_evidence datasets/receipts/korie/val --out artifacts/eval/smoke --pipeline stub
uv run --frozen python -X utf8 -m experiments.evaluate_evidence datasets/receipts/korie/val --out artifacts/eval/val-001 --limit 50
uv run --frozen python -X utf8 -m experiments.evaluate_evidence datasets/receipts/korie/val --out artifacts/eval/val-001 --rescore
uv run --frozen python -X utf8 -m experiments.evaluate_evidence datasets/receipts/korie/val --out artifacts/eval/val-001 --rescore --no-overrides   # 원천 라벨 그대로 (라벨 오류율)
uv run --frozen python -X utf8 -m experiments.evaluate_evidence datasets/receipts/korie/val --out artifacts/eval/val-003-tiling --limit 50 --tiling  # 긴 영수증 타일링 실험
uv run --frozen python -X utf8 -m experiments.analyze_failures datasets/receipts/korie/val artifacts/eval/val-001   # 실패 유형별 묶기 (val 만)
uv run --frozen python -X utf8 -m experiments.analyze_review_gate datasets/receipts/korie/test artifacts/eval/test-final  # 검토 게이트 임계값 (집계만, test 가능)
uv run --frozen python -X utf8 -m experiments.analyze_corrections --simulate datasets/receipts/korie/test artifacts/eval/test-final  # 사용자 수정 이력 분석기 (실로그 오면 파일만 바꿔 넣는다)
# 3) 촬영 열화 합성판 (GT 동일, 별도 표로 보고)
uv run --frozen python -X utf8 -m experiments.degrade datasets/receipts/korie/val --out datasets/receipts/korie-mobile-sim/val --preset medium --seed 42
# 4) POS 매출현황 합성 (레이아웃당 30장: screen · printout80 · printout58) → 요구 4건 채점
uv run --frozen python -X utf8 -m experiments.synth_product_sales --out datasets/product-sales --count 30 --seed 7
uv run --frozen python -X utf8 -m experiments.evaluate_product_sales datasets/product-sales --out artifacts/eval/sales-001 --limit 30
# 5) 증빙 유형별 합성 (세금계산서·거래명세서·현금영수증 각 15장) → 증빙 평가기로 그대로 채점
uv run --frozen python -X utf8 -m experiments.synth_evidence --out datasets/receipts/synthetic --count 15 --seed 11
uv run --frozen python -X utf8 -m experiments.evaluate_evidence datasets/receipts/synthetic --out artifacts/eval/synth-001
```

`evaluate_evidence` 는 데이터 디렉터리 이름에 `test` 가 있으면 경고를 찍고 `failures.jsonl` 을 쓰지 않는다.
프롬프트를 고칠 때 보는 파일은 **val 의** `failures.jsonl` 이다.

## 지표 (`metrics.json` 이 정본, `summary.md` 는 요약)

| 지표 | 키 | 의미 |
| --- | --- | --- |
| Processing Failure / Schema Valid | `processingFailureRate` `schemaValidRate` | 추출 자체가 실패한 비율 |
| Field Accuracy | `fields.<name>.accuracy` | `supplierName`(유사도 ≥ 0.9) · `issuedDate` · `supplierBusinessNo`(숫자 exact) |
| Amount Accuracy | `fields.{supplyAmount,vatAmount,totalAmount}.accuracy` | 정확 일치 |
| Line-item P / R / F1 | `items.precision` `items.recall` `items.f1` | 행 매칭 = 이름 유사도 ≥ 0.8, 1:1 |
| Hallucinated Item Rate | `items.hallucinatedRowRate` `items.receiptsWithHallucination` | 라벨에 없는 예측 행 — **P1-22 는 0 이 절대 기준** |
| Business No. Exact vs Checksum | `fields.supplierBusinessNo.accuracy` / `businessNoChecksumPassRate` | 둘은 별개 — 틀리게 읽은 번호도 체크섬을 통과할 수 있다 |
| Amount Reconciliation | `amountReconciliationRate` | 과세물품 + 부가세 + 면세물품 = 합계(마트형) 또는 공급가 + 부가세 = 합계(세금계산서형). 인쇄값으로만 검산 |

**정직하게 말해야 하는 한계** (발표에서 먼저 밝힌다)

0. **실사용 정확도가 없다.** 아래 모든 수치가 KORIE(라벨 노이즈 있음) + 합성이다. 사용자가
   검토 화면에서 무엇을 고쳤는지 기록하면 처음으로 실사용 라벨이 생긴다 — 백엔드 합의 ⑦ 로
   올렸고, 분석기(`analyze_corrections.py`)는 미리 만들어 뒀다. 로그가 오면 파일만 바꿔 넣는다.
1. **실제 촬영 데이터가 없다.** 직접 수집·촬영을 하지 않아 KORIE 스캔 + 합성 열화로만 평가했다.
   실제 폰 촬영 분포와 실제 POS 벤더 레이아웃은 검증되지 않았다.
2. **KORIE 라벨에 노이즈가 있다.** test 의 상호명 91.3%·부가세 90.6% 미달분은 모델이 아니라 라벨
   오류다(val 50장을 이미지로 확인해 11장이 라벨 오류였고, val 원천 라벨 수치 91.5%·86.1% 와 같은
   수준). test 라벨 교정은 분할 규칙상 금지라 원천 라벨 그대로 보고했다.
3. **P1-22 표본은 전부 합성이다.** 공개 POS 인쇄물 데이터가 없어 생성기로 만들었다. 요구 4건 통과는
   우리가 만든 레이아웃 3종에 대한 결과다.
4. **행 밀림은 남은 약점이다.** 세 번 관측했고 둘은 검사로 잡게 됐지만, 값이 온전한 채로 정렬만
   어긋나는 경우는 원리적으로 산술 검증이 불가능하다.
5. **`boundingBox` 는 비어 있고, 채우지 않기로 했다.** VLM 에게 좌표를 요구해 15장에서 쟀더니
   중심 적중 33%, IoU ≥ 0.5 는 9% 였다(아래 절). 틀린 하이라이트는 없는 것보다 나쁘므로 검토 화면은
   **`needsReview` 정렬 + `fieldConfidence` 필드 강조**로 간다. 이는 13.2 의 P1-02 완료 기준
   (좌표 하이라이트)에서 벗어나는 것이라 완료 기준 수정을 팀에 올렸다(`98_AI_백엔드_합의.md` ⑥).
   발표에서는 "안 만든 것" 이 아니라 "재보고 안 넣은 것" 으로 말한다.
6. **품목 정규화 3차는 절반만 자동 측정된다.** **거절** 방향(비슷하지만 다른 상품을 안 붙이는가)은
   어휘 강화 세트로 자동 측정했다 — **22/22 = 100%**. **확정** 방향(같은 상품의 다른 표기를 붙이는가)은
   원리적으로 자동 측정이 불가능하다(인쇄된 표기가 곧 라벨이라 사전 alias 가 되어 3차까지 안 온다) —
   두 번의 독립 실행 손검증 **7/7** 로 보고한다.

#### 자동 승인은 넣지 않는다 (2026-09-08 결정)

`needsReview` 를 게이트로 승격해 "통과하면 자동 승인" 으로 바꾸면 어떻게 되는지 재봤다
(`analyze_review_gate.py` 가 이 표를 낸다).

| 오류 기준 | FAR (자동승인 중 오류) | 놓친 오류 | 불필요 보류 |
| --- | ---: | ---: | ---: |
| 스칼라 필드 오류 | 51/308 = **16.6%** | 85% | 82% |
| **회계 영향 오류**(날짜·합계·사업자번호) | 6/308 = **1.9%** | **100%** (6/6) | 100% |

회계 영향 오류 6건을 결정적 검사가 **하나도** 못 잡는다. 자동 승인으로 바꾸면 날짜나 합계가 틀린
영수증 1.9% 가 그대로 가계부에 들어간다. 신뢰도로 보완하는 길은 위 스윕에서 막혔다 — 정밀도가
데이터 자체의 오류율(16.7% = 무작위)과 거의 같다.

**그래서 현재 구조를 유지한다.** 명세 13.2 대로 모든 추출이 `EXTRACTED`(사용자 확인 대기)를
거치므로 잘못 승인되는 경우(FAR)가 **구조적으로 0** 이고, 대가는 재검증률 100% 다. 자동 승인 비율을
올리는 것은 이 FAR 을 허용할지에 대한 제품 결정이며, 지금 근거로는 권하지 않는다.
`needsReview` 14.2% 는 "재검증 대상" 이 아니라 **먼저 볼 것**의 정렬 신호다.

**그래서 숫자를 고르는 대신 역할을 나눴다.** 신뢰도를 불리언에 합치면 "어느 필드가 의심스러운가"
라는 정보가 사라지는데, 정작 쓸모 있는 신호는 그 필드 지목(날짜)이다. `needsReview` 는 "인쇄된
숫자들이 서로 모순된다"는 설명 가능한 게이트로 두고, 신뢰도는 `fieldConfidence` 로 그대로 내보내
검토 화면이 강조할 필드를 고르게 한다. 명세 13.2 의 `ocrStatus` 에는 `REVIEW` 상태가 없고 모든
추출이 `EXTRACTED`(사용자 확인 대기)를 거치므로, 이 게이트가 가르는 것은 "사람이 보는지" 가 아니라
**무엇을 먼저 보여줄지** 다 — 6건을 놓쳐도 사용자 확인 단계에서 날짜 필드가 강조된 채 올라간다.

### `boundingBox` — VLM 좌표는 쓸 수 없다 (2026-09-08, 15장, $0.0841)

    uv run python -X utf8 -m experiments.synth_evidence --out datasets/receipts/synthetic-boxes         --count 5 --seed 11 --with-boxes --no-degrade          # 좌표 정답 세트 (토큰 0)
    uv run python -X utf8 -m experiments.measure_boxes datasets/receipts/synthetic-boxes         --out artifacts/eval/boxes-001                          # 측정 (--rescore 면 토큰 0)

명세 13.2 는 검토 화면에서 원본 위치를 하이라이트하라고 한다. 그동안 "VLM 이 좌표를 못 낸다" 는
**측정 없이** 단정하고 스키마에서 뺐는데, 이제 쟀다. **운영 프롬프트는 건드리지 않고** 실험용
프롬프트(`evidence-boxes/v1`)로 값과 박스를 함께 요구했다.

정답은 생성기가 남긴 텍스트 레이어다(`--with-boxes`). 라벨과 값을 한 문자열로 그린 곳
(`거래일시: 2026-03-31 09:28:05`)은 값 구간만 글자 수 비례로 좁혔다 — 줄 전체를 정답으로 쓰면
모델이 값을 정확히 가리켜도 오답이 되어 채점이 부당하게 후해진다(좁히기 전 33% → 39%였다).

| 필드 | 채점 | 값 정확 | 박스 냈나 | 중심 적중 | IoU ≥ 0.5 | 평균 IoU |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| supplierName | 15 | 93% | 100% | **73%** | 40% | 0.44 |
| supplierBusinessNo | 15 | 100% | 100% | 27% | 0% | 0.22 |
| issuedDate | 15 | 100% | 100% | 13% | 0% | 0.11 |
| totalAmount | 15 | 100% | 100% | 27% | 0% | 0.11 |
| vatAmount | 9 | 100% | 100% | 22% | 0% | 0.11 |
| **합계** | **69** | **99%** | **100%** | **33%** | **9%** | **0.21** |

**결론: 쓸 수 없다.** 하이라이트가 세 번 중 한 번만 옳은 곳을 가리킨다. 없는 것보다 나쁘다 —
사용자가 강조된 곳을 보고 "여기가 합계구나" 판단하면 3분의 2는 틀린 곳을 본다.

세 가지가 함께 드러났다.

1. **값 정확도는 99% 로 멀쩡하다.** 좌표를 같이 요구해도 값 추출이 나빠지지 않는다. 즉 문제는
   "물어보는 비용" 이 아니라 좌표 자체의 품질이다.
2. **박스를 100% 낸다 — null 을 내지 않는다.** 모를 때 모른다고 하지 않으므로 "모델이 자신 없는
   건만 버린다" 는 방식으로 걸러낼 수 없다.
3. **큰 글자만 된다.** 맨 위 큰 상호명은 73%인데 표 안의 작은 값(날짜 13%, 합계 27%)은 못 짚는다.
   하이라이트가 가장 필요한 쪽이 정확히 안 되는 쪽이다.

깨끗한 렌더(열화 없음)에서 이 수치다 — 실제 촬영·감열지에서 더 나아질 이유가 없다.

**그래서 남은 선택은 둘이다.** ① 로컬 OCR 로 좌표만 얻는다 — 값은 VLM 이 이미 냈으니 OCR 은
**아는 문자열의 위치를 찾는 용도**이고, 이건 인식 정확도가 낮아도 `rapidfuzz` 로 붙는다
(`pyproject.toml` 의 `paddle` extra 가 이미 그 자리다). ② 좌표 없이 간다 — 검토 화면은
`needsReview` 정렬 + `fieldConfidence` 필드 강조로 구성한다. 발표 기준으로는 ②를 권한다.

**왜 0건인가 — 생성기가 그 조건을 만들지 못한다.** `blur_rows` 는 `GaussianBlur(radius=6)` +

채울 일이 없고, 경고만 남으면 그것은 정당하다.

**그래서 중간 강도를 만들었다.** `faint_rows` 는 `radius=1.6` + 22% 혼합이다 — 눈으로 값이
읽히고(실제 이미지 확인), **정답에도 남는다.** 그러면 세 갈래가 구분된다.

| 모델 동작 | 뜻 |

#### 행 밀림을 실측으로 갈랐다 — 「검출률 3.5%」 정정 (2026-09-09, 비용 0)

`Σ품목` 을 뺀 뒤에도 숫자 오답 57행의 정체를 **눈으로 본 것**으로만 적어 두었다("대부분이 행
밀림"). 근거가 없으니 셌다. 예측한 숫자 뭉치(수치 7열)를 **이웃 라벨 행의 뭉치와 대조**한다 —
그대로 일치하면 값을 잘못 읽은 것이 아니라 **다른 행의 값을 받아온 것**이다.

| 계열 | 행 | 비중 | 행 산술이 잡는 것 |
| --- | ---: | ---: | ---: |
| 이웃 행의 숫자 뭉치를 그대로 받음 (**행 밀림**) | 52 | 91.2% | 0 |
| 값 자체를 잘못 읽음 (**진짜 오독**) | 5 | 8.8% | **2** |

밀린 방향은 앞으로 37행 · 뒤로 15행이고, 전부 **한 칸**이다.

**그래서 「검출률 3.5%(2/57)」는 검사를 깎아 적은 값이었다.** 분모 57 중 52는 열이 통째로
움직여 행 안의 산술이 그대로 성립하는 행이다 — 어떤 행 내부 검사로도 원리적으로 볼 수 없다.
겨냥한 계열만 보면 **40%(2/5)** 다. 명세 20장 v1.18 문단·99_구현현황·`sales_validators.py`
세 곳을 고쳤다.

**구성비(share) 정합 검사는 쓸 수 없다.** `결제금액 / 구성비` 는 표본 안에서 일정해야 하고,
합계 행을 안 쓰니 `Σ품목 = 합계 행` 이 깨지는 문제도 비켜간다. 구성비가 0.1%p 로 반올림되는 것을
허용범위(`0.05 / 구성비`)로 감안하면 **라벨 1,059행에서 오탐 0** 이라 식 자체는 옳다. 그런데
**이 계열을 0/57 잡는다** — 구성비도 밀린 뭉치에 같이 실려 오므로 행 안에서는 일관적이다.
오탐 0 은 식이 옳다는 뜻이지 무언가를 본다는 뜻이 아니다. 누가 또 세우지 않도록 기록한다.

#### 반대 방향의 실수 — 검산이 맞는 것을 틀렸다고 한 건 (2026-09-09 수정)

예측이 라벨과 완전히 같았다.** 공급가액·세액 줄이 인쇄되지 않은 양식이었다 — 행 금액은 공급가액인데

#### 검산이 원리적으로 못 잡는 것 — 금액 칸 밀림 (v1.14 로 보완)

**덧셈은 교환법칙이 성립하므로 합계 검산은 순열을 볼 수 없다.** 다른 한 건은 과세를 아예 비워

세율 관계는 순열에 깨진다 → **`부가세 = 과세분 × 10%`** 검사를 추가했다(`check_vat_ratio`,

면세물품` 순으로 잡는다. 마지막 유도식은 항등식이 아니라 `11 × 부가세 = 합계 − 면세` 라는 독립
제약(10/110 관계)이다. 세액 0 은 영세율·면세에서 정상이므로 판정하지 않는다.

보완), 그리고 이번 품목 이름 밀림. **모델이 이름 열과 숫자 열의 행 정렬을 잃는 것**이 하나의 계열이다.
그리고 세 경우 모두 **산술 검사로는 잡히지 않는다** — 금액 자체는 온전해서 합·검산이 다 맞는다.

**다만 구조 신호로는 잡힌다 (토큰 0 측정).** 품목 행 이름이 표 머리글 낱말이거나(`상품명`·`수량`·
`금액` …), 마지막 행만 금액이 비어 있으면 정렬이 밀린 것이다.

| 신호 | 밀림 1건 포착 | test 359장 오탐 | val 50장 오탐 |
| --- | :---: | ---: | ---: |
| 품목 이름이 표 머리글 낱말 | ✅ | **0건** | 0건 |
| 마지막 행만 금액 없음 | ✅ | 1건 | 0건 |
| 둘 다 | ✅ | **0건** | 0건 |

머리글 신호 하나만으로도 실제 영수증 409장에서 오탐이 0 이다. **계약 v1.15 로 검사에 넣었다**
(`check_item_alignment`, 사유 `ITEM_ROWS_MISALIGNED`) — 두 신호를 OR 로 쓰고, test 359장 게이트
비율은 13.9% → **14.2%**(+1건)로 올랐다. 산술로 볼 수 없는 계열을 잡는 대가가 359장당 1건이다.

**v4 를 유지한다.** 규칙 ②가 근거 있는 개선이고(매출 인쇄물에서 환각 0 을 만든 규칙), 실패한 규칙 ①은
한 줄이라 비용이 작다. 대신 **측정된 프롬프트와 배포된 프롬프트를 같게 유지**하려고 실패한 줄도
그대로 둔다 — 재측정 없이 프롬프트를 또 고치면 "v4 수치" 가 무엇의 수치인지 알 수 없게 된다.
규칙 ① 교체와 정렬 지시 추가는 v5 후보다. 출력 토큰이 장당 약 630 → 1,028 로 늘어(warnings 가
길어졌다) 이 유형 비용이 오른 것도 v5 에서 함께 볼 사항이다.

### P1-03 품목 정규화 3단 캐스케이드 첫 실측 (2026-09-08, test 359장 + val 20장, Sonnet 5)

재현: `uv run python -X utf8 -m experiments.evaluate_item_normalization <labels> <run> --out <dir>`
(1·2차만 = 토큰 0, `--llm` 을 붙이면 3차를 실제로 부른다). 표본을 만드는 방식·한계는 스크립트
docstring 에 적었다 — 요약하면 **사전**은 라벨 품목명으로 만든 사업장 품목 마스터,
**입력**은 그 영수증에서 OCR 이 실제로 읽은 이름, **정답**은 같은 영수증 안의 라벨↔예측 짝이다.

**§6.5 "규칙이 90% 이상을 처리" 는 성립한다.** 단 분모를 조심해야 한다.

| 지표 | test 359장 (rawName 2,026건) |
| --- | ---: |
| 1차 규칙 (정규화 후 동일) | 21.7% (439) |
| 2차 유사도 (≥ 0.92) | 2.8% (57) |
| 미매칭 → 신규 품목 제안 | 75.5% (1,530) |
| **사전에 정답이 있는 239건 중 붙인 비율** | **91.6%** |
| **그중 1·2차가 처리한 비율** | **100.0%** (3차 없이) |
| 위험한 오매칭 (사전에 정답이 있는데 다른 항목) | **0.05%** (1건) |
| 신규 품목을 비슷한 기존 항목에 오인 | 13.6% (276건) |
| 정답이 있는데 미매칭으로 둔 것 | 0.9% (19건) |

미매칭 75.5% 는 대부분 **정답**이다 — KORIE 는 여러 점포의 영수증 모음이라 200개 사전에
안 들어오는 품목이 많다. 단일 사업장에서 사전이 쌓이는 실제 운영과는 다르므로 **처리율의 절대값은
보수적으로 읽는다.** 의미 있는 수치는 "사전에 정답이 있을 때 붙이는가"(91.6%)와 오매칭률이다.

**"오매칭이 매칭 실패보다 나쁘다" 는 지켜진다** — 사전에 정답이 있는데 다른 항목에 붙인 건이
2,026건 중 1건(0.05%)이다. 대신 **신규 품목을 비슷한 기존 항목으로 오인하는 것이 13.6%** 로 크다.
임계값을 올려도 해결되지 않는다.

| 2차 자동매칭 임계값 | 자동매칭 | 신규를 기존에 오인 | 정답 있는데 놓침 | 3차 후보 |

| 0.94 | 24.0% | 13.3% (270) | 1.1% (23) | 328 |
| 0.96 | 21.9% | 11.9% (241) | 1.8% (36) | 370 |
| 0.98 | 21.7% | 11.7% (238) | 1.9% (38) | 375 |
| 1.00 (완전 일치만) | 21.7% | 11.7% (238) | 1.9% (38) | 375 |

완전 일치만 허용해도 오인이 11.7% 남는다 — **유사도 임계값 문제가 아니다.** OCR 이 이름을 짧게
읽으면(`서울우유 1L` → `우유`) 그 짧은 이름이 사전의 더 일반적인 항목과 **정확히** 일치해 버린다.
0.92 → 1.00 은 오인을 1.9pp 줄이는 대신 놓침을 두 배로 만든다. **0.92 를 유지한다.**

**3차 LLM 은 계약대로 동작한다 (live 첫 실측).** test 25회 + val 20회 호출, effort low.

시간 제한 8초 안에 들어오고, 후보 밖 itemId 를 내거나 스키마를 어긴 건이 없다. 확정률은 보수적이다
(val 49후보 중 3건 = 6%).

#### 3차 거절 정확도 — 자동 측정 완료 (2026-09-09, 18회 호출 $0.03)

    uv run python -X utf8 -m experiments.synth_evidence --out datasets/receipts/synthetic-vocab         --count 12 --seed 23                                        # 어휘 강화 세트 (토큰 0)
    uv run python -X utf8 -m experiments.evaluate_item_normalization         datasets/receipts/synthetic-vocab --use-labels --withhold 0.0         --withhold-names "서울우유 500ml,에스프레소 원두 500g,점보롤 화장지 30롤,종이컵 8oz,계란 10구"         --out artifacts/eval/norm-vocab-001 --llm --only-candidates

생성기 어휘에 **이름이 비슷하고 규격만 다른 짝** 6종을 넣고(`서울우유 1L` ↔ `서울우유 500ml` 등),
짝의 한쪽을 사전에서 **지목해서** 뺐다(`--withhold-names`). 비율만 쓰면 어느 항목이 빠지는지가
itemId 나머지로 정해져 짝을 우연히 하나만 맞춘다.

`--use-labels` 는 rawNames 를 라벨에서 만든다 — **OCR 을 거치지 않아 추출 비용이 0** 이고,
재는 것이 "3차의 판정" 하나로 좁혀진다.

| 사례 | 후보 | 유사도 | 정답 | 3차 판정 |
| --- | --- | ---: | --- | --- |
| `계란 10구` | `계란 30구` | 0.83 | 거절 | **6/6 거절** |
| `서울우유 500ml` | `서울우유 1L` | 0.71 | 거절 | **6/6 거절** |
| `에스프레소 원두 500g` | `에스프레소 원두 1kg` | 0.80 | 거절 | **4/4 거절** |
| `종이컵 8oz 1000개` | `종이컵 12oz 1000개` | 0.89 | 거절 | **6/6 거절** |
| **합계** | | | | **22/22 = 100%** |

거절만 한 것이 아니라 **신규 품목 이름도 정확히 제안**했다(`suggestedCanonicalName` = 원래 이름).
즉 사용자에게 "이건 새 품목입니다" 로 올라간다. 프롬프트가 "용량·규격이 다르면 다른 상품" 이라고
지시한 대로다.

**이 방향이 안전상 더 중요하다** — §6.5 는 "오매칭이 매칭 실패보다 나쁘다" 고 못 박는다.
반대 방향(같은 상품, 표기만 다름을 **확정**하는 능력)은 **자동 측정이 불가능하다**: 인쇄된 표기가
곧 라벨이라 사전의 alias 가 되어 완전 일치로 끝나고 3차까지 오지 않는다. 그쪽은 손검증으로
보고한다 — 두 번의 독립 실행에서 7/7 정답이다(아래).

**부수 발견 — 0.92 자동매칭이 다른 상품을 붙인다.** 짝 6종 중 `양파 5kg` ↔ `양파 15kg` 는
유사도가 **0.92** 로 자동매칭 구간에 들어간다. 규격이 다른 다른 상품인데 3차에 오지도 않고 붙는다.
임계값을 올리는 것은 test 359장 스윕에서 손해가 더 크다고 이미 판정했으므로(오인 13.6% → 11.7%,
놓침 0.9% → 1.9%) 그대로 두고 한계로 기록한다.

#### 왜 KORIE·기존 합성으로는 못 쟀나 (2026-09-09, $0.056)

**3차 정확도는 지금 가진 데이터로 자동 측정이 불가능하다 (2026-09-09 확정, $0.056).**
사전 묶음 키를 고친 뒤 재호출해 확인했다. 두 데이터셋이 **서로 반대 이유로** 막힌다.

| 데이터셋 | 정답 매핑 | 3차 후보 | 왜 못 재나 |
| --- | ---: | ---: | --- |
| KORIE val 50장 | **9%** (27/297) | 47건 | **품목 라벨이 부분 라벨**이다. 모델이 올바르게 읽은 행이 라벨에 없으면 정답이 `None` 이 되어 어떤 매칭도 오답으로 세어진다 |
| 합성 증빙 45장 | **83%** (139/168) | **0건** | 라벨은 완전한데 **상품 어휘가 15개로 좁아** 유사도 0.70~0.92 구간이 생기지 않는다. 1·2차가 100% 를 처리한다 |

즉 사전 결함이 아니었다. `가지(특) 3개/1팩` 의 정답이 `None` 이던 이유는 **그 행이 KORIE 라벨에
아예 없었기** 때문이다(IMG00059 라벨은 6행이고 가지가 없다).

**그래서 3차 정확도는 손검증으로 보고한다 — 두 번의 독립 실행에서 7/7 정답이다.**

| 실행 | 확정 | 손검증 | 예 |
| --- | ---: | ---: | --- |
| val (2026-09-08) | 3건 | **3/3** | `토스트앤샌드위치 768g` → `삼립) 토스트&샌드위치식빵 768g` |
| val (2026-09-09, 사전 개선 후) | 4건 | **4/4** | `마이디빌크링클컷 2kg` → `마이디벨크링클컷 2kg`(한 글자 오독), `아삭이고추 100g` → `아삭이고추` |

**자동화하려면** 합성 생성기의 상품 어휘에 표기 변형(브랜드 접두·등급·포장·약어)을 넣어 0.70~0.92
구간을 만들어야 한다 — 생성은 토큰 0 이고 측정은 ~$0.05 다. 3차가 전체의 6% 만 처리하고 1·2차가
붙일 수 있는 건의 100% 를 이미 처리하므로 우선순위는 낮다.

**사전 묶음 키 (`dictionary_key`) — 벗기는 규칙은 적을수록 안전하다.** 채점 도구의 사전 구성에만
쓰고 **운영 매처는 건드리지 않는다.** 지금 벗기는 것은 둘뿐이다 — 선행 브랜드(`삼립) 강력분 20kg`
→ `강력분 20kg`)와 등급 토큰(`가지(특)` → `가지`). 둘 다 상품 정체성을 바꾸지 않는다.

**한때 포장·규격 숫자(`N개`·`N롤`)도 벗겼는데 되돌렸다.** `가지(특) 3개/1팩` 을 `가지` 로 합치려던
것인데, 같은 규칙이 `점보롤 화장지 16롤` 과 `30롤` 도 합친다 — 그건 실제로 다른 SKU 다. 게다가 그
병합은 원래 목표(3차 채점)를 해결하지도 못했다: `가지(특)` 의 정답이 `None` 이던 진짜 이유는
**KORIE 품목 라벨이 부분 라벨**이라 그 행이 라벨에 아예 없던 것이었다.

되돌린 효과 — 둘 다 좋아졌다.

| 지표 | 과하게 병합했을 때 | 되돌린 후 |
| --- | ---: | ---: |
| KORIE test 규격 어긋난 자동매칭 | 27건 | **8건** |
| 그중 오매칭 의심 | 16건 (자동매칭의 3.4%) | **4건 (0.8%)** |
| 어휘 강화 세트 3차 후보 | 22건 / 4사례 | **24건 / 5사례** |

앞 수치(3.4%)는 내 과한 병합이 만든 허수였다.

**운영에 규격 불일치 가드를 넣지 않는다.** `양파 5kg` ↔ `양파 15kg` 처럼 숫자만 다른 자동매칭을
막는 규칙을 검토했는데, 그런 자동매칭 8건 중 **4건이 오매칭이고 4건이 정답**이다. 잡는 만큼
깨뜨리므로 넣을 근거가 없다 — 임계값 스윕과 같은 결론이다.

`itemId` 는 빈도 순위 값이라 사전을 바꾸면 번호가 전부 밀린다 — 저장된 3차 판정을 재채점할 수 없다.
그래서 위 24건 중 **다섯째 사례(`점보롤 화장지 30롤`, 2건)는 아직 3차를 부르지 않았다**. 보고된
22/22 는 네 사례에 대한 것이다.

**자동 채점의 "3차 정확도" 는 아직 믿을 수 없다 — 채점 사전의 결함이다.** val 에서 확정 3건을 눈으로
확인하니 **3건 모두 같은 상품이 맞았다**: `토스트앤샌드위치 768g` → `삼립) 토스트&샌드위치식빵 768g`
(브랜드 탈락 + `&`→`앤` 오독, 768g 일치), `가지(특) 3개/1팩` → `가지`, `양파(중) 1망` → `양파`.
자동 채점이 이 셋을 전부 오답으로 센 이유는 사전을 `normalize_name` **문자열**로 묶어 같은 상품이
`가지` 와 `가지(특) 3개/1팩` 두 항목으로 쪼개졌기 때문이다(가까운 키를 0.92 로 합치는 처리를
넣었지만 이 쌍은 유사도가 그보다 낮아 안 합쳐진다). KORIE 라벨에 잘린 이름(`상추(적`)이 섞인 것도
같은 원인이다. **그래서 3차 정확도는 손검증(val 3/3)으로만 보고하고, `llm.correct` 는 채점기
지표로 읽는다.**

**남은 판단.** 3차가 추가로 붙이는 양이 6% 이고 동기 응답에 3.2초를 더한다. 반면 1·2차가 붙일 수
있는 건의 100% 를 이미 처리한다. 끄는 쪽이 싸지만, 붙인 3건이 실제로 맞았고 §6.5 의 전제(`ITEM.aliases`
가 채워진 상태)가 이 데이터에서는 미충족(사전 200개 중 alias 가 있는 항목 10개)이라 **사전이 실제
사용으로 쌓인 뒤 다시 판단한다.** 지금은 `AI_PIPELINE_MODE=live` 에서만 켜지는 현 동작을 유지한다.
