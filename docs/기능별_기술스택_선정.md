## 1. 선정 원칙

**원칙 1 — 돈을 세는 일에 LLM을 쓰지 않는다.**
잔액·부족액·세액·상환액·준비금·정산 대사는 Java 계산 엔진의 `BigDecimal` 순수 함수가 담당한다.
SRS 12장이 "수치 계산과 확정 분류를 LLM에 위임하지 않음"을 명시하고, 인수 조건에
"동일한 입력에 대해 재현된다"가 들어 있다. LLM은 재현을 보장하지 못한다.

**원칙 2 — LLM은 네 가지 일만 한다.**
분류(classification) · 추출(extraction) · 구조화(structuring) · 문장화(generation).
전부 사람이 눈으로 검수할 수 있고, 틀려도 되돌릴 수 있는 작업이다.

**원칙 3 — 값싼 단계가 먼저 거른다.**
`사용자 확정 → 규칙 → 사전/pg_trgm → LLM → 사용자 확인` 순서를 모든 AI 기능에 적용한다.
LLM 도달 건수를 줄이는 것이 모델을 바꾸는 것보다 비용 효과가 크다.

**원칙 4 — 출력은 두 번 검증한다.**
AI 워커에서 Pydantic v2로 한 번, API 서버에서 Java DTO + 허용값 검사로 다시 한 번.
`allowedCategories` 밖의 값, 입력에 없던 숫자·날짜는 저장 전에 폐기한다.

## 3. 공통 기술 스택

### 3.1 이미 들어 있는 것

`backend/build.gradle` 실측이다. 아래는 추측이 아니라 현재 의존성이다.

| 영역 | 기술 | 비고 |
| --- | --- | --- |
| 언어 | **Java 21** (toolchain) | |
| 프레임워크 | **Spring Boot 4.1.1** | `spring-boot-starter-webmvc` (Boot 4에서 `-web` → `-webmvc` 개명) |
| 모듈 경계 | **Spring Modulith 2.1.1** | core / forecast 등. `starter-core`, observability. **`starter-jpa`는 제외** — 아래 주의 |
| 인증·인가 | Spring Security + **JWT** (jjwt 0.12.6, HMAC-SHA256) | Access Token + Refresh Token 회전. `api` 컴파일, `impl`·`jackson` 런타임 |

| 검증 | Jakarta Validation | |
| 관측 | Actuator + Micrometer + Modulith observability | |
| 테스트 | JUnit 5, **Testcontainers** (PostgreSQL), Modulith test·docs | |
| 배포 | Docker Compose, **Nginx 1.27** (Reverse Proxy), Jenkins | `infra/compose.yml` |

**Spring Modulith 의존 규칙** — ERD가 이미 정해 두었다: **`forecast → core` 단방향만 허용**.
그래서 `ALERT`처럼 두 모듈이 다 쓰는 테이블은 `core` 스키마가 소유한다.
새 모듈을 만들 때 이 방향을 먼저 확인한다. Modulith 테스트가 위반을 잡아 준다.

> 🚫 **`spring-modulith-starter-jpa`를 넣으면 부팅이 실패한다.** 도메인 이벤트 발행 레지스트리
> (`event_publication` 테이블)를 요구하는데 아직 이벤트를 발행하지 않고, `ddl-auto: validate`라
> **쓰지도 않는 테이블이 없다는 이유로 앱이 뜨지 않는다.** 근거는 `backend/build.gradle` 주석에 있다.
> 첫 모듈 간 이벤트(forecast → core 알림 등)를 도입할 때 **스타터와 마이그레이션을 함께** 넣는다.

### 3.4 모든 기능이 지나가는 두 개의 축

새 기능을 붙일 때 **"이 둘 중 어디에 닿는가"** 를 먼저 묻는다.

**① `PLANNED_TRANSACTION` — 예측의 단일 입력**

ERD 역할 설명 그대로다: *"모든 출처(사용자·패턴·세금·대출)의 통합 미래 예정 거래.
예측 계산의 단일 입력"*. `source_type`이 `USER` · `PATTERN` · `TAX` · `LOAN` 넷이다.

```
P0-06 일회성 등록 ─┐
P0-03/04 반복 패턴 ─┼→ PLANNED_TRANSACTION ─→ P0-07 예측 엔진 ─→ DAILY_BALANCE_FORECAST
P1-11 세금 일정   ─┤                                              └→ P0-08 공백 탐지
P1-13 대출 상환   ─┘
```

> 새 기능이 예측에 반영되어야 하는가? → **`PLANNED_TRANSACTION`에 행을 쓰는가**로 답이 나온다.
> 예측 엔진에 특수 케이스를 더하지 않는다.

`expected_date`(보정 후)와 `original_expected_date`(보정 전)를 **둘 다** 저장한다.
값이 다르면 공휴일 보정이 걸린 것이고, 화면에서 "공휴일로 밀림"을 보여줄 수 있다.

**② `JOB` — 모든 비동기 작업**

`job_type` 6종이 이미 정의돼 있다: `ACCOUNT_SYNC` · `TRANSACTION_IMPORT` ·
`TRANSACTION_CLASSIFICATION` · `EVIDENCE_EXTRACTION` · `EXPORT_GENERATION` · `LOAN_SYNC`.
상태는 `QUEUED` → `PROCESSING` → `COMPLETED` / `FAILED`.

- **Redis를 작업 큐로 쓰지 않는다.** 작업 상태의 단일 기준은 PostgreSQL `JOB`이다.
  워커는 `SELECT ... FOR UPDATE SKIP LOCKED`로 집어 간다.
- Redis는 Refresh Token · 멱등성 키 · 단기 캐시만. `infra/secrets/redis.conf.example`이
  **`maxmemory 512mb` + `maxmemory-policy volatile-lru`** 로 설정돼 있다.
  `volatile-lru`는 **TTL이 있는 키 중에서만** 축출하므로, TTL 없는 키가 쌓이면
  축출할 대상이 없어 쓰기가 실패한다. **모든 Redis 키에 TTL을 건다.**
- 모든 Job은 반드시 완료·실패·타임아웃 중 **하나의 종료 상태에 도달**해야 한다.
  `PROCESSING`에서 멈춘 Job을 걷어내는 감시 배치(10분 초과 시 1회 재시도)를 함께 만든다.

### 3.5 보안 — 이미 설계에 들어 있는 것

`ACCOUNT` 테이블이 계좌번호를 세 벌로 나눠 갖는다. 이 패턴을 다른 민감 필드에도 그대로 쓴다.

| 컬럼 | 용도 |
| --- | --- |
| `account_number_encrypted` | 실제 값. 복호화는 꼭 필요한 지점에서만 |
| `account_number_hash` | 조회·중복 검사용. 평문 없이 매칭 |
| `account_number_masked` | 화면 표시용. 복호화 없이 응답 |

- 목록·상세 응답에는 `masked`만 싣는다. 복호화 경로를 최소화한다.
- 사업장 범위 검사는 서비스마다 복붙하지 말고 **`BusinessGuard` 한 곳**에 모아
  Modulith 모듈 경계에서 건다. 화면 하나를 빠뜨리면 남의 가게 잔고가 보인다.
- `BUSINESS_MEMBER`는 ERD에서 제거됐다. 권한은 `BUSINESS.owner_user_id` 1:N이다.
  세무대리인 공유가 필요해지면 그때 멤버십 테이블로 확장한다.
- 계좌번호·주민번호·사업자번호는 **로그 금지**. 외부 AI 전송 전에 서버에서 제거한다.

**신고서 민감 항목은 한 단계 더 강하다 — 저장 자체를 하지 않는다**

SRS 12장 개인정보 요구사항: *"신고서 민감 항목(**주소지 · 생년월일 · 주민등록번호 ·
계좌번호 · 부양가족 인적사항**) 서버 미저장 · AI 미전달"*.

| | 일반 민감 필드 | 신고서 민감 항목 |
| --- | --- | --- |
| 저장 | 암호화 저장 (`*_encrypted`) | **저장하지 않는다** |
| 조회 | 마스킹해서 응답 | 마스킹된 초안만 재조회 |
| AI 전송 | 자리표시자로 치환 | **키 자체를 안 보낸다** |
| 존재 구간 | DB에 상주 | **내보내기 요청 안에서만** |

`TAX_FORM_TEMPLATE.fields[].sensitive`가 플래그이고,
`TAX_FILING_DRAFT`는 값을 갖지 않는다([4.9](#49-p0-12-종합소득세-신고서-초안-p1-23-검토-화면-포함)).
로그 마스킹 필터를 **테스트로 검증**한다 — 인수 조건이 "AI 워커 로그 어디에도"를 명시했다.

### 3.6 SSAFY 금융망 — 실제 인터페이스가 요구하는 것

근거: `SSAFY_교육용_금융망_API_Inferface_예제.xlsx` (173시트) · `SSAFY_교육용_금융망_API+플로우.pdf`.
**여기 적힌 것은 일반적인 오픈뱅킹과 다르다.** 설계에 직접 영향을 준다.

**① REST가 아니다 — 단일 URL에 전부 POST**

모든 API가 `https://finopenapi.ssafy.io/ssafy/` 하나로 POST 하고,
**무엇을 호출하는지는 요청 본문의 `Header.apiName`이 정한다.** 개발 URL은 `https://ssafy-dev.maum.ai/ssafy/`.

```jsonc
{ "Header": {
    "apiName": "inquireTransactionHistoryList",   // 호출 URI의 마지막 path 와 동일
    "transmissionDate": "20260903",               // YYYYMMDD
    "transmissionTime": "113000",                 // HHMMSS — 서버 시각 ±5분 이내만 허용
    "institutionCode": "00100",                   // 고정
    "fintechAppNo": "001",                        // 고정
    "apiServiceCode": "inquireTransactionHistoryList",  // apiName 과 동일
    "institutionTransactionUniqueNo": "20260903113000123456",  // 20자, 매 요청 새 번호
    "apiKey": "...",                              // 앱(팀) 단위
    "userKey": "..."                              // 사용자 단위
  },
  "accountNo": "0011234567890123", "startDate": "20260801", ... }
```

- 리소스별 인터페이스를 만들지 말고 **공통 Header 빌더 + `apiName` 스위치** 하나로 간다.
  `@HttpExchange`로 메서드를 40개 만들면 URL이 전부 같아 의미가 없다.
- **`transmissionTime`이 ±5분을 벗어나면 전부 `H1003`으로 실패한다.**
  운영 서버에 **NTP 동기화가 필수**다. 시계가 6분 밀리면 금융망 연동 전체가 죽는다.
- `institutionTransactionUniqueNo`는 **요청마다 새로 채번**한다(20자, `YYYYMMDD+HHMMSS+일련번호`).
  중복이면 `H1007`. 이건 우리 `X-Request-Id` 멱등성과 **별개**다 —
  재시도할 때 같은 번호를 다시 쓰면 거절당하므로 **재시도마다 새로 채번**한다.
- `MEMBER_01`(계정 생성)만 예외로 공통 Header를 쓰지 않고 `apiKey` + `userId`만 보낸다.

**실측으로 확인한 것 (2026-09-08)** — xlsx 에 없거나 놓치기 쉬운 것들이다.

| 항목 | 사실 |
| --- | --- |
| 경로 규칙 | `/ssafy/api/v1/edu/{도메인}/{apiName}` — `apiName` 이 곧 마지막 path 다. 없는 경로는 `404` 에 응답 형태도 다르다(`responseCode` 가 아니라 `code`/`payload`) |
| **`transactionBalance` 는 문자열** | 숫자로 보내면 `Q1001`("요청 본문의 형식이 잘못되었습니다"). **문서 어디에도 없고 어댑터 구현에서 반드시 걸린다.** 금액 필드는 전부 문자열로 취급한다 |
| `transactionSummary` 생략 | 빈 문자열이 아니라 **`null`** 로 저장된다. 분류가 적요 텍스트에 거의 전적으로 의존하므로(8장) null 처리가 필요하다 |
| **`userKey` 검증은 API 마다 다르다** *(2026-09-08 정정)* | **"조회 계열은 검증하지 않는다"가 아니다.** 사용자별 데이터가 없는 것(`inquireBankCodes`·`inquireDemandDepositList`)만 빈 값으로도 `H0000` 이고, **계좌를 지목하는 조회는 검증한다** — `inquireTransactionHistoryList` 에 빈 `userKey` 를 넣으면 `H1009`("USER_KEY가 유효하지 않습니다")다. 앞의 관대함만 보고 "조회는 안 본다"로 일반화하면 계좌 단위 조회에서 원인을 늦게 찾는다 |
| 호출 한도 | 40건 연속 호출에 스로틀 없음(전부 `H0000`, 초당 약 3건 — 왕복 지연이 상한이다). 일일 한도는 이 방법으로 배제할 수 없으나, 시딩 규모(1년치 수백 건)에는 문제되지 않는다 |
| `transactionUniqueNo` | 계좌 내 순번인 짧은 숫자다(예: `191427`). 중복 제거 키로 그대로 쓸 수 있다 |
| **`REC` 가 배열인 API 가 있다** | `inquireBankCodes` 의 `REC` 는 객체가 아니라 **배열**이다 (은행 18종). 어댑터에서 `REC` 를 단일 타입 하나로만 받게 만들면 여기서 막힌다 — 배열 경로를 함께 둔다 |
| `BANK_01` 경로 확정 | `/ssafy/api/v1/edu/**bank**/inquireBankCodes` (2026-09-08 실측). 도메인 구간이 xlsx 에 없어 호출해 봐야 안다. `userKey` 를 빈 문자열로 보내도 `H0000` 이고, 응답 `Header` 에 `userKey` 는 에코되지 않는다 |
| **`institutionTransactionUniqueNo` 는 정확히 20자** | 짧으면 `H1010`("기관거래고유번호가 유효하지 않습니다"). `YYYYMMDD`(8) + `HHMMSS`(6) + 난수 6자리를 **0 패딩**해야 한다 — 난수를 그냥 이어붙이면 길이가 들쭉날쭉해져 간헐적으로 실패한다. 실제로 이것 때문에 userKey 문제로 오진했다 |

**확정된 경로와 응답 형태 (2026-09-08 실측)** — 도메인 구간이 xlsx 에 없어 호출해야만 안다.
**추측으로 채우지 않는다.** 아래는 실제로 호출해 확인한 것만이며, 새로 확인하면 여기 추가한다.

| ID | 경로 | 요청 | 응답 |
| --- | --- | --- | --- |
| `MEMBER_01` | `/member/` | `{apiKey, userId}` | **201**, 평평한 본문(`userKey` 포함). `responseCode` **없음** |
| `MEMBER_02` | `/member/search` | `{apiKey, userId}` | **201**(조회인데 201 이다). 없으면 `400 E4003` |
| `BANK_01` | `edu/bank/inquireBankCodes` | — | `REC` **배열** (18종) |
| `DD_02` | `edu/demandDeposit/inquireDemandDepositList` | — | `REC` **배열** |
| `DD_03` | `edu/demandDeposit/createDemandDepositAccount` | `{accountTypeUniqueNo}` | **201**, `REC` 객체 `{bankCode, accountNo, currency}` |
| `DD_04` | `edu/demandDeposit/inquireDemandDepositAccountList` | — | `REC` **배열** |
| `DD_12` | `edu/demandDeposit/inquireTransactionHistoryList` | `{accountNo, startDate, endDate, transactionType, orderByType}` | `REC` **객체** `{totalCount, list[]}` |
| `DD_08` | `edu/demandDeposit/updateDemandDepositAccountWithdrawal` | `{accountNo, transactionBalance, transactionSummary}` | `REC` **객체** `{transactionUniqueNo, transactionDate}` |
| `DD_09` | `edu/demandDeposit/updateDemandDepositAccountDeposit` | `{accountNo, transactionBalance, transactionSummary}` | `REC` **객체** `{transactionUniqueNo, transactionDate}` |
| `ACCOUNT_AUTH_01` | `edu/accountAuth/openAccountAuth` | `{accountNo, authText}` | `REC` `{transactionUniqueNo, accountNo}` |
| `ACCOUNT_AUTH_02` | `edu/accountAuth/checkAuthCode` | `{accountNo, authText, authCode}` | `REC` `{status: "SUCCESS", ...}`. 틀리면 `400 A1090` |

여기서 나온 함정들이다.

| 사실 | 왜 걸리나 |
| --- | --- |
| **`REC` 는 배열일 때도 객체일 때도 있다** | 같은 `demandDeposit` 도메인 안에서 갈린다 — `DD_04` 는 배열, `DD_12` 는 객체(`{totalCount, list[]}`)다. 어댑터가 `REC` 를 한 형태로만 받으면 절반이 막힌다 |
| **오류는 `responseCode` 가 최상위로 온다** | 성공은 `Header.responseCode`, 실패는 **최상위**다(`A1090`·`E4002`·`E4003` 실측). 한 자리만 보면 오류를 통째로 놓친다 |
| **정상 응답이 `201` 일 수 있다** | `DD_03`·`MEMBER_01/02` 가 그렇다. `200` 만 성공으로 보면 계좌 생성이 실패로 잡힌다 |
| **숫자로 보이는 값이 전부 문자열** | `transactionBalance` 뿐 아니라 `totalCount`·`transactionUniqueNo` 도 문자열이다. 4.1 표의 `Long` 표기는 의미상 정수라는 뜻이지 JSON 타입이 아니다 |
| 1원 인증 적요 형식 | **`"{authText} {4자리}"`** — 공백 하나로 이어붙는다(예: `잔고예보 4653`). 코드는 마지막 4자다 |
| **쓰기 계열 `REC` 는 객체이고 두 필드뿐이다** *(2026-09-14 실측)* | `DD_08`·`DD_09` 모두 `{transactionUniqueNo, transactionDate}` 다. 그 번호가 곧 `DD_12` 의 `transactionUniqueNo` 이고 우리 `external_transaction_id` 라, 보낸 즉시 어느 거래인지 1:1 로 안다 — 예정 거래 자동 반영(API 9.6)의 정확 매칭이 이것에 기댄다 |
| **`transactionDate` 는 호출한 날이다** *(2026-09-14 실측)* | 채번 접두사를 어제로 보내도 응답의 `transactionDate` 는 오늘이다. §4.1.1 의 「과거 날짜 거래를 만들 수 없다」가 쓰기 응답에서도 그대로 확인됐다 — **따라잡기 실행은 실행한 날로 찍힌다** |
| **채번 접두사의 날짜를 금융망이 검증하지 않는다** *(2026-09-14 실측)* | 접두사가 어제·그저께인 20자리 채번이 `H0000` 으로 통과했다. 자동 반영이 `yyyyMMdd(예정일) + 해시 12자리` 로 **결정적 채번**을 만들 수 있는 근거다(공통규약 23장) |
| **같은 채번 재전송은 `H1007` 이고 잔액이 움직이지 않는다** *(2026-09-14 실측)* | 중복 거부가 **호출이 처리되기 전에** 걸린다. 두 서버가 같은 회차를 보내도 둘째가 돈을 옮기지 못한다 — 로컬·배포가 같은 시연 계좌를 볼 때의 마지막 방어선이다 |
| **잔액 부족은 `A1014` 다** *(2026-09-14 실측)* | 잔액 10,100원 계좌에 1,010,100원 출금 → `HTTP 400` · "계좌 잔액이 부족하여 거래가 실패했습니다". 자동 반영에서는 결함이 아니라 **정산 공백이 실제로 일어난 것**이라 다음 날 재시도로 갈린다 |
| 인증 코드 오입력의 부작용 없음 | 틀린 코드를 넣어도 인증이 무효화되지 않는다. 바로 다시 맞는 코드를 넣으면 통한다 |
| **인증 결과 코드가 넷이다** *(2026-09-08 워크북 대조)* | `ACCOUNT_AUTH_02` 시트에 `A1090`(유효하지 않음)·`A1088`(일치하지 않음)·`A1087`(시간 만료)·`A1086`(발급 기록 없음)이 다 있다. **실측으로는 `A1090`·`A1087` 둘만 만난다.** 나머지 둘을 안 다루면 그대로 `502` 로 샌다 — 앞 둘은 재입력, 뒤 둘은 재발송이라 사용자가 할 일이 갈린다 |
| **`H1003` 은 형식과 시각 오차를 둘 다 덮는다** | 워크북 문구는 "전송시각 **형식**이 유효하지 않습니다" 뿐이지만 **30분 전 시각을 보내도 `H1003`** 이다(실측). 날짜 쪽 짝은 `H1002` 이며 어제 날짜를 보내면 그게 온다. 문구만 보고 "형식만 본다"고 읽으면 시계 문제를 놓친다 |
| **`A1003` 은 세 가지를 뭉갠다** | 존재하지 않는 계좌 · 형식 이상 · **타인 계좌**가 전부 `A1003`("계좌번호가 유효하지 않습니다", HTTP 400)이다. 금융망이 구분해 주지 않으며 **우리도 구분해 알려주면 안 된다** — 계좌 존재 여부가 새어 나간다. `ACCOUNT_NO_INVALID` 하나로 모은다 |
| **금융망도 자체 유효시간을 갖는다** | 넘기면 `A1087`("인증시간이 만료되었습니다", 워크북 `ERROR_01`). **값은 문서에 없다.** 우리 Redis TTL 은 그 값을 모른 채 정한 것이라, 우리가 더 길면 금융망이 먼저 끝낸다 — 그래서 `A1087` 을 `ACCOUNT_AUTH_EXPIRED` 로 모은다. **우리 TTL 을 금융망보다 짧게 잡으면 아직 유효한 코드를 우리가 거절하므로, 모르는 동안은 넉넉한 쪽이 안전하다.** 프론트 실측(S15P21C105-111) |
| `MEMBER_01` 중복 이메일 = `E4002` | 이메일은 금융망 전역 유니크다. **우리가 이전 시도에서 만든 것일 수도, 다른 팀 것일 수도 있어 구분이 안 된다.** ERD 가 "계좌 연결 시 재시도"를 설계했으므로 `E4002` → `MEMBER_02` 로 복구하되, 다른 팀 계정을 집어 오면 계좌 목록이 빈 채로 보인다 |

> 실측에 쓴 자원 — owner 시드 계정에 수시입출금 계좌 1개(`001` 한국은행), 그리고 `MEMBER_01`
> 계약 확인용 일회성 계정 `probe-20260908@jango.test`. 회원은 삭제 API 가 없어 남는다.
> 수시입출금 상품은 이미 등록돼 있었다(`001-1-bae1077908ed4e`) — `DD_01` 을 다시 부르지 않는다.

**② 우리가 은행을 만들어야 한다 — 샌드박스**

플로우 문서가 명시한다: *"교육생(개발 앱)은 상품 등록 API를 통해 상품을 생성해야 합니다."*

```
apiKey 발급(MANAGER_01) → 사용자 계정 생성(MEMBER_01, userKey)
  → 은행코드 조회(BANK_01) → 수시입출금 상품 등록(DEMAND_DEPOSIT_01)
  → 계좌 생성(DEMAND_DEPOSIT_03) → 입금·출금·이체로 거래 발생
```

- **실제 은행 데이터가 아니다.** 배달앱 정산도 카드 매출도 존재하지 않는다.
  데모에 필요한 거래는 **우리가 심어야 한다.**
- 그래서 xlsx에 **일괄 API 시트 23종**이 따로 있다 — 「수시입출금 계좌 일괄 입금」
  「계좌 일괄 이체」 「대출 상품 일괄 등록」 「회원 일괄 등록」 등. **시드 스크립트에 이걸 쓴다.**
- 예금·적금·대출·카드 계좌는 **수시입출금 연결계좌가 먼저 있어야** 만들어진다.
  연결된 수시입출금 계좌는 해지도 안 된다.
- **이메일은 금융망 전역에서 유니크**하다. 다른 팀 앱에 이미 쓰인 이메일로는 계정을 못 만든다.
  회원가입에서 이 실패를 "다른 이메일을 쓰세요"로 안내해야 한다.

**③ 금융망 스케줄러 — 동기화 시각이 여기서 정해진다**

금융망이 자동으로 돌리는 작업과 시각이다. 전부 한국시간.

| 시각 | 작업 | 우리 쪽 영향 |
| --- | --- | --- |
| 00:00 | 마이너스통장 일별 이자 · 정기구독 결제 · 가상계좌 만료 | |
| 00:10 | 마이너스통장 납입 · 자동상환 · 만기 · **연체 처리** | 연체 알림 원천 |
| 06:30 | **적금 자동이체** (연결 수시입출금에서 출금) | 잔액 부족 시 `FAIL` |
| 07:00 | 예금·적금 만기이자 지급 후 계좌 해지 | |
| 07:30 (월) | 카드 주간 청구서 발행 (월~일 → 차주 월요일) | |
| **08:30** | **대출 상환 — 매일** | [4.13](#413-대출지원-p1-1314) 참조 |
| **09:00** | **예약이체 실행** | [4.3](#43-반복예정-거래-p0-03040506-p1-04) 참조 |
| 16:00 | 카드값 출금 (납입일) | |

> **자동 처리가 00:00~09:00에 몰려 있다.** 그날 확정된 잔고를 보려면
> **동기화 배치를 09:30 이후**에 돌린다. 그 전에 부르면 아직 안 빠진 돈을 잔액으로 읽는다.
> 카드값(16:00)까지 반영하려면 **16:30에 한 번 더** 돈다.

실패 처리 패턴도 공통이다 — **당일 재시도 없음, 다음 날 같은 시각.**
즉 06:30 적금 이체가 잔액 부족으로 실패하면 그날은 끝이고 내일 06:30에 다시 시도한다.
우리 예보가 "오늘 아침에 막았어야 했다"를 말할 수 있는 근거다.

**④ 에러 코드 214종**

접두어별로 `H`(Header) 12 · `A`(계좌) 103 · `E`(환전·외화) 92 · `G` 5 · `Q`(공통) 2.
우리 API 오류 코드 45종 enum과 **매핑 표를 만들어 두고**, 매핑되지 않은 금융망 코드는
`Q1000`(기타)으로 떨어뜨린 뒤 원본 코드를 로그에 남긴다. 안 그러면 장애 원인을 못 찾는다.

**① 일괄 API — CSV·JSON 세 가지 방식**

`BULK_REGISTER_*`가 세 형식을 받는다: **JSON Body**(`items[].payload`) · **JSON File** · **CSV File**
(둘 다 `multipart/form-data`). 공통 옵션 셋이 붙는다.

| 옵션 | 뜻 |
| --- | --- |
| `validation` | `Y`면 **검증만 하고 저장하지 않는다.** 시드 스크립트를 먼저 `Y`로 돌린다 |
| `continueOnError` | 항목 하나가 실패해도 나머지를 계속 처리 |
| `reference` | 요청 참조값. 응답에 그대로 돌아온다 — 배치 추적용 |

CSV 방식은 Header를 행마다 넣지 않고 form-data 필드로 따로 준다.
**시드는 CSV 방식이 가장 짧다.**

**② 가상계좌 — 「예상 입금」을 미리 등록하는 구조**

`VIRTUAL_ACCOUNT_01` 발급 시 `mainAccountNo`(연결 계좌) · **`depositorName`(입금자명)** ·
**`expectedAmount`(예상 입금 금액)** · `expiryDate`(**발급일부터 최대 30일**) ·
`autoTransfer`(입금 후 연결 계좌로 자동 이체, 기본 `true`)를 등록한다.
`VIRTUAL_ACCOUNT_04` 입금 내역에는 **`nameMatched`(입금자명 일치)** 와
**`settledAt`(정산 일시, 미정산 시 null)** 이 온다. 상태는 `ACTIVE → DEPOSITED → EXPIRED/CLOSED`.

> **이 구조가 P0-11 정산 대사와 개념이 같다.** "얼마가 누구 이름으로 들어올 것"을 미리 걸어 두고
> 실제 입금과 대조한다. 다만 **30일 만료**라 매주 반복되는 플랫폼 정산에는 못 쓴다.
> **1회성 큰 입금**(지원금 수령, 보증금 반환)에만 쓰고, 반복 정산은 예약이체로 간다.
>
> [`예측엔진_설계노트.md`](./예측엔진_설계노트.md)는 다른 용도를 하나 더 든다 —
> 시연 환경에서 가상계좌를 쓰면 **매출 시점을 관측할 수 있다**(G-5).
> 은행 거래내역만으로는 일별 매출을 알 수 없고 POS 연동도 하지 않으므로(SRS 1.3),
> 가상계좌가 "매출 발생 → N일 뒤 입금"의 앞쪽을 보여 주는 유일한 수단이다.
> 다만 그 데이터도 결국 우리가 만드는 것이라 학습 표본으로는 쓰지 않는다.

**③ 정기구독 — 서비스 마스터가 이미 있다**

`SUBSCRIPTION_02`가 카테고리별 구독 서비스 목록(`serviceId` · `serviceName` · `category` ·
`planName` · `monthlyPrice`)을 준다. 우리가 상품을 등록할 필요가 없다.
매일 00:00 결제, **연속 3회 실패 시 `PAUSED`**.
구독형 고정비를 데모에 넣고 싶으면 여기가 가장 싸다.

### 3.8 매출 용어 3층 — 금액의 단일 출처

공통규약이 매출을 **세 낱말로만** 쓰도록 고정했다. 구현에서 이 셋을 섞으면 같은 매출이 두 번 계상된다.

| 층 | 낱말 | 무엇 | 출처 | 저장 | 쓰는 곳 |
| ---: | --- | --- | --- | --- | --- |
| 1 | **입금** | 계좌에 실제로 찍힌 돈 | 금융망 동기화 · CSV | `TRANSACTION` | 잔액 예측 · 월별 리포트 · 부가세 · 신고서 ⑪ |
| 2 | **정산** | 플랫폼 총매출 − 취소 − 수수료 | 사용자가 명세서 보고 입력 | `SETTLEMENT` | 정산 대사(P0-11) |
| 3 | **판매** | 기간·상품별 판매 실적 | POS 인쇄물 촬영 + OCR | `PRODUCT_SALES_PERIOD` | **구성비만** — 상품 지표 · 리포트 기여도 · What-if 배율 |

> **금액의 단일 출처는 1층(입금)이다.** 3층은 **비율만** 내보내고 금액은 내보내지 않는다.
> [6.8](#68-p1-22-상품별-매출-인쇄물-추출)가 `vatAmount`까지 읽지만
> 부가세 계산(P1-11)에는 **쓰지 않는다**(명세 12장).

**「카드」가 방향이 반대인 두 가지를 가리킨다**

| | 무엇 | 방향 | 출처 |
| --- | --- | --- | --- |
| `CARD_SETTLEMENT` | 카드사가 **가맹점에 주는 정산금** | 입금 | 계좌 거래내역 적요 |
| 금융망 `CREDIT_CARD_*` | 사업자가 **카드로 쓴 결제·청구** | 출금 | 카드 API |

명세도 같은 결론에 도달해 있다 — *"금융망 API에는 가맹점 매출 입금 구조가 없다
(`createMerchant`에 계좌번호가 없고 워크북 전체에 `settlement` 0건)"*.
카드 정산 입금은 **은행 거래내역에 찍혀 계좌 동기화·CSV 경로로** 들어온다
([4.1.1](#411-데이터-시드--과거는-csv-현재미래는-금융망)).

**매출성 입금 4종** — `CARD_SETTLEMENT` · `PLATFORM_SETTLEMENT` · `CASH_SALES` · `TRANSFER_SALES`.
[P0-02 분류](#42-p0-02-거래-분류-규칙-층)와 [P1-01](#63-p1-01-거래-적요-자동-분류)의
`allowedCategories`가 이 넷을 구분해야 신고서 ⑪ 매출액이 맞는다.

### 4.1 P0-01 거래내역 수집

| 금융망 호출 | 단일 POST 클라이언트 + 공통 Header 빌더 ([3.6①](#36-ssafy-금융망--실제-인터페이스가-요구하는-것)) |
| 장애 격리 | 재시도 + 백오프 + Circuit Breaker ([3.2](#32-기능이-요구하는-추가-의존성) 주의 참조) |

| 스케줄 | `@Scheduled` **09:30 · 16:30** ([3.6③](#36-ssafy-금융망--실제-인터페이스가-요구하는-것)) |

**쓰는 인터페이스**

| 인터페이스 ID | 기능 | 쓰는 곳 |
| --- | --- | --- |
| `MANAGER_01` | API KEY 발급 | 앱 최초 설정 (1회, 수동) |
| `MEMBER_01` / `MEMBER_02` | 사용자 계정 생성 / 조회 → **`userKey`** | 회원가입 → `USER.fin_user_key` |
| `ACCOUNT_AUTH_01` | 1원 송금 (`accountNo`, `authText`) | 계좌 등록 시작 |
| `ACCOUNT_AUTH_02` | 1원 송금 검증 (`authText`, **`authCode` 숫자 4자리**) → `status: SUCCESS/FAIL` | 계좌 `CONNECTED` 전환 |
| ~~`DEMAND_DEPOSIT_04`~~ | 계좌 목록 조회 | **미채택** — 사업장 계좌는 우리가 관리한다 (아래) |
| `DEMAND_DEPOSIT_07` | 계좌 잔액 조회 | `ACCOUNT.balance` |
| **`DEMAND_DEPOSIT_12`** | **계좌거래내역조회** | 수집의 본체 |
| `DEMAND_DEPOSIT_13` | 계좌거래내역조회(단건) | 개별 재확인 |

**`DEMAND_DEPOSIT_12` 실제 계약**

요청은 `accountNo`(16) · `startDate`/`endDate`(YYYYMMDD) · `transactionType`(`M`입금 / `D`출금 / `A`전체) ·
`orderByType`(`ASC`/`DESC`, 거래고유번호 기준). 응답은 `totalCount` + `list[]`:

| 필드 | 타입 | 우리 쪽 |
| --- | --- | --- |
| `transactionUniqueNo` | Long | **중복 제거 키.** `TRANSACTION` UNIQUE |
| `transactionDate` + `transactionTime` | String(8) + String(6) | **분리돼 있다.** 합쳐서 `Asia/Seoul` 기준 `Instant`로 |
| `transactionType` | String(1) | **`1`=입금, `2`=출금.** `M`/`D`(요청값)와 다른 코드계다 |
| `transactionBalance` | **Long** | 거래금액. **원 단위 정수** |
| `transactionAfterBalance` | **Long** | **거래후잔액** — 아래 참조 |
| `transactionSummary` | String(255) | **적요.** 분류의 유일한 단서 |
| `transactionMemo` | String(255) | 거래 메모 (`TRANSACTION_MEMO_01`로 우리가 쓸 수도 있다) |
| `transactionAccountNo` | String(16), Optional | 상대 계좌번호 |

**두 가지가 설계를 바꾼다.**

**⑴ 거래처명 필드가 없다.** 있는 것은 적요(`transactionSummary`) 한 줄과 상대 계좌번호뿐이다.
`COUNTERPARTY` 사전은 **적요 문자열에서 만들어야** 하고,
[P1-01](#63-p1-01-거래-적요-자동-분류)의 입력이 "적요 한 줄"이라는 전제가 여기서 확정된다.

**⑵ `transactionAfterBalance`로 검산할 수 있다.** 우리가 시작 잔액에 거래를 누적한 값과
금융망이 준 거래후잔액이 어긋나면 **누락된 거래가 있다는 뜻**이다.
수집 직후 이 검산을 돌리고, 어긋나면 그 구간을 다시 조회한다.
잔액이 틀린 채로 예보가 나가는 것보다 낫다.

**왜 `JdbcTemplate.batchUpdate`인가** — ERD에 근거가 적혀 있다. PK를 `IDENTITY`로 잡으면
Hibernate가 JDBC 배치 삽입을 못 한다. 시퀀스 + `allocationSize`로 우회할 수 있지만 설정이 복잡하다.
**대량 삽입 경로만 JPA를 우회**하는 쪽을 골랐다. 거래 수천 건을 `saveAll`로 넣으면 안 된다.

**함정**
- **거래내역조회에 페이지네이션이 없다.** `startDate`~`endDate`로 자르는 것이 유일한 수단이다.
  초기 적재는 **한 달 단위로 쪼개고**, 한 번에 오는 건수를 로그로 남겨 한계를 파악한다.
  **하한은 `ACCOUNT.created_at`(계좌를 연결한 날)이다** — 고정 기간을 쓰면 계좌 개설 이전
  구간에서 빈 응답만 받는다. 연결 이전 거래를 안 가져오는 것은 손실이 아니라 4.1.1 의
  경계 그대로다(과거는 CSV). 결정 근거는 공통규약 23장.
- 증분 동기화는 **마지막 성공 시각 전날부터** 다시 조회한다.
  중복은 `transactionUniqueNo`가 막아 준다.
- 금액이 `Long`(원 단위 정수)이라 **수집 단계에는 `BigDecimal`이 필요 없다.**
  `BigDecimal`은 배분·비율 계산([4.8](#48-p0-11-정산-수동-대사) 등)에서 쓴다.
- **1원 인증 코드는 거래내역에 들어온다.** `ACCOUNT_AUTH_01`로 1원을 보내면
  숫자 4자리 인증코드가 `transactionSummary`에 찍히고, 사용자가 그걸 읽어 입력한다.
  즉 **1원 인증 화면이 거래내역조회에 의존**한다. `authText`(기업명)는 01·02에서 같아야 한다.
- **그 1원들은 수집에서 제외한다** *(2026-09-08 결정)*. 인증 아티팩트지 사업 거래가 아닌데,
  거르지 않으면 거래 목록에 보이고 분류 파이프라인을 타고 **잔액 곡선에까지 들어간다.**
  계좌를 연결할 때마다 최소 1건씩 쌓이고 재발송하면 더 쌓인다.

  판정 규칙 — **입금이고 · 금액이 1원이고 · 적요가 `authText` 로 시작**하면 제외한다.
  세 조건을 모두 봐야 한다. 실측 적요는 `"잔고예보 5020"` 형태이므로 셋 다 만족하는 실제
  사업 거래는 사실상 없다.

  > 더 정확한 방법이 있긴 하다 — `ACCOUNT_AUTH_01` 응답이 `transactionUniqueNo` 를 주므로
  > 그 값을 저장해 두면 오탐이 원천적으로 0 이 된다. **채택하지 않았다.** 인증 흔적을 계좌
  > 수명 내내 들고 있어야 해서 Redis(10분 TTL)로는 안 되고 컬럼·테이블이 필요한데,
  > 위 세 조건으로 충분한 문제에 마이그레이션을 붙이는 값이 크다. 오탐이 실제로 관측되면
  > 그때 옮긴다.
- 실패해도 `lastSyncedAt`과 재시도 상태를 남긴다 (SRS 12장 가용성 요구).
  현재 `syncStatus`가 항상 `NEVER`인 것은 금융망 미연동 때문이다.
- 은행 CSV는 EUC-KR/CP949가 많으므로 BOM 확인 + 인코딩 감지 후 변환하고,
  실패하면 사용자에게 인코딩을 묻는다.

**계좌는 「등록」이 아니라 「선택」이다 — 제안, 미채택 (2026-09-08)**

> ⚠ **이 제안은 채택되지 않았다. 계좌 연결은 명세 7.2대로 계좌번호 입력으로 간다.**
> 명세 7.2 요청 본문이 `accountNo` 이고 화면구성도 SC-01-4 도
> "은행 선택(`GET /bank-codes`) → 계좌번호 입력"으로 그려져 있다.
> 문서가 갈리면 **API 명세를 따른다**(ERD 서문·백엔드 작업 계획).
> 따라서 `DEMAND_DEPOSIT_04` 는 P0-01 최소 범위에서 **뺀다.**
>
> 이 절이 "현재 API 는 계좌번호를 받는 구조라 **바꿔야 한다**"고 단정해 두는 바람에
> 구현 착수 시점에 명세와 정면으로 충돌했다. 근거는 남기되 판정을 함께 적는다.

`DEMAND_DEPOSIT_04`는 `userKey` 하나만으로 사용자의 **전체 계좌 목록**을 준다 —
`accountNo` · `bankName` · `accountName` · `accountTypeCode`(`1`수시입출금 `2`정기예금
`3`정기적금 `4`대출) · **`accountBalance`** · `lastTransactionDate`.

| 제안이 노렸던 것 | 미채택으로 치르는 값 |
| --- | --- |
| 계좌번호를 입력할 이유가 없다 — 목록에서 고르게 한다 | 사용자가 계좌번호를 입력한다. 대신 1원 인증이 오타를 잡는다 |
| 목록에 잔액이 있으니 계좌마다 `DD_07` 을 안 부른다. N번이 1번이 된다 | **잔액은 `DEMAND_DEPOSIT_07` 로 계좌마다 부른다.** 사업장당 계좌 1~3개라 N이 작다 |
| `lastTransactionDate` 가 안 바뀐 계좌는 거래내역 조회를 건너뛴다 | 이 최적화도 함께 포기한다. `transactionUniqueNo` UNIQUE 가 중복을 막으므로 손실은 호출 몇 번뿐이다 |

되돌린다면 조건은 하나다 — **명세 7.2 와 화면 SC-01-4 를 먼저 고치는 것.**
그 전에 어댑터만 바꾸면 프론트가 붙일 화면이 사라진다.

#### 4.1.1 데이터 시드 — 과거는 CSV, 현재·미래는 금융망

**금융망에는 과거 날짜의 거래를 만들 수 없다.**
`DEMAND_DEPOSIT_09`(입금) · `08`(출금) · `10`(이체) · 일괄 API(`BULK_REGISTER_04`) 모두
요청 항목이 `accountNo` · `transactionBalance` · `transactionSummary` 뿐이고 **날짜 파라미터가 없다.**
Header의 `transmissionDate`로 우회할 수도 없다 — 서버 시각 ±5분을 벗어나면 `H1003`이다.

> **실측 확인 (2026-09-08).** 위 판단이 문서상 추론이었으므로 샌드박스에서 직접 확인했다.
> `DEMAND_DEPOSIT_09` 요청에 `transactionDate`·`transactionTime` 을 넣어도 **`H0000`(정상처리)이
> 돌아오지만 값이 무시된다** — `DEMAND_DEPOSIT_12` 로 조회하면 전부 호출 당일 날짜로 기록돼 있다.
> **성공을 반환하면서 조용히 버리는 형태**라, 이 사실을 모르고 시딩 스크립트를 만들면
> "동작하는 것처럼 보이는데 전부 오늘 날짜"인 데이터가 만들어진다. 4.1.1 의 CSV 분리가 유일한 경로다.

그런데 우리에게는 과거가 필요하다.

| 필요한 것 | 왜 |
| --- | --- |
| 과거 6주 정산 이력 | P0-03 반복 탐지 최소 관측 3~4회 |
| 과거 3개월 지출 이력 | P1-08 안전선(고정비 rolling aggregate) |
| 과거 거래 수백 건 | P1-01 few-shot과 분류 대상 |

**그래서 경로를 둘로 나눈다.**

```
과거 3~6개월 ── CSV 업로드 ─────┐
                               ├─→ TRANSACTION ─→ 반복 탐지 · 분류 · 안전선
현재 잔액   ── DEMAND_DEPOSIT_07 ┘                          │
미래        ── 예약이체 ────────────────────────────────────┴─→ 예측 · 공백 · 시나리오
```

이 분리가 성립하는 이유: **과거 거래는 잔액 계산에 들어가지 않는다.**
예측 엔진의 입력은 `FORECAST_RUN.opening_balances` + `PLANNED_TRANSACTION`이고,
`opening_balances`는 금융망 현재 잔액에서 온다. 과거 거래는 **패턴 탐지와 분류 학습용**이다.
설계가 이미 그렇게 되어 있어 두 경로가 충돌하지 않는다.

- CSV 업로드는 **이미 구현된 경로**다(`POST /accounts/{accountId}/transactions/import`, 202 + Job).
- **`transactionAfterBalance` 검산은 금융망 연동 시작 시점 이후에만 건다.**
  CSV 구간에는 거래후잔액이 없다.
- 중복 제거 키가 경로마다 다르다 — 금융망은 `transactionUniqueNo`, CSV는 (계좌·일시·금액·적요) SHA-256.
- 데모 서사도 이 구조가 낫다 — "거래내역 CSV를 올리면 예보가 나오고, 계좌를 연결하면 이후는 자동으로 갱신된다."

**시드 순서**

1. `MANAGER_01` apiKey 발급 → 앱 설정
2. `MEMBER_01` × 3 → `userKey` 확보
3. `BANK_01` → `DEMAND_DEPOSIT_01`(상품) → `DEMAND_DEPOSIT_03`(계좌)

6. **미래**: `TRANSFER_RESERVATION_01`로 정산 입금 등록. **공백 구간은 비워 둔다**
7. `LOAN_05` → `06` → `07` 대출 가입. 상환액이 공백일에 걸리도록 금액·기간 설계

7번까지 하면 **금융망이 스스로 공백을 만든다** — 매일 08:30 상환이 잔액을 밀어내고,
정산이 없는 구간에서 잔고가 내려가며, 실패하면 `LOAN_09.failureReason`에
"자동이체 실패 잔액 부족"이 남는다([4.13](#413-대출지원-p1-1314)).

**시드 스크립트는 버리는 코드가 아니라 데모 시나리오 그 자체다.** 저장소에 넣고,
발표 전날 다시 돌려 상태를 고정한다. 금융망 스케줄러가 매일 잔고를 바꾼다.

### 4.2 P0-02 거래 분류 (규칙 층)

| 구분 | 선정 |
| --- | --- |
| 카테고리 | `TRANSACTION_CATEGORY` (flat Enum 시드) — **API 이미 구현됨** |
| 규칙 | `CLASSIFICATION_RULE` — 우선순위 있는 패턴 매칭 |
| 거래처 사전 | `COUNTERPARTY` + `pg_trgm` GIN 인덱스 |
| 이력 | `TRANSACTION_CLASSIFICATION_HISTORY` — 감사 로그이자 [P1-01](#63-p1-01-거래-적요-자동-분류) few-shot 원천 |
| 순서 | 사용자 확정 → 규칙 → 사전 → AI → 사용자 확인 |

**입력이 적요 한 줄뿐이다** — 금융망 거래내역에 거래처명 필드가 없다([4.1](#41-p0-01-거래내역-수집)).
쓸 수 있는 것은 `transactionSummary`(255자)와 `transactionAccountNo`(상대 계좌번호)뿐이다.

- `COUNTERPARTY` 사전은 **적요 문자열에서 만들어야 한다.** 계좌번호가 있는 거래는
  계좌번호를 키로 삼는 편이 문자열보다 안정적이다 — 적요는 은행·플랫폼마다 표기가 흔들린다.
- 규칙(`CLASSIFICATION_RULE`)은 적요에 대한 패턴 매칭이 된다. 정규식보다
  **포함 문자열 + 우선순위** 로 시작하고, 사장님이 직접 규칙을 만들 수 있게 한다.
- `TRANSACTION_MEMO_01`로 금융망 거래에 메모를 되쓸 수 있지만, **하지 않는다.**
  분류 결과의 단일 기준은 우리 DB다. 두 곳에 쓰면 동기화 문제가 하나 더 생긴다.

**함정**
- **사용자 확정값을 절대 덮어쓰지 않는다.** 재분류 배치가 돌 때 확정 플래그를 먼저 본다.
  이 한 줄이 빠지면 사장님이 고친 분류가 다음 날 원상복구된다.
- `pg_trgm`은 `CREATE EXTENSION pg_trgm`과 GIN 인덱스가 필요하다. **Flyway 마이그레이션에 넣는다.**
- 규칙 우선순위가 같으면 결과가 비결정적이 된다. 정렬 키를 `(priority, id)`로 고정한다.
- 분류를 고칠 때마다 `TRANSACTION_CLASSIFICATION_HISTORY`에 남긴다. 나중에 AI few-shot이 여기서 나온다.
  지금 안 쌓으면 P1-01 착수 시점에 학습 재료가 없다.

### 4.3 반복·예정 거래 (P0-03/04/05/06, P1-04)

**P0-03 탐지**

| 구분 | 선정 |
| --- | --- |
| 주기 추정 | 날짜 간격의 **median + MAD**. 평균·표준편차는 이상치 한 건에 무너진다 |

"왜 이게 반복이라고 판단했나"에 "최근 6주 화요일마다 78만~96만원"이라고 답할 수 있어야 한다.

**P0-03 이 예측 곡선의 품질을 지배한다** *(2026-09-09 실측 · 3번 파트)*

M-1 이 받는 것은 잔여(`실제 − 예정 매칭분`)이고, 그 뺄셈을 P0-03 이 해 준다. 그래서
**탐지 품질이 곧 예측 품질**이다. 민감도를 재 봤다 (합성 데이터, hold-out 창 9,600개).

| ---: | ---: | ---: |
| 100% | 0.687 | 8.99일 |

- **재현율 95% 이상이 필요하다.** 90%가 경고선, 80%면 예측이 의미를 잃는다.
- **정밀도는 느슨해도 된다** — 미탐 5%가 **−0.064**(창 9,600개)인 반면, 오탐 28%의 대가는 **방향만 확인됐다**. *(2026-09-10 정정: −0.018 → −0.032 → −0.016 으로 하루에 두 번 바뀌었다. 그 표는 **창이 63개**뿐이라 TP 한 개가 값을 흔든다. 설계노트 M-3 참조. 요구사항은 미탐 쪽만으로 선다.)*
- **P0-03 이 없으면 F1 0.029 다.** 예정 항이 비면 곡선의 「알려진 값」이 사라진다.
  우리 데이터에서 **입금의 79%·출금의 51%가 예정거래**이므로, 탐지가 없으면 들어오는 돈의
  80%가 빠진 곡선이 된다.

**구현할 때 밟을 함정 넷** — 같은 방식으로 파이썬 대역을 만들어 보고 실제로 밟은 것이다.
*(2026-09-10 확인: **들어온 구현은 넷 다 피했다.** 아래 채점 결과와 코드 근거 참고.
남겨 두는 이유는 허용폭을 나중에 느슨하게 조정할 때 다시 밟을 자리라서다 — 실제로
③④는 허용폭을 둔 내 대역이 밟았고 엄격한 BE 구현은 안 밟았다.)*

1. **공휴일 밀림 관대함이 주기를 삼킨다.** 밀림을 견디려 ±3일을 허용하면 **7일 주기에서
   그건 4/7 을 덮는다.** 주 2~3회 사는 식자재가 「매주 수요일」로 적합도 1.00 이 나왔다.
   **「그 주기에 한 번인가」를 같이 봐야 한다** — 실측에서 진짜 예정거래는 주당 발생이
   최대 1.02 였고, 식자재는 2.40 · 현금입금은 2.88 이었다.
2. **금액 흔들림(MAD/median)으로 소액지출을 거를 수 있다.** 임차료 0.005 · 급여 0.05 ·
   카드정산 0.14~0.39 · 소액지출 0.31~0.43 이다. **0.40 이 경계**고 더 조이면 카드정산이
   잘려 나간다(현대카드정산 0.391). 이 둘로 정밀도가 47.7% → 72.0% 로 올랐고 재현율은
   100% 를 유지했다.
3. **`WEEKLY` 는 요일뿐 아니라 간격도 봐야 한다** *(2026-09-10 추가)*. **①의 다른
   얼굴이다** — ①은 「주 2~3회가 매주로 통과한다」였고, 이쪽은 **「2주에 한 번·한 달에
   한 번도 매주로 통과한다」**다. ±3일이 4/7 을 덮으므로 간격이 14일이든 30일이든 요일만
   맞으면 걸린다. **①의 밀도 검사로는 안 잡힌다** — 주당 발생이 0.5, 0.23 이라 상한
   1.15 아래로 조용히 통과한다. 관측일 간격의 **중앙값이 6~8일인지** 보는 한 줄이 필요하다.
4. **주기당 발생 횟수는 n−1 로 센다** *(2026-09-10 추가)*. n 번 관측되면 그 사이 간격은
   **n−1 개**다. `len(days)` 로 세면 한국전력 5회/121일이 「월 1.26회」가 되어 ①의 상한
   1.15 에 걸리고 **정답인 `MONTHLY` 가 후보에서 걸러진다.** n−1 로 세면 1.01 이라 통과한다.
   **①을 구현하면 같이 따라오는 함정이다.**

> **BE 구현에는 해당하지 않는다** *(2026-09-10 코드 확인)*. `Weekly.tryMatch` 가
> **요일 일치율 1.0 을 요구하고 그 위에 `gaps.anyMatch(g -> g != 7L)` 로 간격까지 막는다**
> — 주석도 「같은 요일이어도 격주면 간격이 14일이다 — 그건 INTERVAL 이 맞다」로 적혀 있다.
> `Monthly` 도 간격 26~35일을 검사한다. ④는 `gaps()` 가 `i = 1` 부터 돌아 **구조적으로
> n−1 개**다. **아래 채점의 재현율 100% · 정밀도 86.8% 가 그 결과다.**
>
> **③④는 내가 ①을 여기에 적어 놓고도 밟았다.** 팀원 시연 CSV 로 곡선을 그려 보니 축
> 쳐져 있었고, 파 보니 월 1회 청구(한전·가스·KT)가 30일 예측에 **4번씩** 찍히고 격주
> 식자재가 **2번씩** 찍혔다. 30일 순증감이 **−3,817,400원**으로 투영됐는데 실제는
> −52,800원이었다. 고친 뒤 **+311,300원**이 됐고, **내 파이썬 대역**을 같은 시험 데이터로
> 다시 채점하니 **정밀도가 72.0% → 74.7%** 로 올랐다(재현율 100% 유지 · 오탐 398 → 347건).
> 격주를 매주로 잡던 오탐이 사라져서다. **BE 구현의 86.8% 는 이 정정과 무관하다** —
> 위에 적었듯 애초에 안 밟았다.
>
> **합성 데이터에서는 안 보였다.** 생성기가 격주·월간을 다른 적요로 만들어 섞이지 않는다.
> 실제 형태 CSV 한 개가 이 둘을 포함해 **버그 다섯**을 찾았다.

**채점용 시험 데이터가 있다** — 사업장 3곳 × 1년, 규격 그대로의 거래 CSV + **어느 거래가
예정거래인지 적힌 정답 JSON**. `private/현재/P0-03_인계/` (담당 이한호).

**들어온 구현을 그 데이터로 채점했다** *(2026-09-09 · `RecurringPatternDetector`)*

| 사업장 | 정답 | 재현율 | 정밀도 |
| --- | ---: | ---: | ---: |
| shop0 | 424건 | 100.0% | 89.1% |
| shop1 | 332건 | 100.0% | 86.5% |
| shop2 | 268건 | 100.0% | 83.8% |
| **합계** | **1,024건** | **100.0%** | **86.8%** |

**요구했던 재현율 95% 를 넘는다.** 위 「함정 ①」이 걱정한 방향과 반대로 갔는데도 그렇다 —
`Weekly` 가 「전부 같은 요일 AND 간격이 정확히 7일」이라 엄격한데, **떨어진 것을
`INTERVAL` 이 받는다**(편차 25% 허용 = 7일 ±1.75일). 판정 분포가 `INTERVAL` 16 ·
`MONTHLY` 23 · `WEEKLY` 3 인 게 그 증거다. **엄격함이 바꾼 것은 라벨이고 탐지 여부가
아니다.** 함정 ①은 이 구현에는 해당하지 않는다.

재현율을 실제로 지킨 것은 **적요 정규화**다 — `GroupKey.normalize` 가 숫자·구분자를
지워 `급여1`·`급여2` 를 한 그룹으로 묶는다. 그게 없으면 그룹마다 표본이 3건 미만이 되어
**아무것도 탐지되지 않는다.**

⚠ **두 가지가 이 점수를 실제보다 높게 만든다.**
① 시험 데이터 CSV 는 규격이라 `categoryId` 가 없어 그룹 키가 거칠다 — 실제로는 분류가
갈리면 그룹이 쪼개져 표본이 줄어든다. ② 우리 생성기의 적요는 `임차료`·`한스빌딩` 처럼
깨끗하고 항상 같다. **실제 통장 표기는 지저분해서 그룹핑부터 실패한다.**

*재현율 상한이 하나 숨어 있다.* `MAX_CANDIDATES = 30` 이 신뢰도 상위 30건만 남긴다.
시험 데이터는 후보가 13~15개라 안 걸렸지만, **거래처가 많은 사업장에서는 걸리고 그때
잘려 나가는 것이 곧 미탐**이다. 미탐이 오탐보다 **약 2배** 비싸므로 그 시점에 재봐야 한다.

**금융망 예약이체 — 데모에서 돈이 실제로 움직인다**

| `TRANSFER_RESERVATION_01` 요청 | 값 |
| --- | --- |
| `withdrawalAccountNo` / `depositBankCode` / `depositAccountNo` | 출금·입금 계좌 |
| `transactionBalance` | 이체 금액 |
| `reservationName` | 예: `매월 월세` |
| `reservationType` | `ONCE` / `REPEAT` |
| `startDate` / `endDate` | YYYYMMDD (종료일 선택) |
| `transferCycle` | `DAILY` / `WEEKLY` / `MONTHLY` |
| `transferDay` | **월간** 반복일 `01`~`31` |
| **`depositTransactionSummary`** / `withdrawalTransactionSummary` | **입금·출금측 적요를 따로 지정** |

응답은 `reservationId` · `nextTransferDate` · `status`(`ACTIVE`/`PAUSED`/`CANCELED`/`COMPLETE`).
실행 이력은 `TRANSFER_RESERVATION_02`가 `transferDate` · `transferTime` ·
`resultCode` · `resultMessage`로 준다.

- **`WEEKLY`에는 요일 지정 필드가 없다.** `startDate`의 요일로 반복된다 —
  화요일 정산을 만들려면 `startDate`를 화요일로 잡는다.
- `depositTransactionSummary`에 `우아한형제들`을 넣으면 사장님 통장에 그 적요로 찍힌다.
  **분류 데모의 입력이 여기서 만들어진다.**
- 우리 `PLANNED_TRANSACTION`과 개념이 겹치지만 **역할이 다르다.**
  예약이체는 금융망에서 **실제로 돈이 움직이고**, `PLANNED_TRANSACTION`은 **우리가 예측하는 것**이다.
  둘이 맞아떨어지는지가 곧 P1-05 예측 정확도다.
- 실패해도 **당일 재시도가 없고 다음 날 09:00**에 다시 실행한다.
  일반 실패는 `ACTIVE` 유지, 계좌 해지 같은 영구 오류만 `FAILED`로 끝난다.

**함정 (공통)**
- **`BigDecimal.equals()`는 scale까지 비교한다.** `1.0`과 `1.00`이 다르다. 값 비교는 반드시 `compareTo`.
- 월말 처리 — 매월 31일 패턴의 2월은 며칠인가. `TemporalAdjusters.lastDayOfMonth()` 규칙을
  **명시적으로 정하고 테스트를 쓴다.** 암묵적으로 두면 2월마다 버그가 난다.
- 시간대는 `Asia/Seoul` 하나로 고정하고, `Instant` ↔ `LocalDate` 변환 지점을 한 곳으로 모은다.
  금융망은 `transactionDate`(8) + `transactionTime`(6)을 **따로** 주므로 합치는 지점이 여기다.

### 4.4 예측 엔진 (P0-07 + P1-05 + P1-07)

> **이 절의 범위는 결정론 부분이다.** [`예측엔진_설계노트.md`](./예측엔진_설계노트.md) v2의
> **Layer 1(회계 항등식)** 과 **Layer 3(What-if)**, 그리고 **Layer 2의 통계 베이스라인**까지가 여기다.
> Layer 2에 얹히는 **모델은 [6.9](#69-p0-07p1-05-예측-모델)** 에서 다룬다.
> 통계 베이스라인은 모델을 채택해도 **지우지 않는다** — 채택 게이트의 기준선이자 폴백 경로다.

**P0-07 예상 잔액 — 이 제품의 심장**

| 구분 | 선정 |
| --- | --- |
| 계산 | Java **순수 함수**. 입력 = 계좌 시작 잔액 + `PLANNED_TRANSACTION`. 부수효과 없음 |
| 루트 | `FORECAST_RUN` (base_at, start_date, end_date, model_version, applied_options, opening_balances, basis) |
| 곡선 | `DAILY_BALANCE_FORECAST` (balance_min / expected / max, expected_deposit, expected_withdrawal, confidence) |
| 근거 | `FORECAST_RUN.basis` JSONB — 화면의 "확정 11건 · 예측 7건" 이 여기서 나온다 |
| 캐시 | 사전 계산 결과가 DB에 있으므로 조회는 SELECT. Redis는 짧은 TTL 보조 |

**함정**
- **순수 함수 유지가 인수 조건이다.** "7/14/30일 잔액과 부족일이 동일한 입력에 대해 재현된다."
  함수 안에서 `LocalDate.now()`를 부르면 그 순간 깨진다. **기준 시각을 인자로 받는다.**
  → 같은 입력을 두 번 돌려 결과가 같은지 검사하는 테스트를 **CI에 넣는다.**
- 재계산할 때 이전 `FORECAST_RUN`을 지우지 않는다. **P1-05가 과거 예측을 필요로 한다.**
  보관 기간을 정하고 그 뒤에 정리한다.
- min/expected/max 세 계열은 뒤로 갈수록 벌어져야 한다. 폭이 일정하면 신뢰 구간 계산이 틀린 것이다.

**P1-05 예측 정확도**

| 구분 | 선정 |
| --- | --- |
| 자동 매칭 | (날짜 차이, 금액 오차율, 거래처 유사도) 가중 점수 → 임계값 위만 |
| 수동 매칭 | 1:1 연결 API |
| 지표 | 적중률, 평균 날짜 오차(일), 평균 금액 오차율 |
| 보정 | 표본이 충분한 사업장에만 계수 적용 |

**P1-07 계절성**

| 단계 | 방법 | 조건 |
| --- | --- | --- |
| 1 | 월·요일별 median 계수 → `SEASONAL_FACTOR.multiplier` | 즉시 |
| 2 | STL decomposition | 사업장별 6~12개월 데이터 |

`SEASONAL_FACTOR.confirmed`가 이미 컬럼에 있다 = **사용자가 직접 지정한 성수기**.
표본이 부족하면 추정 계수보다 이쪽을 우선한다.

> **층 구조 (설계노트 v2).** 예측 엔진은 4층이다 —
> **Layer 1 회계 항등식**(영구 결정론) · **Layer 2-A 원장**(항목별 예정일·금액 범위) ·
> **Layer 2-B 잔여 흐름**(원장이 설명하지 못한 나머지, v2 신설) · **Layer 3 What-if**(결정론적 변환).
> 이 절은 Layer 1·3과 Layer 2의 통계 베이스라인을 담고,
> [4.6](#46-p0-0913-what-if-시나리오)이 Layer 3, [6.9](#69-p0-07p1-05-예측-모델)가 Layer 2의 모델이다.
>
> **모델을 얹어도 이 절의 코드는 그대로다.** 모델 출력은 순수 함수에 **인자로 주입**되고,
> 함수 안에서 추론을 호출하지 않는다. 그래서 재현성 인수 조건이 유지된다.

### 4.5 P0-08 자금 부족 알림

| 구분 | 선정 |
| --- | --- |
| 탐지 | `DAILY_BALANCE_FORECAST` 순회 → 0원·안전선 하회 **연속 구간** 추출 |
| 저장 | `ALERT` (core 스키마) — `alert_type = CASH_GAP` / `SAFETY_LINE` |
| 중복 방지 | `ALERT.dedup_key` |
| 식별자 | **`ALERT.id` = API `cashGapId`** (화면 SC-03-2의 `/dashboard/gaps/{cashGapId}`) |
| 등급 | `risk_level`: `SAFE` · `CAUTION` · `DANGER` · `GAP` |
| 표기 | 색 + 도형 + 문구 3채널 (SRS 12장 UI 요구) |

`ALERT`는 범용 인앱 알림이다. `alert_type` 6종: `CASH_GAP` · `SAFETY_LINE` · `RESERVE_SHORTFALL` ·
`SETTLEMENT_MISMATCH` · `PATTERN_CANDIDATE` · `EVIDENCE_MISSING`.
`CASH_GAP`이라는 **테이블은 없다.** 알림 유형 값이다.

**함정**
- 예측이 다시 돌 때마다 알림을 새로 만들면 **알림 폭탄**이 된다.
  "어제의 9/13 공백"과 "오늘의 9/13 공백"이 같은 공백인지 판정하는 규칙을 먼저 정하고
  `dedup_key`에 반영한다.
- 안전선(P1-08)이 바뀌면 기존 `SAFETY_LINE` 알림의 유효성을 재평가한다.
- `message`는 확정 표현 금지 (ERD 컬럼 설명에 명시). "부족합니다"가 아니라 "가능성이 있습니다".

### 4.6 P0-09·13 What-if 시나리오

**두 기능이 한 API를 쓴다.** 명세 11장: *"P0-09 기본 3종과 P0-13 확장 파라미터를 하나의 API로
처리한다. 파라미터는 자유롭게 조합할 수 있다."* 구현은 하나지만 완료 기준이 둘이다.

| | P0-09 기본 시나리오 분석 | P0-13 What-if 고도화 |
| --- | --- | --- |
| 파라미터 | **3종** — 정산 지연 · 입금 감소 · 추가 지출 | 확장 — 추가 **입금** · 지출일 변경 · **조합** |
| 화면 | SC-06-1 빌더 | **SC-06-2 저장 시나리오 목록** |
| 요구 | 재계산이 된다 | **원본 보존 + 저장 + 비교** |
| 우선순위 | P0 | P0 (v1.2에서 P1-10 → 승격) |

| 구분 | 선정 |
| --- | --- |
| 계산 | **P0-07 엔진 재사용.** 별도 엔진을 만들지 않는다 |
| 파라미터 | `SCENARIO`, `SCENARIO_ADJUSTMENT` (조합 자유) |
| 실행 | **파라미터만 저장.** 결과는 조회 시 현재 데이터로 재계산 |
| 비교 | 원본 `FORECAST_RUN` vs 시나리오 run 두 계열 |
| 저장 목록 | `SCENARIO` 목록 조회 — P0-13의 산출물 |
| 자연어 입력 | [6.1](#61-p0-09-시나리오-자연어-해석) — 파라미터 변환만, 계산은 엔진 |

[`예측엔진_설계노트.md`](./예측엔진_설계노트.md)의 **Layer 3**가 이 절이다 —
원장 스냅샷에 결정론적 변환을 걸고 Layer 1을 재실행할 뿐, **모델 재추론이 없다.**
`PRODUCT_SALES_CHANGE`(11.1)도 상품 구성비로 **배율 하나**를 만들어 기존 입금 패턴에 곱하는
결정론적 변환이라 여기 들어온다([3.8](#38-매출-용어-3층--금액의-단일-출처)).

**함정**
- **결과를 저장하면 안 된다.** 어제 만든 시나리오를 오늘 열면 어제 예측과 비교하게 된다.
  파라미터만 저장하고 열 때마다 다시 돌린다. 그래서 엔진이 빨라야 한다.
- 원본 예측을 건드리지 않는다. 복제 후 조정한다.
- **실제 이체·대출 실행을 하지 않는다.** 가상 시뮬레이션이라는 표시를 화면에 남긴다.

### 4.7 P0-10 증빙 관리 (저장 층)

| 구분 | 선정 |

| 접근 | 사전서명 URL 또는 서버 프록시. **정적 경로 직접 노출 금지** |

`EVIDENCE_EXTRACTION`에 `model_name` · `model_version` · `pipeline` · `is_current`가 있다.
**모델 비교 실험을 설계에 이미 반영해 둔 것**이므로 [6.4](#64-p1-02-멀티모달-증빙-인식매칭)의
3자 비교를 그대로 저장할 수 있다.

**함정**

- 디스크 309GB. 영수증 원본을 무제한 보관하면 찬다. **보관 기간 정책을 정한다** (세법상 5년).
- 원본 이미지와 추출 원문은 로그 금지.

### 4.8 P0-11 정산 수동 대사

| 구분 | 선정 |
| --- | --- |
| 계산 | `BigDecimal` 배분·차액 |
| 데이터 | `SETTLEMENT` (gross_sales, cancellation_amount, fee_amount) + `SETTLEMENT_TRANSACTION` |
| 불변식 | **Σ배분액 = 실제 입금액.** 어긋나면 저장 거부 |
| 잔여 | 배분되지 않은 금액을 항상 화면에 노출 |
| 알림 | 불일치 시 `ALERT.alert_type = SETTLEMENT_MISMATCH` |

**함정**
- 수수료·취소가 있어 "매출 − 수수료 = 입금"이 딱 안 맞는 게 **정상**이다.
  차액을 숨기지 말고 사유를 적을 칸을 둔다.
- 배분 반올림에서 1원 오차가 난다. **마지막 행에 몰아주는 규칙**을 명시하고 테스트한다.

### 4.9 P0-12 종합소득세 신고서 초안 (P1-23 검토 화면 포함)

기능 이름이 v1.5에서 「신고 준비자료 내보내기」에서 **「신고서 초안 자동 채움·내보내기」** 로 바뀌었다.
파일을 뽑는 기능이 아니라 **서식을 채우는 기능**이다. 화면도 셋으로 갈렸다.

| 화면 | 무엇 | 기능 | 기기 |
| --- | --- | --- | --- |
| SC-07-6 | 신고 준비자료 내보내기 (XLSX·ZIP) | P0-12 부속 | PC |
| **SC-07-7** | 신고자료 검토 상태 확정 | P0-12 · **P1-23** | PC |
| **SC-07-8** | **신고서 초안** — 자동 채움 · 근거 · 민감 항목 입력 · 내보내기 | P0-12 | PC |

| 구분 | 선정 |
| --- | --- |
| 서식 기준 데이터 | **`TAX_FORM_TEMPLATE`** — 귀속연도별 서식 항목·출처·민감 여부·카테고리 매핑 |
| 초안 저장 | **`TAX_FILING_DRAFT`** — 항목 값·출처·근거 요약 JSONB. **민감 항목 값은 저장하지 않는다** |
| 집계 | 검토 확정 거래 + 연결 증빙 → 서식 항목별 Java 집계 |
| 검토 상태 일괄 변경 | JPA Bulk Update (`@Modifying`). **Spring Batch는 과하다** |
| XLSX | Apache POI **SXSSF** (스트리밍) |
| PDF | HTML → PDF 렌더링 또는 OpenPDF. **한글 폰트 임베딩 필수** |
| ZIP | `ZipOutputStream` 스트리밍 |
| 비동기 | `JOB.job_type = EXPORT_GENERATION` → `result.storage_key` + `expires_at` |
| AI | **초안 생성에는 호출하지 않는다.** 점검 보조만 [6.2](#62-p0-12-신고서-초안-점검-보조-p1-옵션) |

**민감 항목은 저장하지 않는다 — 마스킹이 아니라 미저장이다**

SRS 12장이 개인정보 요구사항을 확장했다: 신고서 민감 항목
(**주소지 · 생년월일 · 주민등록번호 · 계좌번호 · 부양가족 인적사항**)은
**서버 미저장 · AI 미전달**이다.

- `TAX_FORM_TEMPLATE.fields[].sensitive`가 어느 항목이 민감한지 정한다.
- 민감 값은 **사용자가 내보내기 시점에 입력**하고, 그 요청 안에서만 존재한다.
- 초안을 다시 조회하면 **마스킹된 상태만** 돌아온다.
- 인수 조건(SRS 13장)이 *"서버 저장소·AI 워커 로그 어디에도 남지 않는다"* 로 못 박았다 —
  로그 필터를 별도로 검증한다([3.5](#35-보안--이미-설계에-들어-있는-것)).

**함정**
- **RAM 15GB.** XSSF(비스트리밍)로 수만 행을 만들면 OOM이다. SXSSF + 임시 파일로 간다.
- 생성 파일에 만료 시각을 둔다 (`JOB.result.expires_at`이 이미 설계돼 있다).
  **만료 파일 정리 배치를 같이 만든다.** 안 만들면 디스크가 조용히 찬다.
- **개인 사용 가능성 거래는 항목 금액에서 빼고 별도 합계로 보여 준다**(ERD 1.9 「소비처와 비소비처」).
  금액에 섞으면 사장님이 그대로 신고하고 나중에 문제가 된다.
- 각 항목에서 **근거 거래·증빙 목록을 열 수 있어야** 한다. 숫자만 보여 주면 검증이 불가능하다.
- **상품별 매출(P1-22)은 이 집계에 들어가지 않는다.** 매출 대사에 **참고값으로만** 나온다
  ([3.8](#38-매출-용어-3층--금액의-단일-출처)).
- **세무 판단을 하지 않는다.** 세액은 계산하지 않고 **소득금액까지만** 채운다(SRS 1.3).
  기준연도·출처·전문가 확인 안내를 **생성 파일 안에도** 넣는다.

### 4.10 (결번)

원자재 가격 지표(P1-06)의 선정이 여기 있었다 — KAMIS·ECOS 배치, `COMMODITY_INDEX`·`COMMODITY_PRICE`, `BUSINESS_INGREDIENT`, 「가격 변동률 × 재료비 비중」 영향 계산. **SRS v1.10 에서 P1-06 이 범위 제외(결번)되어 전부 삭제했다.** 절 번호는 다른 절 참조 때문에 그대로 비워 둔다.

What-if 의 재료비 변화(`MATERIAL_COST_CHANGE`)도 **함께 빠졌다**(SRS v1.11). 시세가 사라지자 이 절의 「가격 변동률 × 재료비 비중」이 유일한 근거였다는 것이 드러났고, 남은 `rate` 만으로는 무엇에 곱하는지가 정의되지 않았다. 매출 쪽 시뮬레이션은 `PRODUCT_SALES_CHANGE`(P1-22 구성비 연동)가 맡는다.

### 4.11 자금 안전 (P1-08/09/11)

**P1-08 운영자금 안전선**

| 구분 | 선정 |
| --- | --- |
| 계산 | 최근 N일 고정비·필수지출 rolling aggregate |
| 저장 | `SAFETY_BALANCE_POLICY` + `calculation_basis` JSONB |
| 조정 | 슬라이더 → 화면 즉시 재계산 |

사용자가 슬라이더를 움직이면 곡선과 위험일 목록이 바로 바뀌어야 한다.
**계산이 싸야 한다**는 요구가 여기서 나온다 ([4.4](#44-예측-엔진-p0-07--p1-05--p1-07)의 순수 함수와 같은 이유).

**P1-09 가상 준비금**

| 구분 | 선정 |
| --- | --- |
| 계산 | 잔여 목표액 ÷ 잔여 가용 **영업일** |
| 저장 | `RESERVE_GOAL`, `RESERVE_CONTRIBUTION` |
| 배분 | 목표가 여럿이면 목표일 + priority 기준 |
| 알림 | 미달 시 `ALERT.alert_type = RESERVE_SHORTFALL` |

**P1-11 부가세 예수금**

| 구분 | 선정 |
| --- | --- |
| 계산 | 기준연도별 Tax Policy **Strategy 패턴** |
| 저장 | `TAX_ESTIMATE` (최소~최대 범위), `TAX_SCHEDULE` |
| 근거 | 기준연도·공식·입력값 JSONB |
| 예정 거래 | `PLANNED_TRANSACTION(source_type = TAX)`로 흘려보낸다 |

**함정**
- **세율·기준을 코드 상수로 박지 않는다.** 기준연도를 키로 정책을 조회한다.
  세법은 매년 바뀌고, 과거 데이터는 그때 세율로 계산돼 있어야 한다.
- 부가세 예수금은 "이미 받아 둔 남의 돈"이다. **가용 잔고에서 빼서 보여준다.**
  목업이 이미 그렇게 하고 있다 (`잔고 4,182,400 − 예수금 1,873,200 = 쓸 수 있는 돈 2,309,200`).
- 금액은 항상 범위로 낸다. 단일 값으로 내면 확정으로 읽힌다.

### 4.12 P1-12 다사업장·자금 융통

| 구분 | 선정 |
| --- | --- |
| 집계 | 사업장별 집계 쿼리 |
| 시뮬레이션 | What-if 엔진 재사용 |
| 권한 | 사업장 범위 검사 (Modulith 모듈 경계) |
| 실행 | **가상 시뮬레이션만.** 실제 이체 없음 |

**함정**
- **N+1이 여기서 터진다.** 사업장 3곳 × 계좌 × 예측 곡선을 순회하면 쿼리가 폭발한다.
  `@EntityGraph`나 집계 쿼리 한 방으로 간다. 통합 화면은 응답 3초 목표(SRS 12장)의 최대 난관이다.
- 사업장이 지갑(통장)을 공유하는 경우가 있다. 안전선이 사업장별인지 지갑별인지 먼저 정한다.
  목업은 지갑 기준으로 그렸다 (성수 단독 230만 vs 서울숲 합산 380만).

### 4.13 대출·지원 (P1-13/14)

**P1-13 대출 현황**

| 구분 | 선정 |
| --- | --- |
| 수집 | `LOAN_08`(가입 목록) + `LOAN_09`(상환 내역) + `JOB.job_type = LOAN_SYNC` |
| 저장 | `LOAN`, `LOAN_REPAYMENT` |
| 마이너스통장 | **보류** — 아래 참조 |
| 상환 일정 | 금융망 규칙 그대로 계산 → `PLANNED_TRANSACTION(source_type = LOAN)` |

`LOAN_08` 응답: `accountNo` · `accountName` · `status`(개설/상환중/연체) · `loanPeriod`(일) ·
`loanDate` · `maturityDate` · `loanBalance` · `interestRate` · `withdrawalAccountNo`.
`LOAN_09` 응답의 `repaymentRecords[]`: `installmentNumber` · `status`(SUCCESS/FAIL) ·
`paymentBalance` · `repaymentAttemptDate/Time` · `repaymentActualDate/Time` · **`failureReason`**.

> **⚠ 대출 상환이 매일이다.** 플로우 문서: *"개설일 다음날부터 매일 `(대출금+이자) / 대출기간`으로
> 계산되어 **오전 08:30**에 수시입출금 계좌에서 상환됩니다."* 대출 기간은 **2~365일**(일 단위),
> 금액 1천원~3억원, 금리 0.1~20%.
>
> **⚠ 이자는 플로우 문서 식이 아니다 (2026-09-16 실측).** 대출 셋을 실제로 실행해 `LOAN_09` 의 총액을 읽으니
> **`총상환액 = P·(1 + r·d²/365)`** — 일할이자 `P·r·d/365` 를 **d 번** 부과한다. 14일·19.5%·10만 → 110,471,
> 90일·17.5%·10만 → 488,356, 365일·8.4%·500만 → 158,300,000. 정상 단리 대비 **기간(일)배**다. 실제 대출은
> 금융망이 준 총액을 그대로 쓰고(16.1), 미리보기(16.3 · 11.1 `LOAN_EXECUTION`)는
> `LoanRepaymentSchedule.InterestModel.FIN_NETWORK` 로 같은 값을 낸다.
>
> 우리 목업은 「9월 10일 대출 상환 1,680,000원」처럼 **월 1회 큰 금액**으로 그렸다.
> 금융망에서는 **매일 소액**이 빠진다. 예보 곡선의 모양이 완전히 달라진다 —
> 월 1회면 그날 절벽이 생기지만, 매일이면 완만한 우하향이 된다.
> **어느 쪽에 맞출지 정해야 한다**([12장](#12-결정이-남은-것)).

**`failureReason`이 이 제품의 핵심 시나리오를 만들어 준다**

`LOAN_09`의 실패 사유에 **"자동이체 실패 잔액 부족"** 이 그대로 들어온다.
마이너스통장도 정기 이자 출금이 실패하면 `OVERDUE`가 되고, **3일 전 납입 예정 알림 ·
연체 발생 · 연체 3일 경고** 를 금융망이 저장한다(`MINUS_ACCOUNT_10`으로 조회).

즉 **"정산이 밀려 상환에 실패했다"는 우리 서비스의 핵심 장면을 금융망이 실제로 재현한다.**
데모 시나리오를 이 위에 세운다 — 잔액을 상환액 아래로 떨어뜨려 놓고 08:30을 지나면
실패 이력이 생기고, 우리 예보는 그 전날 그것을 경고했어야 한다.

**P1-14 신용 기반 대출 추천**

| 구분 | 선정 |
| --- | --- |
| 신용 조회 | **`LOAN_04`** 내 신용등급 조회 → `CREDIT_SNAPSHOT` |
| 등급 기준 | `LOAN_01` 신용등급 기준 조회 (상품 등록 시 참고) |
| 상품 | `LOAN_02`(등록) · `LOAN_03`(조회) → `LOAN_PRODUCT` |
| 심사·가입 | `LOAN_05`(심사 신청) → `LOAN_06`(심사 목록) → `LOAN_07`(가입) |
| 자격 필터 | 규칙 엔진 (등급·금액·기간) |
| 순위 | (금리, 총상환액, 공백 개선 효과) 점수 |
| 시뮬레이션 | What-if 엔진의 `LOAN_EXECUTION` |
| 설명 문장 | 템플릿 우선. 선택적으로 LLM |

`LOAN_04` 응답이 `CREDIT_SNAPSHOT` 컬럼과 1:1로 맞는다 —
`ratingName` → `grade`, `demandDepositAssetValue` → `demand_deposit_asset`,
`depositSavingsAssetValue` → `deposit_savings_asset`, `totalAssetValue` → `total_asset`.
ERD가 이 API를 보고 설계된 것이다.

**함정**
- **금융망 신용등급은 자산 합계로만 산출된다.** 수시입출금 + 예·적금 잔액이 전부다.
  연체 이력도 소득도 반영되지 않는다. **화면에서 실제 신용등급처럼 보이게 하면 안 된다.**
  "보유 자산 기준 참고 등급"으로 표기한다.
- 대출 상품 가입은 **심사 승인된 것만** 가능하다(`LOAN_05` → `LOAN_06` → `LOAN_07`).
  추천 화면에서 바로 가입으로 넘어가지 않는다.
- **자격 판정과 금액 계산에 AI를 쓰지 않는다.** 잘못된 추천은 사장님이 시간을 버리게 만든다.
- `CREDIT_SNAPSHOT`은 이력 테이블이다. 등급이 떨어졌을 때 언제부터인지 보여줄 수 있다.
**마이너스통장을 보류하는 이유**

`MINUS_ACCOUNT_*` 14종은 대출과 **같은 테이블에 담기지 않는다.**

| | 대출 `LOAN_*` | 마이너스통장 `MINUS_ACCOUNT_*` |
| --- | --- | --- |
| 기간 | **2~365일** | **12·24·36개월** |
| 상환 | **매일 08:30**, `(대출금+이자)/기간` | 이자 납입일·자동 상환일 **매월 01~28일** |
| 상태 | 개설 · 상환중 · 연체 | `NORMAL` · `OVERDUE` |
| 거래 유형 | — | `MINUS_ACCOUNT_13`: `W`출금 `R`상환 `I`이자납입 |
| 알림 | 없음 | `MINUS_ACCOUNT_10` — 3일 전 예정 · 연체 · 연체 3일 경고 |
| 스케줄 | 08:30 | 이자 00:00 · 납입·연체 00:10 |

`LOAN` 하나로 둘을 담으면 상환 주기 계산이 두 갈래로 갈리고, 예정 거래 생성 규칙도 달라진다.
**한 달 일정에서는 보류한다.** 넣는다면 별도 테이블과 별도 예정 거래 생성기가 필요하다.

`MINUS_ACCOUNT_10`의 알림(3일 전 납입 예정 · 연체 경고)은 우리 `ALERT`와 겹친다.
도입 시 **두 알림이 중복되지 않도록** `dedup_key` 규칙을 먼저 정한다.

### 5.1 LLM (Anthropic Claude)

| 모델 | 모델 ID | 컨텍스트 | 입력 $/1M | 출력 $/1M |
| --- | --- | --- | --- | --- |
| Claude Opus 5 | `claude-opus-5` | 1M | $5.00 | $25.00 |

| Claude Haiku 4.5 | `claude-haiku-4-5` | 200K | $1.00 | $5.00 |

- **기본값은 `claude-opus-5`로 잡는다.** 7개 AI 기능 모두 Opus 5로 시작하고,
  [9장](#9-비용을-낮추는-순서)의 절차대로 **측정한 뒤에** 라우트별로 내린다.
  처음부터 싼 모델로 시작하면 품질이 낮을 때 모델 탓인지 프롬프트 탓인지 구분할 기준선이 없다.
- 세 모델 모두 **텍스트 + 이미지(vision)** 를 받는다. [6.4](#64-p1-02-멀티모달-증빙-인식매칭)
  VLM 보정에 별도 모델이 필요 없다.
- **모델 ID에 날짜 접미사를 붙이지 않는다.** `claude-opus-5-20260101` 같은 문자열은 존재하지 않는다.
- 운영에서는 검증한 ID를 설정값(`ai.model.classification` 등)으로 고정하고,
  결과에 `modelName`·`promptVersion`을 함께 기록한다 (`20_내부_AI워커.md` 규약).
- 단가는 **2026-06-24 스냅샷**이다. 도입 시점에 재확인한다.

### 5.2 LLM이 아닌 것

| 용도 | 선정 | 비고 |
| --- | --- | --- |
| 영수증 OCR (주) | NAVER CLOVA Receipt OCR | 한국어 영수증 특화. 종량 과금 — 단가 확인 필요 |
| 영수증 OCR (비교·폴백) | PaddleOCR PP-OCRv5 Korean | 자체 호스팅. GPU 없음 → **동시 처리 1건 제한** |
| 이미지 전처리 | OpenCV (기울기 보정·이진화·crop) | 정확도를 올리는 가장 싼 수단 |
| 임베딩 | **아래 주의 참조** | MVP에서 도입하지 않는다 |
| **잔여 흐름 예측 (주)** | **`residual-gru` 0.3.0** — GRU 요약 + 하루씩 분위수, 88,390 파라미터 (자체 구현) | **2026-09-08 실측으로 확정.** 파운데이션 모델을 대체했다. **적용 구간은 컨텍스트 30~364일** — 365일(창 상한)은 통계 베이스라인이 남는다. *(2026-09-10 정정: 「1년 이상」이 아니라 「워커에 넣은 일수가 365」다 — 기록의 나이가 아니다. 설계노트 M-3)* |
| **잔여 흐름 예측 (비교)** | 통계 베이스라인(요일 중앙값) · LightGBM 분위수 · Chronos fine-tune / zero-shot | 4자 비교. zero-shot 은 **통계보다 유의하게 나빠 탈락** |
| **정산 지연·금액 보정** | XGBoost 분위수 회귀 (`reg:quantileerror`) | 오프라인 학습 → 아티팩트 배포. 런타임은 추론만 |

> **예측 모델 — 2026-09-08 갱신.** 잔여 흐름 축은 **실측을 끝내고 확정했다.**
> 세 확인 항목 전부 통과했다 — ① 라이선스: 자체 구현이라 외부 가중치를 쓰지 않는다
> ② CPU 추론: 중앙 **9.7 ms** (타임아웃 15초) ③ 상주 메모리: **203 MiB**(torch 런타임 182 +
> 모델 7). 전체 표와 신뢰구간은 [`예측엔진_설계노트.md`](./예측엔진_설계노트.md) M-3
> 「실측 결과」에 있다.
>
> **후보가 바뀐 이유** — zero-shot 파운데이션 모델이 통계 베이스라인보다 **유의하게 나빴다**
> (공백 F1 0.600 vs 0.692, −0.092 [−0.105, −0.080]). 같은 계열을 fine-tune 하면 0.687 까지
> 오르는데 **88K 자체 모델과 소수점 넷째 자리까지 같아**(둘 다 0.6867) 200M 을 얹을 근거가
> 없다.
>
> **XGBoost 보정(M-2)은 여전히 미실측이다.** 위 세 항목을 그쪽에는 아직 재지 않았다.
>
> **주의 — 합성 데이터 실측이다.** 실제 소상공인 통장 데이터가 아니다. 모델을 우리 생성
> 규칙으로 학습했으므로 순환논법이 적용되고, 그래서 「같은 데이터에서 통계보다 낫다」까지만
> 주장한다. 절대 성능으로 인용하지 않는다.
> GPU가 없으므로 대형 모델은 후보가 아니다.

> **임베딩 주의** — Anthropic API에는 임베딩 엔드포인트가 없다(Messages / Batches / Files /
> Token Counting / Models 뿐). pgvector 의미 검색을 하려면 별도 공급자가 필요하다.
> 다만 **P1-15 공고는 월 300건 규모**라 PostgreSQL Full Text Search + `pg_trgm`으로 충분하다.
> 임베딩은 FTS로 못 찾는 사례가 실제로 쌓인 뒤에 도입한다.
> 도입 시 후보는 ① 외부 임베딩 API(단가·약관 확인) ② CPU에서 도는 다국어 임베딩 모델 자체 호스팅.

### 6.3 P1-01 거래 적요 자동 분류

`POST /internal/v1/ai/transaction-classification` · 비동기 · Callback

| 항목 | 내용 |
| --- | --- |
| 모델 | `claude-opus-5` |
| 호출 방식 | **Batch API** — 단가 50% |
| 출력 | Structured Outputs `output_config.format` (strict JSON Schema) |
| effort | `low` 또는 `medium`부터 측정 |
| max_tokens | 배치 20건 기준 2,048 |
| 캐싱 | 시스템 프롬프트 + `allowedCategories` + few-shot을 프리픽스로 고정 |
| 폴백 | ① 규칙·사전 결과 유지 ② `needsConfirmation = true`로 사용자 확인 큐 |
| 평가 | Macro F1, 카테고리별 Precision/Recall, **사용자 수락률** |

**근거** — 입력은 적요 한 줄(`"김영자"`)과 금액·방향·주기 힌트뿐이다.
**이건 우리가 아껴 쓰는 게 아니라 금융망이 그것밖에 주지 않는다** —
`DEMAND_DEPOSIT_12` 응답에 거래처명 필드가 없고 `transactionSummary` 하나가 전부다([4.1](#41-p0-01-거래내역-수집)).
정보가 극도로 적은 상태에서 "매월 25일 동일 금액 출금 → 임차료"를 추론하고 근거 문장까지 써야 한다.
few-shot이 사업장마다 다르고 카테고리 체계도 업종마다 다르므로, 지시 따르기와 스키마 준수가
그대로 정확도가 된다. 여기서 아낀 몇 달러는 사용자 정정 노동으로 되돌아온다.

**설계 메모**
- 배치는 **한 요청에 거래 20건**. 1건씩 보내면 시스템 프롬프트를 20번 낸다.
- `cycleHint`(P0-03 결과)를 반드시 실어 보낸다. LLM이 주기를 추론하는 것보다
  Java 통계가 계산한 주기를 주는 쪽이 정확하고 싸다.
- few-shot은 `TRANSACTION_CLASSIFICATION_HISTORY`에서 최신순 상위 N건. 단
  **하루 1회만 갱신**한다. 매 요청 재구성하면 프리픽스 캐시 적중률이 0이 된다.
- 신뢰도 0.85 미만 또는 신규 거래처는 저장하되 `needsConfirmation`을 세운다.
- 초기에는 파인튜닝하지 않는다. 정정 이력이 few-shot으로 먼저 효과를 낸다.

### 6.4 P1-02 멀티모달 증빙 인식·매칭

`POST /internal/v1/ai/evidence-extraction` · 비동기 · Callback

| 항목 | 내용 |
| --- | --- |
| 1차 | OpenCV 전처리 → **CLOVA Receipt OCR** |
| 2차 (저신뢰 보정) | `claude-opus-5` vision |
| 비교군 | PaddleOCR PP-OCRv5 Korean (`preferredPipeline: OCR_PIPELINE`) |
| 출력 | Structured Outputs — 공급자·날짜·사업자번호·합계·공급가·부가세·품목 배열 |
| 검산 | `공급가 + 부가세 = 합계`, `Σ품목금액 ≒ 합계`, 날짜 유효성, 사업자번호 체크섬 |
| 폴백 | 검산 실패 → `review` 상태 → 사용자 수기 확인 |
| 평가 | CER·WER **와 함께** 날짜·합계·부가세·품목 **필드 단위 정확도** |

**근거** — 영수증은 정형 문서라 전용 OCR이 VLM보다 싸고 정확하다. VLM은 전용 OCR이
흔들리는 곳(구겨진 감열지, 흐린 촬영, 손글씨 메모)에서만 쓴다.
요청에 `preferredPipeline`(`AUTO`/`OCR_PIPELINE`/`VLM`)이 이미 있고
`EVIDENCE_EXTRACTION`에 `model_name`·`pipeline`·`is_current`가 있으므로
**세 파이프라인을 같은 표본에 돌려 비교**한 뒤 `AUTO` 임계값을 정한다.

**설계 메모**
- 로컬 OCR은 GPU가 없어 **동시 처리 1건**으로 제한한다. 큐가 밀리면 CLOVA로 우회한다.
- 전처리 후 장변 1,600px 내외로 리사이즈한다. 원본 4,000px을 그대로 보내면
  이미지 토큰만 3배가 되고 정확도는 거의 안 오른다.
- 원본 이미지와 추출 원문을 **로그에 남기지 않는다.**
- **읽어낸 값만 저장한다.** 부가세를 LLM에게 계산시키지 않고 검산만 한다.

### 6.5 P1-03 영수증 품목 정규화

`POST /internal/v1/ai/item-normalization` · **동기** · 10초 타임아웃

| 항목 | 내용 |
| --- | --- |
| 1차 | 단위 규칙 사전 (`1L` = `1000ml`) — Python 자체 변환기 또는 Pint |
| 2차 | `ITEM.aliases` + PostgreSQL `pg_trgm` 유사도 |
| 3차 (저신뢰만) | `claude-opus-5`, effort `low` |
| max_tokens | 50건 묶음 기준 1,536 |
| 폴백 | `matchedItemId: null` + `suggestedCanonicalName`만 반환 → 사용자 확인 |
| 평가 | 자동 매칭률, **오매칭률**(이쪽이 더 중요), 규칙 처리 비율 |

**근거** — `우유 1000ml → 우유 1L`은 규칙으로 끝난다. LLM은
`대파 한 단 → 대파`, `삼겹살(냉장) → 돼지고기 삼겹살`처럼 규칙으로 못 잡는 나머지에만 쓴다.
동기 호출이라 지연이 사용자에게 직접 보인다. **LLM 도달 건수를 줄이는 게 곧 UX다.**

**설계 메모**
- 규칙 + `pg_trgm`이 **90% 이상**을 처리하도록 `ITEM.aliases`를 먼저 채운다.
  이 비율을 대시보드에 노출해 떨어지면 알아챈다.
- 저신뢰 건은 **묶어서 한 번에** 보낸다. `rawNames` 배열이 이미 그 모양이다.
- **오매칭이 매칭 실패보다 나쁘다.** 임계값을 보수적으로 잡고 애매하면 `null`을 낸다.

**설계 메모**

- `sourceUrl`과 `collectedAt`을 항상 보존해 화면에서 원문으로 갈 수 있게 한다.
- 공고는 **사업장 공용 데이터**다. 사업장이 늘어도 이 비용은 늘지 않는다.

### 6.7 P1-17 주간·월간 AI 브리핑

`POST /internal/v1/ai/briefing-generation` · 비동기 · Callback

| 항목 | 내용 |
| --- | --- |
| 모델 | `claude-opus-5` |
| 호출 방식 | **Batch API** — 예약 생성이라 지연 허용 |
| 입력 | 계산 엔진이 산출한 `metrics` 배열 **만**. 원본 거래를 보내지 않는다 |
| 출력 | Structured Outputs — `{ headline, content }` → `REPORT.headline`, `REPORT.narrative` |
| effort | `medium`부터 측정 |
| max_tokens | 2,048 |
| 검증 | **입력 `metrics`에 없는 숫자·날짜가 본문에 있으면 그 문장을 폐기하고 `status = PARTIAL`** |
| 폴백 | `PARTIAL`이어도 지표 카드는 정상 노출 |

**근거** — 이 기능의 위험은 문장력이 아니라 **환각**이다.
"매출이 4.2% 늘었는데 재료비가 18.1% 올라 남는 돈은 오히려 줄었습니다" 같은 문장에서
숫자 하나가 틀리면 사장님이 그 숫자로 판단한다. `toneGuide`가 요구하는
"확정 표현 금지 · 입력에 없는 수치 생성 금지"를 지키는 능력이 곧 품질이다.

`REPORT.status`에 `PARTIAL`이 이미 정의돼 있다 — **실패를 설계에 넣어 둔 것**이므로
`narrative`가 null이어도 화면이 정상 동작해야 한다.

**설계 메모**
- 숫자 검증은 **정규식으로 기계적으로** 한다. 본문에서 숫자·날짜를 전부 뽑아
  `metrics` 값 집합과 대조하고, 없는 값이 나오면 그 문장을 버린다.
- 반올림 표기(`748,000` → `74만`)를 허용하려면 허용 오차를 명시적으로 정의한다.
- 월간은 주간보다 지표가 많고 인과 설명이 길다. 프롬프트를 분리한다.

### 6.8 P1-22 상품별 매출 인쇄물 추출

`POST /internal/v1/ai/product-sales-extraction` · 비동기 · Callback *(명세 20.9)*

| 항목 | 내용 |
| --- | --- |
| 모델 | `claude-opus-5` vision |
| 입력 | `captureType`(`SCREEN`/`PRINTOUT`) · `fileObjectKeys[]` 여러 장 · `knownProducts[]` |
| 출력 | Structured Outputs — `period` · `columnsDetected[]` · `items[]` · `printedTotal` · `warnings[]` |
| effort | `high` |
| max_tokens | 80행 기준 8,192 |
| 저장 | `PRODUCT_SALES_PERIOD` (14.4) |
| 폴백 | 수기 입력·정정 (2차 경로) |
| 평가 | 행 누락률 · 체크섬 일치율 · 기간 추출 정확도 |

**근거** — POS와 API로 연동하지 않으므로(SRS 1.3) **인쇄물 촬영이 유일한 자동 입력 경로**다.
한 달 80행을 손으로 치는 사람은 없다. 정형 양식(상품 행 반복 + 합계 행)이라
[6.4](#64-p1-02-멀티모달-증빙-인식매칭)의 자유 양식 영수증보다 정확도가 잘 나올 여지가 있다.

**명세가 요구하는 4건이 그대로 프롬프트 요구사항이다**

| # | 요구 | 지키지 않으면 |
| --- | --- | --- |
| 1 | **기간을 헤더에서 읽는다.** 못 읽으면 `period.source = null` | 촬영 시각으로 추론하면 반달치를 그 달 전체로 오인해 **오류 없이 틀린 답**이 나온다 |
| 2 | **합계 행을 `printedTotal`로 분리** | 항목 합과 대조하는 체크섬이 무력화된다 |
| 3 | **읽은 열을 `columnsDetected`로 밝힌다** | 감열지 58/80mm에 8열이 안 들어가 열이 접힌다. 없는 열을 0으로 채우면 안 된다 |
| 4 | **행을 만들어내지 않는다.** 못 읽으면 `warnings` | 누락은 체크섬이 잡지만 **환각은 아무것도 못 잡는다** |

**설계 메모**
- **`SCREEN`과 `PRINTOUT`의 프롬프트를 나눈다.** 화면 촬영은 표·안티앨리어싱·반사·모아레,
  감열 인쇄물은 좁은 폭·도트 번짐·종이 곡률·그림자로 실패 양상이 다르다.
- 여러 장을 **하나의 기간으로 병합**하고 장 경계 중복 행을 제거한다.
- `knownProducts`에 **스냅되도록 유도**하면 표기 흔들림이 준다. 단 신규 상품은 그대로 받는다.
- 체크섬 불일치는 실패가 아니라 **`checksumStatus: MISMATCHED`로 사용자에게 보여 준다** —
  "합계와 502,800원 차이가 있습니다. 아래쪽 행이 빠진 것 같습니다."
  인수 조건은 여기서 한 걸음 더 간다 — **경고 상태로도 저장할 수 있고, 저장된 기간에
  「불완전」 표시가 남는다.** 저장을 막지 않는 대신 흔적을 남기는 쪽이다.
- **같은 기간을 다시 등록하면 새 행이 쌓이지 않고 갱신된다.**
  `(business_id, period_start, period_end)` UNIQUE + upsert. 상품명 일괄 변경(14.6)으로
  표기가 다른 두 상품을 합치면 수량·금액이 합산된다.
- **금액이 아니라 구성비만 밖으로 나간다**([3.8](#38-매출-용어-3층--금액의-단일-출처)).
  신고서 초안 매출액과 부가세 예수금에 **반영되지 않는다** — 매출 대사에 참고값으로만 나온다.
- What-if에 넣으면 상품 배율과 구성비로 환산한 **총매출 배율**이 곡선에 반영되고,
  **적용한 구성비의 근거 기간을 함께 표시**한다([4.6](#46-p0-0913-what-if-시나리오)).
- 화면은 **등록 모바일 / 조회 PC**로 갈린다(SC-09-3). 촬영은 폰으로, 표는 넓은 화면에서 본다.


### 6.9 P0-07·P1-05 예측 모델

비동기(일 1회 배치) + 온디맨드 · 잔액 곡선의 Layer 2

> **원칙 1을 깨지 않는다.** [1장](#1-선정-원칙)이 금지한 것은 **"돈을 세는 일에 LLM을 쓰는 것"**이다.
> 여기 쓰는 것은 LLM이 아니라 **시계열·회귀 모델**이고, 모델이 내는 것은 금액이 아니라
> **분위수(범위)** 다. 잔액 합산은 여전히 Java 순수 함수가 한다([4.4](#44-예측-엔진-p0-07--p1-05--p1-07)).
> 원칙 1의 근거였던 "재현을 보장하지 못한다"는 아래 「재현성」에서 저장 구조로 해결한다.

근거 문서는 [`예측엔진_설계노트.md`](./예측엔진_설계노트.md) **v2**의 M-1·M-2·M-3이다.

**두 자리에 각각 다른 모델이 들어간다**

| | 자리 | 모델 | 학습 | 필수 |
| --- | --- | --- | --- | :---: |
| **M-1** | Layer 2-B 잔여 흐름 (P0-07) | **`residual-gru`** (GRU, 88,390) | **오프라인** | ○ |
| **M-2** | Layer 2-A 지연·금액 보정 (P1-05) | XGBoost 분위수 회귀 | 오프라인 | 조건부 |

**순환논법을 어떻게 다루는가 (2026-09-08 개정)** — 설계노트 v1이 ML을 배제한 근거는 지금도
맞다. 합성 시드로 학습하면 **정보 상한이 우리 생성 규칙 `R`** 이라 `R`을 코드로 쓰는 것보다
나을 수 없다. v2 는 여기서 **zero-shot 이면 이 반박을 피한다**고 보고 M-1 을 파운데이션
모델로 잡았다.

**실측에서 그 길이 막혔다** — zero-shot 은 통계 베이스라인보다 유의하게 나빴다
(공백 F1 0.600 vs 0.692). 그래서 채택 모델 `residual-gru` 는 **우리 데이터로 학습하고,
순환논법이 그대로 적용된다.** 회피하는 대신 경계를 재서 그었다.

- **상한을 같이 잰다.** 요일 참값을 직접 보는 부정 팔(모수 오라클) 0.733 에
  `residual-gru` 0.687 이 **못 미친다** — 생성 규칙을 외운 것이 아니라는 뜻이다.
- **주장 범위를 좁힌다.** 「같은 데이터에서 통계 베이스라인보다 낫다」까지만 말한다.
  성과 표기는 SRS 16장대로 **「합성 벤치마크 기준」**을 붙인다.

M-1 이 필수이고 M-2 가 조건부인 이유는 이제 순환논법이 아니라 **채우는 구멍의 크기**다 —
M-1 이 없으면 비패턴 흐름이 곡선에서 통째로 0 이 된다.

#### M-1 잔여 흐름 (P0-07)

| 구분 | 선정 |
| --- | --- |
| 채우는 구멍 | 예측 입력이 `PLANNED_TRANSACTION`뿐이라 **패턴에 안 걸리는 흐름이 0으로 취급**된다 — 현금 매출 입금, 소액 부정기 지출, 미분류 거래 |
| 잔여 정의 | `실제 입금 합계(d) − Σ 예정 거래에 매칭된 입금(d)` (출금도 동일). **뺄셈이라 이중 계상이 구조적으로 불가능** |
| 입력 | 일별 잔여 시계열 2개, 컨텍스트 **30~365일** (`features.MIN_HISTORY`~`LOOKBACK`) |
| 출력 | horizon 30일 × `q10 / q50 / q90` |
| 반영 | `DAILY_BALANCE_FORECAST.residual_deposit`·`residual_withdrawal`(q50), 곡선 `balance_min/max` 폭에 q10·q90 |
| 계약 | `POST /internal/v1/ai/forecast-residual` (동기 — [20.11](./api/20_내부_AI워커.md)) |
| 제외 | `TRANSACTION.is_excluded = true` 거래는 실제 합계에서 뺀다 |
| 표본 부족 | **30일 미만** 미적용(잔여 0 + `warnings`) · **30~180일** `confidence` 강등 · 180일 이상 정상. *(2026-09-09 에 90 → 30. 실측(합성 데이터, 창 9,600개) — 30~89일 구간에서 **잔여 0 은 공백 F1 0.457 · 최초 부족일 오차 19.4일**, **모델은 0.676 · 9.28일**이다. 통계도 0.652 로 멀쩡히 나온다. 90 은 「근거 없는 숫자를 내느니 모른다고 하자」는 원칙에서 나온 값인데, **원칙은 맞고 값이 틀렸다.**)* |

**분위수를 모델이 직접 낸다는 점이 중요하다.** `balance_min/expected/max` 3계열이
지금까지는 통계로 폭을 지어냈는데, 모델 출력과 1:1로 대응하므로
SRS 12장 「예측에 범위·신뢰 수준·근거 표시」가 근거 있는 값으로 채워진다.

#### M-2 지연·금액 보정 (P1-05, 조건부)

| 구분 | 선정 |
| --- | --- |
| 타깃 | 지연일(`실제일 − 예정일`)과 금액 배율(`실제 ÷ 예정`)의 q10/q50/q90 — **한 모델의 다중 분위수 출력** |
| 피처 | `merchant_master_id`, 요일, 연휴 인접 거리(±3일), 직전 회차 지연일, 회차 간격, 금액 밴드, `industry_type`, 표본 수 |
| 전제 | **전역 `MERCHANT_MASTER`**(설계노트 G-3). 없으면 표본이 사업장당 3~5건이라 성립하지 않는다 |
| 학습 | **오프라인.** 아티팩트(`.ubj`)를 워커 이미지에 포함 — 런타임은 추론만 |
| 계약 | `POST /internal/v1/ai/settlement-delay` (동기 — [20.12](./api/20_내부_AI워커.md)) |

**한계를 문서에 남긴다.** M-2는 우리 시드로 학습하므로 **순환논법이 그대로 적용된다.**
방어는 두 가지 — ① **blind split**(시드 생성기를 모델 담당자가 아닌 팀원이 작성, 규칙 비공개,
마지막 4~6주 hold-out) ② **표현의 정확성**(발표·문서에서 "정확도가 좋아졌다"고 쓰지 않고
**"합성 벤치마크에서 베이스라인 대비 개선"**으로만 쓴다). ①을 확보하지 못하면
M-2는 시연에 노출하지 않고 내부 실험으로만 남긴다.

**오프라인 학습이 일정 의존성을 끊는다.** P1-05는 도입 순서 13단계인데,
학습을 빼면 워커 착수(6단계) 직후 6.5단계에 얹을 수 있다.

#### 모델 선정 — 2종 비교와 채택 게이트 (M-3)

컨설팅이 OCR/VLM에 요구한 **「2개 이상 모델 비교」와 같은 형식**이다.
`EVIDENCE_EXTRACTION`이 `model_name`·`model_version`을 남기듯,
예측도 `FORECAST_RUN.model_version`에 **엔진 버전 + 모델 아티팩트 버전**을 남긴다
(예: `engine-1.2/residual-gru-0.3.0+a82bc981` — 아티팩트 버전에 **학습 데이터 지문**을 붙여 재학습을 구분한다).

| 팔 | 성격 | 공백 F1 (전체 / 30일~1년) |
| --- | --- | --- |
| **`residual-gru` (채택)** | GRU 요약 + 하루씩 분위수, 88,390 파라미터 | 0.687 / **0.680** |
| LightGBM 분위수 | 요일·달력 피처 37종, 부스터 6개 | 0.697 / 0.682 |
| Chronos fine-tune (48M) | T5 기반 경량 파운데이션 모델 | 0.687 / — |
| Chronos zero-shot | 사전학습 가중치 고정 | **0.600 — 탈락** |
| 통계 베이스라인 | seasonal naive + 요일 median | 0.692 / 0.664 — 하한선이자 폴백 경로 |

실측일 2026-09-08. 합성 데이터 사업장 200곳, **시간 hold-out 창 9,600개**(창 간격 7일이라 정답이 겹친다 — 독립 표본으로는 2,200개 규모), 짝지은 부트스트랩 95%. **채택 게이트는 「컨텍스트 30~364일」 구간에서만 통과한다** — `+0.016 [+0.008, +0.024]` 유의, 최초 부족일 오차 9.27→9.14일. **컨텍스트가 상한(365일)까지 차면 모델이 통계를 넘지 못하고**(−0.006, 구간이 0 을 포함), 전체 창을 한 덩어리로 채점하면 **미채택**이다. ⚠ **구간 이름은 「기록의 나이」가 아니라 「워커에 넣은 일수」다** — `LOOKBACK` 이 365라 운영에서 컨텍스트가 그보다 길어지는 일이 없다(2026-09-10 정정). 그래서 적용 범위를 컨텍스트 구간으로 한정했다. 전체 표는 [`예측엔진_설계노트.md`](./예측엔진_설계노트.md) M-3 「실측 결과」.

| 층 | 지표 | 용도 |
| --- | --- | --- |
| 모델 | pinball loss(q10/q50/q90), MASE | 후보 간 비교 |
| **다운스트림** | **공백 발생 F1**, **최초 부족일 오차(일)** | **채택 게이트** |

**게이트** — ① 통계 베이스라인을 먼저 구현해 다운스트림 지표를 잰다
② 모델이 **다운스트림 지표에서** 베이스라인을 못 넘으면 채택하지 않는다.
pinball loss만 좋은 것은 채택 사유가 아니다 ③ 채택해도 베이스라인은 폴백으로 남긴다.

#### 재현성 — `basis` 스냅샷

SRS 13장이 "같은 입력에 대해 재현된다"를 요구한다. 모델 추론은 CPU 스레드 수만 바뀌어도
부동소수점 합산 순서가 달라져 **비트 단위 동일을 보장하지 못한다.**

**해법은 추론 결과를 `FORECAST_RUN.basis`에 스냅샷으로 남기는 것**이다.
`basis`는 이미 "실행 시점 불변 스냅샷" 용도로 설계돼 있다(ERD `FORECAST_RUN`).
잔여 분위수와 보정 계수를 여기 기록하면 같은 `FORECAST_RUN`의 재조회는 항상 같은 값이고,
**재현성이 저장 구조에서 보장된다.** 인수 조건 문구는
"동일 입력 **+ 동일 모델 버전**에 대해 재현된다"로 개정한다.

#### 폴백 — AI가 죽어도 곡선은 나온다

[11장 6번의 원칙](#11-도입-순서)("AI 없이도 제품이 성립해야 한다")을 예측에도 적용한다.

| 상황 | 동작 |
| --- | --- |
| 워커 타임아웃·오류 | 잔여 = 0, 통계 보정만으로 산출. `warnings` 표시 + `confidence` 강등 |
| 표본 부족 | M-1 「표본 부족」 규칙 |
| 사용자 토글 OFF | `applyResidualModel = false` — 모델 경로를 타지 않는다 |

**셋 다 곡선은 반드시 나온다.** 모델 실패가 P0-07 실패가 되면 안 된다.

#### 서버 예산 (4 vCPU / 15 GB / GPU 없음)

| 항목 | 판단 |
| --- | --- |
| 상주 메모리 | 200M급 fp32 ≈ 0.8 GB, 48M급 ≈ 0.2 GB. 워커 컨테이너에 상한을 건다 |
| 동시 실행 | **PaddleOCR과 동시 실행 금지.** 워커 내 세마포어 1로 직렬화 |
| 사용자 체감 | 없음. 곡선은 `DAILY_BALANCE_FORECAST`에 캐시되고 조회는 SELECT다 |
| PyTorch 설치 | **CPU 전용 인덱스**를 쓴다. 기본 인덱스는 CUDA 휠을 받아 이미지가 2 GB 넘게 는다 |

#### 함정

- **잔여 시계열을 캐시하지 말 것.** 사용자가 새 패턴을 승인하면 과거 잔여가 **소급해서 준다**
  (매칭 항목이 늘기 때문). 캐시하면 승인 직후 이중 계상이 생긴다. 예측 실행마다 재집계한다.
- **모델을 순수 함수 안에서 부르지 말 것.** 출력을 **인자로 주입**한다.
  함수 안에서 추론을 부르면 [4.4](#44-예측-엔진-p0-07--p1-05--p1-07)의 재현성 인수 조건이 그 순간 깨진다.
- **`torch` 스레드 수를 고정한다.** 가변이면 스냅샷 이전 단계에서 값이 흔들린다.
- 워커 기동 시 모델을 **lazy load 후 상주**시킨다. 요청마다 로드하면 첫 응답이 수십 초가 된다.
- **모델을 켠 것 자체를 성과로 쓰지 않는다.** 게이트를 통과하지 못하면 베이스라인으로 되돌리고,
  그 사실을 문서에 남긴다. 측정 없이 채택하면 [10.2](#102-ai-기능)의 나머지 기준과 일관성이 깨진다.

## 8. AI 호출 규약

### 8.1 SDK와 배치 구조

| 위치 | SDK |
| --- | --- |
| AI 워커 (Python 3.12 / FastAPI / Pydantic v2) | `anthropic` — `Anthropic()` |
| API 서버 (Java 21 / Spring Boot) | `com.anthropic.*` — `AnthropicOkHttpClient.fromEnv()` |

`20_내부_AI워커.md`는 **무상태 Python 워커**를 전제한다. 이유가 맞다 —
[6.4](#64-p1-02-멀티모달-증빙-인식매칭)가 OpenCV·PaddleOCR을 쓰기 때문에 Python이 필요하다.

다만 **동기 두 개**(`item-normalization`, `document-assist`)는 이미지 처리가 없다.
Python 서비스 배포·모니터링 비용이 부담이면 이 둘은 Java SDK로 API 서버에서 직접 호출해도 된다.
`20_내부_AI워커.md`의 계약을 바꾸는 결정이므로 **팀에서 정하고 문서에 반영**한다.

원시 HTTP(`RestClient`/`requests`)로 Anthropic API를 직접 호출하지 않는다.
재시도·타임아웃·타입·스트리밍을 SDK가 이미 처리한다.

### 8.2 구조화 출력

7개 기능 전부 JSON을 받는다. `output_config.format`에 JSON Schema를 넣는다.

```python
resp = client.messages.create(
    model="claude-opus-5",
    max_tokens=2048,
    output_config={
        "format": {"type": "json_schema", "schema": CLASSIFICATION_SCHEMA},
        "effort": "low",
    },
    messages=[...],
)
```

- 구버전 `output_format` 파라미터는 폐기됐다. `output_config.format`을 쓴다.
- 도구를 쓰는 경로라면 도구 정의에 `strict: true` + `additionalProperties: false` + `required`.
- 파싱은 반드시 `json.loads()`로 한다. 직렬화된 문자열을 문자열 매칭하지 않는다.

### 8.3 프롬프트 캐싱

캐시는 **프리픽스 정확 일치**다. 렌더 순서는 `tools → system → messages`.
안정적인 것을 앞에, 변하는 것을 뒤에 둔다.

| 기능 | 프리픽스로 고정할 것 | 뒤에 둘 것 |
| --- | --- | --- |
| P1-01 | 시스템 프롬프트, `allowedCategories`, few-shot | 거래 배열 |
| P1-17 | 시스템 프롬프트, `toneGuide`, 출력 스키마 설명 | `metrics` |
| P1-15 | 시스템 프롬프트, 필드 정의 | 공고 원문 |

- **`datetime.now()`를 시스템 프롬프트에 넣지 않는다.** 캐시가 매번 깨진다.
- JSON을 프롬프트에 직렬화할 때 **키 순서를 고정**한다(`sort_keys=True`).
- 최소 캐시 가능 프리픽스가 모델마다 512~4,096 토큰이라 짧으면 조용히 캐시되지 않는다.
  **`usage.cache_read_input_tokens`로 실제 적중을 확인한다.** 0이 계속 나오면 무언가가 깨고 있다.

### 8.4 Batch API

P1-01 · P1-15 · P1-17은 사용자가 기다리지 않는다. **단가가 50%** 다.

```python
batch = client.messages.batches.create(requests=[...])   # custom_id 필수
# processing_status 가 "ended" 가 될 때까지 폴링 → results() 스트리밍
```

결과는 **요청 순서와 무관하게** 도착한다. 인덱스가 아니라 `custom_id`로 매칭한다.
`custom_id`에 `jobId`와 `transactionId`를 인코딩해 두면 Callback 조립이 쉬워진다.

### 8.5 thinking과 effort

- 모든 호출에 `thinking: {"type": "adaptive"}`. Opus 5는 생략해도 adaptive로 동작한다.
- **`budget_tokens`는 Opus 5에서 400 오류다.** 예전 코드·문서에서 옮겨 붙이지 않는다.
- 깊이는 `output_config.effort`로 조절한다: `low` / `medium` / `high`(기본) / `xhigh` / `max`.
- 라우트별 시작점: 분류·정규화·시나리오 해석 `low`, 브리핑·다듬기 `medium`,
  공고 구조화·문서 초안 `high`. **전역이 아니라 라우트별로** 튜닝한다.
- `thinking: {"type": "disabled"}`는 쓰지 않는다. Opus 5에서 도구 호출이 본문 텍스트로
  새는 실패 모드가 있다. 싸게 하려면 effort를 내린다.

### 8.6 거부 폴백과 오류 처리

- Opus 5 요청에는 서버측 폴백을 켠다:
  `betas=["server-side-fallback-2026-07-01"]` + `fallbacks="default"`.
  분류기가 요청을 거절하면(HTTP 200 + `stop_reason: "refusal"`) 자동으로 다른 모델로 넘어간다.
  **`content`를 읽기 전에 항상 `stop_reason`을 먼저 확인**한다.
- **Assistant prefill은 Opus 5에서 400이다.** 출력 형식은 구조화 출력으로 강제한다.
- 예외는 넓게 한 번 잡지 말고 체인으로 잡는다:
  `NotFoundError → RateLimitError → APIStatusError → APIConnectionError`.
  재시도 가능(429·5xx·네트워크)과 불가능(400·404)을 구분해야 Circuit Breaker가 제대로 돈다.
- 연속 5회 실패 시 60초 Circuit Open — **해당 AI 기능만 끄고 나머지 화면은 계속 동작**한다.
- Callback 유실에 대비해 5분 주기로 검사하고 10분 이상 `PROCESSING`인 Job은 한 번 재시도한다.
- 토큰 수는 `messages.count_tokens`로 센다. `tiktoken`은 Claude 토크나이저가 아니다.

### 8.7 AI 워커 운영 규칙 (체크리스트)

구현·리뷰에서 그대로 훑는 목록이다. 근거는 `docs/api/20_내부_AI워커.md`.

| # | 규칙 |
| --- | --- |
| 1 | AI 워커는 **DB에 직접 접속하지 않는** 무상태 서비스다. 영속화는 API 서버만 한다 |
| 2 | 내부 인증은 `Authorization: Bearer {serviceToken}`. 외부에 노출하지 않는다 |
| 3 | 모든 변경 요청에 `X-Request-Id`. 같은 ID 재시도는 중복 저장하지 않는다 |
| 4 | 비동기는 API 서버가 `JOB`을 만들고 워커가 Callback으로 결과를 돌려준다 |
| 5 | 동기 호출(`item-normalization`, `document-assist`)은 **10초 타임아웃** |
| 6 | 연속 5회 실패 시 **60초 Circuit Open**. 해당 AI 기능만 끄고 나머지는 살린다 |
| 7 | Callback 유실 대비 5분 주기 검사, `PROCESSING` 10분 초과 Job은 1회 재시도 |
| 8 | 계좌번호·주민번호·사업자번호·증빙 원본을 **로그에 남기지 않는다** |
| 9 | 외부 AI로 보내기 전에 **서버에서 민감 필드를 제거**한다 ([3.5](#35-보안--이미-설계에-들어-있는-것)) |
| 10 | 출력은 워커에서 Pydantic, 서버에서 Java DTO로 **이중 검증**한다 |
| 11 | 결과에 `modelName` · `modelVersion` · `promptVersion` · `confidence` · 근거를 기록한다 |
| 12 | 운영 모델은 alias가 아니라 **검증한 ID를 설정값으로 고정**하고, 평가 후에 교체한다 |

11번이 있어야 나중에 "언제부터 정확도가 떨어졌나"에 답할 수 있다.
`EVIDENCE_EXTRACTION`에 `model_name` · `model_version` · `pipeline` · `is_current` 컬럼이
이미 있는 것도 같은 이유다.

## 9. 비용을 낮추는 순서

싼 것부터. **품질을 깎는 수단은 마지막이다.**

| 순서 | 수단 | 기대 효과 | 품질 영향 |
| --- | --- | --- | --- |
| 1 | LLM 도달 건수 줄이기 (규칙·사전 강화) | 큼 | 없음 (오히려 개선) |
| 2 | Batch API | 해당 라우트 −50% | 없음 |
| 3 | 프롬프트 캐싱 | 입력 토큰 대폭 | 없음 |
| 4 | 입력 위생 (불필요한 필드·원문 제거) | 중간 | 없음 |
| 5 | 이미지 해상도·출력 길이 제한 (P1-02·P1-22) | 중간 | 작음 |
| 6 | effort 내리기 (`high` → `medium` → `low`) | 라우트별 상이 | 측정 필요 |
| 7 | 모델 내리기 (Opus 5 → Sonnet 5 → Haiku 4.5) | 큼 | **측정 필수** |

**7번은 6번까지 다 하고 나서** 라우트별로 판단한다. 6번까지는 공짜인데 7번은 정확도와 교환이다.

| 라우트 | 내려도 될 여지 | 이유 |
| --- | --- | --- |
| P1-03 품목 정규화 | 큼 | 규칙이 90% 처리, 나머지도 오매칭이면 사용자가 고침 |
| P0-09 시나리오 해석 | 큼 | 사용자 확인을 거침, 실패해도 손잡이 UI가 있음 |
| P1-01 거래 분류 | 중간 | 수락률로 측정 가능. 떨어지면 되돌린다 |
| P1-17 브리핑 | 중간 | 숫자 검증이 기계적이라 환각은 걸러짐. 문장 품질만 비교 |
| P1-02 증빙 VLM | 작음 | 이미 저신뢰 건만 옴. 여기서 또 틀리면 수기 입력 |
| P0-12 초안 점검 | 작음 | 옵션 기능이고 실패해도 초안은 나온다 |
| P1-15 공고 구조화 | **없음** | 자격 조건 오독 = 잘못된 추천. 사업장 수와 무관해 비용도 고정 |
| P1-22 매출 인쇄물 | **없음** | 감열지 도트 번짐. 여기서 틀리면 구성비 전체가 틀린다 |

**캐시는 모델 단위다.** 여러 모델로 나누면 캐시 재사용이 그만큼 깨진다.
"한 모델 + 낮은 effort"가 "여러 모델 캐스케이드"보다 나은 경우가 많으니 6번을 먼저 시도한다.

## 10. 검증 기준

### 10.1 AI를 쓰지 않는 기능

SRS 13장 인수 조건(v1.7)에서 온 것들이다. **CI에 넣어 자동으로 돈다.**

| 대상 | 검사 | 출처 |

| 예측 엔진 | 모델 경로를 꺼도(`applyResidualModel = false`) **곡선이 정상 산출된다** | 비기능 |

| 시나리오 | 변경값이 **원본과 구분되어** 표시된다 | 인수 |
| 시나리오 | 저장한 것을 다시 조회하면 **최신 데이터 기준으로 재계산**된다 | 인수 |

| **신고서 초안** | 검토 확정 후 생성하면 간편장부 서식 항목이 확정 거래 집계로 채워지고, **각 항목에서 근거 거래·증빙 목록**을 열 수 있다 | 인수 |
| **신고서 초안** | **개인 사용 가능성 거래는 항목 금액에서 제외**되고 별도 합계로 표시된다 | 인수 |
| **민감 항목** | 내보내기 요청에만 담기고 **서버 저장소·AI 워커 로그 어디에도 남지 않는다.** 마스킹된 초안만 재조회된다 | 인수 |
| **P1-22** | 같은 기간을 다시 등록하면 **새 행이 쌓이지 않고 갱신**된다. 상품명 일괄 변경으로 두 상품을 합치면 수량·금액이 합산된다 | 인수 |
| **P1-22** | 상품별 매출이 **신고서 초안 매출액·부가세 예수금에 반영되지 않는다.** 매출 대사에 참고값으로만 나타난다 | 인수 |
| 권한 | 다른 사업장 거래를 조회할 수 없다 | 인수 |
| 가용성 | 금융망·AI 장애가 다른 기능의 **조회**를 막지 않는다 | 비기능 |
| Job | 모든 Job이 `COMPLETED` / `FAILED` 중 하나에 도달한다 | 규약 |
| 정산 대사 | Σ배분액 ≠ 입금액이면 저장이 거부된다 | 불변식 |
| 금액 | `BigDecimal` 비교에 `equals` 대신 `compareTo`를 쓴다 | 구현 |
| 날짜 | 월말·윤년·공휴일 보정 경계값 테스트가 있다 | 구현 |

### 10.2 AI 기능

모델·프롬프트를 바꾸기 전에 **고정 평가 세트**를 만든다. 없으면 나아졌는지 알 수 없다.

| 기능 | 평가 세트 | 통과 기준 (초안) | 실패 시 |

| P1-15 | 공고 30건 (조건 수기 정답) | 필드 정확도 ≥ 90%, **근거 없는 조건 0건** | 프롬프트 재작성 |
| P1-17 | 지표 세트 30건 | **환각 숫자 0건**, 문장 적절성 사람 평가 | 검증 로직 강화 |
| P1-22 | 인쇄물 40장 (`SCREEN` 20 · `PRINTOUT` 20) | 체크섬 일치 ≥ 90%, **행 환각 0건**, 기간 추출 ≥ 95% | 촬영 유형별 프롬프트 분리 |
| **P0-07 잔여 축** | 시드 기간 마지막 4~6주 hold-out | **통계 베이스라인 대비** 공백 발생 F1·최초 부족일 오차 개선 | 모델 미채택, 베이스라인 유지 |
| **P1-05 보정** | 동일 hold-out | 동일. 추가로 **blind split** 성립 여부 | 내부 실험으로만 남김 |

**"근거 없는 조건 0건"과 "환각 숫자 0건"은 비율이 아니라 절대 기준이다.**
한 건이라도 나오면 배포하지 않는다. 나머지는 데이터가 쌓이면 조정한다.

공통 검사:
- 계좌번호·주민번호·사업자번호가 외부 요청과 로그에 포함되지 않는다.
- AI 실패 시 규칙 결과·수기 입력·지표 전용 화면으로 정상 대체된다.
- 모든 결과에 `modelName`·`promptVersion`·`confidence`·근거가 기록된다.

**1.5단계(데이터 시드)를 따로 둔 이유** — 금융망은 우리가 만든 데이터만 갖고 있고
([3.6②](#36-ssafy-금융망--실제-인터페이스가-요구하는-것)),
**과거 날짜의 거래는 아예 만들 수 없다**([4.1.1](#411-데이터-시드--과거는-csv-현재미래는-금융망)).
반복 탐지·안전선·AI 분류가 전부 과거 데이터를 입력으로 받으므로,
CSV 생성기와 예약이체 등록이 끝나기 전에는 3단계 이후가 착수되지 않는다. **크리티컬 패스다.**

**6번(AI 워커)을 5번 뒤에 두는 이유** — AI 없이도 제품이 성립해야 한다.
P0가 다 돌아가는 상태에서 AI를 얹으면, AI가 실패해도 서비스가 산다.
반대 순서로 하면 AI 장애가 곧 서비스 장애가 된다.

**7번(거래 분류)을 첫 AI 기능으로 두는 이유** — AI 워커 계약 전체를 관통하는
가장 단순한 비동기 경로다. 여기서 Job·Callback·검증·재시도가 검증되면 나머지는 스키마만 바뀐다.
