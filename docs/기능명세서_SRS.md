## 1. 개요

### 1.1 목적

사업용 계좌의 입출금 기록에서 반복 패턴을 찾아 미래 날짜별 예상 잔액과 정산 공백(자금 부족)을 사전에 예측한다. 거래·증빙 데이터를 자금 운영, **종합소득세 신고 준비**, 요식업 운영 의사결정으로 연결해 소상공인의 현금흐름 대응을 돕는다.

**대상 매장** — 홀·포장 카드 결제와 배달 플랫폼 정산이 **함께 발생하는** 요식업 매장을 기준으로 한다(월별 리포트 수익 구조 예시: 카드 61% · 배달 30% · 현금 9%). 입금 채널마다 주기가 다르다는 점이 이 서비스의 출발점이다 — 카드사 정산은 영업일마다 소액으로, 배달 플랫폼 정산은 주 단위로 묶여서, 현금은 불규칙하게 들어온다. 배달 전문점으로 좁히지 않는다.

### 1.2 프로젝트 배경

소상공인은 정산일, 고정비, 세금, 대출 상환이 서로 다른 주기로 발생해 잔액 부족을 사전에 파악하기 어렵다. 계좌 거래만으로는 거래 성격과 미래 반복 여부를 알기 어려우므로 규칙 기반 분석, 사용자 확인, AI 분류·요약을 결합한다.

### 1.3 프로젝트 범위

**포함 범위**

- SSAFY 금융망 API 및 CSV/테스트 데이터 기반 계좌 거래 수집
- 거래 분류, 반복 거래 탐지, 미래 입출금 예측, 7/14/30일 잔액 곡선
- **예측 엔진의 AI 모델 적용** — 반복 패턴으로 설명되지 않는 잔여 현금흐름을 **잔여 예측 모델**로 추정하고, 정산 지연·금액 편차를 회귀 모델로 보정한다. 잔액 합산 자체는 결정론 계산 엔진이 수행하며, 모델은 **범위(분위수) 산출에만** 관여한다
- 정산 공백 알림과 What-if 시나리오 분석(파라미터 조합·저장 포함)
- 증빙 업로드·누락 표시, 정산 수동 대사, **종합소득세 신고서 초안 자동 채움·내보내기**(민감 항목은 사용자 직접 입력)
- 요식업 우선의 거래 이해, 안전선·준비금·대출·지원 제도 보조 기능
- 반응형 매장용 화면과 심층 분석용 웹 대시보드

**제외·보류 범위**

- 서비스가 세액·신고 유형·대출 실행을 자동 확정하거나 대신 실행하는 기능
- 지원사업 신청 문서(사업계획서 등)의 AI 작성·편집기 — v1.5에서 범위 제외(P1-16 결번). 서류 발급처 링크는 P1-15 상세에 유지
- **원자재 가격 지표 수집·반영** — v1.10에서 범위 제외(P1-06 결번). KAMIS·ECOS 시세 배치도, 사업장별 재료비 비중 설정도 만들지 않는다
- **재료비 변화 What-if**(`MATERIAL_COST_CHANGE`) — v1.11에서 범위 제외. 시세 없이 변화율만으로는 **무엇에 곱하는지가 정의되지 않고**, 패턴으로 잡히지 않은 재료비는 잔여 흐름 축에 섞여 분류로 골라낼 수 없다. 매출 쪽 시뮬레이션은 `PRODUCT_SALES_CHANGE`(P1-22 구성비 연동)가 맡는다. **`MATERIALS` 거래 분류는 그대로 유지한다**(P0-02)
- 홈택스 전자신고 파일 생성·자동 제출, 복식부기 재무제표(재무상태표·손익계산서·조정계산서)와 성실신고확인서 작성
- **POS 사업자 API 연동** — 하지 않는다. 상품별 판매 실적은 사장님이 POS에서 인쇄한 매출현황을 촬영해 OCR로 등록한다(P1-22). POS의 「인쇄」는 실물 출력이라 자동 연동 경로가 없다
- 사용자의 명시적 승인 없는 이체·결제일 변경
- P2 기능은 P1 완료 후 착수

### 1.4 핵심 용어

| 용어 | 정의 |
| --- | --- |
| **입금** | 계좌에 실제로 찍힌 돈. **매출 금액의 단일 출처**다 |

| 가상 준비금 | 세금·고정비 등 미래 지출을 위해 매일 따로 모아둘 금액 |

## 3. 사용자 정의 및 권한

### 3.1 사용자 유형

| 유형 | 주요 목표 | 구현 범위 |
| --- | --- | --- |
| 소상공인·점주 | 자금 부족일 예측, 거래·세금·운영 의사결정 | P0 |
| 세무대리인(공유 사용자) | 신고 준비자료 검토 및 전달 | **범위 외** — 아래 참조 |
| 관리자 | 사용자·연동·데이터 품질 및 운영 관리 | 범위 외 (`USER.system_role`만 예약) |

### 3.2 권한 원칙

사업장과 계좌를 최상위 접근 범위로 삼는다. 사용자는 **자신이 소유한** 사업장만 조회·수정한다. 이체·대출·결제 변경 등 실행성 기능은 항상 별도 사용자 승인을 요구한다.

> **세무대리인 계정은 이번 범위에서 제외한다** (API 21장, ERD v1.1). 사용자-사업장 관계는 `BUSINESS.owner_user_id`를 통한 **1:N 소유**이며 멤버십(N:M) 테이블을 두지 않는다. 세무대리인에게 자료를 전달하는 목적은 **P0-12 신고자료 내보내기 파일**로 갈음한다.
>
> 공유 계정이 필요해지면 `BUSINESS_MEMBER(business_id, user_id, role)` 테이블을 추가하고 읽기 전용 Role을 도입한다. 그때까지 어떤 API도 교차 사업장 접근을 허용하지 않는다.

## 4. 시스템 아키텍처

```text
[반응형 웹: 매장용 / 분석용]
          │ HTTPS
          ▼
[API 서버: 인증·사업장·거래·예측·리포트]
      │             │              │
 [PostgreSQL]    [Redis/Queue]   [Object Storage]
      │             │              │
 [금융 API·CSV]  [AI/OCR Worker] [증빙·내보내기]
```

- API 서버는 인증·인가, 거래·사업장 도메인, 예측 결과와 사용자 승인 흐름을 담당한다.
- AI 워커는 OCR/VLM, 거래 분류, 공고문 구조화, 자연어 브리핑을 비동기로 처리한다.
- 수치 계산은 백엔드 엔진이 수행하고 LLM은 분류·추출·문장화만 담당한다.
- ERD는 처음부터 다사업장·다계좌를 전제로 한다.

### P0-09 시나리오 분석

사용자가 정산 지연 일수, 입금 감소율, 추가 지출을 입력하면 원본과 변경 시나리오의 잔액 곡선·부족일·최저잔액을 비교한다. 서비스는 결과를 제시할 뿐 금융 실행을 자동 수행하지 않는다.

### P0-13 What-if 시뮬레이션 고도화

원본 예측을 변경하지 않고 시나리오를 복제한다. 정산 지연 일수, 입금 감소율, 추가 지출·입금, 지출일 변경을 조합할 수 있으며 결과에는 원본 대비 최저잔액·부족일·회복일을 포함한다. **파라미터는 8종이다**(API 11.1). 시나리오는 저장해 재조회·비교·공유할 수 있고, 저장한 시나리오는 조회 시점의 최신 데이터로 재계산한다.

**상품 단위 매출 시뮬레이션 (`PRODUCT_SALES_CHANGE`)** — 상품 하나의 판매량·단가를 조정해 총매출 배율을 환산하고 그 배율을 매출성 입금 패턴에 곱한다. P1-22 구성비가 등록된 사업장에서만 동작한다.

```text
라떼 판매량 −5%, 단가 +10%  →  상품 배율 0.95 × 1.10 = 1.045
라떼 구성비 24.2%           →  총매출 배율 1 + 0.242 × 0.045 = 1.0109
                            →  매출성 입금 패턴 전체 × 1.0109
```

구성비(비율)를 쓰기 때문에 POS 판매 총액과 계좌 입금액의 기준이 달라도(수수료 차감·정산 지연·현금 미입금) 변화율만 보존되어 환산이 필요 없다. 매출 레이어를 만드는 것이 아니라 배율 하나를 만드는 것이므로 예측 원장을 건드리지 않는다.

- **판매량과 단가는 사용자가 각각 가정한다.** 가격 탄력성("10% 올리면 얼마나 덜 팔릴까")은 서비스가 모른다.
- 어느 기간 구성비를 적용했는지 항상 표시한다. 계절성 있는 메뉴는 기간에 따라 구성비가 달라진다.
- **매출 변화까지만 계산하고 이익 변화는 다루지 않는다.** 원가·레시피가 필요한 마진 계산은 P2-03 범위다.

> v1.2~v1.6에는 "메뉴 단가 변경 등 판매 데이터 기반 파라미터는 P2 발주·메뉴 기능과 함께 보류한다"고 적혀 있었다. **그 전제는 v1.4 P1-22 신설로 무효가 됐다** — 판매 데이터가 P1으로 돌아왔는데 보류 문구만 남아 있었다. v1.7에서 폐기하고 위 파라미터로 대체한다.
>
> v1.11에서 **재료비 변화(`MATERIAL_COST_CHANGE`)를 뺐다.** P1-06 시세가 사라진 뒤 남은 `rate` 만으로는 무엇에 곱하는지가 명세에 없었고, 새로 정의해도(예정 거래 중 `MATERIALS` 출금) 패턴으로 안 잡힌 재료비는 잔여 흐름 축에 섞여 골라낼 수 없다. 상품 단위 매출 시뮬레이션이 실측 구성비를 근거로 삼는 더 나은 도구다.

### P0-10 증빙 및 P0-12 신고서 초안 자동 채움·내보내기

거래별 증빙을 업로드하고 누락 상태를 표시한다. 검토 상태를 확정한 뒤에는 신고 유형에 맞는 종합소득세 서식 초안을 거래·증빙 데이터로 채우고, 민감 항목만 사용자가 직접 입력해 PDF와 홈택스 입력용 시트로 내보낸다. 기존 XLSX/ZIP 준비자료 패키지는 세무대리인 전달용 부속 산출물로 유지하며 개인정보와 기준일을 명시한다.

**목적** — 종합소득세 신고 준비다. 신고에는 매출자료뿐 아니라 세금계산서·카드 사용내역·현금영수증·임대료·급여·공과금 자료가 필요한데, 신고 직전에 한꺼번에 모으면 증빙 누락과 중복 처리 가능성이 커진다(기획정리본 §4.6). 그래서 평소 거래에 증빙을 붙여 두는 것이 이 기능의 존재 이유다.

**산출물** — 주 산출물은 **신고서 초안**이다. 신고 유형별 서식(v1은 간편장부소득금액계산서와 부표 총수입금액 및 필요경비명세서)을 항목 단위로 채운 PDF 초안과, 홈택스 화면 입력 순서에 맞춘 항목·값·출처·근거 건수 시트를 생성한다(API 14.3). 부속 산출물은 기획정리본 §6.8·§6.10의 준비자료 패키지다: 연간 매출요약, 사업용계좌 거래내역, 필요경비 후보 명세서, 플랫폼별 정산 대사표, 고정비·반복지출, 증빙누락·확인필요, 거래증빙 연결목록, 증빙 원본 폴더(API 14.2). 어느 산출물도 **세액을 계산하거나 신고를 대신하지 않는다.** 소득금액까지만 채우고 세액 산출과 제출은 홈택스에서 사용자가 한다.

**검토 상태 확정 (내보내기 선행 단계)** — 계좌에서 출금되었다는 사실만으로 필요경비 인정 여부가 확정되지 않으므로, 거래별 검토 상태를 8종으로 관리한다(기획정리본 §6.5, API 8.7).

- **자동 판정 2종** — `증빙 확인 완료`·`증빙 누락`. 증빙 연결 여부로 기계적으로 결정된다.
- **사용자 지정 5종** — `사업 관련성 확인 필요`·`개인 사용 가능성 있음`·`중복 등록 가능성 있음`·`세무전문가 확인 필요`, 그리고 기본값 `미검토`.
- **예약 1종** — `자산 등록 또는 감가상각 검토 필요`. 자산대장·감가상각 관리가 상용화 확장이라 값만 예약하고 화면은 P2로 둔다.

서비스는 후보와 확인 사유만 제시하고 세무 판단을 확정하지 않는다(1.3 제외 범위). 검토 상태는 `07_거래증빙_연결목록.xlsx`의 **검토 상태** 열에 반영된다.

**신고서 초안 자동 채움 (검토 확정 후 단계)** — 서식의 각 항목은 다음 여섯 출처 중 하나로 채워지며, 화면과 시트에 항목마다 출처를 표시한다(API 14.3).

| 출처 | 의미 | 예 |
| --- | --- | --- |
| `AUTO_TRANSACTION` | 검토 확정 거래와 연결 증빙을 카테고리→서식 항목 매핑표로 집계 | 매출액, 임차료, 급료, 소모품비 |
| `AUTO_SETTLEMENT` | 정산 대사(P0-11) 결과에서 총매출·수수료를 집계 | 플랫폼 매출 총액, 지급수수료 |
| `AUTO_PROFILE` | 사업장·사용자 프로필에서 채움 | 상호, 사업자등록번호, 소재지, 업종, 성명, 전화번호, 소득종류(사업소득 40) |
| `REFERENCE_HOMETAX` | 홈택스 신고도움서비스에서 사용자가 보고 옮겨 적는 값. 서비스 집계와의 차이를 표시 | 신고안내 유형, 기장의무, 업종코드, 국세청 수입금액 |
| `USER_SENSITIVE` | 사용자가 직접 입력. AI 워커에 전달하지 않고 서버에 저장하지 않음 | 74호 본표의 주소지·생년월일. 홈택스 본표(별지 제40호)에 직접 입력하는 주민등록번호·환급계좌·부양가족 인적사항 |
| `CALCULATED` | 서식 산식으로 백엔드가 계산 | 소득금액 = 총수입금액 − 필요경비 |

- 집계 대상은 검토 상태가 `증빙 확인 완료`·`증빙 누락`·`미검토`인 거래다. `개인 사용 가능성 있음`은 제외하고, `사업 관련성 확인 필요`·`중복 등록 가능성 있음`·`세무전문가 확인 필요`는 항목 금액에 넣지 않고 "확인 필요 합계"로 분리 표시한다. 증빙 누락 거래가 섞인 항목은 누락 건수를 함께 표시한다.
- 자동 채움 항목은 모두 근거 거래·증빙 목록으로 추적할 수 있어야 한다(근거 보기).
- 신고 유형은 서비스가 판정하지 않는다. 사용자가 홈택스 신고안내문의 유형을 선택하고 서비스는 그 유형에 맞는 서식만 제시한다. 복식부기 의무자와 성실신고확인 대상자에게는 초안 대신 필요 서류 체크리스트와 세무대리인 전달용 패키지를 안내한다.
- 초안에는 "초안 · 생성 기준일 · 확정 세무 자료 아님" 표기가 항상 들어간다(12장 세무 요구사항).
- 서식은 개인 단위다. 사업장이 여럿이면 사업장별 열과 합계 열로 배치한다(74호 본표·부표 모두 사업장 열 4개). 본표 세무조정 가감액(⑫⑬⑯⑰)과 기부금 한도초과·이월(⑳㉑)은 기본값 0의 사용자 확인 항목이며, 값이 있으면 해당 조정명세서 첨부를 안내한다. 부표 제조비용란(⑱~㉔)은 제조업 전용이라 음식점업은 기재하지 않고, 기초·기말 재고를 구분하기 어려우면 당기 매입액만 기재한다(부표 작성방법 4).

**대상 서식과 우선순위** — ① 간편장부소득금액계산서(별지 제74호서식) + 총수입금액 및 필요경비명세서(제74호서식 부표)(v1 필수. 음식점업 간편장부대상자는 직전연도 수입금액 1억 5천만원 미만 또는 신규 개업), ② 추계소득금액계산서(기준경비율 적용대상자용) + 주요경비지출명세서(v1 선택. 매입비용·임차료·인건비를 정규증빙 수취분과 미수취분으로 구분), ③ 단순경비율 대상자는 국세청 모두채움으로 갈음하고 매출 대사 결과만 제공, ④ 복식부기 재무제표·조정계산서와 성실신고확인서는 범위 외(1.3).

**민감 항목 원칙** — 서식 인적사항(주소지·생년월일)과 홈택스 본표에 직접 입력하는 주민등록번호·계좌번호·부양가족 인적사항은 서비스가 저장하지 않는다. 서식 PDF에 들어가는 값은 내보내기 요청 본문에만 담기고, 생성된 파일은 즉시 다운로드 응답으로만 제공한다. 서버 저장소·로그·AI 워커 어디에도 남기지 않는다. 재조회용으로는 민감 항목이 비어 있는 초안만 저장한다.

**홈택스 제출 방식** — 홈택스 종합소득세 신고는 파일 업로드가 아니라 화면 입력이므로 산출물은 입력 순서에 맞춘 값 시트와 서식 PDF다. 전자신고 파일 생성·자동 제출은 범위 외다. 정기신고 화면은 5월에만 열리므로 시연·테스트는 서비스 화면과 PDF로 한다.

**AI의 역할** — 항목 값은 규칙 매핑과 백엔드 집계로만 만든다. AI는 거래 분류(P1-01)·증빙 추출(P1-02) 결과가 집계에 들어가는 형태로 간접 기여하고, 확인 필요 항목의 사유 문장화와 누락 점검(P1 옵션, API 20.10)에만 직접 쓰인다. 초안 생성 자체는 AI 호출 없이 완료된다(공통규약 23장 "P0 경로 AI 미호출").

**예측 제외와 세무 제외의 분리** — `isExcluded`(예측·집계 제외)와 검토 상태(세무 판단)는 독립적이다. 장비 구입은 예측에서 빼되 경비로 인정될 수 있고, 개인 사용 지출은 경비에서 빼되 예측에는 반영해야 한다.

### 8.1 P1 상세 처리 규칙

#### 거래 이해·예측 고도화

- **분류 파이프라인**: 확정된 거래처 매핑과 규칙을 먼저 조회하고, 미지 패턴만 LLM에 보낸다. LLM 응답은 허용된 카테고리 enum, 거래처 추정, 신뢰도, 근거를 포함해야 한다. 사용자가 수정한 결과는 이력으로 저장한다.
- **증빙 매칭**: 금액·거래일·거래처 유사도를 이용해 후보를 제시한다. 자동 연결은 높은 신뢰도에서만 허용하고, 그 외에는 사용자 승인을 요구한다.
- **예측 보정**: 영업일/명절 보정과 계절성 계수를 적용한 값은 원본 규칙과 함께 표시한다. 예측-실제 오차가 누적되면 다음 예측의 범위와 신뢰 수준을 조정한다.

#### 자금 운영·위험 관리

- **안전선·준비금**: 사용자가 최소 잔액과 목적별 준비금 목표를 직접 수정할 수 있다. 안전선 하회, 준비금 부족, 정산 공백은 서로 다른 상태로 표시한다.
- **다사업장**: 모든 조회·계산 API에 businessId를 요구하고, 사업장 간 자금 이동은 가상 거래로만 계산한다. 실제 이체 API는 범위에서 제외한다.

#### 지원·운영 보조

- **지원 제도**: 공고문 원문과 수집일을 보존하고, 조건 일부가 불명확하면 ‘확인 필요’로 표시한다. 서비스는 자격을 확정하지 않는다.
- **AI 브리핑**: 브리핑 문장에 사용한 지표와 기준 기간을 연결한다. 계산되지 않은 수치를 LLM이 임의로 생성하지 못하도록 구조화된 입력만 허용한다.
- **신고서 초안**: 서식 항목 값은 확정 거래 카테고리 → 서식 항목 매핑표(API 14.3)와 백엔드 집계로만 만든다. LLM은 수치를 만들지 않고 확인 필요 사유 문장화·누락 점검(API 20.10)에만 쓰며, 초안 생성은 LLM 호출 없이 완료된다.

```text
P0-01~05 → P1-01~05 → P1-07
P1-05(최소 매처) → P0-07   ← 방향이 거꾸로다. 아래 설명
P0-10    → P1-02~03 → P2-03/P2-09
P0-07~09 → P0-13 → P2-12
P0-07~09 → P1-04/P1-08~09/P1-11 → P2-04/P2-07
P0-01    → P1-12~14
P1-15    → P2-02
P0-02/P0-10/P0-11 → P0-12(신고서 초안) → P1-23
P1-19    → P1-17
P1-22    → P1-19 (매출 변동 기여도) / P1-17 (브리핑 근거) / P0-13 (PRODUCT_SALES_CHANGE 배율)
P1-02    → P1-22 (OCR 워커 인프라 공유, 추출 스키마는 별개)
P2-14    → P2-15 → P2-03/P2-09
```

**⚠ P1-05 → P0-07 은 우선순위가 뒤집힌 의존이다** *(2026-09-10 추가)*. 잔여 현금흐름을 `일별 실제 합계 − 예정 거래 매칭분`으로 정의했으므로(P0-07), 그 매칭을 만드는 자동 매칭(P1-05, API 9.5)이 없으면 잔여가 「실제 거래 전부」가 되어 **예정 거래를 두 번 센다.** 해소는 둘 중 하나다 — ① 매칭 규칙을 줄인 **최소 매처를 P0-07 범위로 올리거나**(API 9.5 에 규칙을 적어 뒀다), ② 잔여 모델을 끄고(`applied: false`) 곡선을 예정 거래만으로 낸다. **매칭 없이 모델을 태우는 세 번째 길은 안 된다** — 곡선이 위로 발산해 부족일을 아예 못 잡는다. 근거는 [예측엔진 설계노트 M-1](예측엔진_설계노트.md).

**P1-22가 이어지지 않는 곳** — 의도적으로 끊은 것이다. 매출 금액의 단일 출처는 계좌 입금이며, 판매 층을 더하면 같은 매출이 두 번 계상된다.

## 11. AI 파이프라인 명세

1. 규칙·사전 캐시로 거래를 먼저 분류한다.
2. 미지 거래만 LLM에 구조화 JSON으로 전달하고 신뢰도·근거를 저장한다.
3. 증빙은 OCR/VLM으로 항목을 추출하고 거래와 매칭 후보를 제시한다.
4. 공고문은 지원 대상·금액·기간·서류를 구조화하며 원문 링크와 수집일을 보존한다.
5. **수치 계산에 LLM을 쓰지 않는다.** 잔액 합산·부족액·세액·상환액은 백엔드 계산 엔진의 결정론 함수가 담당하고, LLM은 요약·브리핑·문장화만 맡는다. **LLM이 아닌 예측 모델**(시계열·회귀)은 예측 엔진 안에서 **범위(분위수) 산출에만** 관여하며, 그 출력은 계산 엔진에 인자로 주입된다 — 계산 함수 안에서 모델을 호출하지 않는다. 모델 산출값은 실행 시점 스냅샷으로 보존해 재현성을 보장하고, 통계 베이스라인 대비 개선을 확인한 뒤에만 채택한다. 모델 경로가 실패해도 예측은 베이스라인으로 정상 산출된다.
6. 사용자 정정 사례는 사전/few-shot 데이터로 축적하되 확정값과 추정값을 구분한다.
7. 신고서 초안은 확정 카테고리·증빙 연결 데이터를 서식 항목 매핑표로 집계한다. 민감 항목은 AI에 전달하지 않고 서버에도 저장하지 않으며, LLM은 확인 필요 사유 문장화에만 관여한다.
8. POS 매출현황 인쇄물은 3번(증빙 OCR)과 **다른 추출 작업**이다. 증빙은 자유 양식의 매입 영수증이고 이쪽은 정형 양식의 판매 실적(상품 행 반복 + 합계 행)이다. 기간은 인쇄물 헤더에서 읽고, 합계 행을 분리 추출해 행 누락을 대조하며, **읽지 못한 행을 만들어내지 않는다.** 결과는 저장하지 않고 사용자 확인 후 저장한다.

## 13. 인수 조건 / 테스트 시나리오

- CSV 거래를 업로드하면 중복 없이 계좌·사업장에 귀속된다.
- 반복 거래 후보를 승인·수정하면 이후 예측에 반영된다.
- 7/14/30일 잔액과 부족일이 동일한 입력과 동일한 모델 버전에 대해 재현된다.
- 예측 모델 반영을 끄거나 모델 호출이 실패해도 잔액 곡선과 부족일이 정상 산출되고, 신뢰 수준 강등과 사유가 함께 표시된다.
- 잔여 현금흐름 추정치는 예정 거래와 중복 계상되지 않는다. 반복 후보를 승인한 직후 재계산해도 해당 금액이 두 번 반영되지 않는다.
- 정산 지연 시나리오의 변경값이 원본과 구분되어 표시된다.
- 저장한 What-if 시나리오를 다시 조회하면 최신 데이터 기준으로 재계산된 결과가 반환된다.
- 증빙 누락 거래를 필터링하고 XLSX/ZIP을 다운로드할 수 있다.
- 검토를 확정한 뒤 신고서 초안을 생성하면 간편장부 서식 항목이 확정 거래 집계로 채워지고, 각 항목에서 근거 거래·증빙 목록을 열 수 있다. 개인 사용 가능성 거래는 항목 금액에서 제외되고 별도 합계로 표시된다.
- 신고서 초안의 민감 항목은 내보내기 요청에만 담기며 서버 저장소·AI 워커 로그 어디에도 남지 않는다. 마스킹된 초안만 재조회된다.
- POS 매출현황 인쇄물을 촬영해 올리면 기간이 헤더에서 인식되고, 항목 행 합이 인쇄물 합계 행과 다르면 차이 금액과 함께 누락 경고가 표시된다. 경고 상태로도 저장할 수 있고 저장된 기간에는 "불완전" 표시가 남는다.
- 같은 기간을 다시 등록하면 새 행이 쌓이지 않고 갱신된다. 상품명 일괄 변경으로 표기가 다른 두 상품을 합치면 수량·금액이 합산된다.
- 상품별 매출을 등록한 사업장에서 시나리오에 상품 매출 변화를 넣으면, 상품 배율과 구성비로 환산한 총매출 배율이 잔액 곡선에 반영되고 적용한 구성비의 근거 기간이 함께 표시된다.
- 상품별 매출은 신고서 초안 매출액과 부가세 예수금에 반영되지 않는다. 신고서 초안의 매출 대사에는 참고값으로만 나타난다.
- 권한이 없는 사용자는 다른 사업장 거래를 조회할 수 없다.
- AI 결과에는 근거·신뢰 수준이 있고, 실패 시 규칙 기반 결과 또는 오류 상태가 제공된다.
