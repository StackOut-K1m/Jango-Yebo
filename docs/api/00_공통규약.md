# Jango-Yebo API 명세서 — 공통 규약 (1·2·21·22·23장)

> 모든 도메인 API가 공통으로 따르는 문서다: 설계 원칙(1장), 공통 규약(2장), 권한(21장), 주요 오류 코드(22장), 구현 전 확인 사항(23장). `GET /jobs/{jobId}`는 2.7 공통 Job 패턴에서 정의한다. 도메인별 상세와 전체 목록은 [README.md](./README.md)를 본다.

### 1.3 설계 원칙

1. **다사업장·다계좌 우선.** 사업장 범위 데이터는 모두 `/businesses/{businessId}` 하위 경로로 접근하고, 서버는 모든 요청에서 사업장 소유권을 검증한다. "사용자 = 사업장 1곳" 가정을 어디에도 두지 않는다.
2. **예측은 확정값이 아니다.** 예측을 반환하는 모든 응답은 기준 시각(`baseTime`), 신뢰 수준(`confidence`), 근거(`basis`)를 포함하고, 금액은 가능하면 범위(`amountMin`/`amountMax`)로 표현한다. 필드명도 `expected*`, `estimated*`를 사용한다.
3. **수치 계산은 백엔드 엔진, LLM은 분류·추출·문장화만.** LLM이 산출한 수치를 그대로 저장·반환하지 않는다. AI 관련 작업은 모두 비동기 Job으로 처리하고 클라이언트는 Job 폴링으로 상태를 확인한다. 별도의 실시간 푸시 채널은 두지 않는다.
4. **자동 실행 금지.** 이체·결제일 변경·대출 실행을 수행하는 API는 정의하지 않는다. 시뮬레이션 API는 결과만 반환한다.
5. **확정 분류는 캐시 재사용.** 한 번 확정된 `거래처 ↔ 분류` 매핑은 거래처 사전에 축적해 재사용하고, LLM 호출은 규칙·사전으로 해결되지 않는 신규 패턴에만 발생한다(규칙 → 사전 → LLM 파이프라인).
6. **세무 표현 제약.** 세무 관련 산출물은 "후보" 명칭을 사용하고(`expenseCandidates` 등), 응답에 기준연도·계산 기준·전문가 확인 안내를 포함한다. 서비스는 세액·신고유형을 확정하지 않는다.
7. **현금흐름과 세무 데이터 분리.** 잔액 예측은 실제 입출금 시점 기준, 신고자료는 과세기간 기준으로 집계하며 같은 거래를 연결하되 동일 값으로 취급하지 않는다.

### 1.5 매출 용어 — 판매 / 정산 / 입금

**"매출"을 단독으로 쓰지 않는다.** 성격이 다른 세 층이 모두 매출로 불려 문서 간 혼동이 반복됐다. 아래 세 낱말로만 쓴다.

| 층 | 낱말 | 무엇 | 출처 | 저장 | 쓰는 곳 |
| --- | --- | --- | --- | --- | --- |
| 1 | **입금** | 계좌에 실제로 찍힌 돈 | 금융망 동기화·CSV | `TRANSACTION` (`CARD_SETTLEMENT`·`PLATFORM_SETTLEMENT`·`CASH_SALES`·`TRANSFER_SALES`) | 잔액 예측, 월별 리포트, 부가세, 신고서 ⑪ |
| 2 | **정산** | 플랫폼 총매출 − 취소 − 수수료 | 사용자가 플랫폼 명세서를 보고 입력 | `SETTLEMENT` | 정산 대사(P0-11), 신고서 ⑪ `AUTO_SETTLEMENT` |
| 3 | **판매** | 기간·상품별 판매 실적 | POS 인쇄물 촬영 + OCR | `PRODUCT_SALES_PERIOD` | **구성비만** — 상품 지표, 월별 리포트 기여도, What-if 배율 |

**금액의 단일 출처는 1층(입금)이다.** 3층은 구성비(비율)만 밖으로 내보내고 금액은 내보내지 않는다. 세무 집계와 부가세 계산에 3층이 들어가지 않는 이유가 이것이다 — 넣으면 같은 매출이 두 번 계상된다(ERD 1.9 「소비처와 비소비처」, API 14.3).

**"카드"는 방향이 반대인 두 가지를 가리킨다. 붙여 쓰지 말 것.**

| | 무엇 | 방향 | 출처 |
| --- | --- | --- | --- |
| `CARD_SETTLEMENT` | 카드사가 가맹점에 주는 **정산금** | 입금 | 계좌 거래내역의 적요 |
| 금융망 `CREDIT_CARD_*` | 사업자가 카드로 쓴 **결제·청구** | 출금 | 카드 API (7.3) |

금융망 API에는 **가맹점 매출 입금 구조가 없다**(`createMerchant`에 계좌번호가 없고 워크북 전체에 `settlement` 0건). 카드 정산 입금은 은행 거래내역에 찍혀 계좌 동기화·CSV 경로로 들어온다. 상세는 `docs/예측엔진_설계노트.md` G-4·G-5.

## 2. 공통 규약

### 2.1 URL과 인증

- Base URL: `/api/v1`
- 인증 헤더: `Authorization: Bearer {accessToken}` (JWT)
- Access Token 만료: 30분, Refresh Token 만료: 14일
- Refresh Token은 쿠키로 전달한다 *(v1.4 상세 확정)*:

  | 속성 | 값 | 이유 |
  | --- | --- | --- |
  | `HttpOnly` | true | JS가 읽지 못하게 해 XSS로 탈취되지 않도록 한다 |
  | `Secure` | true | HTTPS 전용. edge nginx가 TLS를 종단한다 |
  | `SameSite` | `Lax` | 프론트와 API가 같은 오리진(nginx가 `/`와 `/api/`를 모두 받는다)이라 `None`이 필요 없다 |
  | `Path` | `/api/v1/auth` | 갱신·로그아웃 경로에만 실린다. 일반 API 요청에 매번 딸려가지 않는다 |

  - 프론트는 이 쿠키를 직접 읽거나 저장하지 않는다. `POST /auth/refresh`·`/auth/logout` 호출 시 브라우저가 자동으로 싣는다(`credentials: 'include'` 필요).
  - Refresh Token은 **회전**한다 — 갱신 시 이전 토큰은 즉시 폐기되므로 같은 토큰을 두 번 쓸 수 없다. 서버는 `jti`를 Redis에 보관하며 **저장소에 있는 것만 유효**로 취급한다(로그아웃 강제를 위해).
- **앱(React Native)은 본문으로 주고받는다** *(v1.26 추가)*. 앱에는 쿠키 저장소가 없어 위 쿠키를 받을 수도 읽을 수도 없다. 그대로 두면 Access Token이 만료되는 30분마다 다시 로그인해야 한다.

  | 요청 | 어떻게 | 응답 |
  | --- | --- | --- |
  | `POST /auth/login` | 헤더 `X-Client-Type: app` | 본문에 `refreshToken`·`refreshExpiresIn` 추가, **`Set-Cookie` 없음** |
  | `POST /auth/refresh` | 본문 `{ "refreshToken": "..." }` | 새 토큰 네 값을 **본문으로**, 쿠키 없음 |
  | `POST /auth/logout` | 본문 `{ "refreshToken": "..." }` | 그 토큰을 폐기, `204` |

  - 서버는 **본문을 쿠키보다 먼저** 본다. 회전·폐기·오류(`401 AUTH_TOKEN_INVALID`)는 쿠키 방식과 똑같다.
  - Refresh Token은 기기의 보안 저장소(`expo-secure-store`)에 넣는다. Access Token은 웹과 같이 메모리다.

  > ⚠ **갱신·로그아웃의 채널은 헤더가 아니라 「토큰이 온 곳」이 정한다.** 쿠키로 온 요청에는 절대 본문으로 토큰을 주지 않는다 — `X-Client-Type`만 보고 갈랐다면 웹에 XSS가 생겼을 때 스크립트가 그 헤더를 붙여 쿠키로 갱신을 요청하고 **Refresh Token을 본문으로 빼 갈 수 있다.** 그러면 `HttpOnly` 쿠키를 쓴 의미가 없다. 규칙은 **「받은 곳으로 돌려준다」** — 쿠키로 받았으면 쿠키로, 본문으로 받았으면 본문으로. **로그인만 헤더로 가른다**(비밀번호를 아는 쪽에만 답하므로 탈취 경로가 아니다).
- Access Token은 응답 본문으로 받아 메모리에 보관한다. `localStorage` 저장은 권장하지 않는다.
- `/auth/**`, `GET /bank-codes`를 제외한 모든 API는 인증이 필요하다.
- `/businesses/{businessId}/**` 경로는 로그인 사용자가 해당 사업장의 소유자인지 검증하며, 아니면 `403 BUSINESS_ACCESS_DENIED`를 반환한다. 하위 리소스를 직접 접근하는 경로(`/transactions/{id}` 등)도 리소스가 속한 사업장의 소유권을 동일하게 검증한다.

### 2.2 데이터 형식

| 항목 | 규칙 |
| --- | --- |
| ID | JSON number, DB `bigint` |
| 필드명 | `camelCase` |
| 금액 | 원(KRW) 단위 정수. 입출금 구분은 `direction` 필드로 하고 금액에 부호를 두지 않는다. 예상 잔액만 음수를 허용한다. **DB는 `NUMERIC(19,4)`이며 응답 직전 `HALF_UP`으로 정수 변환**한다(중간 단계에서 반올림하지 않는다 — ERD 11장) |
| 비율 | 소수 (`0.12` = 12%) |
| 날짜 | `YYYY-MM-DD`, Asia/Seoul 기준 (영업일·세금 일정·잔액 곡선의 기준 시간대) |
| 시각 | ISO 8601 UTC (`2026-08-31T02:00:00Z`) |
| Enum | `UPPER_SNAKE_CASE` |
| 파일 업로드 | `multipart/form-data` |

### 2.3 페이지네이션

- 요청: `page`(0부터 시작, 기본 0), `size`(기본 20, 최대 100), `sort`(예: `sort=occurredAt,desc`)
- 목록 응답은 아래 공통 구조를 사용한다.

```json
{
  "success": true,
  "data": {
    "items": [],
    "page": 0,
    "size": 20,
    "totalElements": 0,
    "totalPages": 0
  }
}
```

### 2.4 응답 Envelope

성공:

```json
{
  "success": true,
  "data": {}
}
```

오류:

```json
{
  "success": false,
  "error": {
    "code": "BUSINESS_ACCESS_DENIED",
    "message": "해당 사업장에 접근할 수 없습니다."
  }
}
```

외부 연동 오류(`502`)는 원인 식별을 위해 `error.detail`에 외부 시스템의 오류 코드를 담을 수 있다. 예: 금융망 오류 시 `"detail": { "finCode": "A1003" }`.

| HTTP | 사용 기준 |
| --- | --- |
| `200` | 조회·수정·계산 성공 |
| `201` | 리소스 생성 성공 |
| `202` | 비동기 작업 접수 (Job 생성) |
| `204` | 본문 없는 성공 (삭제 등) |
| `400` | 요청값 오류 |
| `401` | 인증 실패·토큰 만료 |
| `403` | 접근 권한 없음 (다른 사업장 등) |
| `404` | 리소스 없음 |
| `409` | 현재 상태와 충돌 (중복 연결, 상태 전이 불가 등) |
| `422` | 요청은 유효하나 처리 불가 (데이터 부족 등) |
| `500` | 서버 오류 |
| `502` | 외부 연동(금융망·공공 API·AI 워커) 실패 |

### 2.5 예측 응답 공통 필드

예측·전망을 반환하는 API(`forecast/*`, `scenarios`, `reserves/daily-plan`, `credit`, `seasonality` 등)는 다음 필드를 공통으로 포함한다.

| 필드 | 설명 |
| --- | --- |
| `baseTime` | 계산 기준 시각. 이 시각 이후의 거래·수정은 반영되지 않았음을 의미한다 |
| `confidence` | `HIGH`, `MEDIUM`, `LOW`, `UNPREDICTABLE` 중 하나. 근거 데이터의 양·변동성·과거 적중률로 산정한다 |
| `basis` | 근거 요약. 반영된 확정 거래 수, 예측 거래 수, 사용자 입력 수, 참조 기간 등 |
| `warnings` | 데이터 부족·보정 실패 등 품질 경고 배열. 없으면 빈 배열 |

데이터가 부족한 경우 오류가 아니라 `confidence: "LOW"` 또는 `UNPREDICTABLE`과 `warnings`로 상태를 표시하고, 예측 범위를 넓혀 반환한다. 거래가 전혀 없어 계산 자체가 불가능할 때만 `422 FORECAST_INSUFFICIENT_DATA`를 반환한다.

### 2.6 위험 등급 공통 체계

P1-08의 4단계 위험 등급을 대시보드·캘린더·알림·예측 곡선 전반에서 공통으로 사용한다.

| 등급 | 기준 |
| --- | --- |
| `SAFE` | 예상 잔액이 안전선 이상 |
| `CAUTION` | 예상 잔액이 안전선 미만 |
| `DANGER` | 예상 잔액이 0원 근접 (기본: 안전선의 25% 미만) |
| `GAP` | 예상 잔액이 0원 미만 (정산 공백) |

클라이언트는 색상 단독으로 등급을 구분하지 않고 상태명과 아이콘을 병기한다(비기능 요구사항).

### 2.7 비동기 작업(Job) 공통 패턴

계좌 동기화, CSV 업로드, LLM 분류, OCR 추출, 내보내기 생성 등 오래 걸리는 작업은 `202 Accepted`와 함께 Job을 반환하고, 클라이언트는 Job을 폴링한다.

`GET /jobs/{jobId}`

```json
{
  "success": true,
  "data": {
    "jobId": 9001,
    "jobType": "EVIDENCE_EXTRACTION",
    "status": "COMPLETED",
    "progress": 1.0,
    "resultRef": { "evidenceId": 501 },
    "error": null,
    "createdAt": "2026-08-31T02:00:00Z",
    "completedAt": "2026-08-31T02:00:41Z"
  }
}
```

- `status`: `QUEUED`, `PROCESSING`, `COMPLETED`, `FAILED`
- `jobType`: `ACCOUNT_SYNC`, `TRANSACTION_IMPORT`, `TRANSACTION_CLASSIFICATION`, `EVIDENCE_EXTRACTION`, `EXPORT_GENERATION`, `TAX_DRAFT_GENERATION`, `PRODUCT_SALES_OCR`, `LOAN_SYNC`, `PROGRAM_STRUCTURING` *(v1.27 추가 — 20.6 이 `jobId` 를 요구하는데 그 타입이 없었다)*
- `resultRef`는 완료 후 결과 리소스를 다시 조회할 수 있는 식별자를 담는다.
- 본인이 생성하지 않은 Job 조회는 `404`를 반환한다.
- 실패한 Job의 `error`에는 공통 오류 Envelope과 동일한 `code`, `message`를 담는다.

### 2.8 멱등성

- 외부 클라이언트의 생성성 POST는 `Idempotency-Key` 헤더(선택)를 지원한다. 동일 키의 재시도는 최초 응답을 재반환한다.
- 내부 API(20절)의 모든 변경 요청은 `X-Request-Id`가 필수이며, 동일 ID 재시도는 중복 저장하지 않는다. 처리 결과는 Redis에 단기 보관한다.

  - **최신 `COMPLETED` 실행이 아직 없을 때** *(2026-09-10)* — 연결된 계좌가 하나도 없으면 `422 FORECAST_INSUFFICIENT_DATA`, 계좌는 있는데 실행만 없으면 재계산을 예약하고 **`409 FORECAST_NOT_READY`** 를 준다. 조회 API 가 계산하지 않는다는 위 규칙을 지키면서 첫 방문이 첫 실행을 걸 수 있게 하는 경로다

    ⚠ **자동 반영의 채번은 「호출마다 새로 채번한다」의 의도된 예외다.** 같은 회차는 `(계좌·예정일·방향·금액·적요·순번)` 해시로 **항상 같은 20자리**를 만든다 — 로컬 DB 와 배포 DB 는 서로를 보지 못하는데 같은 시연 계좌를 가리킬 수 있어서, 두 번째 요청을 `H1007` 로 막아 주는 것이 금융망 자신뿐이다. 그래서 이 경로에서 `H1007` 은 **재시도 신호가 아니라 「이미 나갔다」** 는 뜻이고, 새 번호로 다시 부르면 돈이 두 번 나간다.

    **2026-09-14 실측으로 이 전제를 확인했다** — 접두사가 어제·그저께인 채번이 `H0000` 으로 통과했고(금융망은 접두사의 날짜를 검증하지 않는다), 같은 번호를 다시 보내니 `H1007` 에 **잔액이 움직이지 않았다.** 중복 거부가 호출이 처리되기 전에 걸린다는 뜻이다.
