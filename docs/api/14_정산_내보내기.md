## 14. 정산 대사, 신고서 초안, 신고자료 내보내기, 상품별 매출 구성비

### 14.1 정산 수동 대사 (P0-11)

`POST /businesses/{businessId}/settlements`

```json
{
  "platformName": "배달의민족",
  "periodStart": "2026-08-18",
  "periodEnd": "2026-08-24",
  "grossSales": 1000000,
  "cancellations": 50000,
  "fees": 100000,
  "matchedTransactionIds": [88001]
}
```

```json
{
  "success": true,
  "data": {
    "settlementId": 71,
    "platformName": "배달의민족",
    "periodStart": "2026-08-18",
    "periodEnd": "2026-08-24",
    "grossSales": 1000000,
    "cancellations": 50000,
    "fees": 100000,
    "expectedPayout": 850000,
    "actualDeposit": 850000,
    "difference": 0,
    "status": "MATCHED",
    "createdAt": "2026-08-31T02:00:00Z"
  }
}
```

- 계산식: `expectedPayout = grossSales − cancellations − fees`. `actualDeposit`은 `matchedTransactionIds` 거래의 입금 합계다.
- `status`: `MATCHED`(차이가 허용 오차 이내, 기본 0원), `MISMATCHED`(차이 존재), `PENDING`(매칭된 입금 거래 없음)
- `MISMATCHED`이면 정산 지연·누락·추가 차감 확인을 안내하는 `SETTLEMENT_MISMATCH` 알림을 생성한다.
- 대사 결과는 신고자료의 플랫폼 정산 대사표 원천 데이터가 된다.
- `PATCH /settlements/{settlementId}`로 금액·기간·매칭 거래를 수정하면 차이를 재계산한다.

### 14.2 신고 준비자료 내보내기 (P0-12 부속 산출물)

`POST /businesses/{businessId}/exports`

```json
{
  "exportType": "TAX_PREP",
  "periodStart": "2026-01-01",
  "periodEnd": "2026-08-31",
  "includeEvidenceFiles": true
}
```

```json
{
  "success": true,
  "data": {
    "exportId": 81,
    "exportType": "TAX_PREP",
    "status": "PROCESSING",
    "jobId": 9003
  }
}
```

- `202 Accepted`. 생성은 `EXPORT_GENERATION` Job으로 비동기 처리한다.
- 이 자료는 **세무대리인 전달용 준비자료 패키지**다(기획정리본 §6.10). 홈택스 직접 신고용 주 산출물은 14.3 신고서 초안이며, 이 패키지는 부속 산출물이다. 신고서 자체를 대신하지 않는다.
- 산출물은 기획정리본 6.10의 패키지 구조를 따르는 XLSX/ZIP이다: 연간 매출요약, 사업용계좌 거래내역, 필요경비 후보명세서, 플랫폼별 정산대사표, 고정비·반복지출, 증빙누락·확인필요, 거래증빙 연결목록, 증빙 원본 폴더.
- 모든 시트에 기준일(`generatedAt`)과 대상 기간, 개인정보 고지를 명시한다.
- 필요경비 시트의 명칭은 항상 "필요경비 후보 명세서"를 사용한다(자동 확정 금지 원칙).
- `07_거래증빙_연결목록.xlsx`의 **검토 상태** 열은 거래의 `tax_review_status` 한글 라벨로 채운다(8.7).
- `03_필요경비_후보명세서.xlsx`에서 `PERSONAL_SUSPECTED` 거래는 **별도 구획으로 분리**한다. 삭제하지 않는다 — 판단 근거를 남겨야 세무대리인이 재검토할 수 있다.
- 검토가 끝나지 않아도 생성은 가능하다. 다만 `summary.taxReviewRate`로 진행률을 함께 반환해 사용자가 보완 여부를 판단하게 한다.

`GET /exports/{exportId}`

```json
{
  "success": true,
  "data": {
    "exportId": 81,
    "exportType": "TAX_PREP",
    "status": "COMPLETED",
    "periodStart": "2026-01-01",
    "periodEnd": "2026-08-31",
    "fileName": "신고준비자료_카페한잔_2026.zip",
    "fileSize": 18349222,
    "downloadExpiresAt": "2026-09-07T02:10:00Z",
    "summary": {
      "transactionCount": 1204,
      "evidenceLinkRate": 0.72,
      "unverifiedCount": 96,
      "unverifiedAmount": 8210000,
      "taxReviewedCount": 1108,
      "taxReviewRate": 0.92
    },
    "generatedAt": "2026-08-31T02:10:00Z"
  }
}
```

`GET /exports/{exportId}/download`

- 파일 바이너리를 반환한다 (`Content-Disposition: attachment`).
- 다운로드는 소유 사용자만 가능하며 모든 다운로드는 이력으로 남긴다(비기능: 보안).
- `status`가 `COMPLETED`가 아니면 `409 EXPORT_NOT_READY`를 반환한다.

### 14.3 종합소득세 신고서 초안 (P0-12)

검토 상태(8.7)를 확정한 거래와 연결 증빙을 신고 유형별 서식 항목으로 집계해 **신고서 초안**을 만든다. 민감 항목은 사용자가 내보내기 시점에만 입력하며 서버에 저장하지 않는다. 세액은 계산하지 않고 소득금액까지만 채운다(SRS 1.3, 기획정리본 §10). 초안 생성은 AI 워커를 호출하지 않는다(공통규약 23장).

- 서식은 **개인 단위**다. 본표·부표 모두 사업장별 열(4개)과 합계로 구성되므로, 사업장이 여럿인 사용자는 내보내기에서 열을 합친다(`includeBusinessIds`).

**초안 생성**

`POST /businesses/{businessId}/tax-drafts`

```json
{
  "taxYear": 2026,
  "formType": "SIMPLE_LEDGER",
  "periodStart": "2026-01-01",
  "periodEnd": "2026-12-31",
  "hometaxReference": {
    "filingGuideType": "D",
    "bookkeepingDuty": "SIMPLE_LEDGER",
    "industryCode": "552305",
    "ntsRevenue": 98500000
  }
}
```

```json
{
  "success": true,
  "data": { "draftId": 301, "status": "PROCESSING", "jobId": 9101 }
}
```

- `202 Accepted`. 생성은 `TAX_DRAFT_GENERATION` Job으로 비동기 처리한다.
- `hometaxReference`는 선택이며 사용자가 홈택스 신고도움서비스에서 확인해 옮겨 적는 값이다. 서비스는 신고 유형·기장의무를 판정하지 않고 표시와 대사에만 쓴다.
- `supportLevel`이 `GUIDE_ONLY`·`CHECKLIST_ONLY`인 유형에 생성을 요청하면 `400 FORM_NOT_SUPPORTED`.
- 검토 진행률(`taxReviewRate`)이 100%가 아니어도 생성할 수 있다. 미검토 거래는 집계에 포함하되 항목별 `unreviewedCount`로 표시한다.

| `AUTO_PROFILE` | 사업장·사용자 프로필에서 채움 — 상호, 사업자등록번호(⑧), 소재지(⑤), 업종(⑥), 성명(③), 전화번호(②), 소득종류(⑩, 사업소득 40) |
| `REFERENCE_HOMETAX` | 사용자가 옮겨 적은 홈택스 참고값. 서비스 집계와의 차이를 `revenueCheck`로 표시 |
| `USER_SENSITIVE` | 사용자 직접 입력. AI 미전달·서버 미저장. 조회 응답에서 값은 항상 `null`. 74호 본표에서는 주소지(①)·생년월일(④). 주민등록번호·환급금 계좌는 별지 제40호 본표 항목이라 서식 PDF에 없고 홈택스에서 직접 입력한다 |
| `CALCULATED` | 서식 산식으로 백엔드가 계산 |

`USER_CONFIRM`은 자동 계산하지 않는 항목으로, 사용자가 `PATCH`로 값을 넣는다 — 감가상각비(㉛, 기재 시 조정명세서 첨부 안내), 기초·기말 재고(⑭·⑯), 본표 세무조정 가감액(⑫⑬⑯⑰)과 기부금 한도초과·이월(⑳㉑)은 기본값 0. `status`는 `FILLED`·`NEEDS_REVIEW`·`EMPTY`다.

집계 규칙:

- 대상 거래는 `tax_review_status`가 `EVIDENCE_CONFIRMED`·`EVIDENCE_MISSING`·`UNREVIEWED`인 확정 분류 거래다. `PERSONAL_SUSPECTED`는 제외해 `excluded.personalSuspected`에, `BUSINESS_USE_UNCLEAR`·`DUPLICATE_SUSPECTED`·`EXPERT_REVIEW`는 항목 금액에서 빼고 `excluded.needsReview`에 담는다.
- `is_excluded`(예측 제외)는 집계에 영향을 주지 않는다. 두 판단은 독립적이다(8.7).
- 서비스는 세액·신고 유형을 확정하지 않는다. `disclaimer`는 항상 포함한다.
- 부표 제조비용란(⑱~㉔)은 제조원가명세서를 쓰는 제조업 전용이므로 음식점업은 기재하지 않는다. 기초·기말 재고(⑭·⑯)를 구분하기 어려우면 당기 매입액(⑮)만 기재한다(부표 작성방법 4).
- 본표 ⑭ 세무조정 후 수입금액은 별지 제40호서식(1) 사업소득명세서 ⑨ 총수입금액과 같아야 한다(본표 작성방법 6). 입력용 시트에 대조 행을 넣는다.

| --- | --- | --- |

> **상품별 매출(P1-22, 14.4~14.7)은 이 매핑표에 들어가지 않는다.** 의도적으로 뺀 것이다. ⑪ 매출액은 계좌 입금과 정산 대사에서만 집계하며, 판매 층을 더하면 같은 매출이 두 번 들어간다(중복 계상). 판매 층은 **구성비만** 밖으로 내보내고 금액은 내보내지 않는다 — ERD 1.9 「소비처와 비소비처」.
>
> 다만 `revenueCheck`가 묻는 "현금 매출 누락 여부"는 판매 층이 답을 갖고 있다. POS 인쇄물은 결제수단과 무관하게 판매 전량을 담기 때문이다. 따라서 상품별 매출이 등록된 기간에는 `revenueCheck.productSalesTotal`(참고값)을 함께 반환해 세 값을 나란히 보여준다 — 서비스 집계(입금 기준) · 국세청 수입금액(사용자 입력) · POS 판매 총액(참고). **참고값이며 항목 금액에 반영하지 않는다.**

**항목 수정·참고값 입력**

`PATCH /tax-drafts/{draftId}`

```json
{
  "hometaxReference": { "filingGuideType": "D", "ntsRevenue": 98500000 },
  "overrides": [
    { "fieldKey": "DEPRECIATION", "value": 680000, "note": "정액법 5년, 세무사 확인" }
  ],
  "confirmedFieldKeys": ["RENT", "PAYROLL"]

```

- `sensitive: true` 항목은 이 API로 보낼 수 없다. 포함되면 `400 SENSITIVE_FIELD_NOT_STORABLE`.
- 수정값은 `overrides`로 원래 집계값과 분리 저장해 근거 추적을 유지한다.
- 검토 상태(8.7)가 바뀌면 초안은 `STALE`로 표시되며 재생성(`POST`)으로 갱신한다.

**근거 조회**

`GET /tax-drafts/{draftId}/basis?fieldKey=RENT&page=0&size=50`

    "items": [

- 근거는 저장하지 않고 `TRANSACTION`·`TRANSACTION_EVIDENCE`를 매핑표로 조회해 계산한다.

**내보내기**

`POST /tax-drafts/{draftId}/export`

```json
{
  "format": "PDF",
  "includeBusinessIds": [11, 12],
  "sensitiveValues": {
    "BIRTH_DATE": "1988-**-**",
    "HOME_ADDRESS": "광주광역시 서구 ****"
  }
}
```

- `format`: `PDF`(별지 제74호서식 본표 + 부표 한 묶음 — 본표 첨부서류란 "부표 1부" — 에 "초안 · 생성 기준일 · 확정 세무 자료 아님" 워터마크), `XLSX_HOMETAX_INPUT`(홈택스 일반신고서 입력 순서 — 기본사항 → 사업소득명세서 → 총수입금액 및 필요경비명세서 → 소득공제 → 세액공제·감면 → 기납부세액 — 에 맞춘 항목·값·출처·근거 건수·확인 필요 메모. 별지 제40호서식(1) 기본사항의 주민등록번호·환급금 계좌는 값 없는 "직접 입력" 행으로, 74호 본표 ⑭ = 40호 사업소득명세서 ⑨ 총수입금액 대조 행을 함께 넣는다).
- `includeBusinessIds`(선택): 서식이 개인 단위이므로 사업장이 여럿이면 같은 사용자·같은 귀속연도의 `READY` 초안을 사업장별 열과 합계 열로 합쳐 한 서식으로 만든다. 생략하면 해당 초안의 사업장 한 열만 채운다.
- 동기 처리이며 파일 바이너리를 즉시 반환한다(`Content-Disposition: attachment`). **파일과 `sensitiveValues`는 저장하지 않는다.** 감사 로그에는 필드 키와 다운로드 시각만 남긴다.
- 민감 항목이 비어 있어도 내보낼 수 있다. 빈 칸은 PDF에 "직접 기재" 표시로 남긴다.
- `status`가 `READY`가 아니면 `409 TAX_DRAFT_NOT_READY`.

**목록**

`GET /businesses/{businessId}/tax-drafts?taxYear=2026` — 귀속연도별 초안 목록(`draftId`, `formType`, `status`, `basedOnReviewRate`, `generatedAt`). 민감 항목은 포함되지 않는다.

### 14.4 상품별 매출 등록 (P1-22)

**기간 단위로 등록한다.** 일 단위가 아니다. 저장 목적은 매출 절대액이 아니라 **상품 구성비**이며, 매출 금액의 단일 출처는 계좌 입금(`TRANSACTION`)이다. 안 쓰는 곳과 그 이유는 ERD 1.9 「소비처와 비소비처」를 본다.

입력 경로는 두 가지이고 **OCR이 1차**다.

| 순위 | 경로 | 비고 |
| --- | --- | --- |
| 1차 | **인쇄물 촬영 + OCR** (14.7) | 한 달 80행을 손으로 치는 사람은 없다 |
| 2차 | 수기 입력·정정 | OCR 결과 수정, 인쇄물이 없는 경우 |

> POS 벤더 백오피스에서 CSV를 받을 수 있는 경우가 있으나 **범위에 넣지 않는다.** 벤더마다 제공 여부·컬럼이 다르고, 인쇄물 촬영만으로 기능이 성립하기 때문이다. 필요해지면 `sourceType`에 값을 추가하고 P0-01 CSV 업로드 인프라를 재사용한다.

`POST /businesses/{businessId}/product-sales`

```json
{
  "periodStart": "2022-12-01",
  "periodEnd": "2022-12-14",
  "sourceType": "OCR_CORRECTED",
  "checksum": { "quantity": 139, "grossAmount": 690000, "billedAmount": 670450 },
  "items": [
    { "productName": "카페라떼", "quantity": 47, "grossAmount": 163000,
      "discountAmount": 1050, "netAmount": 147235, "vatAmount": 14715, "billedAmount": 161950 },
    { "productName": "아메리카노", "quantity": 2, "grossAmount": 6000, "billedAmount": 5700 }
  ]
}
```

```json
{
  "success": true,
  "data": {
    "periodStart": "2022-12-01",
    "periodEnd": "2022-12-14",
    "savedCount": 2,
    "shareBasis": "BILLED",
    "checksumStatus": "MISMATCHED",
    "checksumDetail": {
      "field": "billedAmount",
      "itemsTotal": 167650,
      "printedTotal": 670450,
      "difference": 502800,
      "message": "합계와 502,800원 차이가 있습니다. 아래쪽 행이 빠진 것 같습니다."
    },
    "newProducts": ["카페라떼", "아메리카노"],
    "bootstrap": true
  }
}
```

**기간**

- `periodStart`·`periodEnd`는 **영업일**이다. 자정을 넘긴 매출은 전날 영업일에 귀속한다.
- 달력 월과 일치하지 않아도 된다. 사장님이 월중에 뽑으면 반달치가 정상 입력이다.
- **기간은 인쇄물 헤더에서 읽는다**(14.7). 촬영 시각으로 추론하지 않는다 — 12월 중순에 뽑은 "12월 것"을 그대로 12월 구성비로 저장하면 오류 없이 틀린 답이 나온다. 검토 화면이 인식된 기간을 가장 크게 보여주고 확인받는다.
- **같은 기간 재등록은 그 기간을 통째로 교체한다** *(v1.23에서 「upsert」를 이렇게 못박았다)*. 오입력 정정이 잦으므로 `409`를 내지 않는다. **이번 제출에서 빠진 상품은 지워지고**, 응답의 `removedCount`가 몇 행을 지웠는지 알린다. 순수 upsert로 두면 지난번에 잘못 읽힌 유령 상품이 계속 남아 **구성비 분모에 들어간다** — 인쇄물 한 장은 그 기간 전체를 말하는 입력이므로 교체가 맞다.
- 기간이 겹치되 동일하지 않으면(12/1~12/14 위에 12/1~12/31) 서로 건드리지 않고 둘 다 남는다. 조회가 겹침 경고를 반환한다(14.5).
- **같은 상품이 두 번 들어오면 `400`이다** *(v1.23)*. 합치면 그 상품의 구성비가 조용히 두 배가 된다. OCR 워커가 장 경계 중복을 이미 제거하므로(20.9) 여기까지 온 것은 검토 화면에서 만들어진 중복이고, 사람이 고칠 수 있는 자리에서 잡는 편이 낫다. 정규화 후 같은 키면 중복이다 — `카페라떼`와 `카페 라떼`는 같은 상품이다.
- 월 단위를 권장한다. 주 단위는 카드 D+2·배달 주 1회 때문에 기간 경계 오차가 크다.

**필드**

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `productName` | 필수 | 인쇄물 원문 |
| `quantity` | 선택 | 취소·반품 상계 후 값. 수량 열이 없는 인쇄물이 있다 *(v1.23)* |
| `grossAmount` · `billedAmount` | **둘 중 하나** | 구성비의 분모다. 둘 다 없으면 `400 VALIDATION_FAILED` *(v1.23)* |
| `discountAmount`·`netAmount`·`vatAmount` | 선택 | 인쇄물에 열이 없으면 생략 |

- **금액 필드를 하나씩 필수로 걸지 않는다.** 58/80mm 감열지에 8열이 한 줄로 들어가지 않아 실제 인쇄물은 열이 줄거나 두 줄로 접힌다. 필수로 걸면 **정상 인쇄물을 반려**하게 된다.
- **`grossAmount`도 필수가 아니다** *(v1.23, 실측 2026-09-10)*. 58mm 인쇄물에는 **총매출 열 자체가 인쇄되지 않는다** — 합성 90표본 중 `printout58` 30표본 전부, 전체 행의 33.3%가 그렇다. 좁은 감열지에서 살아남는 금액 열은 총매출이 아니라 **결제금액**이다. 대신 **분모가 될 값이 하나는 있어야 한다**: `grossAmount`와 `billedAmount`가 둘 다 없으면 구성비를 만들 수 없으므로 그때만 거절한다(DB에도 같은 `CHECK`가 있다 — ERD 1.9).
- **`quantity`도 필수가 아니다** *(v1.23)*. OCR 워커 계약이 `float | null`이고, 구성비는 금액으로 만들므로 수량이 없어도 기능이 성립한다. 무게 단위 상품(정육·반찬)이 있어 정수도 아니다.
- 금액 검증은 **네 값이 모두 있을 때만** 한다: `grossAmount − discountAmount = netAmount + vatAmount`(= `billedAmount`). 어긋나면 `400 VALIDATION_FAILED`. 하나라도 없으면 검증을 건너뛴다.
- **취소·반품은 음수로 넣는다.** `quantity: -12`, `grossAmount: -42000`. 서버는 양수 제약을 걸지 않는다. 기간 집계에서는 대개 상계되지만 기간 합계가 음수인 상품도 가능하다.
- `vatAmount`는 받아 두되 **세무 계산에 쓰지 않는다.** 부가세 예수금은 과세 매출 입금의 10/110(12.4) 한 방식만 유지한다. 두 번째 부가세 숫자를 만들지 않는다.
- `sourceType`: `OCR` · `OCR_CORRECTED`(OCR 결과를 사람이 고침) · `MANUAL`. 행 단위로 다르면 항목별로 지정할 수 있다. 생략하면 `OCR`이다.
- `extractionId`는 **선택이고 명세 확장이다** *(v1.23)*. 14.7이 남긴 추출 기록과 이 행들을 잇는다 — 나중에 구성비가 틀린 것으로 드러났을 때 "모델이 그때 무엇을 읽었나"에 답하려면 이 연결이 있어야 한다. 수기 입력이면 생략한다.

**합계 행 체크섬**

인쇄물 맨 아래 합계 행이 무료 정합성 검사다. 항목 행의 합이 합계 행과 다르면 **행이 누락된 것**이고, 이것이 긴 인쇄물의 주 실패 모드(잘림·접힘·하단 흐림)를 정확히 잡는다.

- `checksum`을 함께 보내면 서버가 대조해 `checksumStatus`(`MATCHED`·`MISMATCHED`·`UNAVAILABLE`)와 차이 금액을 반환한다.
- **`MISMATCHED`여도 저장은 허용한다.** 막으면 인쇄물이 잘린 사장님이 아무것도 넣을 수 없다. 대신 그 기간의 구성비 응답에 `incomplete: true`를 달아 리포트에서 구분한다.
- 월 1회 촬영이면 OCR 실패 1건이 그 달 데이터 전체다. 일 단위 대비 **실패 비용이 30배**이므로 이 검증은 선택이 아니다.
- ⚠ **`MISMATCHED`는 오류 상태가 아니다** *(v1.23, 실측 2026-09-10)*. 합성 라벨 90개 중 **20개(22.2%)** 가 `Σ항목 ≠ 합계 행`이고 그것이 정상이다 — 인쇄물이 여러 장으로 잘리면 합계 행은 기간 전체를 담고 촬영된 장에는 일부 행만 보인다. **화면이 이것을 빨간 경고로 그리지 않는다.** 다섯 장 중 한 장꼴이라 그렇게 그리면 사장님이 매달 경고를 본다(도메인 규칙 6 — 색상 단독으로 상태를 구분하지 않는다). 리포트에는 **「보이는 행 기준」** 임을 표시하고, 구성비 분모는 합계 행이 아니라 **보이는 행의 합**을 쓴다 — 합계 행을 분모로 잡으면 구성비 총합이 100%가 되지 않는다.

**신규 상품 확인**

- `newProducts`는 이번에 처음 등장한 상품이다. 클라이언트는 저장 전 사용자 확인을 받는다 — 마스터 테이블 없이 의도치 않은 신규 상품(특히 OCR 오인식)을 거르는 장치다.
- **사업장 최초 등록은 `bootstrap: true`로 일괄 수락**한다. 첫 달은 전 품목이 신규라 80개를 하나씩 확인시키는 것은 의미가 없다. 2회차부터 진짜 신규만 표시한다.
- 기존 상품과 표기가 유사하면 경고를 함께 반환한다: `"warnings": [{ "productName": "카페라며", "similarTo": "카페라떼" }]`. 월 단위는 중간 검토가 없어 오인식이 다음 달까지 살아남으므로 이 경고가 일 단위보다 중요하다.

### 14.5 상품별 매출 구성비 조회 (P1-22)

`GET /businesses/{businessId}/product-sales?from=2022-12-01&to=2022-12-14`

```json
{
  "success": true,
  "data": {
    "period": { "from": "2022-12-01", "to": "2022-12-14" },
    "shareBasis": "BILLED",
    "incomplete": false,
    "totals": { "quantity": 139, "grossAmount": 690000, "discountAmount": 19550,
                "netAmount": 609526, "vatAmount": 60924, "billedAmount": 670450 },
    "items": [
      {
        "productName": "카페라떼", "productKey": "카페라떼", "quantity": 47,
        "grossAmount": 163000, "discountAmount": 1050, "billedAmount": 161950,
        "share": 0.242,
        "discountRate": 0.006,
        "changeRate": -0.08,
        "contributionToChange": -14000
      }
    ]
  }
}
```

| 지표 | 계산 |
| --- | --- |
| `share` | **합계 기준 점유율** — `billedAmount / totals.billedAmount`. `billedAmount`가 없는 기간은 `grossAmount` 기준이며 `shareBasis`로 밝힌다 |
| `discountRate` | `discountAmount / grossAmount` — 할인을 많이 먹는 상품 식별. `discountAmount`가 없으면 `null` |
| `changeRate` | 직전 동일 길이 기간 대비 증감률 |
| `contributionToChange` | **총매출 변동 중 이 상품이 차지한 금액.** "이번 달 매출이 왜 줄었나"에 답하는 지표 |

**`share`는 합계 기준이다.** POS가 인쇄하는 점유율과 분모를 맞춘 것이다.

| 기준 | 카페라떼 계산 | POS 화면 |
| --- | --- | --- |
| 합계 | 161,950 / 670,450 = 24.2% | **24.2%** 일치 |
| 총매출 | 163,000 / 690,000 = 23.6% | 불일치 |

카페모카로 교차 검증해도 같다(69,650 / 670,450 = 10.4% 일치 · 70,000 / 690,000 = 10.1% 불일치). 합계 기준이 목적에도 더 맞다 — 합계는 손님이 실제 낸 금액이고 정산으로 흘러가는 것도 그 금액이다.

- 정렬 기본값은 **구성비 기준 금액** 내림차순이다 — `billedAmount`가 원칙이지만 그 열이 없는 인쇄물에서는 `grossAmount`로 내려간다(`COALESCE`). `sort`로 `AMOUNT`(기본) · `QUANTITY` · `NAME` · `CHANGE`(기여도) 중에 고른다 *(v1.23 — 값 집합을 여기서 정했다)*. 모르는 값은 `400`이다. **값이 없는 행은 어느 정렬에서도 뒤로 간다** — 열이 없는 인쇄물이 목록 맨 위를 차지하면 안 된다.
- `from`·`to`를 생략하면 **이번 달 1일부터 오늘까지**다 *(v1.23)*. 입력 단위가 월이라 그 창이 자연스럽다.
- 등록이 하나도 없으면 **빈 목록으로 답한다**(`200`). 아직 인쇄물을 안 올린 사업장이 정상이다 — 화면구성도 6.4의 빈 상태다.
- `contributionToChange`는 P1-19 월별 피드백(15.3)과 P1-17 AI 브리핑의 근거 지표로 재사용한다.
- `checksumStatus = MISMATCHED`인 기간이 섞이면 `incomplete: true`를 반환한다. 구성비는 계산하되 화면에서 "불완전" 표시를 요구한다.
- **구성비의 분모는 「보이는 행의 합」이다.** 인쇄된 합계 행을 쓰지 않는다 — 잘린 인쇄물에서 합계 행을 분모로 잡으면 구성비 총합이 100%가 되지 않는다. 잘렸다는 사실은 `incomplete`가 따로 말한다.
- 요청 기간에 **겹치는** 등록 기간을 전부 합산한다. 포함이 아니라 겹침인 것은 데이터가 기간 단위 집계라 잘라 쓸 수 없기 때문이다 — 12/1~12/31로 등록된 것을 12/1~12/14로 물었을 때 포함 조건이면 **빈 화면**이 나온다.
- `warnings[]`는 `{ code, message }`다 *(v1.23 — 모양을 여기서 정했다)*. 숫자를 그대로 믿으면 안 되는 사정을 담는다.

| `code` | 언제 |
| --- | --- |
| `PERIODS_OVERLAP` | 등록 기간이 서로 겹친다. 겹친 날의 매출이 두 번 더해진다 |
| `PERIOD_PARTIALLY_OUTSIDE` | 등록 기간이 조회 범위 밖으로 걸쳐 있다. **물어본 것보다 넓은 기간**의 숫자다 |
| `PARTIAL_COLUMN` | 어떤 등록에만 있던 열이 있다. 그 열의 합계는 **일부 기간만 더한 값**이다 |
| `MIXED_SHARE_BASIS` | 결제금액이 없는 상품이 섞여 총매출 기준으로 내려갔다 |

- `changeRate`·`contributionToChange`는 **직전 기간에 등록이 아예 없으면 둘 다 `null`이다** *(v1.23)*. 비교 대상이 없는 것을 "전부 신규 성장"으로 말하면 첫 달 리포트가 통째로 거짓이 된다. 직전 기간은 있는데 그 상품만 없었다면 기여도는 금액 전부이고 증감률은 `null`이다(0으로 나눌 수 없다).
- 비율(`share`·`discountRate`·`changeRate`)은 **소수 셋째 자리**다. POS 인쇄물의 자리수에 맞춘 것이라 161,950/670,450이 화면의 24.2%와 같다. ⚠ 80품목짜리 인쇄물의 꼬리에서는 0.05%가 `0.001`로, 그보다 작으면 `0`으로 떨어진다.

**표현 제약 — 원가를 모르므로 수익성을 말하지 않는다.**

| 말할 수 있음 | 말하면 안 됨 |
| --- | --- |
| "가장 많이 팔린 상품" | "가장 수익성 높은 상품" |
| "매출 감소의 주원인 상품" | "단종 권고" |
| 점유율·증감·할인율 | 마진·가격 조정 권고 |

매출 1위 상품이 적자일 수 있다. 마진 계산은 레시피·매입단가가 필요하며 **P2-03** 범위다. 가격 인상 시뮬레이션(11.1 `PRODUCT_SALES_CHANGE`)도 **매출 변화까지만**이고 이익 변화는 다루지 않는다. 클라이언트 문구도 이 선을 지킨다(SRS 12장 "확정 표현 금지").

`GET /businesses/{businessId}/product-sales/{productKey}`

특정 상품의 **기간별 추이**를 반환한다. 응답 항목은 14.5와 동일하되 등록 기간 단위다(월별 라떼 구성비 변화). 일자별 추이는 제공하지 않는다 — 일 단위 원본을 받지 않는다.

### 14.6 상품명 일괄 변경 (P1-22)

`PATCH /businesses/{businessId}/product-sales/rename`

```json
{ "from": "카페라며", "to": "카페라떼" }
```

```json
{
  "success": true,
  "data": {
    "from": "카페라며", "to": "카페라떼", "productKey": "카페라떼",
    "keyUnchanged": false,
    "renamedCount": 1,
    "mergedCount": 1,
    "periods": [
      { "from": "2026-11-01", "to": "2026-11-30" },
      { "from": "2026-12-01", "to": "2026-12-31" }
    ]
  }
}
```

- 해당 사업장의 **모든 기간**을 `product_key` 기준으로 병합한다. 같은 기간에 양쪽이 다 있으면 **수량·금액을 합산**하고(`mergedCount`), 대상 상품이 없던 기간은 옮기기만 한다(`renamedCount`).
- **한 기간만 고치지 않는다** *(v1.23)*. 과거를 두면 추이 조회(14.5)에서 같은 상품이 두 줄로 갈라진 채 남는다 — 표기 정리의 목적이 그것을 없애는 것이다.
- 마스터 테이블이 없으므로 표기 흔들림·오타 정리의 유일한 수단이다.
- 상품 마스터를 두지 않은 배경과 리스크 통제는 ERD 1.9를 본다.

⚠ **두 이름이 정규화하면 같은 키일 수 있다** *(v1.23)*

이 절의 **옛 예시 `{ "from": "카페 라떼", "to": "카페라떼" }` 는 병합이 일어나지 않는 경우였다.** `product_key` 정규화가 공백을 이미 지우므로(ERD 1.9) 두 표기는 **처음부터 한 행**이었다. 그래서 예시를 바꿨다.

| 경우 | 무엇이 일어나나 |
| --- | --- |
| `카페 라떼` → `카페라떼` (키 같음) | 합칠 행이 없다. **보이는 글자만** 바뀌고 `keyUnchanged: true` 다. 거절하지 않는다 — 표시 이름 정리도 쓸모가 있다 |
| `카페라며` → `카페라떼` (오독) | 키가 다르다. **실제로 합쳐진다** |
| `아메리카노(HOT)` → `아메리카노` (괄호 변형) | 키가 다르다(괄호는 정규화가 보존한다). 합쳐진다 |

- 바뀐 행의 `sourceType`이 `OCR`이면 **`OCR_CORRECTED`로 올린다** *(v1.23)*. 사람이 손으로 고친 것이라 실사용 정확도를 볼 때 "모델이 읽은 그대로"와 구분돼야 한다. `MANUAL`은 그대로 둔다.
- **합칠 때 없는 열을 0으로 채우지 않는다** *(v1.23)*. 58mm 인쇄물에는 총매출 열이 없는데 0으로 만들면 "총매출 0원인 상품"이 되고 그 값이 구성비에 섞인다. 양쪽 다 없으면 `null`로 남는다.
- **바꿀 상품이 하나도 없으면 `400`이다** *(v1.23)*. 0건으로 조용히 답하면 사용자는 바뀐 줄 안다 — 화면이 목록에서 고르는 값이라 여기 걸리면 목록이 낡은 것이다.
- `from`과 `to`가 완전히 같으면 `400`이다.

### 14.7 인쇄물 OCR 등록 (P1-22, P1-02 연계)

**이것이 1차 입력 경로다.** 사장님이 POS 「상품별 매출현황」 또는 「월별 매출현황」을 인쇄하고, 그 출력물을 촬영해 올린다. 우리는 POS와 API로 연동하지 않는다.

`POST /businesses/{businessId}/product-sales/ocr`

`multipart/form-data`로 이미지를 **여러 장** 전달한다. 결과는 **후보이며 저장하지 않는다.** 사용자가 검토 화면에서 확인·수정한 뒤 14.4로 저장한다.

| 파트 | 설명 |
| --- | --- |
| `files` | 이미지 1장 이상, **최대 10장** *(v1.23)*. 화면 촬영은 스크롤 때문에, 인쇄물은 길이 때문에 여러 장이 된다. JPG/PNG/PDF, 장당 10MB |
| `captureType` | `PRINTOUT`(감열 인쇄물, **기본값**) · `SCREEN`(POS 화면 촬영). 프롬프트와 정확도 기대치가 다르다 |

- 파트 이름은 **`files`** 다 *(v1.23)* — 위 표의 `files[]` 표기는 "여러 장"이라는 뜻이지 파트 이름이 아니다. 같은 이름의 파트를 반복해 보낸다.
- **10장 상한을 둔다** *(v1.23)*. 명세에 없던 제약인데, 여러 장 곱하기 80행이 워커의 출력 토큰 상한을 밀어내고 Job 스위퍼 임계값(10분) 안에 끝나야 한다. 넘으면 `400`이고 기간을 나눠 올리도록 안내한다.
- **형식 검증이 Job 생성보다 먼저다** *(v1.23)*. 한 장이라도 거부되면 Job이 아예 만들어지지 않는다 — 만든 뒤에 걸리면 아무것도 안 한 Job이 목록에 남고, 사장님은 그것이 실패한 추출인지 알 수 없다.
- **`knownProducts`는 서버가 채운다** *(v1.23)*. 이미 등록된 상품명(인쇄된 원문, 최대 300개)을 워커에 함께 넘겨 스냅을 유도한다. 첫 등록이면 빈 목록이고 그래도 추출은 된다.
- 파일 키는 `product-sales/{businessId}/{jobId}-{n}.{ext}`다(합의 ⑧-1). `n`은 **올린 순서**이고 워커가 장 경계를 이어 붙일 때 그 순서를 쓴다.

`202 Accepted` — `PRODUCT_SALES_OCR` Job으로 비동기 처리하고 `jobId`를 반환한다(공통규약 2.7 Job 폴링).

```json
{
  "success": true,
  "data": {
    "periodStart": "2022-12-01",
    "periodEnd": "2022-12-14",
    "periodSource": "HEADER",
    "shareBasis": "BILLED",
    "checksum": { "quantity": 139, "grossAmount": 690000, "billedAmount": 670450 },
    "checksumStatus": "MISMATCHED",
    "checksumDetail": {
      "itemsTotal": 406500, "printedTotal": 690000, "difference": 283500,
      "message": "합계와 283,500원 차이가 있습니다. 아래쪽 행이 빠진 것 같습니다."
    },
    "items": [
      { "productName": "카페라떼", "quantity": 47, "grossAmount": 163000,
        "billedAmount": 161950, "confidence": 0.91 }
    ],
    "warnings": ["3행 금액을 읽지 못했습니다"]
  }
}
```

**기간은 헤더에서 읽는다.** `periodSource`가 `HEADER`(인쇄물 헤더의 `영업일자 from ~ to`)인지 `USER`(사용자 지정)인지 밝힌다. 촬영 시각은 쓰지 않는다.

**합계 행을 함께 추출한다.** 인쇄물 맨 아래 합계 행이 항목 행 누락을 잡는 체크섬이다(14.4). 위 예시는 스크롤로 7행만 찍힌 화면이라 항목 합 406,500과 인쇄 합계 690,000이 283,500원 어긋난다 — 정확히 이 상황을 잡기 위한 장치다.

**비동기인 이유** — 여러 장 곱하기 80행이면 동기 호출로는 타임아웃 위험이 있다. 사용자가 기다리는 작업이지만 진행률을 보여주는 편이 안전하다. 이로써 P1-02 증빙 인식과의 차별점 중 "동기 vs 비동기"는 사라지고 **추출 스키마** 하나가 남는다.

**저장하지 않는 이유** — OCR이 실패해도 사용자가 손으로 이어갈 수 있어야 한다. 신규 상품 확인(14.4)·합계 체크섬과 함께 오인식에 대한 삼중 방어가 된다.

**다만 추출 <u>기록</u>은 남는다** *(v1.23)*. `PRODUCT_SALES_EXTRACTION`에 기간·읽은 열(`columnsDetected`)·합계 행(`printedTotal`)·워커 검산(`validation`)·모델 메타가 저장된다. **상품 행은 저장하지 않는다** — 위 결정 그대로다. 기록을 남기는 이유는 수명이다: 결과가 `JOB.result`에만 있으면 Job 정리(90일, 공통규약 23장) 때 검산 근거가 함께 사라져, 나중에 구성비가 틀린 것으로 드러났을 때 "모델이 그때 무엇을 읽었나"에 답할 수 없다. 14.4로 저장한 행은 `extraction_id`로 그 기록을 가리킨다.

**`validation`은 `checksumStatus`와 다른 검사다** *(v1.23)*. 워커 검산(계약 v1.18)은 **행 안의 산술 4식**(`판매−할인 = 공급가+부가세` 등)과 합계 행 자체의 정합을 보고, `checksumStatus`는 **행이 빠졌는지**를 본다. 하나를 다른 하나로 대신할 수 없다. 워커 검산에 `Σ항목 = 합계 행`이 **없는 것은 의도**다 — 넣으면 정상 인쇄물의 22%를 틀렸다고 잡는다(위 `MISMATCHED` 항목).

**인쇄된 구성비(`share`)는 저장하지 않는다** *(v1.23)*. 워커가 인쇄물에 찍힌 구성비를 함께 보내지만(열 정확도 95.0%, n=1,051) 쓰임은 **대조** 하나다 — 우리가 계산한 값과 다르면 금액 오독이거나 분모 선택이 틀린 것이므로 서버가 로그로 남긴다. 저장하면 `billedAmount`와 `share` 두 곳에서 같은 사실이 관리되고 반드시 갈라진다. ⚠ 이 대조는 **행 밀림을 잡지 못한다** — 구성비도 밀린 숫자 뭉치에 같이 실려 온다(실측 0/57).

**`productKey`는 서버가 만든다** *(v1.23)*. 워커는 `productName` 원문만 보낸다. 규칙(NFKC · 공백 제거 · 대소문자 통일 · **괄호 보존**)과 그 이유는 ERD 1.9를 본다.

**P1-02 증빙 인식과 다른 작업이다.**

| | P1-02 증빙 | P1-22 매출 |
| --- | --- | --- |
| 대상 | 매입 영수증·세금계산서 | POS 매출현황 인쇄물 |
| 양식 | 자유. 편차 큼 | **정형. 행 반복 + 합계 행** |
| 추출 | 공급자·일자·금액·품목·부가세 | 기간·상품명·수량·금액·할인·부가세·합계 |
| 저장 | `EVIDENCE`에 저장 | **저장 안 함** — 후보만 반환 |

**촬영 유형별 난점** — 프롬프트를 둘로 나눠 잡는다.

| | 화면 촬영(`SCREEN`) | 감열 인쇄물(`PRINTOUT`) |

| 레이아웃 | 표, 열 정렬 명확 | 좁은 폭, 열 생략·접힘 |

| 방해 요소 | 반사·모아레 | 종이 곡률·그림자 |

내부 워커 API는 20.9 `/internal/v1/ai/product-sales-extraction`이다. 요청에 `knownProducts`(해당 사업장의 기존 상품명)를 함께 보내 스냅을 유도하되, 목록에 없는 신규 상품을 임의로 가장 가까운 이름으로 바꾸지는 않는다 — 실제 신메뉴를 놓치게 된다.
