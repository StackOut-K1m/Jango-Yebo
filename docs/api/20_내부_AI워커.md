## 20. 내부 수집·AI 워커 API

외부 클라이언트에는 노출하지 않는다. API 서버(백엔드)가 DB 영속화와 수치 계산을 담당하고, AI 워커는 DB에 직접 접속하지 않는 무상태 추론 서버로 둔다.

워커가 다루는 모델은 두 종류다 — **LLM/OCR 계열**(20.3~20.10)과 **예측 모델 계열**(20.11~20.12). 뒤쪽은 LLM이 아니며 자체 호스팅 추론이다. 둘 다 무상태라는 점은 같지만, 예측 모델은 **결정론적 수치 계산의 입력값을 만들 뿐 계산 자체를 대신하지 않는다** — 잔액 합산은 언제나 API 서버가 한다.

### 20.1 호출 방향과 공통 규약

| 방향 | 역할 |
| --- | --- |
| 배치 수집기 → API 서버 | 지원 제도 공고 원문, 특일 정보 적재 |
| API 서버 → AI 워커 | LLM 분류·추출·구조화·문장화 요청 |
| API 서버 → AI 워커 | **예측 모델 추론 요청** — 잔여 흐름 시계열, 정산 지연·금액 보정 |
| AI 워커 → API 서버 | 비동기 작업 결과 Callback |

- 내부 인증: `Authorization: Bearer {serviceToken}` (서비스 간 고정 토큰, 회전 정책 별도)
- 모든 변경 요청은 `X-Request-Id`가 필수이며 동일 ID 재시도는 중복 저장하지 않는다.
- 요청·응답 모두 공통 `success`/`data`/`error` Envelope을 사용한다.
- AI 워커는 계좌번호·주민번호 등 민감 정보와 원본 파일을 로그에 남기지 않는다. 신고서 초안(14.3)의 민감 항목은 워커에 전달 자체를 하지 않는다.
- LLM 응답의 수치·Enum은 API 서버가 저장 전에 검증한다: 허용 카테고리 외 값, 근거 없는 수치는 폐기하고 해당 항목만 제외한다.
- **예측 모델(20.11~20.12) 공통 규약** — ① 응답에 `modelName`·`modelVersion`을 반드시 담고 API 서버가 `FORECAST_RUN.model_version`·`basis`에 기록한다. **20.11 은 `judgmentAlpha` 도 담는다** — 분위수를 어느 쪽으로 읽어 판정할지가 모델 채택의 전제이고, 그 값이 응답에 없으면 API 서버가 임의로 정하게 된다 (20.11 참조). ② 분위수는 `q10 ≤ q50 ≤ q90` 단조성을 API 서버가 검증하고, 깨지면 응답 전체를 폐기한다. ③ **실패는 예측 실패가 아니다** — 타임아웃·오류·Circuit Breaker open 시 API 서버는 통계 베이스라인으로 곡선을 산출한다. ④ 워커는 모델을 기동 시 lazy load 후 상주시키고, OCR 계열과 **동시 실행하지 않는다**(GPU 없는 4 vCPU 환경, 세마포어 1).
- 예측 모델 요청 본문에는 **금액과 날짜만** 담는다. 적요·거래처명·계좌번호는 보내지 않는다 — 추론에 필요하지 않고, 보내면 로그 금지 대상만 늘어난다.

| 방향 | Method | Endpoint | 처리 | 설명 |
| --- | --- | --- | --- | --- |
| 서버 → 워커 | POST | `/internal/v1/ai/transaction-classification` | 비동기 | 거래 배치 LLM 분류 (P1-01) |
| 서버 → 워커 | POST | `/internal/v1/ai/evidence-extraction` | 비동기 | 증빙 OCR/VLM 구조화 (P1-02) |
| 서버 → 워커 | POST | `/internal/v1/ai/item-normalization` | 동기 | 품목명 정규화 매핑 (P1-03) |
| 서버 → 워커 | POST | `/internal/v1/ai/program-structuring` | 비동기 | 공고문 구조화 (P1-15) |
| 서버 → 워커 | POST | `/internal/v1/ai/briefing-generation` | 비동기 | 브리핑 문장 생성 (P1-17) |
| 서버 → 워커 | POST | `/internal/v1/ai/product-sales-extraction` | **비동기** | 매출현황 인쇄물 상품 행·합계 행 추출 (P1-22) |
| 서버 → 워커 | POST | `/internal/v1/ai/document-assist` | 동기 | 신고서 초안 확인 필요 사유 문장화·누락 점검 (P0-12 보조, P1 옵션 — 20.10) |
| 서버 → 워커 | POST | `/internal/v1/ai/forecast-residual` | 동기 | **잔여 현금흐름 분위수 예측 (P0-07 — 20.11)** |
| 서버 → 워커 | POST | `/internal/v1/ai/settlement-delay` | 동기 | **정산 지연·금액 배율 보정 (P1-05, 조건부 — 20.12)** |
| 워커 → 서버 | POST | `/internal/v1/ai-jobs/{jobId}/result` | - | 비동기 작업 결과 Callback |
| 수집기 → 서버 | POST | `/internal/v1/support-programs:batch` | - | 공고 원문 배치 적재 (P1-15) |
| 수집기 → 서버 | POST | `/internal/v1/holidays:batch` | - | 특일 정보(공휴일) 연 단위 적재 (P1-04) |

비동기 요청은 `202 Accepted`와 `{ "jobId": 9012 }`를 반환하고, 완료 시 워커가 Callback을 호출한다.

**Callback 본문은 공통 Envelope이다**(20.1). 작업 유형별 결과 스키마는 `data` 안에 평면으로 담고, 모델 식별 정보를 함께 싣는다. *(v1.9 — 워커 구현 반영. 이전 판의 20.3 예시는 Envelope 없이, 20.9 예시는 Envelope으로 적혀 있어 서로 달랐다.)*

- 완료: `{ "success": true, "data": { "status": "COMPLETED", "modelName": "claude-opus-5", "modelVersion": null, "promptVersion": "evidence-extraction/v1", "pipeline": "VLM", ...작업별 결과 } }`. 브리핑(20.7)처럼 일부만 살린 경우 `status`는 `PARTIAL`.
- 실패: `{ "success": false, "error": { "code": "AI_ANALYSIS_FAILED", "message": "...", "detail": { ... } } }`. API 서버는 Job을 `FAILED`로 바꾸고 `error`에 `code`·`message`를 그대로 담는다(공통규약 2.7).
- `pipeline`은 요청의 `preferredPipeline`이 아니라 **실제로 사용된 경로**다(`OCR_PIPELINE`·`VLM`·`RULE`·`LLM`). 연동 검증용 고정 응답은 `STUB`으로 표기해 운영 데이터와 구분한다.
- Callback의 `X-Request-Id`는 `ai-job-{jobId}-result`로 고정한다. 워커가 재시도해도 같은 ID이므로 API 서버는 중복 저장하지 않는다.
- 워커는 5xx·연결 오류에 3회 재시도(0.5s × 2ⁿ)하고 4xx는 즉시 포기한다. 끝내 전달되지 않은 Job은 스위퍼(23장, 10분 초과)가 회수한다.
- 워커는 요청을 **접수하기 전에** 실패 가능한 것을 거른다 — 요청한 `preferredPipeline`이 구성되지 않았으면 `422 AI_ANALYSIS_FAILED`(`detail.reason = "PIPELINE_UNAVAILABLE"`), `fileObjectKey`의 파일이 없으면 `400 VALIDATION_FAILED`. 이 경우 Job은 `PROCESSING`에 들어가지 않는다.

### 20.3 거래 분류 (P1-01)

`POST /internal/v1/ai/transaction-classification`

```json
{
  "jobId": 9012,
  "business": { "industryType": "FOOD_CAFE" },
  "allowedCategories": ["RENT", "PAYROLL", "MATERIALS", "PLATFORM_SETTLEMENT", "..."],
  "fewShotExamples": [
    { "description": "우아한형제들", "direction": "DEPOSIT", "category": "PLATFORM_SETTLEMENT", "merchantName": "배달의민족" }
  ],
  "transactions": [
    {
      "transactionId": 88031,
      "description": "김영자",
      "direction": "WITHDRAWAL",
      "amount": 1200000,
      "occurredAt": "2026-08-25T01:00:00Z",
      "cycleHint": "매월 25일 반복 (최근 4회)"
    }
  ]
}
```

Callback 결과:

```json
{
  "success": true,
  "data": {
    "status": "COMPLETED",
    "modelName": "claude-opus-5",
    "modelVersion": null,
    "promptVersion": "transaction-classification/v1",
    "pipeline": "LLM",
    "results": [
      {
        "transactionId": 88031,
        "category": "RENT",
        "merchantName": "김영자(임대인 추정)",
        "confidence": 0.72,
        "reason": "매월 25일 동일 금액 반복 출금은 임차료 패턴과 일치합니다."
      }
    ]
  }
}
```

- API 서버는 `confidence`가 기준(기본 0.85) 미만이거나 신규 거래처인 결과에 `needsConfirmation = true`를 설정한다.
- few-shot 예시는 사용자 정정 이력(`ClassificationHistory`)에서 최신순으로 구성한다.

### 20.4 증빙 추출 (P1-02)

`POST /internal/v1/ai/evidence-extraction`

```json
{
  "jobId": 9013,
  "evidenceId": 501,
  "fileObjectKey": "evidences/11/501.jpg",
  "evidenceTypeHint": "RECEIPT",
  "preferredPipeline": "AUTO"
}
```

- `preferredPipeline`: `AUTO`, `OCR_PIPELINE`(전처리+OCR 전용 모델), `VLM`(멀티모달 모델). 모델 비교 실험을 위해 강제 지정할 수 있다.
- Callback 결과는 13.2의 `extraction` 구조와 동일하며 `modelName`, `pipeline`, `fieldConfidence`를 포함한다. 여기에 `evidenceId`와, 검산용 공급가 **`supplyAmount`**(인쇄된 값. 없으면 `null`)가 더해진다 *(v1.9)*.
- **금액 필드의 의미 (v1.10 — KORIE 영수증 50장 실측으로 확정).** 한국 마트·편의점 영수증의 합계 구역은 `과세물품 + 부가세 + 면세물품 = 결제금액`이고, 할인이 있으면 `총합계(할인 전) − 할인 = 결제금액`이 따로 인쇄된다. 이를 담기 위해 인쇄값 그대로 옮기는 확장 필드를 추가했다: **`taxableAmount`**(과세물품·과세금액 줄), **`taxFreeAmount`**(면세물품 줄. 0으로 인쇄되면 0), **`discountAmount`**(할인·에누리 총액, 양수), 품목별 **`items[].discountAmount`**(그 행 아래 에누리 줄. 할인 줄을 별도 음수 행으로 만들지 않는다). `supplyAmount`는 "공급가액"이라고 인쇄된 줄(세금계산서·거래명세서·간이영수증)만 받는다. **`totalAmount`는 최종 결제 금액**(결제대상금액·청구액)이며 할인 전 총합계가 아니다 — 가계부 지출은 이 값이고 할인은 참고 필드다 *(팀 합의 필요: 백엔드 저장 컬럼 매핑)*. 모든 값은 인쇄된 값만 옮기며 워커도 모델도 계산하지 않는다.
- 워커는 검산 결과를 **`validation`**으로 함께 보낸다 *(v1.9)*: `amountsConsistent` · `itemsSumConsistent` · `businessNoValid`(사업자등록번호 체크섬) · `dateValid` · `issues[]`. 값이 없어 판정할 수 없으면 `null`. *(v1.10)* 검산식은 `taxableAmount + vatAmount + taxFreeAmount = totalAmount`(과세 줄이 있을 때) 또는 `supplyAmount + vatAmount = totalAmount`(세금계산서형)이고, 품목 합은 `Σ(amount − items[].discountAmount) ≒ totalAmount` 또는 `Σamount − discountAmount ≒ totalAmount`다. v1.9의 `공급가 + 부가세 = 합계` 하나로는 면세 품목이 있는 영수증(50장 중 26장)이 전부 실패했다.
- *(v1.10)* 워커가 **`validation.needsReview`**(boolean)와 **`validation.reviewReasons[]`**를 함께 보낸다. API 서버는 `needsReview`만 보면 된다. 사유 코드: `AMOUNTS_INCONSISTENT` · `ITEMS_SUM_INCONSISTENT` · `BUSINESS_NO_INVALID` · `DATE_INVALID` · `TOTAL_MISSING` · `DATE_MISSING` · `SUPPLIER_MISSING` · `LOW_CONFIDENCE`. 판정 불가(`null`)는 사유가 아니다.
- *(v1.24)* **뒤집힌 기간은 보내지 않는다.** `period.start > period.end` 면 기간을 통째로 비우고(`source = null`) `warnings` 에 남긴다. 백엔드가 `V8` 에서 `CHECK (period_end >= period_start)` 를 걸었으므로 그대로 보내면 INSERT 가 거절되어 **추출 전체**(상품 행·검산·모델 메타)가 사라진다 — 기간만 잃는 편이 낫고, 기간 없음은 요구 1 이 지시한 정상 상태다. 합성 90표본에서 라벨·예측 모두 **0건**이라 관측된 적은 없다. 그래도 넣는 이유는 오탐이 원리적으로 불가능하고(시작 > 종료는 판단이 아니라 순서다) 나면 잃는 것이 크기 때문이다. 요청 스키마 변경 없음.
- *(v1.22)* **`evidenceType` 은 다시 `null` 로 나간다 — v1.21 을 실측으로 되돌렸다.** 모델에게 본문 추출과 **문서 종류 판별을 함께** 시켰더니 품목 행의 숫자가 이웃 행 것으로 밀렸다. 합성 현금영수증 15장 A/B(프롬프트 외 설정 4개 동일): **품목 금액 86.4% → 69.0%, 수량 86.4% → 72.4%**, v4 에서 맞던 **8행이 틀리고 반대는 0건**. 이름 exact 는 93.2% → 100% 로 올랐는데 이것도 밀림의 징표다 — 이름은 제자리에 있고 숫자만 움직인다. **프롬프트에 규칙을 더하면 품목 행이 밀리는 것을 두 번 관측했다**(v5 정렬 규칙, v6 종류 판별). 프롬프트는 `evidence-extraction/v4` 로 되돌렸고 바이트 단위로 같다. 스키마 필드는 `boundingBox` 와 같은 처리로 남긴다 — 판별을 본문 추출과 **분리**할 방법이 생기면 채운다. 그때까지 종류는 업로드에서 사용자가 고른 값이 정본이고, 안 고르면 `OTHER` 로 남는다. 백엔드의 `applyExtraction` 가드(현재 종류가 `OTHER` 일 때만 적용)는 그대로 두면 된다 — 값이 `null` 이라 발동하지 않는다. 재현: `artifacts/eval/synth-004-cash-v6` vs `synth-002-cash-v4`.
- *(v1.21)* **결과에 `evidenceType` 을 넣는다 — 백엔드가 읽는데 워커가 보내지 않던 필드다.** 13.1 업로드에서 종류는 **선택**이라, 안 고르면 `EVIDENCE.evidence_type = OTHER` 로 저장되고 워커는 `evidenceTypeHint=OTHER` 로 불린다. 백엔드 `EvidenceExtractionService` 는 콜백의 `evidenceType` 으로 종류를 채우도록 짜여 있었는데("종류를 안 주면 추출이 추정한다") 계약에 그 필드가 없어 **항상 `null` 이었다** — 종류가 영영 `OTHER` 로 남는다. 값 집합은 요청 힌트와 같다(`RECEIPT`·`TAX_INVOICE`·`INVOICE`·`CASH_RECEIPT`·`SETTLEMENT_STATEMENT`·`CONTRACT`·`PAYROLL`·`OTHER`). 모델은 **힌트가 아니라 이미지에 인쇄된 제목**을 보고 고르고, 제목이 안 보이면 `OTHER` 로 둔다.
  - ⚠ **백엔드 쪽 가드가 하나 필요하다.** 지금 `applyExtraction` 은 `type != null` 이면 무조건 덮어쓴다. 사용자가 업로드에서 `TAX_INVOICE` 를 골랐는데 모델이 `RECEIPT` 를 내면 **사용자 선택이 지워진다.** 현재 종류가 `OTHER` 일 때만 적용해야 한다 — 도메인 규칙 4(세무 값을 자동 확정하지 않는다)와 같은 취지다.

- *(v1.11)* 매핑마다 **`matchedBy`**(`RULE` 단위 규칙 정규화 후 동일 · `SIMILARITY` 별칭 유사도 ≥ 0.92 · `LLM` 3차 · 미매칭 `null`)가 붙는다. 기술스택 §6.5 의 "규칙이 90% 이상을 처리" 비율을 여기서 센다.
- 3차(LLM)는 유사도 0.70~0.92 구간의 저신뢰 건만 **한 번에 묶어** 묻는다(effort low). 모델이 후보에 없는 `itemId` 를 내거나 confidence < 0.8 이면 버리고 `suggestedCanonicalName`·`suggestedCategory`(`MATERIALS`/`SUPPLIES`/`EQUIPMENT`/`SERVICE`/`OTHER`)만 돌려준다. 호출 실패·시간 초과(기본 8초)면 그 건은 미매칭으로 응답한다 — 동기 10초 안에 반드시 답한다. stub 모드에서는 3차를 부르지 않는다.

`rawSummary`는 이 계약에 없다 — **수집기가 채운다**(기업마당 `bsnsSumryCn`, `V24`). 서류의 `issueUrl`·`fee`도 없다 — **서류 사전(17.4)이 붙인다.** 공고 본문에서 주워 온 URL은 죽은 링크이거나 다른 기관 페이지다.

**추출 요구사항 4건**

| # | 요구 | 이유 |
| --- | --- | --- |
| 1 | **기간을 헤더에서 읽는다** (`영업일자 from ~ to`). 못 읽으면 `period.source = null` | 촬영 시각으로 추론하면 월중에 뽑은 반달치를 그 달 전체로 오인해 **오류 없이 틀린 답**이 나온다 |
| 2 | **합계 행을 항목 행과 분리해 `printedTotal`로 반환한다** | 항목 합과 대조해 행 누락(잘림·접힘·하단 흐림)을 잡는 체크섬이다. 합계 행을 항목으로 섞으면 이 검사가 무력화된다 |
| 3 | **읽은 열 목록을 `columnsDetected`로 밝힌다** | 58/80mm 감열지에 8열이 안 들어가 실제 인쇄물은 열이 줄거나 접힌다. 없는 열을 0으로 채우면 안 된다 — 서버가 Optional로 저장하고 검증을 건너뛴다(14.4) |
| 4 | **행을 만들어내지 않는다.** 흐려서 못 읽은 행은 `warnings`에 남기고 건너뛴다 | 누락은 체크섬이 잡지만 환각은 아무것도 잡지 못한다 |

**촬영 유형별로 프롬프트를 나눈다**

| | `SCREEN` (POS 화면 촬영) | `PRINTOUT` (감열 인쇄물) |
| --- | --- | --- |
| 레이아웃 | 표, 열 정렬 명확 | 좁은 폭, 열 생략·접힘 |
| 글꼴 | 안티앨리어싱 화면 폰트 | 도트·열전사, 번짐 |
| 다중 장 원인 | 스크롤 | 길이 |
| 방해 요소 | 반사·모아레 | 종이 곡률·그림자 |

- **여러 장을 하나의 기간으로 병합한다.** 화면 촬영은 스크롤 때문에, 인쇄물은 길이 때문에 여러 장이 된다. 장 경계에서 같은 행이 두 번 찍히면 중복을 제거한다.
- **비동기로 바꿨다.** 여러 장 곱하기 80행이면 동기 10초 타임아웃 안에 끝나지 않을 수 있다. 사용자가 기다리는 작업이지만 진행률을 보여주는 편이 안전하다. 이로써 P1-02 증빙 인식과의 차별점 중 "동기 vs 비동기"는 사라지고 **추출 스키마** 하나가 남는다.
- **P1-02 증빙 인식과 다른 작업이다.** 증빙은 자유 양식의 매입 영수증(공급자·일자·금액·품목)이고 이쪽은 **정형 양식의 매출 인쇄물**(상품 행 반복 + 합계 행)이다. 양식이 정형이라 정확도가 더 잘 나올 여지가 있어 모델 비교 실험의 표본으로도 쓸 만하다 — `SCREEN`·`PRINTOUT` 두 조건을 분리하면 표본 가치가 더 크다.
- `knownProducts`는 해당 사업장에 이미 등록된 상품명이다. **워커가 이 목록에 스냅되도록 유도**하면 표기 흔들림과 오인식이 줄어든다. 다만 목록에 없는 신규 상품도 그대로 반환해야 한다 — 임의로 가장 가까운 이름으로 바꾸지 않는다. 월 단위 입력은 중간 검토가 없어 오인식이 다음 달까지 살아남으므로 이 스냅이 일 단위보다 중요하다.
- 결과는 **저장되지 않는다.** API 서버가 사용자에게 확인받은 뒤 14.4로 저장한다.

### 20.11 잔여 현금흐름 예측 (P0-07)

`POST /internal/v1/ai/forecast-residual` (동기, 타임아웃 15초 + Circuit Breaker — 23장)

반복 패턴·사용자 등록 어느 쪽으로도 설명되지 않는 일별 현금흐름을 예측한다. 근거는 [`예측엔진_설계노트.md`](../예측엔진_설계노트.md) M-1이다.

**API 서버가 잔여 시계열을 만들어 보낸다.** 워커는 시계열만 받고 계산 규칙을 모른다.

```
residual_deposit(d)    = 실제 입금 합계(d) − Σ 예정 거래에 매칭된 입금(d)
residual_withdrawal(d) = 실제 출금 합계(d) − Σ 예정 거래에 매칭된 출금(d)
```

```json
{
  "series": [
    { "name": "DEPOSIT",    "startDate": "2026-02-01", "values": [0, 0, 180000, 0, 95000, "..."] },
    { "name": "WITHDRAWAL", "startDate": "2026-02-01", "values": [24000, 0, 61000, 0, 0, "..."] }
  ],
  "horizonDays": 30,
  "quantiles": [0.1, 0.5, 0.9],
  "calendar": {
    "holidays": ["2026-09-24", "2026-09-25", "2026-09-26", "2026-09-27"]
  }
}
```

```json
{
  "success": true,
  "data": {
    "modelName": "residual-gru",
    "modelVersion": "0.3.0+a82bc981",
    "startDate": "2026-09-01",
    "contextDays": 365,
    "lagAvailable": true,
    "forecasts": [
      {
        "name": "DEPOSIT",
        "q10": [31000, 12000, 0, "..."],
        "q50": [48000, 29000, 0, "..."],
        "q90": [77000, 61000, 22000, "..."]
      },
      {
        "name": "WITHDRAWAL",
        "q10": [8000, 0, 0, "..."],
        "q50": [21000, 14000, 9000, "..."],
        "q90": [46000, 38000, 27000, "..."]
      }
    ],
    "judgmentAlpha": 0.0,
    "inferenceMs": 1840
  }
}
```

- **`modelName` 은 `residual-gru` 다.** 파운데이션 모델(TimesFM·Chronos)이 아니라 과거 1년을 GRU 로 한 번 요약하고 **하루씩** 분위수를 내는 88,390 파라미터 모델이다. 후보를 바꾼 근거는 [`예측엔진_설계노트.md`](../예측엔진_설계노트.md) M-3 「실측 결과」에 있다.
- **`modelVersion` 에는 학습 데이터 지문이 붙는다** (`<아티팩트 버전>+<데이터 지문 8자>`). 위 ①이 「동일 입력 + 동일 `modelVersion` → 동일 결과」를 요구하는데, **구조를 안 바꾸고 데이터만 바꿔 재학습하면 아티팩트 버전은 그대로인데 가중치가 달라진다.** 그러면 그 보증이 조용히 깨지므로 지문을 함께 담는다. 지문이 없는 옛 아티팩트는 버전만 나간다.
- **`judgmentAlpha` 는 「이 분위수를 어떻게 읽어야 하는가」다.** 곡선을 만들어 「0 아래냐」를 판정하는 것은 API 서버(Layer 1)이고, 그 판정을 어느 분위수로 하느냐가 α 다. **적어 두지 않으면 API 서버가 자연히 `q50`(α=0)을 쓴다.**

  ```
  잔여입금(d) = q50(d) + α · (q10(d) − q50(d))      적게 들어온다고 본다
  잔여출금(d) = q50(d) + α · (q90(d) − q50(d))      많이 나간다고 본다
  ```

  **α 는 계약의 선택 사항이 아니라 모델 채택의 전제다.** α 는 모델 경로와 통계 폴백 경로에 똑같이 적용되므로, α 를 바꾸면 「모델이 통계보다 낫다」는 판정 자체가 바뀐다. 운영 구간(과거 30일~1년)에서 모델 − 통계 베이스라인을 짝지은 부트스트랩으로 재면 —

  | α | 공백 F1 차이 [95% CI] | 채택 게이트 |
  | ---: | --- | --- |
  | **0.00** | **+0.0162 [+0.0080, +0.0244]** 유의 | **통과** |
  | 0.05 | +0.0055 [−0.0027, +0.0131] 유의차 없음 | 탈락 |
  | 0.10 | −0.0096 [−0.0169, −0.0027] 유의하게 나쁨 | 탈락 |

  α 를 올리는 것은 **정밀도를 팔아 경보를 앞당기는 거래**다 — 모델 기준 0.00 → 0.05 에서 최초 부족일 오차가 9.14 → 7.63일로 줄고(−1.51일 [−1.73, −1.28]) 정밀도가 0.708 → 0.637 로 떨어진다. 양쪽 다 유의하다. **그 거래를 하려면 채택 판정을 다시 돌려야 하고, 지금 숫자로는 그때 쓸 것은 통계 경로다.**

  값은 **응답에 실어 보낸다.** 문서에만 적으면 재학습했을 때 α 가 가중치와 어긋난다 — α 는 모델 상수가 아니라 **데이터에 딸린 값**이고, 옛 데이터에서 정한 0.10 을 새 데이터에 그대로 썼다가 공백 F1 이 0.687 → 0.612 로 깎인 적이 있다. 아티팩트가 자기 α 를 갖고 있으면 워커가 그것을 내보낸다. *(근거: `private/현재/forecast-lab/audit/alpha_gate.py` · 창 9,600개 · 데이터 `a82bc981`)*

  *표본 하한과 묶여 있다.* 과거 7~30일 구간은 α=0.00 이면 게이트를 떨어지고 0.05 면 통과한다. 지금은 하한이 30일이라 그 구간이 호출되지 않아 문제가 없지만, **하한을 내리면 α 도 같이 다시 정해야 한다.**
- `contextDays` 는 워커가 **실제로 본 일수**(최대 `LOOKBACK` 365). `lagAvailable` 은 작년 같은 날 채널이 채워졌는지다 — 컨텍스트가 1년보다 짧으면 `false` 이고, 이 값이 없으면 API 서버가 「작년 매출 0」과 「작년 데이터 없음」을 구분할 수 없다.
- **하한은 30일 하나다** (`features.MIN_HISTORY` = `baseline.MIN_SAMPLE_DAYS` = 30). 미만이면 워커가 `422` 로 거절하고 API 서버도 잔여를 0 으로 둔다. **30~180일은 값을 내되 `confidence` 를 한 단계 내린다.**
  *2026-09-09 이전에는 통계만 90일이라 30~89일에서 통계가 침묵했다. 그 구간 실측이 모델 0.676 · 통계 0.652 · 잔여 0 0.457 이라 하한을 맞췄다.*

| 필드 | 설명 |
| --- | --- |
| `series.values` | 일별 값. **결측일은 0**이며 `null`을 보내지 않는다(영업하지 않은 날도 잔여는 0이다) |
| `series.startDate` | `values[0]`의 날짜. 이후는 1일 간격 연속이어야 한다 |
| `horizonDays` | `7` · `14` · `30` 중 하나. 응답 배열 길이와 일치 |
| `calendar.holidays` | 선택. 모델이 공변량을 받는 경우에만 사용하고, 받지 않으면 무시한다 |
| `judgmentAlpha` | 응답 필드. 판정 보수성 α (현재 **0.00**). API 서버가 위 식으로 대표값을 만들 때 쓰고 `FORECAST_RUN.basis` 에 기록한다 |
| `inferenceMs` | 실측 추론 시간. 서버 예산 관리와 후보 모델 비교의 근거값 |

- **컨텍스트는 최대 365일**이다(`features.LOOKBACK`). 더 길게 보내도 워커가 마지막 365일만 쓴다 — 버리는 것이 아니라 **학습 때와 창 길이를 맞추려는** 것이다. 하한은 위에 적은 대로 30일이다.
- 응답의 세 배열은 길이가 같아야 하고 `q10 ≤ q50 ≤ q90`이어야 한다. 어기면 API 서버가 응답을 폐기하고 베이스라인으로 넘어간다.
- **잔여 시계열은 캐시하지 않는다.** 사용자가 반복 후보를 승인하면 매칭 항목이 늘어 과거 잔여가 소급해서 줄어든다. 예측 실행마다 API 서버가 새로 집계한다.
- 워커는 이 요청을 **학습에 쓰지 않는다.** 아티팩트의 가중치는 고정이고, 입력은 컨텍스트로만 쓰이고 저장되지 않는다. **재학습은 수동 트리거이며 오프라인에서 별도 데이터로 한다** — 사용자 요청이 학습에 흘러드는 경로는 없다. (v2 는 이 자리를 zero-shot 추론으로 적었다. 채택 모델이 자체 학습 모델로 바뀌었어도 **「요청을 학습에 쓰지 않는다」는 그대로**다.)

### 20.12 정산 지연·금액 보정 (P1-05, 조건부)

`POST /internal/v1/ai/settlement-delay` (동기, 타임아웃 10초 + Circuit Breaker — 23장)

예정 거래별로 **지연일**과 **금액 배율**의 분위수를 낸다. 근거는 [`예측엔진_설계노트.md`](../예측엔진_설계노트.md) M-2이며, **채택은 조건부다** — 통계 베이스라인 대비 다운스트림 지표 개선을 확인한 뒤에만 호출 경로를 켠다.

```json
{
  "items": [
    {
      "plannedTransactionId": 4021,
      "merchantMasterId": 12,
      "industryType": "FOOD_CAFE",
      "expectedDate": "2026-09-28",
      "dayOfWeek": "MON",
      "daysToNearestHoliday": 1,
      "intervalDays": 7,
      "amountBand": "700K_1M",
      "prevDelayDays": 1,
      "sampleCount": 44
    }
  ],
  "quantiles": [0.1, 0.5, 0.9]
}
```

```json
{
  "success": true,
  "data": {
    "modelName": "xgboost-settlement",
    "modelVersion": "2026-09-04.1",
    "results": [
      {
        "plannedTransactionId": 4021,
        "delayDays": { "q10": 0, "q50": 1, "q90": 3 },
        "amountRatio": { "q10": 0.92, "q50": 1.08, "q90": 1.31 }
      }
    ],
    "inferenceMs": 40
  }
}
```

- `delayDays`는 `실제 입금일 − 예정일`, `amountRatio`는 `실제 금액 ÷ 예정 금액`이다. API 서버가 q50으로 `expected_date`·`amount_expected`를 보정하고 q10·q90으로 범위를 만든다.
- **학습은 런타임에 하지 않는다.** 아티팩트를 워커 이미지에 포함하고 추론만 한다. 재학습은 수동 트리거이며 `modelVersion`이 바뀐다.
- `merchantMasterId`가 `null`(전역 거래처 사전에 없는 로컬 거래처)이면 API 서버가 이 항목을 요청에서 제외하고 사업장 내 통계 보정을 쓴다. 전역 표본 없이 모델을 태우면 근거 없는 보정이 된다.
- **적요·거래처명을 보내지 않는다.** 거래처는 `merchantMasterId` 정수로만 식별한다.
