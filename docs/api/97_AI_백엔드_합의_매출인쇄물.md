모두에 수량 열을 넣었으니 그 0건은 인쇄물이 아니라 생성기의 성질이다. 계약이 `float | None` 인

유지했을 때 정해야 했던 "행 버림 / 0 으로 저장 / 전체 실패" 는 셋 다 나쁜 선택지였다.

**③은 스키마 변경 없이 문서 셋에 못박았다** — [ERD §1.9](../ERD.md)「⚠ `MISMATCHED`는 오류 상태가
아니다」, [14.4](./14_정산_내보내기.md) 합계 행 체크섬, [화면구성도 SC-09-3](../화면구성도.md).
요지는 그대로다: 22.2%는 정상값이고, 빨간 경고로 그리면 사장님이 매달 경고를 본다. 구성비 분모도
합계 행이 아니라 **보이는 행의 합**으로 적어 두었다.

**④는 `PRODUCT_SALES_EXTRACTION` 을 두는 쪽으로 갔다.** 절충안(`needsReview` 만 BOOLEAN)은
"무엇이 왜 걸렸나"를 잃는다는 지적이 그대로 맞고, 행마다 JSONB 를 복사하는 쪽은 80행짜리
인쇄물에서 같은 값이 80번 저장된다. 다만 **이 테이블에 상품 행은 넣지 않았다** — 14.7 의
"OCR 결과는 후보이며 저장하지 않는다"가 살아 있어야 하고, 행은 사용자가 확인한 뒤 14.4 가 쓴다.
여기 남는 것은 기간·`columns_detected`·`printed_total`·`validation`·모델 메타뿐이다.

**⑤는 대조를 코드로 넣었다.** `ProductSalesExtractionService.crossCheckPrintedShare` 가 인쇄된
구성비와 우리 계산을 행마다 대조하고 0.01(=1%p) 넘게 벌어지면 **행 수와 최대 차이만** 로그로
남긴다(품목명·금액은 남기지 않는다 — 20.1). 저장은 하지 않는다. 「행 밀림은 못 잡는다」는 경고도
javadoc 에 그대로 옮겼다.

**⑥은 `ProductKeys.normalize` 하나로 두었다.** NFKC → 공백 제거 → 소문자, 괄호 보존이다.
**NFKC 를 먼저 하는 것이 요점**이라 주석에 남겼다 — 전각 공백(`U+3000`)·비분리 공백(`U+00A0`)이
그 단계에서 보통 공백이 돼야 다음 단계가 지운다. 순서를 바꾸면 POS 가 찍은 전각 공백이 키에 남아
같은 상품이 두 행이 된다. 정규화 결과가 빈 문자열이면 `400` 이다(빈 키는 서로 다른 상품을 한
행으로 접는다).

**⑦은 지금대로 둔다.** 콜백에 `businessId` 를 싣지 않고 Job 으로 푼다 — `job.getBusinessId()` 가
곧 사업장이다. 대신 **`job_id` 를 추출 행에 남겼다**: 같은 Job 의 콜백이 두 번 오면(스위퍼 회수 뒤
재실행) 두 행이 되는데, 그걸 막는 판정 키가 필요했다. 실어 줄 필요는 없다.

## ① `gross_amount` 의 `NOT NULL` — 58mm 인쇄물을 전부 반려한다

**현재 ERD.** `gross_amount | NUMERIC | NN | 총매출. **음수 허용.**`

ERD 는 `discount`·`net`·`vat`·`billed` 를 Optional 로 내리면서 이유를 정확히 적었다 —
"58/80mm 감열지에 8열이 한 줄로 들어가지 않아 실제 인쇄물은 열이 줄거나 두 줄로 접힌다.
`NOT NULL` 을 걸면 정상 인쇄물을 반려하게 된다." **`gross_amount` 만 그 목록에서 빠졌다.**

**실측 (합성 90표본 1,059 라벨 행, 2026-09-10).**

| 컬럼 | null 행 | 비율 | 현재 ERD 제약 |
| --- | ---: | ---: | --- |
| `quantity` | 0 | 0.0% | INT **NN** |
| `gross_amount` | **353** | **33.3%** | NUMERIC **NN** ← 문제 |
| `discount_amount` | 353 | 33.3% | Optional |
| `net_amount` | 722 | 68.2% | Optional |
| `vat_amount` | 722 | 68.2% | Optional |
| `billed_amount` | 0 | 0.0% | Optional |

레이아웃별로 보면 원인이 분명하다.

| 레이아웃 | 폭 | 인쇄되는 열 | `gross_amount` |
| --- | --- | --- | --- |
| `screen` (POS 화면) | 1280px | 8열 전부 | 있음 |
| `printout80` (80mm) | 576px | 6열 | 있음 |
| **`printout58` (58mm)** | 384px | **상품명·수량·결제금액·구성비 4열** | **30표본 전부 없음** |

58mm 감열지에서 살아남는 금액 열은 **총매출이 아니라 결제금액**이다. 손님이 실제 낸 금액이
남는 것이 자연스럽고, ERD 자신도 구성비 분모를 `COALESCE(billed_amount, gross_amount)` 로
정의해 이 경우를 이미 전제하고 있다.

**권고.** `gross_amount` 를 Optional 로 내리고, 대신 **구성비를 만들 수 있는지**를 제약으로 건다.

```sql
gross_amount NUMERIC(14, 2),          -- NN 해제
CONSTRAINT ck_product_sales_share_basis
    CHECK (billed_amount IS NOT NULL OR gross_amount IS NOT NULL)
```

이 테이블의 존재 이유가 구성비이므로, 진짜 지켜야 할 불변식은 "총매출이 있다"가 아니라
"분모가 될 값이 하나는 있다"이다. 실측 1,059행 전부 이 제약을 만족한다.

## ② `quantity` 의 `INT NOT NULL` — 내 표본은 근거가 못 된다

라벨 1,059행에서 `quantity` 는 null 0건·소수 0건이라 `INT NN` 이 성립한다. **그런데 이 수치를
근거로 쓰면 안 된다** — 합성 생성기가 세 레이아웃 모두에 수량 열을 넣도록 만들어졌기 때문이다.
"실제 인쇄물이 수량 열을 항상 인쇄한다"는 증거가 아니라 "내가 그렇게 만들었다"는 뜻이다.

워커 계약(`ProductSalesRow.quantity`)은 `float | None` 이다. 수량 열이 없는 인쇄물이 오면
워커는 `null` 을 보내고, `NOT NULL` 이면 그 행이 INSERT 에서 죽는다.

**권고.** Optional 로 내린다. 구성비는 금액으로 만들고 수량은 쓰지 않으므로 잃는 것이 없다.
유지하기로 한다면 **백엔드가 null 을 어떻게 처리할지 정해야 한다**(행 버림 / 0 으로 저장 /
전체 실패). 조용히 500 이 나는 것만 피하면 된다.

## ③ `checksum_status` — `MISMATCHED` 가 22.2% 나온다

ERD 의 체크섬은 **항목 행의 합 vs 인쇄된 합계 행**이고, 잘림·접힘·하단 흐림을 잡는 것이
목적이다. 설계는 맞다. 다만 **얼마나 자주 어긋나는지**가 적혀 있지 않아 적어 둔다.

**실측: 라벨 90개 중 20개(22.2%)가 `Σ항목 ≠ 합계 행` 이다.** 그리고 이것은 **오독이 아니라
정상**이다 — POS 인쇄물이 여러 장으로 잘리면 합계 행은 기간 전체를 담고 촬영된 장에는 일부
행만 보인다. ERD 도 같은 현상을 예시로 들고 있다("283,500원 / 39.5%가 아래에 남아 있다").

그래서 워커의 검산(20.9 `validation`)에는 **이 식을 넣지 않았다.** 넣으면 정상 인쇄물의 22% 를
틀렸다고 잡는다.

**권고.** `checksum_status` 는 그대로 두되 두 가지를 못박는다.

1. `MISMATCHED` 는 **오류 상태가 아니다.** 다섯 장 중 한 장꼴로 나오는 정상값이고, ERD 도
   저장을 허용한다. 화면이 이것을 빨간 경고로 그리면 사장님이 매달 경고를 본다.
2. 리포트에서는 **「보이는 행 기준」** 임을 표시한다. 구성비 분모를 합계 행으로 잡을지 보이는
   행의 합으로 잡을지가 여기서 갈린다 — 잘린 인쇄물에서 합계 행을 분모로 쓰면 구성비 총합이
   100% 가 되지 않는다.

## ④ 워커 `validation`(v1.18) 을 어디에 둘지 — `checksum_status` 와 다른 검사다

두 검사는 **보는 것이 다르다.** 하나를 다른 하나로 대신할 수 없다.

| | 무엇을 보나 | 누가 계산 | 실측 |
| --- | --- | --- | --- |
| `checksum_status` (ERD) | Σ항목 vs 합계 행 — **행이 빠졌나** | 백엔드 | 22.2% 가 MISMATCHED (정상) |
| `validation` (워커 v1.18) | **행 안의** 산술 4식 + 합계 행 자체의 정합 | 워커 | 게이트 2.2%, 정밀도 2/2 |

워커 검산이 보는 식은 `판매−할인 = 공급가+부가세`, `공급가+부가세 = 결제`,
`부가세 = 공급가×10%`(세액 0 제외), `판매−할인 = 결제` 넷이다. 합성 90표본 1,059 라벨 행에서
전부 100% 성립한다.

**권고.** 워커 `data.validation` 을 **JSONB 한 칸에 그대로** 넣는다. 증빙의 `header_data` 와 같은
이유다 — 검산 필드가 계약 개정마다 늘어나는데(v1.14 세율, v1.15 정렬, v1.18 매출) 그때마다
컬럼을 파면 마이그레이션이 따라붙는다.

```sql
validation JSONB,   -- 워커 data.validation 을 가공 없이
```

행 단위 저장이라 추출 1회분에 대한 값을 어디 둘지가 문제인데, **행마다 같은 값을 복사하지 말고**
아래 부록 A 처럼 `PRODUCT_SALES_EXTRACTION`(추출 1회분) 을 따로 두는 편을 권한다. 증빙이
`EVIDENCE_EXTRACTION` / `EVIDENCE_ITEM` 으로 나뉜 것과 같은 모양이다.

**받아들이지 않는다면** `validation` 을 버려도 된다 — `needsReview` 만 `PRODUCT_SALES_PERIOD` 에
BOOLEAN 으로 남기고 나머지는 `JOB.result` 에 두는 절충도 가능하다. 다만 그러면 "무엇이 왜
걸렸나"를 나중에 되짚을 수 없다.

## ⑤ `share` 는 저장하지 않는다 — 워커가 보내는 값의 용도

ERD 가 정했다: "구성비는 조회 시 계산, 저장 없음". **이 결정을 그대로 따른다.** 저장하면
`billed_amount` 와 `share` 두 곳에서 같은 사실이 관리되고 반드시 갈라진다.

워커는 인쇄물에 **찍혀 있는** 구성비를 함께 보낸다(열 정확도 95.0%, n=1,051). 쓰임은 하나다 —
**대조.** 백엔드가 계산한 구성비와 인쇄된 구성비가 다르면 금액 오독이거나 분모 선택이 틀린
것이다. 저장할 필요는 없고, 어긋날 때 로그로 남기면 충분하다.

> 참고로 이 값은 **행 밀림을 잡지 못한다.** 구성비도 밀린 숫자 뭉치에 같이 실려 오기 때문이다
> (실측 0/57). `ai/experiments/analyze_row_shift.py` 에 근거가 있다.

## ⑥ `product_key` 정규화는 백엔드가 한다

ERD 가 규칙까지 정해 두었다 — NFKC · 공백 제거 · 대소문자 통일 · **괄호 보존**
(`아메리카노(HOT)` 과 `(ICE)` 가 같아지면 안 된다).

**워커는 이 값을 만들지 않는다.** UK `(business_id, period_start, period_end, product_key)` 를
가진 쪽이 만들어야 upsert 가 성립하고, 규칙이 두 곳에 살면 반드시 갈라진다. 워커는
`productName` 원문만 보낸다(상품명 exact 99.8%).

> 워커의 `experiments/evaluate_item_normalization.py` 에도 `normalize_name` 이 있지만 그것은
> **매입 품목(20.5)** 사전 매칭용이고 규칙이 다르다(브랜드 접두·등급 토큰 제거). 매출 상품에
> 그 규칙을 쓰면 `아메리카노(ICE)` 같은 것이 뭉개진다. 이름이 비슷하다고 재사용하면 안 된다.

## ⑦ 콜백에 `businessId` 를 실을지

지금 20.9 성공 콜백의 `data` 에는 `businessId` 가 없다. 백엔드가 `jobId` 로 푼다. 증빙 콜백은
`evidenceId` 를 싣고 있어 비대칭이다.

**권고.** 지금대로 둔다. `PRODUCT_SALES_OCR` Job 은 사업장 단위로 만들어지므로 Job 이 곧
사업장이고, 워커가 되돌려 보내는 값은 검증에 쓰이지 않는다. 백엔드가 Job 조회 없이 저장하고
싶다면 실어 주겠다 — **계약 한 줄 추가로 끝난다.**

## 부록 A. `V8__product_sales.sql` 초안

> 작성 당시에는 `V7` 이었다. 그 사이 `V7__forecast_setting.sql` 이 들어가 **실제로는 `V8`**
> 로 반영됐다(위 백엔드 답변). 아래는 제안 원문이고, 백엔드가 바꾼 넷은 답변 표에 있다.

증빙(V6)과 같은 모양으로 **추출 1회분**과 **행**을 나눴다. 근거는 ④ — 검산·모델 메타는 추출
단위 값이고, 행마다 복사하면 80행짜리 인쇄물에서 같은 JSONB 가 80번 저장된다.

`PRODUCT_SALES_PERIOD` 자체는 ERD §1.9 를 따르되 ①·②만 고쳤다.

```sql
-- 1. 추출 1회분 (모델 메타 · 검산 · 원본 기간)
CREATE TABLE core.product_sales_extraction (
    id             BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    business_id    BIGINT       NOT NULL,
    job_id         BIGINT,
    period_start   DATE,                       -- 헤더에 기간이 없으면 null (요구 1 의 정상 동작)
    period_end     DATE,
    period_source  VARCHAR(10),                -- 'HEADER' 또는 null. 워커는 추론하지 않는다
    capture_type   VARCHAR(10)  NOT NULL,      -- SCREEN · PRINTOUT
    model_name     VARCHAR(100) NOT NULL,
    model_version  VARCHAR(100),               -- 워커는 항상 null (V6 와 같은 이유)
    prompt_version VARCHAR(100),
    pipeline       VARCHAR(20)  NOT NULL,
    status         VARCHAR(20)  NOT NULL,
    columns_detected JSONB,                    -- 인쇄물에 실제로 있던 열 (요구 3)
    printed_total  JSONB,                      -- 합계 행 원본 (요구 2 의 체크섬 재료)
    validation     JSONB,                      -- ④ 워커 data.validation 을 가공 없이
    warnings       JSONB,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT fk_ps_extraction_business FOREIGN KEY (business_id) REFERENCES core.business (id),
    CONSTRAINT ck_ps_extraction_capture  CHECK (capture_type IN ('SCREEN', 'PRINTOUT')),
    CONSTRAINT ck_ps_extraction_pipeline CHECK (pipeline IN ('OCR_PIPELINE', 'VLM', 'STUB')),
    CONSTRAINT ck_ps_extraction_status   CHECK (status IN ('COMPLETED', 'PARTIAL')),
    CONSTRAINT ck_ps_extraction_period   CHECK (period_source IS NULL OR period_source = 'HEADER')
);

-- 2. 기간·상품별 집계 (ERD §1.9)
CREATE TABLE core.product_sales_period (
    id              BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    business_id     BIGINT       NOT NULL,
    extraction_id   BIGINT,                    -- MANUAL 입력이면 null
    period_start    DATE         NOT NULL,
    period_end      DATE         NOT NULL,
    product_name    VARCHAR(255) NOT NULL,     -- 인쇄된 원문. 화면 표시용
    product_key     VARCHAR(255) NOT NULL,     -- ⑥ 백엔드가 정규화해 만든다

    quantity        NUMERIC(14, 3),            -- ② NN 해제. 취소 상계로 음수 가능
    gross_amount    NUMERIC(14, 2),            -- ① NN 해제 — 58mm 는 이 열이 없다
    discount_amount NUMERIC(14, 2),
    net_amount      NUMERIC(14, 2),
    vat_amount      NUMERIC(14, 2),            -- 세무 계산에 쓰지 않는다 (ERD)
    billed_amount   NUMERIC(14, 2),            -- 있으면 구성비의 기준

    source_type     VARCHAR(16)  NOT NULL,     -- OCR · OCR_CORRECTED · MANUAL
    checksum_status VARCHAR(12)  NOT NULL,     -- MATCHED · MISMATCHED · UNAVAILABLE
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT fk_ps_period_business   FOREIGN KEY (business_id) REFERENCES core.business (id),
    CONSTRAINT fk_ps_period_extraction FOREIGN KEY (extraction_id)
        REFERENCES core.product_sales_extraction (id) ON DELETE SET NULL,
    CONSTRAINT uk_ps_period UNIQUE (business_id, period_start, period_end, product_key),
    CONSTRAINT ck_ps_period_source   CHECK (source_type IN ('OCR', 'OCR_CORRECTED', 'MANUAL')),
    CONSTRAINT ck_ps_period_checksum
        CHECK (checksum_status IN ('MATCHED', 'MISMATCHED', 'UNAVAILABLE')),
    -- ① 이 테이블의 존재 이유가 구성비다. 분모가 될 값이 하나는 있어야 한다
    CONSTRAINT ck_ps_period_share_basis
        CHECK (billed_amount IS NOT NULL OR gross_amount IS NOT NULL)
);

CREATE INDEX ix_ps_period_business ON core.product_sales_period (business_id, period_start);
```

**금액·수량에 `> 0` CHECK 를 걸지 않는다** — ERD 가 적은 대로 취소가 상계돼 음수가 될 수 있다.

| --- | --- | --- |
| `status` · `modelName` · `modelVersion` · `promptVersion` · `pipeline` | `product_sales_extraction.*` 동명 | |
| `period.start` · `.end` · `.source` | `period_start` · `period_end` · `period_source` | 헤더에 없으면 셋 다 null |

## 승인 후 순서

1. **백엔드** — ①~④ 반영해 마이그레이션 작성 (부록 A). **완료 — `V8__product_sales.sql`.**
2. **합동** — stub 모드로 Job → 콜백 → 저장 1회 통과 (부록 B 픽스처).
3. **백엔드** — 14.6 조회 API. 구성비는 `COALESCE(billed_amount, gross_amount)` 분모로 조회 시
   계산하고 `shareBasis` 로 어느 기준이었는지 밝힌다(ERD §1.9).
4. **프론트** — SC-09-3 상품별 매출 화면. ③ 때문에 **`MISMATCHED` 를 오류로 그리지 않는다.**

②를 유지하기로 한다면 1번 전에 "수량 열이 없는 인쇄물을 어떻게 할지"를 정해야 한다.
