## 9. 반복 거래와 예정 거래

### 9.1 개념과 상태 흐름

- **RecurringPattern**: 과거 거래에서 탐지한 반복 규칙. `CANDIDATE`(탐지됨) → `CONFIRMED`(사용자 승인) / `DISMISSED`(무시) / `PAUSED`(일시중지)
- **PlannedTransaction**: 미래 특정 날짜의 예정 거래 인스턴스. 확정 패턴에서 자동 생성되거나(P0-04) 사용자가 직접 등록한다(P0-06). 잔액 예측(P0-07)은 이 목록을 입력으로 계산한다.
- 패턴을 승인하면 서버가 향후 90일의 `PlannedTransaction`을 생성하고, 이후 롤링 배치로 유지한다.

`PlannedTransaction.status`:

| 상태 | 의미 |
| --- | --- |
| `EXPECTED` | 패턴에서 생성된 예측 상태 |
| `CONFIRMED` | 사용자가 등록·확정한 거래 |
| `MATCHED` | 실제 거래와 매칭 완료 (P1-05) |
| `MISSED` | 예정일이 지났으나 실제 거래 미발생 |
| `CANCELLED` | 사용자가 취소 |

### 9.2 반복 패턴 목록·상세

`GET /businesses/{businessId}/recurring-patterns?status=CANDIDATE`

`GET /recurring-patterns/{patternId}`

```json
{
  "success": true,
  "data": {
    "patternId": 31,
    "businessId": 11,
    "accountId": 21,
    "status": "CANDIDATE",
    "direction": "DEPOSIT",
    "category": "PLATFORM_SETTLEMENT",
    "merchantName": "배달의민족",
    "cycle": {
      "type": "WEEKLY",
      "dayOfWeek": "TUESDAY",
      "intervalDays": null,
      "dayOfMonth": null
    },
    "amountStats": {
      "average": 890000,
      "median": 880000,
      "min": 820000,
      "max": 960000
    },
    "nextExpected": {
      "date": "2026-09-01",
      "originalDate": "2026-09-01",
      "holidayAdjusted": false,
      "amountMin": 820000,
      "amountMax": 960000
    },
    "holidayRule": "NEXT_BUSINESS_DAY",
    "confidence": "MEDIUM",
    "hitRate": 0.92,
    "sampleCount": 12,
    "recentTransactions": [
      { "transactionId": 88001, "occurredAt": "2026-08-25T04:12:00Z", "amount": 850000 }
    ],
    "suggestionMessage": "배달의민족에서 매주 화요일 정산금이 입금되고 있습니다. 다음 예상 입금일 9월 1일, 예상 금액 82만~96만 원으로 등록할까요?"
  }

```

- `cycle.type`: `WEEKLY`(요일 반복), `MONTHLY`(일자 반복), `INTERVAL`(N일 간격)
- `holidayRule`: `NEXT_BUSINESS_DAY`(다음 영업일 이월, 카드 정산 기본값), `PREVIOUS_BUSINESS_DAY`(직전 영업일 앞당김, 일부 급여), `NONE`(무관). 공휴일 데이터는 한국천문연구원 특일 정보 API 기반 공휴일 캘린더를 사용한다 (P1-04).
- `hitRate`는 P1-05 매칭 결과로 계산한 과거 적중률이며, 예측 카드의 신뢰도 뱃지 근거로 함께 노출한다.

**입금 채널이 둘이다.** 위 예시는 배달 플랫폼 정산(주 1회 묶음)이고, 홀·포장 카드 결제는 카드사별로 **영업일마다** 들어온다. 같은 매장에서 두 패턴이 동시에 잡힌다.

```json
{
  "patternId": 34,
  "direction": "DEPOSIT",
  "category": "CARD_SETTLEMENT",
  "merchantName": "신한카드",
  "cycle": {
    "type": "INTERVAL",
    "intervalDays": 1,
    "dayOfWeek": null,
    "dayOfMonth": null
  },
  "amountStats": { "average": 310000, "median": 295000, "min": 180000, "max": 520000 },
  "holidayRule": "NEXT_BUSINESS_DAY",
  "confidence": "HIGH",
  "hitRate": 0.96,
  "sampleCount": 44,
  "suggestionMessage": "신한카드 정산금이 영업일마다 입금되고 있습니다. 주 초 금액이 큰 편입니다(주말 매출분 유입)."
}
```

- 카드 정산은 카드사별로 패턴을 나눈다. 정산 주기(D+2/D+3)와 가맹점 수수료율이 달라 순액 비율이 다르고, 적요(`신한카드`·`KB국민카드`)로 거래처 사전에서 자연히 분리된다.
- 금액이 요일마다 다르다. 주말 매출분이 유입되는 주 초 회차가 크고, 이 편차는 계절 계수(P1-07)의 **요일 계수**로 처리한다.
- ⚠ **현행 `cycle.type` 3종으로는 "매 영업일"을 정확히 표현할 수 없다.** `INTERVAL: 1`은 주말에도 입금을 예측하고, `NEXT_BUSINESS_DAY` 보정을 걸면 토·일 예정분이 월요일로 몰려 한 날에 3건이 된다. 실제로는 영업일당 1건이고 금액만 요일마다 다르다. **`BUSINESS_DAILY` cadence 를 채택했다** *(2026-09-09 구현 — 2026-09-10 문서 반영)*. 주말을 건너뛰는 것은 보정이 아니라 **주기의 정의**라 공휴일 캘린더 없이도 계산된다. 근거와 대안 비교는 [예측엔진 설계노트 G-2](../예측엔진_설계노트.md)에 있다.

### 9.3 후보 승인·무시·수정

승인:

`POST /recurring-patterns/{patternId}/confirm`

```json
{
  "category": "PLATFORM_SETTLEMENT",
  "amountMin": 820000,
  "amountMax": 960000,
  "holidayRule": "NEXT_BUSINESS_DAY"
}
```

- 본문 필드는 모두 선택값이며 전달된 값으로 패턴을 보정한 뒤 `status = CONFIRMED`로 바꾸고 예정 거래를 생성한다. 변경된 패턴을 반환한다.

무시:

`POST /recurring-patterns/{patternId}/dismiss` — `status = DISMISSED`, `204 No Content`. 무시된 패턴은 재탐지 시 다시 후보로 올리지 않는다.

두 API 모두 현재 상태가 `CANDIDATE`가 아니면 `409 PATTERN_STATE_CONFLICT`를 반환한다.

수정:

`PATCH /recurring-patterns/{patternId}` — 수정 가능 필드: `category`, `amountMin`, `amountMax`, `holidayRule`, `status`(`CONFIRMED` ↔ `PAUSED`).

수정은 **예정 거래를 함께 다시 맞춘다.**

| 무엇을 바꾸나 | 예정 거래 |
| --- | --- |
| `PAUSED` 로 | 기준일 이후 `EXPECTED` 를 **걷어낸다** |
| `CONFIRMED` 로 되돌림 | 걷어낸 뒤 향후 90일치를 **다시 만든다** |
| 금액·분류·휴일 규칙만 (값이 실제로 달라졌을 때) | 위와 같다 — 옛 금액으로 만들어진 것을 갈아끼운다 |
| 같은 값을 다시 보냄 | 아무 일도 없다 |

걷어내는 범위는 좁다 — **사용자가 손댄 것(`CONFIRMED`·`CANCELLED`), 이미 매칭된 것(`MATCHED`), 이미 금융망에 반영된 것은 남는다.** 다시 만들 때는 그 날짜를 **비켜 간다**: 사장님이 개별로 취소한 회차가 재생성으로 되살아나면 안 된다(자동 반영 계좌에서는 실제로 나간다).

중지가 취소(`CANCELLED`)가 아니라 삭제인 이유가 이것이다. 취소로 남기면 사용자가 끈 회차와 섞여 되돌릴 때 구별할 수 없다.

**기준일보다 이른 회차는 만들지 않는다.** 패턴의 다음 예정일(`nextExpectedDate`)이 과거에 있으면 주기 단위로 굴려 기준일 이후 첫 회차부터 센다 — 위상은 그대로다(임차료 5일은 굴려도 5일).

### 9.4 예정 거래 목록·등록·수정

`GET /businesses/{businessId}/planned-transactions?from=2026-09-01&to=2026-09-30&status=EXPECTED&source=PATTERN`

| Query | 설명 |
| --- | --- |
| `from`, `to` | 예정일 범위 (필수, 최대 92일) |
| `status` | 9.1의 상태 |
| `source` | `PATTERN`, `USER`, `TAX`, `LOAN` |
| `direction` | `DEPOSIT`, `WITHDRAWAL` |

일회성 등록 (P0-06):

`POST /businesses/{businessId}/planned-transactions`

```json
{
  "direction": "WITHDRAWAL",
  "category": "EQUIPMENT",
  "title": "에스프레소 머신 교체",
  "expectedDate": "2026-09-10",
  "amount": 1500000,
  "accountId": 21,
  "memo": "중고 구매 예정"
}
```

```json
{
  "success": true,
  "data": {
    "plannedTransactionId": 501,
    "businessId": 11,
    "source": "USER",
    "status": "CONFIRMED",
    "direction": "WITHDRAWAL",
    "category": "EQUIPMENT",
    "title": "에스프레소 머신 교체",
    "expectedDate": "2026-09-10",
    "originalDate": "2026-09-10",
    "holidayAdjusted": false,
    "amountExpected": 1500000,
    "amountMin": 1500000,
    "amountMax": 1500000,
    "matchedTransactionId": null
  }
}
```

- 금액은 `amount`(확정) 또는 `amountMin`/`amountMax`(범위) 중 한 형태로 전달한다.
- **`expectedDate` 는 지난 날짜를 받지 않는다** — 오늘 이전이면 `400 VALIDATION_FAILED` *(2026-09-11 추가)*. **당일은 받는다**: 곡선에 당일 점은 없지만 첫 점이 합산한다(10장). 곡선이 닿지 않는 구간에 저장해 봐야 어디에도 나타나지 않아, 사용자는 「등록했는데 잔액이 그대로」인 화면을 본다.
- `source = TAX` 예정 거래는 부가세·세금 일정(P1-11, P1-18)에서 서버가 자동 생성하며 사용자는 금액만 수정할 수 있다.
- `source = LOAN` 예정 거래는 대출 상환 스케줄(P1-13)에서 자동 생성된다.
- `PATCH /planned-transactions/{plannedTransactionId}` — 수정 가능 필드: `title`, `category`, `expectedDate`, `amount`/`amountMin`/`amountMax`, `memo`, `status`(`CANCELLED`).
- `DELETE`는 `source = USER`인 예정 거래만 허용하며, 패턴 생성분은 `CANCELLED` 처리로 대신한다 (`409 PLANNED_TX_NOT_DELETABLE`).

### 9.5 실제 거래 매칭 (P1-05)

- 서버는 실제 거래 저장 시 금액·날짜·거래처 유사도로 예정 거래와 자동 매칭하고 `status = MATCHED`, `matchedTransactionId`, `dateDiffDays`, `amountDiff`를 기록한다.
- 자동 매칭이 틀렸을 때 수동 보정한다:

| Method | Endpoint | 설명 |
| --- | --- | --- |
| POST | `/planned-transactions/{plannedTransactionId}/match` | `{ "transactionId": 88001 }`로 수동 매칭 |
| DELETE | `/planned-transactions/{plannedTransactionId}/match` | 매칭 해제, 상태를 `EXPECTED`로 되돌림 |

- 매칭 이력은 거래처별 평균 지연일·금액 오차로 집계되어 다음 예측의 날짜 보정치와 금액 범위 폭에 반영된다.

#### ⚠ 최소 매처는 P0-07 의 선행 조건이다 *(2026-09-10)*

**이 절 전체가 P1-05 지만, 매칭이 없으면 예상 잔액 곡선(P0-07)이 틀린 값을 낸다.** 잔여 현금흐름의 정의가 `일별 실제 합계 − 예정 거래에 매칭된 합계`(10.1)이므로 뺄 대상이 비면 잔여가 「실제 거래 전부」가 되고, 곡선이 `시작잔액 + Σ예정 + Σ실제` 로 **예정 거래를 두 번 센다.**

그래서 아래 규칙만 줄여 **P0-07 범위로 올린다.** 거래처 유사도·가중 점수·수동 보정 API(`/match`)·`MISSED` 전이는 P1-05 그대로다.

| 조건 | 값 |
| --- | --- |
| 방향 | `flow_type` 이 같아야 한다 |
| 계좌 | 예정 거래에 계좌가 지정돼 있으면 같아야 한다 (없으면 사업장의 모든 계좌) |
| 날짜 | `\|실제 거래일 − 예정일\| ≤ N` |
| 금액 | `amountMin ≤ 실제 금액 ≤ amountMax` |
| 중복 | 이미 다른 예정 거래에 매칭된 거래는 제외 (부분 UK 가 1:1 을 강제) |
| 동점 | 날짜 오차 → 금액 오차 → id 순으로 결정적 배정 |

`N` 은 주기마다 다르다 — 탐지기가 후보를 만들 때 쓴 허용폭과 같은 값이다.

| 출처·주기 | N | 근거 |
| --- | ---: | --- |
| 패턴 · `WEEKLY` | 1 | 요일이 고정이라 공휴일 하루 밀림만 흡수하면 된다 |
| 패턴 · `BUSINESS_DAILY` | 1 | 영업일마다 1건이라 창을 넓히면 이웃 회차와 섞인다 |
| 패턴 · `MONTHLY` | 3 | 탐지의 월 반복일 허용폭 2 + 주말 이월 1 |
| 패턴 · `INTERVAL(k)` | `0.25k` 를 1~3 으로 자름 | 탐지의 간격 편차 허용치 25% 와 같은 값 |
| `USER`·`TAX`·`LOAN` | 3 | 사용자가 넣은 날짜라 편차가 크다 |

⚠ **자동 반영이 만든 거래는 이 매처를 거치지 않는다**(9.6). 금융망 거래고유번호로 먼저 1:1 로 붙고, 그 결과는 닻 재조정의 입력이 되지 않는다 — 서버가 꺼져 있어 늦게 나간 것으로 앞으로의 일정을 밀면 안 된다.

⚠ **연휴가 N 보다 길면 놓친다.** 2026년 추석은 4일이라 목요일 예정이 다음 월요일에 실행되면(+4) 매칭되지 않고 잔여로 넘어간다 — 합계는 보존되지만 곡선 폭이 넓어진다. 공휴일을 아는 매칭은 P1-04 와 함께다.

⚠ **금액은 범위 포함으로만 판정한다.** 사용자가 확정 금액으로 넣은 예정 거래(`amountMin = amountMax`)는 이체 수수료 몇백 원 차이로도 매칭되지 않는다. 허용폭은 넣지 않았고, 필요해지면 한 곳(`MatchPolicy`)에서 켠다.

### 9.6 예정 거래 자동 반영 (시연용) *(v1.19 신규)*

**예정 거래는 우리 DB 안의 계획일 뿐이다.** 예정일이 지나도 연결된 계좌에서는 아무 일도 일어나지 않아서, 그 행은 `EXPECTED` 인 채 곡선 창(오늘~+30일) 밖으로 밀려나고 실제 잔액은 그대로다 — 시연 데이터가 하루하루 낡는다. 자동 반영은 그 간극을 메운다: **확정한 패턴의 예정 거래를 예정일에 금융망 `DD_08`(출금)·`DD_09`(입금)로 실제로 반영한다.**

대상은 **`ACCOUNT.auto_execute_planned` 를 켠 계좌**(기본 꺼짐)의 예정 거래 중 **`source = PATTERN`·`USER`** 다. 둘 다 사람이 명시적으로 정한 것이다 — 앞은 탐지된 후보를 사장님이 승인한 것이고 뒤는 직접 적은 것이다. **`TAX`·`LOAN` 은 제외한다**: 서버가 일정에서 만든 것이라 사장님이 주장한 적 없는 돈이다(공통규약 23장 예약이체 표 3행).

**계좌가 비어 있는 예정 거래**(웹 폼이 계좌를 보내기 전에 만들어진 행)는 **그 사업장에 자동 반영을 켠 계좌가 하나뿐일 때만** 그 계좌 몫으로 본다. 둘 이상이면 건너뛴다 — 어느 통장에서 뺄지를 서버가 고르는 셈이라 돈이 나가는 자리의 기본값으로 적절하지 않다.

⚠ **사용자 등록 행에는 사전 조회의 「채택」이 잘 걸리지 않는다.** 패턴 행의 이름은 적요에서 나와 금융망 거래와 글자가 같지만, 사용자 등록은 제목을 자유롭게 적는다 — 「에스프레소 머신」과 통장 적요 「경동프리텍」은 안 맞는다. **이미 일어난 일을 뒤늦게 등록하면 한 번 더 나갈 수 있다.** 등록의 뜻이 「앞으로 나갈 것」이라는 전제에 기대어 둔 자리다.

**언제 보내나.** 당일자는 `09:00`(KST) 이후, 지난 회차는 **3일까지 따라잡는다**(시각 무관). 서버가 꺼져 있던 날을 낮에 켜면 곧 집는다. 금융망은 과거 날짜 거래를 만들 수 없으므로(기술스택 §4.1.1) **따라잡은 거래는 실행한 날로 찍힌다** — 대신 아래 정확 매칭이 원래 회차에 붙여 곡선을 어긋나게 두지 않는다.

**중복을 막는 근거 세 가지.** 로컬 DB 와 배포 DB 는 서로를 보지 못하는데 같은 시연 계좌를 가리킬 수 있다(시드가 이메일로 `userKey` 를 뽑는다). 그래서 DB 잠금으로는 막을 수 없다.

1. **보내기 전에 금융망 거래내역(`DD_12`)을 먼저 본다.** 같은 방향·금액·적요가 예정일 이후에 이미 있으면 **호출하지 않고 그 거래를 주워 온다.** 조회에 실패하면 그 계좌는 그 차례에 아무것도 보내지 않는다.
2. **채번이 결정적이다.** `(계좌·예정일·방향·금액·적요·순번)` 해시로 항상 같은 20자리를 만들어, 두 서버가 같은 초에 사전 조회를 통과해도 둘째 요청이 `H1007` 로 막힌다. 이 경로에서 `H1007` 은 **재시도 신호가 아니라 「이미 나갔다」** 다.
3. **원장(`PLANNED_EXECUTION`)이 한 DB 안의 중복을 막는다.** 예정 거래당 한 행이고, 같은 패턴의 같은 회차도 한 행이다 — 달력을 고쳐 예정 거래가 새 id 로 다시 만들어져도 돈은 한 번만 나간다.

`PLANNED_EXECUTION.status`:

| 상태 | 의미 |
| --- | --- |
| `SENT` | 보냈거나 보내는 중에 답을 못 받았다. **다음 차례가 거래내역부터 확인한다** |
| `EXECUTED` | 금융망에 반영됐다. 동기화가 그 거래를 가져오면 `MATCHED` 로 간다 |
| `MATCHED` | 가져온 거래를 예정 거래에 붙였다. 원장의 종착점 |
| `FAILED` | 실패. `retryAfter` 가 있으면 그날 이후 재시도, 없으면 영구 실패 |
| `SKIPPED` | 보낼 수 없는 것이었다 |

| 금융망 결과 | 원장 | 재시도 |
| --- | --- | --- |
| `H0000` | `EXECUTED` | — (동기화를 접수한다) |
| `H1007` 채번 중복 | 거래내역 재조회 → 있으면 `EXECUTED`(주움), 없으면 `FAILED` 영구 | 없음 |
| `A1014` 잔액 부족 | `FAILED`, `retryAfter = 내일` | 창 안에서 하루 1회. **결함이 아니라 정산 공백이 실제로 일어난 것이다** |
| `A1003`·`H1009`·`Q1001`·`H1010` | `FAILED` 영구 | 없음 — 사람이 본다 |
| 전송 오류·5xx·시계 오차 | `SENT` 유지 | 다음 차례에 거래내역 확인 후 **같은 번호로** 재전송, 3회까지 |

**정확 매칭.** 반영된 거래는 금융망 거래고유번호(= `TRANSACTION.external_transaction_id`)로 **1:1 로** 예정 거래에 붙는다. 최소 매처(9.5)보다 **먼저** 돌고, 닻 재조정의 입력이 되지 않는다 — 따라잡기로 늦게 나간 것은 거래처가 늦게 준 것이 아니라 우리 서버가 꺼져 있었던 것이라, 그걸로 앞으로의 일정을 밀면 곡선이 어긋난다.

**이미 반영된 예정 거래는 잠긴다.** 삭제·취소·날짜·금액 변경이 `409 PLANNED_TX_NOT_DELETABLE` 이다(이름·메모·분류는 열려 있다). 나간 돈은 돌아오지 않으므로 계획만 고치면 통장과 갈린다.

켜고 끄는 것은 `PATCH /accounts/{accountId}/planned-execution`(7.2)이다.
