## AI 1번 회신 *(2026-09-11)*

**백엔드 회신 네 항목을 코드로 확인했고 전부 근거가 맞다.** 아래 원문은 지우지 않는다 —
왜 그렇게 정했는지 읽을 근거가 거기 있다. 틀린 부분은 여기에 적는다.

### ① 배치 정책 — **내 전제가 틀렸다. 청킹을 워커에 넣었다**

원문 108행의 *"워커가 바꿔야 하는 것은 B 뿐이다"* 가 틀렸다. C(400건 Job)도 워커가
바꿔야 한다 — **"Job 하나가 담는 건수" 와 "요청 하나가 담는 건수" 를 분리해서 생각하지
않은 탓**이다.

`1 Job ↔ 1 콜백` 이 코드로 강제돼 있다. `AiResultApplier` 가 이미 종단 상태인 Job 의
콜백을 버리므로, 400건 Job 하나를 20건씩 20번 POST 하면 **첫 콜백만 반영되고 380건이
버려지는데 LLM 비용은 20번 다 나간다.** ①에서 내가 경고한 "중복 과금, 결과는 0" 이
다른 경로로 재현된다.

**구현을 마쳤다.** `BATCH_MAX`(LLM 한 번에 20건)와 `REQUEST_MAX`(요청 하나에 400건)를
분리하고, 워커가 요청 안에서 20건씩 **순차로** 부른 뒤 콜백을 **한 번만** 보낸다.

| 요구 | 반영 |
| --- | --- |
| 요청 상한과 LLM 청크 분리 | `REQUEST_MAX = 400` · `BATCH_MAX = 20` |
| 순차 청킹 | `for` 루프. 동시 호출 없음 |
| 단일 콜백 | 루프가 끝난 뒤 `_deliver` 한 번 |
| 청크마다 `breaker.allow()` 재확인 | 루프 머리에서 확인, 열려 있으면 남은 청크 건너뜀 |
| 부분 실패는 `PARTIAL` + 성공분만 | 실패 청크가 있으면 `status = PARTIAL` |

`classification_max_tokens` 는 청크가 20건 그대로라 손대지 않았다. 400 = 20청크 ×
실측 15.0초 = 약 300초로 `stallTimeout`(10분)의 절반이다.

**실패한 청크에서 멈추지 않는다.** 한 청크가 죽었다고 나머지를 버리면 일시적 429 하나로
380건을 잃는다. 계속 돌되 **차단기가 열리면 그때 멈춘다** — 5연속이라는 경계는 차단기가
이미 들고 있다. 남은 거래는 `UNCLASSIFIED` 로 남아 8.5 재실행이 주워가므로
**재시도 단위가 Job 이 아니라 거래 상태**다.

**백엔드는 상한 20으로 오늘 붙여도 된다.** 워커가 400까지 받으므로 값만 올리면 된다.
체이닝(콜백 반영 후 미분류가 남으면 다음 Job 하나)에도 동의한다 — in-flight 1 이면
타임아웃·429 위험이 0 이고 진행률은 미분류 잔량으로 센다.

### ② `allowedCategories` — 조건 받음

23종 전부, **순서는 시드 id 순 고정.** 프리픽스 캐시가 정확 일치라는 지적이 맞다 —
사업장마다 목록이 갈리면 캐시도 갈린다. 워커는 받은 순서를 바꾸지 않는다.

### ③ `merchantName` — **2단계로 정정한다**

원문이 1단계를 권한 근거가 *"`JOB.result` 에 원본이 남는다"* 인데, **`JOB.result` 는
30일 정리 대상**이다(공통규약 23장). `AiResultApplier.persist` javadoc 이 정확히 그
이유로 도메인 테이블에 옮긴다고 적어 뒀는데, 내가 그 javadoc 을 읽고도 ③에 연결하지
못했다. 1단계는 "미룬다" 가 아니라 **30일 뒤 영구 손실**이다.

`transaction_classification_history.reason` 은 이미 JSONB 이고 LLM 이력은 어차피
`classifier_type = 'LLM'` 으로 남으므로 키 하나 더 넣는 비용이 0 이다. 2단계에 동의한다.

**그리고 내 과장도 정정한다.** *"캐시가 없으면 모든 거래가 매번 LLM 을 탄다"* 고 썼는데
**거래는 한 번만 분류된다.** 실제로 아끼는 것은 다음 달 같은 거래처의 새 거래다 —
반복 거래가 대부분인 도메인이라 효과는 크지만, 표현이 사실과 달랐다.

### ④ 트리거 — 가드 조건 받음

쿼리 기반이면 멱등해진다는 지적이 맞다. `TransactionsChanged` 에 거래 id 가 없으니
리스너는 어차피 미분류를 조회하게 되고, 그러면 *"유실돼도 손실이 없다"* 는 전제가
유지된다. **같은 사업장에 끝나지 않은 Job 이 있으면 새로 넣지 않는 가드**도 필요하다는
데 동의한다 — 콜백 전까지 행이 `UNCLASSIFIED` 라 두 Job 이 같은 거래를 두 번 과금한다.

## 0. 워커는 끝났고 백엔드 쪽 네 조각이 비어 있다

`POST /internal/v1/ai/transaction-classification` 이 `develop` 에 들어가 있다(`-91` 완료).
실측도 끝났다 — 라벨 300건 × 3회로 Macro F1 0.9226, 수락률 0.9927.

그런데 **백엔드가 이 라우트를 부르지 않는다.** 뼈대는 이미 다 있다:

| 이미 있는 것 | 비고 |
| --- | --- |
| `JobType.TRANSACTION_CLASSIFICATION` | enum·DB CHECK 제약에 이미 있다 |
| `JobWorker` · `JobSweeper` | 작업 유형에 독립적 |
| `AiCallbackController` · `AiCallbackService` · `AiResultApplier` | 콜백 수신·멱등 판정까지 동작 |
| CSV 임포트 → `TransactionsChanged.byCsv()` | 이벤트 발행됨 |
| `Transaction` 의 `categoryId`·`classificationStatus`·`classificationConfidence`·`needsConfirmation` | 컬럼·필드 존재 |

비어 있는 것은 넷이다.

1. `TransactionsChanged` 를 듣고 `jobService.enqueue(TRANSACTION_CLASSIFICATION, ...)`
2. `TransactionClassificationHandler implements JobHandler` — 워커 POST 후 `AWAITING_CALLBACK`
3. `AiResultApplier.persist()` 의 분기 — 지금은 `if (jobType == EVIDENCE_EXTRACTION)` 하나뿐
4. 결과를 `Transaction` 에 쓰는 서비스 — 엔티티에 `classifyByUser()` 만 있다

증빙 경로(`EvidenceExtractionHandler` 116줄 + `EvidenceExtractionService` 217줄)와 같은
모양이라 새로 설계할 것은 없다. **다만 아래 네 가지는 워커가 임의로 정하면 안 되는 것들이다.**

## ① CSV 를 Job 으로 어떻게 쪼갤 것인가 — **이것만 막고 있다**

### 제약 두 개가 서로 당긴다

- 워커 요청의 `BATCH_MAX = 20`. 한 번에 20건까지다
- `JobProperties.stallTimeout = 10분`(`application.yml` 의 `JOB_STALL_TIMEOUT:PT10M`).
  주석이 **"이보다 오래 도는 핸들러는 실행 중에 스위퍼가 requeue 해 중복 실행된다"** 고 경고한다
- `JobProperties.maxAttempts = 2`. 재시도가 **한 번뿐**이다

`stall-timeout` 은 환경변수라 올릴 수는 있다. 다만 `AI_CALLBACK_CLAIM_TTL`(1분)이
**"stall-timeout 보다 짧아야 한다"** 로 묶여 있고, 값 자체가 공통규약 23장에서 온 것이라
분류 하나 때문에 전역을 올리는 것은 권하지 않는다.

### 실측 — 10분에 800건이 한계다

`claude-sonnet-5` · 프롬프트 v2 · 배치 20건 기준, 라벨 300건을 3회 돌린 값이다
(`ai/evals/p1-01/report.json`).

| 회차 | 소요 | 배치당 |
| --- | ---: | ---: |
| 1 | 226.8초 | 15.1초 |
| 2 | 231.6초 | 15.4초 |
| 3 | 216.4초 | 14.4초 |

**배치당 15.0초.** 편차가 거의 없다.

| 예산 | 배치 | 건수 |
| ---: | ---: | ---: |
| 600초 (10분 전부) | 40 | **800건** |
| 300초 (절반) | 20 | 400건 |

**800건을 넘기면 실패가 아니라 중복 과금이다.** 실행 → 스톨 → requeue → 실행 → 스톨 →
`maxAttempts` 소진 → `FAILED`. **LLM 비용을 두 번 태우고 결과는 0이다.**
소상공인 1년치 계좌는 800건을 쉽게 넘는다.

### 선택지

**A. Job 하나 = 20건 (Job N개)**

증빙 경로와 완전히 같은 모양이다(1 Job = 1 워커 호출 = 1 콜백). 타임아웃 위험 0.
`JobSweeper` 는 `findByStatusAndStartedAtBefore(PROCESSING, …)` 라 Job 수가 늘어도
인덱스 스캔이고 부담이 적다.

다만 2,000건 CSV 가 **Job 100개**가 된다. `GET /jobs/{jobId}` 로 진행률을 보여주려면
상위 개념이 따로 필요하다.

**B. Job 하나 = CSV 전체 (워커가 내부에서 20건씩)**

Job 1개라 진행률이 단순하다. 하지만 위 실측대로 **800건 상한**이 생기고, 요청 스키마의
`BATCH_MAX = 20` 을 풀어야 한다. 상한을 넘는 CSV 가 들어오면 위의 중복 과금 경로를 탄다.

**C. 혼합 — Job 하나가 최대 400건, 넘으면 분할 (권고)**

- 400건 = 20배치 = 약 300초 → **타임아웃 예산의 절반만 쓴다**
- 400건 이하 CSV(대부분)는 Job 1개로 끝난다
- 2,000건 CSV 는 Job 5개. 100개보다 진행률 표시가 쉽다
- 상한을 설정값으로 두면 모델·프롬프트가 바뀌어 속도가 변할 때 코드를 안 고쳐도 된다

**워커 권고는 C다.** 다만 Job 수명주기와 진행률 UX 는 백엔드 소유라 최종 판단을 요청한다.
A 로 가도 워커는 그대로 동작한다 — 워커가 바꿔야 하는 것은 B 뿐이다(`BATCH_MAX` 완화).

### 참고 — 어느 쪽을 골라도 총 시간은 같다

2,000건이면 100배치 × 15초 = **약 25분**이다. 쪼개는 방식은 실패 모드와 진행률
표시를 바꿀 뿐 총 소요를 줄이지 못한다. 줄이려면 Batch API(`-97`)나 프롬프트
캐싱(`-98`)이 필요하고, 그건 기술스택 §11 의 14단계다.

## ② `allowedCategories` 를 요청에 넣을 것인가

현재 요청 스키마는 **필수**다 — `allowed_categories: list[TransactionCategory] = Field(min_length=1)`.
즉 백엔드가 반드시 보내야 한다. 뺄지 말지가 결정 사항이다.

**권고: 그대로 둔다. 백엔드가 `core.transaction_category` 에서 읽어 보낸다.**

- 시드 SQL 이 정본이라는 것은 이미 못박혀 있다. 워커에 `tests/nlp/test_category_seed_parity.py`
  가 있어 `V2__seed_transaction_category.sql` 과 코드가 어긋나면 테스트가 깨진다
- 업종별 부분집합을 쓸 여지가 생긴다. 요식업에 안 쓰는 카테고리를 빼면 모델이 고를 후보가
  줄어 정확도가 오른다
- 카테고리를 추가할 때 **백엔드만** 고치면 된다. 빼면 워커에 23종이 굳는다

워커는 받은 목록 밖의 값을 `invalid_results()` 로 폐기한다 — 목록이 계약의 일부다.

## ③ `merchantName` 을 어디에 저장할 것인가

워커는 적요에서 추정한 거래처명을 낸다(확신이 없으면 `null`). **그런데 받을 자리가 없다.**

- 마이그레이션 V1~V7 에 `merchant` 테이블이 없다
- `TransactionDtos` 주석: *"`merchantId`·`evidence` 는 각각 P1-01·P0-10 착수 시 채운다"*

**이것은 도메인 규칙 3 과 직결된다** — "확정된 `거래처 ↔ 분류` 매핑은 DB 에 캐시해서
재사용한다. LLM 호출은 처음 보는 패턴에만." 캐시가 없으면 **모든 거래가 매번 LLM 을 탄다.**
지금 상태가 그렇다.

세 갈래가 있다.

| | 무엇 | 비용 | 얻는 것 |
| --- | --- | --- | --- |
| 1단계 | `merchantName` 을 **버린다** | 0 | 카테고리는 화면에 뜬다. 캐시는 없다 |
| 2단계 | `transaction_classification_history.reason`(JSONB)에 넣는다 | 낮음 | 기록은 남는다. 조회로 캐시를 흉내낼 수 있다 |
| 3단계 | `merchant` 테이블 + `transaction.merchant_id` | 마이그레이션 | 규칙 3 이 실제로 동작한다 |

**권고: 1단계로 붙이고 3단계는 별도 티켓.** 분류가 화면에 뜨는 것이 먼저이고, 캐시는
그 뒤에 붙여도 데이터가 유실되지 않는다(`JOB.result` 에 원본이 남는다).

다만 **3단계를 언제 할지는 지금 정해 두는 편이 좋다.** 캐시가 없는 동안 비용은 거래
건수에 그대로 비례한다.

## ④ 분류를 언제 트리거할 것인가

**권고: CSV 임포트 완료 이벤트에서 자동.**

`TransactionImportService` 가 이미 `TransactionsChanged.byCsv(businessId, accountId)` 를
발행한다. `forecast` 쪽 `ForecastTriggerListener` 가 같은 이벤트를 듣는 선례가 있다.

- 사용자가 버튼을 한 번 더 누를 이유가 없다. 업로드하면 분류되는 것이 자연스럽다
- 금융망 동기화(`Source.SYNC`)도 같은 이벤트를 쓰므로 경로가 하나로 합쳐진다

주의 — `TransactionsChanged` 주석이 **"이 이벤트가 유실돼도 손실이 없다"** 를 전제로
영속화를 안 한다고 적어 뒀다. 분류 트리거가 붙으면 그 전제가 약해진다. 유실 시
"미분류 거래를 주기적으로 쓸어 담는 배치"가 대안인데, 이쪽이 오히려 멱등해서 나을 수 있다.
**백엔드 판단을 요청한다.**

### 백엔드 구현 메모 *(2026-09-14)*

**유실은 문제가 아니었다.** 트리거를 붙여도 `TransactionsChanged` 의 전제는 유지된다 —
이벤트에 거래 id 가 없어 핸들러가 어차피 **그때의 미분류 거래를 조회**하므로, 이벤트 하나를
놓쳐도 다음 수집이나 8.5 재실행이 같은 거래를 그대로 주워간다. 영속화하지 않았다.

`Source.ACCOUNT_DISCONNECTED` 는 트리거하지 않는다(이 값은 9월 11일에 추가됐다). 거래 행이
하나도 바뀌지 않은 사건이고, 오히려 그 계좌의 거래는 분류 대상에서 빠지므로 분류할 것이
없는 Job 만 뜬다.

**⚠ 가드는 중복을 완전히 막지 못한다 — 알고 그대로 뒀다.**

`JobService.enqueueIfIdle` 이 "같은 사업장에 끝나지 않은 분류 Job 이 있으면 넣지 않는다"를
**조회로만** 판정한다. 조회와 삽입 사이를 잠그지 않으므로, 동기화 완료와 CSV 임포트 완료가
거의 같은 순간에 끝나면 양쪽이 "없음"을 보고 둘 다 넣을 수 있다. 그러면 **한 배치
(기본 20건)가 중복 과금된다.**

| | |
| --- | --- |
| 잃는 것의 상한 | 배치 하나 = `jango.classification.batch-size`(기본 20건)의 LLM 호출 |
| 데이터 손실 | **없다.** 반영은 거래마다 멱등하고(확정된 거래는 덮지 않는다) 늦게 온 콜백은 이미 분류된 거래를 건너뛴다 |
| 확실히 막으려면 | `JOB` 에 「사업장당 미완료 분류 작업 하나」 부분 유일 인덱스. 마이그레이션이 하나 늘고, 그 제약은 분류 말고 다른 작업 유형에도 영향을 준다 |
| 지금 안 하는 이유 | 사용자당 계좌가 한둘이고 두 수집 경로가 같은 초에 겹칠 일이 드물다. 막는 값이 잃는 값보다 크다 |
| 관측 방법 | 같은 사업장에 **거의 같은 시각의 분류 Job 두 개**. 보이면 그때 인덱스를 얹는다 |

## 부록 A. 워커가 받는 요청 (실제 스키마)

```json
{
  "jobId": 9012,
  "business": { "industryType": "FOOD_CAFE" },
  "allowedCategories": ["RENT", "PAYROLL", "MATERIALS", "PLATFORM_SETTLEMENT"],
  "fewShotExamples": [
    { "description": "우아한형제들", "direction": "DEPOSIT",
      "category": "PLATFORM_SETTLEMENT", "merchantName": "배달의민족" }
  ],
  "transactions": [
    { "transactionId": 88031, "description": "김영자", "direction": "WITHDRAWAL",
      "amount": 1200000, "occurredAt": "2026-08-25T01:00:00Z",
      "cycleHint": "매월 25일 반복 (최근 4회)" }
  ]
}
```

- `transactions` 는 **1~20건**(`BATCH_MAX`)
- `cycleHint` 는 P0-03 반복 탐지가 계산한 값이다. **넣어 주면 정확도가 오른다** —
  주급을 급여로 가르는 근거가 여기서 나온다. 모델에게 주기를 추론시키는 것보다 정확하고 싸다
- `fewShotExamples` 는 사용자가 정정한 이력 상위 N건. `ix_tch_fewshot` 인덱스
  (`classifier_type = 'USER'`)가 이미 그 조회를 위해 준비돼 있다.
  **하루 1회만 갱신해야** 프롬프트 프리픽스 캐시가 산다 — 매 요청 재구성하면 적중률이 0이다

## 부록 B. 워커가 보내는 콜백 (실제 본문)

`POST /internal/v1/ai-jobs/{jobId}/result` · `X-Request-Id: ai-job-{jobId}-result`

```json
{
  "success": true,
  "data": {
    "status": "COMPLETED",
    "modelName": "claude-sonnet-5",
    "modelVersion": null,
    "promptVersion": "transaction-classification/v2",
    "pipeline": "LLM",
    "results": [
      { "transactionId": 1, "category": "CARD_SETTLEMENT", "merchantName": "신한카드",
        "confidence": 0.95, "reason": "카드사 입금은 카드 매출 정산금" },
      { "transactionId": 4, "category": "SUBSCRIPTION", "merchantName": "포스뱅크",
        "confidence": 0.75, "reason": "POS 업체 소액 월정액 이용료" }
    ]
  },
  "error": null
}
```

`AiCallbackDtos.ResultRequest` 와 모양이 맞는 것을 확인했다 — `success` / `data`(status +
모델메타 + 결과 평면 병합) / `error`.

**실패 시**에는 `error.detail` 에 키가 더 붙을 수 있다.

```json
{ "success": false, "data": null,
  "error": { "code": "AI_ANALYSIS_FAILED",
             "message": "거래 분류를 일시적으로 사용할 수 없습니다.",
             "detail": { "jobId": 9012, "transactionCount": 20,
                         "circuit": "open", "retryAfterSeconds": 42.3 } } }
```

`circuit: "open"` 은 워커 → Anthropic 차단기가 열렸다는 뜻이다(연속 5회 재시도 가능
실패 → 60초). `retryAfterSeconds` 뒤에 다시 걸면 된다. `detail` 이 `Map` 이라 백엔드는
무시해도 동작한다.

## 부록 C. 결과를 `Transaction` 에 어떻게 반영할 것인가 (참고용 초안)

백엔드 소유 코드라 초안만 적는다.

| 워커 출력 | `core.transaction` | 규칙 |
| --- | --- | --- |
| `category` | `category_id` | 코드 → id 는 `core.transaction_category` 조회 |
| `confidence` | `classification_confidence` | 그대로 |
| — | `classification_status` | `SUGGESTED` (사용자 확정 전) |
| `confidence < 0.85` 또는 신규 거래처 | `needs_confirmation` | `true` (명세 20.3) |
| `merchantName` | — | ③ 결정 전까지 버린다 |
| `reason` | `transaction_classification_history.reason` | 근거 보존. `classifier_type = 'LLM'` |

**결과에 없는 `transactionId` 는 실패가 아니다.** 워커가 허용 목록 밖·방향 불일치 값을
폐기하면 그 건만 빠진다(명세 20.1 — "해당 항목만 제외"). 빠진 건은 규칙·사전 결과를
유지하고 `needsConfirmation = true` 로 사용자 확인 큐에 넣는 것이 계약이다.
**배치 전건이 빠져도 Job 실패가 아니다.**
