## 11. 시나리오 분석 (What-if)

### 11.1 시나리오 생성·계산

`POST /businesses/{businessId}/scenarios`

P0-09 기본 3종(정산 지연·입금 감소·추가 지출)과 P0-13 확장 파라미터를 하나의 API로 처리한다. 파라미터는 자유롭게 조합할 수 있다.

```json
{
  "name": "정산 지연 + 머신 교체",
  "days": 30,
  "save": true,
  "parameters": [
    { "type": "SETTLEMENT_DELAY", "patternId": 31, "delayDays": 2 },
    { "type": "DEPOSIT_DECREASE", "rate": 0.1 },
    { "type": "EXTRA_EXPENSE", "date": "2026-09-10", "amount": 1500000, "title": "머신 교체" }
  ]
}
```

| 파라미터 `type` | 필드 | 관련 기능 |
| --- | --- | --- |
| `SETTLEMENT_DELAY` | `patternId`(생략 시 입금 패턴 전체), `delayDays` | P0-09 |
| `DEPOSIT_DECREASE` | `rate` (0~1), `patternId`(선택) | P0-09 |
| `EXTRA_EXPENSE` | `date`, `amount`, `title` | P0-09 |
| `EXTRA_DEPOSIT` | `date`, `amount`, `title` | P0-13 |
| `EXPENSE_DATE_SHIFT` | `plannedTransactionId`, `newDate` | P0-13 |
| `SALES_CHANGE` | `rate` (음수 허용) | P0-13 |
| `PRODUCT_SALES_CHANGE` | `productKey`, `quantityRate`(선택), `priceRate`(선택) | P0-13 (P1-22 구성비 연동) |
| `LOAN_EXECUTION` | `amount`, `interestRate`, `loanPeriodDays`, `repaymentCycle`, `disbursementDate` | P1-14 대출 실행 미리 보기 |

**`DEPOSIT_DECREASE`와 `SALES_CHANGE`의 차이** — 둘 다 입금에 배율을 곱하지만 적용 방식이 다르다. 혼동을 막기 위해 명시한다.

| | `DEPOSIT_DECREASE` | `SALES_CHANGE` |
| --- | --- | --- |
| 뜻 | 특정 입금 패턴이 그만큼 덜 들어온다 | 매출 자체가 변해 **모든 매출성 입금**이 달라진다 |
| 대상 | `patternId` 지정 시 그 패턴만, 생략 시 입금 패턴 전체 | `CARD_SETTLEMENT`·`PLATFORM_SETTLEMENT`·`CASH_SALES`·`TRANSFER_SALES` 패턴만. 대출 실행·대표자 자금 투입 등 비매출 입금은 제외 |
| 방향 | 감소만 (`rate` 0~1) | 증감 양방향 (`rate` 음수 허용) |
| 배율 | 기간 내 균일 | 기간 내 균일. 정산 주기 지연은 반영하지 않는다 |

정산 지연(D+2·주 1회)을 매출 변화에 따라 재현하지는 않는다. 매출이 오늘 늘어도 입금은 며칠 뒤에 늘지만, 예측 창(7/14/30일) 안에서 이 시차가 결과 지표(최저잔액·최초 부족일)를 뒤집는 경우는 드물어 균일 배율로 근사한다. 두 파라미터를 함께 쓰면 배율은 곱해진다.

**`PRODUCT_SALES_CHANGE` — 상품 단위 매출 시뮬레이션 (P1-22 연동)**

상품 하나의 판매량·단가를 조정해 총매출 배율을 환산하고, 그 배율을 매출성 입금 패턴에 곱한다. 상품별 구성비(14.5)가 있어야 계산되며, 없으면 `409 PRODUCT_SALES_NOT_REGISTERED`.

```json
{ "type": "PRODUCT_SALES_CHANGE", "productKey": "카페라떼",
  "quantityRate": -0.05, "priceRate": 0.10 }
```

```text
① 상품 배율      (1 + quantityRate) × (1 + priceRate)
                 0.95 × 1.10 = 1.045                      → 라떼 매출 +4.5%
② 구성비 조회     share(카페라떼) = 0.242                    (14.5, 합계 기준)
③ 총매출 배율     1 + 0.242 × 0.045 = 1.0109               → 총매출 +1.09%
④ 입금 적용       매출성 입금 패턴 전체 × 1.0109 → Layer 1 재실행
```

- **구성비를 쓰기 때문에 분모가 무엇이든 결과가 보존된다.** POS 판매 총액과 계좌 입금액의 기준이 달라도(수수료 차감·정산 지연·현금 미입금) 변화율만 쓰므로 환산이 필요 없다.
- 응답 `warnings`에 사용한 구성비와 그 근거 기간을 담는다: `"카페라떼 구성비 24.2% (2026-08-01~08-31 기준)을 적용했습니다."` 계절성 있는 메뉴는 기간에 따라 구성비가 달라지므로 어느 기간을 썼는지 항상 밝힌다.
- 상품 여러 개를 동시에 조정하면 각 상품의 `share × 상품배율 변화분`을 합산한다.
- **판매량과 단가는 사용자가 각각 가정한다.** "가격 10% 올리면 얼마나 덜 팔릴지"(가격 탄력성)는 서비스가 모른다. 화면에 "판매량 변화는 직접 가정하세요"를 명시한다.
- **매출 변화까지만 계산하고 이익 변화는 다루지 않는다.** 원가를 모르므로 마진·수익성을 말하지 않는다(14.5 표현 제약, P2-03 범위).

> **예측 엔진 원칙과 충돌하지 않는다.** 매출 레이어를 만드는 것이 아니라 구성비에서 **배율 하나**를 만들어 기존 입금 패턴에 곱하는 것이므로, 원장(Layer 2)을 건드리지 않고 Layer 3의 결정론적 변환 안에서 끝난다(`docs/예측엔진_설계노트.md`).
>
> 이전 판(v1.2)에는 "메뉴 단가 변경(`MENU_PRICE_CHANGE`)은 메뉴·판매 데이터가 P2(P2-14)로 이관되어 함께 보류한다"고 적혀 있었다. **그 전제는 P1-22 신설로 무효가 됐다** — 판매 데이터가 P1으로 돌아왔다. 레시피·원가가 필요한 마진 계산만 P2-03에 남는다.

응답 (`201 Created`, `save = false`면 저장 없이 `200`으로 결과만 반환):

```json
{
  "success": true,
  "data": {
    "scenarioId": 61,
    "name": "정산 지연 + 머신 교체",
    "baseTime": "2026-08-31T02:00:00Z",
    "days": 30,
    "parameters": [],
    "comparison": {
      "original": {
        "lowestBalance": -420000,
        "lowestBalanceDate": "2026-09-14",
        "firstShortfallDate": "2026-09-14",
        "gapDurationDays": 2,
        "belowSafetyLineDays": 3
      },
      "modified": {
        "lowestBalance": -2150000,
        "lowestBalanceDate": "2026-09-12",
        "firstShortfallDate": "2026-09-12",
        "gapDurationDays": 5,
        "belowSafetyLineDays": 7
      }
    },
    "originalCurve": [ { "date": "2026-09-01", "expectedBalance": 5820000 } ],
    "modifiedCurve": [ { "date": "2026-09-01", "expectedBalance": 5320000 } ],
    "confidence": "MEDIUM",
    "warnings": []
  }
}
```

- 시나리오 계산은 원본 예측 데이터를 절대 변경하지 않는다(복제 계산). "적용" 개념은 없으며, 실제 반영은 사용자가 예정 거래를 직접 수정하는 것으로만 이루어진다.
- `original`과 `modified`를 항상 나란히 반환해 변경 전후 비교 UI를 지원한다 (인수 조건: 원본과 구분 표시).

**오류**

| 코드 | HTTP | 언제 |
| --- | --- | --- |
| `VALIDATION_FAILED` | 400 | 본문 형식 · `days`(7·14·30) · `save` 누락 · `parameters` 개수(1~20) |
| `SCENARIO_PARAM_INVALID` | 400 | 파라미터 한 건이 틀렸다. `message` 가 `parameters[i].field` 를 가리키고 `detail` 에 `{index, field, type}` 이 담긴다. **남의 `patternId`·`plannedTransactionId` 도 없는 것과 같은 문구다**(존재 여부를 흘리지 않는다) |
| `PRODUCT_SALES_NOT_REGISTERED` | 409 | 구성비(14.5)가 없는 사업장의 `PRODUCT_SALES_CHANGE` |
| `FORECAST_NOT_READY` | 409 | 완료된 예측 실행이 없다. 재계산을 예약하고 돌려주므로 잠시 뒤 다시 부른다 |
| `FORECAST_INSUFFICIENT_DATA` | 422 | 연결된 계좌가 없다 |

> **정정 (2026-09-16 · 구현 정합)**
>
> - **기준은 「최신 완료 예측 실행」이다.** 시나리오는 예측을 새로 돌리지 않고 저장된 실행의 원장을 변형해 같은 계산기를 다시 부른다(공통규약 23장 — 조회는 계산하지 않는다). 그래서 `originalCurve` 는 같은 창의 10.1 `expectedBalance` 와 **원 단위까지 같고**, 실행이 없으면 10.1 과 똑같이 `409`·`422` 다. `baseTime` 은 그 실행의 시각이다.
> - **`SALES_CHANGE`·`PRODUCT_SALES_CHANGE` 의 대상은 「매출 4종으로 분류된 예정 입금」이다.** 위 표가 "패턴"이라 적었으나 실제 판별자는 카테고리다 — 사용자가 직접 등록한 현금 매출도 매출이고, 카테고리가 비어 있는 입금은 대상이 아니다. 분류 전에 탐지된 패턴은 카테고리가 비어 있어 **대상이 0건**이 되며, 그때는 「거래 분류 뒤 반복 패턴을 다시 탐지하라」를 `warnings` 로 알린다. **빈 카테고리는 스스로 메워진다**(2026-09-17) — 분류가 끝나면 패턴이 근거로 삼은 거래의 분류를 패턴에 채우고, 확정된 패턴은 예정 거래를 다시 만들어 그 값을 싣는다. 재탐지도 같은 일을 한다. 그래서 이 경고는 **근거 거래까지 아직 미분류인 동안**만 뜬다.
> - **정산 지연은 달력 일수 이동이다.** 밀린 날짜에 영업일·공휴일 보정을 다시 걸지 않는다(P1-04 와 함께 볼 문제다). 창 밖으로 밀린 입금은 사라지고 그 사실이 `warnings` 에 남는다 — 그 돈이 이번 기간에 들어오지 않는다는 것이 곧 시뮬레이션의 결과다.
> - **구성비는 「가장 최근 등록 기간」을 쓴다.** 11.1 에 기간 파라미터가 없고 14.5 의 기본 창(이번 달)은 월초에 비어 스퓨리어스 `409` 를 낸다. 어느 기간을 썼는지는 위 규칙대로 `warnings` 가 밝힌다.
> - **`Idempotency-Key` 를 받지 않는다** — 다른 공개 `POST` 와 같다(2.8 은 「선택」이다).

### 11.2 시나리오 저장·조회·삭제

| Method | Endpoint | 설명 |
| --- | --- | --- |
| GET | `/businesses/{businessId}/scenarios` | 저장된 시나리오 목록 (`scenarioId`, `name`, `createdAt`, 파라미터 요약) |
| GET | `/scenarios/{scenarioId}` | 저장 시점 파라미터로 재계산한 최신 결과 반환 |
| PATCH | `/scenarios/{scenarioId}` | `name` 수정 |
| DELETE | `/scenarios/{scenarioId}` | 삭제 (`204`) |

- `GET /scenarios/{scenarioId}`는 저장된 결과 스냅샷이 아니라 현재 데이터 기준 재계산 결과를 반환하며, 응답의 `baseTime`으로 계산 시점을 구분한다.
- 목록 응답은 `{ "items": [...] }` 이고 **페이징 필드가 없다**(9.2·10.3 과 같다). 최신순이며 각 항목은 저장한 파라미터를 요청과 같은 모양으로 담는다.
- **저장한 시나리오가 예정 거래를 붙잡지 않는다** *(2026-09-16 · `V32`)*. 대상 예정 거래·패턴을 지우면 조정의 대상만 비워지고(`ON DELETE SET NULL`) 행은 남는다. 재계산은 그 조정을 빼고 「대상이 삭제되어 반영하지 않았습니다」를 `warnings` 에 담되, **`parameters` 에는 저장한 그대로 보여 준다** — 목록에서 조용히 사라지면 결과가 왜 달라졌는지 알 수 없다.
