## 13. 증빙과 품목 가계부

### 13.1 증빙 업로드 (P0-10, P1-02)

`POST /businesses/{businessId}/evidences`

`multipart/form-data`:

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `file` | Y | JPG/PNG/PDF, 최대 10MB |
| `evidenceType` | N | 힌트 값. 생략하면 AI가 추정 |
| `transactionId` | N | 업로드와 동시에 연결할 거래 |

```json
{
  "success": true,
  "data": {
    "evidenceId": 501,
    "evidenceType": "RECEIPT",
    "fileName": "receipt_0831.jpg",
    "fileUrl": "https://storage.example.com/evidences/501.jpg",
    "ocrStatus": "QUEUED",
    "ocrJobId": 9013,
    "linkedTransactionId": null,
    "uploadedAt": "2026-08-31T02:00:00Z"
  }
}
```

- `202 Accepted`. 업로드 즉시 OCR/VLM 추출 Job이 등록된다 (P1-02).
- `evidenceType`: `RECEIPT`(영수증), `TAX_INVOICE`(세금계산서), `INVOICE`(계산서·거래명세서), `CASH_RECEIPT`(현금영수증), `SETTLEMENT_STATEMENT`(플랫폼 정산명세서), `CONTRACT`(임대차계약서), `PAYROLL`(급여대장), `OTHER`
- `ocrStatus`: `QUEUED` → `PROCESSING` → `EXTRACTED`(사용자 확인 대기) → `CONFIRMED`(사용자 확정) / `FAILED` / `SKIPPED`(추출 대상 아님)

### 13.2 증빙 목록·상세

`GET /businesses/{businessId}/evidences?linked=false&ocrStatus=EXTRACTED&from=2026-08-01&to=2026-08-31`

| 파라미터 | 설명 |
| --- | --- |
| `linked` | 거래 연결 여부. `false`가 "증빙은 있는데 거래에 안 붙은 것" — 이 화면의 핵심 필터다 |
| `ocrStatus`·`evidenceType` | 상태·종류. 모르는 값은 `400`이다(조용히 무시하면 필터가 안 걸린 전체 목록이 나간다) |
| `from`·`to` | **업로드 시각** 기준이다. 발행일은 추출 후에 채워지므로 그것으로 걸면 갓 올린 증빙이 사라진다 |
| `needsReview` | 검산이 걸린 것만 *(v1.23)*. ⚠ **`null`(아직 추출 전)은 `true`에도 `false`에도 걸리지 않는다** |
| `sort` | 검토 화면은 `sort=needsReview,desc&sort=createdAt,desc`로 **「먼저 볼 곳」을 위로 올린다** *(v1.23)* |

목록 항목은 `evidenceId`·`evidenceType`·`fileName`·`ocrStatus`·`issuedDate`·`totalAmount`·`needsReview`·`linked`·`uploadedAt`이다.

`GET /evidences/{evidenceId}`

```json
{
  "success": true,
  "data": {
    "evidenceId": 501,
    "evidenceType": "RECEIPT",
    "fileName": "receipt_0831.jpg",
    "fileUrl": "https://storage.example.com/evidences/501.jpg",
    "ocrStatus": "EXTRACTED",
    "extraction": {
      "supplierName": "서울우유 광주대리점",
      "supplierBusinessNo": "123-45-67890",
      "issuedDate": "2026-08-30",
      "totalAmount": 156000,
      "vatAmount": 14182,
      "items": [
        {
          "extractionItemId": 1,
          "rawName": "서울우유 1L",
          "quantity": 40,
          "unit": "개",
          "unitPrice": 2900,
          "amount": 116000,
          "boundingBox": { "x": 0.12, "y": 0.31, "width": 0.55, "height": 0.04 },
          "matchedItemId": 601
        }
      ],
      "fieldConfidence": {
        "supplierName": 0.95,
        "totalAmount": 0.99,
        "items": 0.88
      },
      "modelName": "donut-ko-receipt-v2",
      "extractedAt": "2026-08-31T02:00:41Z"
    },
    "linkedTransactionId": null,
    "uploadedAt": "2026-08-31T02:00:00Z"
  }
}
```

- **P1-02 완료 기준은 「필드 강조」다** *(v1.23, 2026-09-11 확정 — 옛 기준은 좌표 하이라이트였다)*. 검토 화면은 `validation.needsReview`로 **정렬**하고 `fieldConfidence`가 낮은 필드를 **강조**한다. 원본 이미지는 추출 필드와 나란히 보여주되 **좌표 표시는 하지 않는다.** 자세한 것은 아래 「`boundingBox`」.
- `fieldConfidence`는 **강조용이지 게이트가 아니다.** "여기만 보면 된다"는 뜻으로 쓸 수 없다 — test 359장에서 임계값 0.7이 정밀도 23%, 0.85가 25%인데 **그 데이터의 기저 오류율이 16.7%**다. 무작위로 찍는 것과 다르지 않다. 모든 추출은 `EXTRACTED`(사용자 확인 대기)를 거친다.
- `modelName`은 추론에 사용한 모델 식별자다. 모델 비교 실험(OCR 파이프라인 vs VLM)의 운영 근거로 기록한다.

**`boundingBox` — 스키마에 있고 값은 항상 `null`이다**

응답 예시에 남아 있지만 **현재 어떤 경로도 이 값을 채우지 않는다.** live·stub 모두 `null`이고, 전역 `non_null` 정책이라 키 자체가 빠진다.

| | |
| --- | --- |
| VLM 좌표 실측 (2026-09-08, 15장) | 중심 적중 **33%** · IoU ≥ 0.5 **9%** |
| 같은 추출의 **값** 정확도 | **99%** |

세 줄을 나란히 놓는 것이 요점이다 — **값은 맞는데 위치만 틀린다.** 사용자가 보는 것은 "이 숫자가 저기서 왔다"는 주장인데 셋 중 둘은 엉뚱한 곳을 가리킨다. **틀린 하이라이트는 없는 것보다 나쁘다** — 근거를 보여줄 수 없으면 보여주지 않는 편이 낫다(SRS 도메인 규칙 1과 같은 성격이다).

좌표를 채울 **공급자가 없다는 것도 확정됐다** *(2026-09-10)*. 후보 두 곳을 다 재 보고 둘 다 종결했다 — Azure Document Intelligence는 리소스 생성 자체가 막혔고, CLOVA OCR은 요금(Document OCR 영수증 실질 38.7~60원/건, 손익분기 11.7원의 3~5배 + 이용량 0에서도 월정액)과 접근 경로(좌표 전용 General OCR 3원/건은 요금이 맞았으나 Invoke URL 호스트가 NCP 권한 DNS 기준 사설 IP라 개발 PC·배포 서버 양쪽에서 미도달) 양쪽에서 막혔다. 호출 0건·비용 0원. 즉 **품질이 나쁜 것이 아니라 채울 방법이 없다.**

**컬럼과 계약 필드는 남긴다.** `OCR_PIPELINE` 공급자가 붙는 날 값만 채우면 되고, 그때 하이라이트를 **얹으면** 된다. 되돌리는 비용이 비대칭이라 이 방향을 골랐다 — 지금 하이라이트를 만들면 좌표가 없는 동안 빈 화면을 그리거나 틀린 위치를 그린다.

**원본 이미지는 보여줘야 한다.** 좌표 없이 나란히 놓는 것은 되고, 그러려면 파일을 내주는 경로가 필요하다. 현재 13.1·13.2 응답에 `fileUrl`이 없는 이유이기도 하다(구현현황 3.17) — **완료 기준이 어느 쪽이든 다운로드 엔드포인트는 필요하다.**

### 13.3 추출 결과 수정·확정

`PATCH /evidences/{evidenceId}/extraction`

```json
{
  "supplierName": "서울우유 광주대리점",
  "issuedDate": "2026-08-30",
  "totalAmount": 156000,
  "vatAmount": 14182,
  "items": [
    { "extractionItemId": 1, "rawName": "서울우유 1L", "quantity": 40, "unitPrice": 2900, "amount": 116000 }
  ],
  "confirmed": true
}
```

- OCR 결과는 사용자가 확인·수정한 후에만 확정 데이터로 등록된다(초기 데이터 오류 방지 원칙). `confirmed = true`가 전달되면 `ocrStatus = CONFIRMED`가 되고, 품목 데이터가 품목 가계부(13.6)에 반영된다.
- `ocrStatus`가 `EXTRACTED` 또는 `CONFIRMED`가 아니면 `409 EVIDENCE_STATE_CONFLICT`를 반환한다.
- **보낸 필드만 바뀐다** *(v1.23)*. `null`은 "안 보냄"이고 "지움"이 아니다 — 화면이 고친 필드만 보내는 것이 정상 동선이라, `null`을 지움으로 읽으면 모델이 제대로 읽은 값이 저장에서 사라진다. 값을 비우는 경로는 두지 않는다. `items[]`는 `extractionItemId`로 행을 찾고, 없는 id는 무시한다(행 추가는 없다).
- **서버가 수정 이력을 남긴다** *(v1.23)*. 필드별 before/after가 `EVIDENCE_CORRECTION`에 쌓인다 — **실사용 정확도를 얻는 유일한 방법**이다(실험 세트 정확도는 우리가 고른 이미지에 대한 값이다). 두 가지가 여기 달려 있다.
  - **고친 것이 없어도 확인을 기록한다.** 그게 분모다 — 없으면 "고칠 것이 없던 추출"과 "아직 안 본 추출"이 구분되지 않아 정확도가 실제보다 높게 나온다.
  - **안 바뀐 값은 이력에 넣지 않는다.** 금액은 수치로 비교한다(`156000`과 `156000.00`은 같다). 넣으면 분자가 부풀어 정확도가 실제보다 낮게 나온다.
- **고친 값으로 검산을 다시 돌린다** *(v1.23)*. 응답의 `extraction.validation`은 재실행 결과이고, 목록 정렬 키(`needsReview`)도 함께 옮겨진다 — 사용자가 금액을 바로잡았는데 목록이 계속 "확인 필요"로 올리면 안 된다. 검산 규칙은 워커 한 곳에 있다(20.4 확장 `evidence-validation`, 모델 미호출·비용 0). **워커가 없으면 옛 검산 결과가 그대로 남고 저장은 그대로 된다** — 검토 저장이 워커 가용성에 묶이면 안 되고, 판정하지 못한 것을 "통과"로 바꾸지도 않는다.
- **발행일을 고치면 목록의 기간 필터도 따라간다** *(v1.23)*. `issuedDate`는 추출 결과이자 `EVIDENCE`의 캐시 컬럼이라 양쪽을 같이 옮긴다 — 안 그러면 12월 영수증이 목록의 1월에 남는다.

### 13.4 거래 매칭

매칭 후보:

`GET /evidences/{evidenceId}/match-candidates`

```json
{
  "success": true,
  "data": {
    "items": [
      {
        "transactionId": 88020,
        "occurredAt": "2026-08-30T06:10:00Z",
        "description": "서울우유광주",
        "amount": 156000,
        "direction": "WITHDRAWAL",
        "score": 0.94,
        "matchedBy": ["AMOUNT_EXACT", "DATE_SAME_DAY", "MERCHANT_SIMILAR"],
        "autoLinkEligible": true
      }
    ]
  }
}
```

연결·해제:

| Method | Endpoint | 설명 |
| --- | --- | --- |
| POST | `/evidences/{evidenceId}/link` | `{ "transactionId": 88020 }` — 거래 연결 |
| DELETE | `/evidences/{evidenceId}/link` | 연결 해제 (`204`) |

- 자동 연결은 `autoLinkEligible = true`(높은 신뢰도)인 경우에만 서버가 수행하고, 그 외에는 사용자 승인을 요구한다 (8.1 P1 처리 규칙).
- 하나의 거래에 여러 증빙을 연결할 수 있으나, 동일 증빙을 다른 거래에 중복 연결하면 기존 연결을 해제 후 재연결해야 한다 (`409 EVIDENCE_ALREADY_LINKED`).

### 13.5 증빙 메타 수정·삭제

- `PATCH /evidences/{evidenceId}` — `evidenceType` 수정.
- `DELETE /evidences/{evidenceId}` — 삭제(`204`). 연결된 거래의 증빙 상태가 갱신되고, 이미 신고자료 내보내기에 포함된 파일 원본은 아카이브에 남는다.

### 13.6 품목 가계부 (P1-03)

품목 마스터:

`GET /businesses/{businessId}/items?q=우유`

```json
{
  "success": true,
  "data": {
    "items": [
      {
        "itemId": 601,
        "canonicalName": "우유 1L",
        "aliases": ["서울우유 1L", "우유 1000ml"],
        "itemCategory": "MATERIALS",
        "unit": "개",
        "lastUnitPrice": 2900,
        "avgUnitPrice90d": 2780,
        "priceChangeRate90d": 0.043,
        "purchaseCount": 14,
        "lastPurchasedAt": "2026-08-30"
      }
    ]
  }
}
```

- 표기 흔들림("서울우유 1L" / "우유 1000ml")은 품목 마스터와 LLM 보조 매핑(20.2)으로 `canonicalName` 하나에 통합한다.
- `PATCH /items/{itemId}` — `canonicalName`, `itemCategory`, `unit` 수정과 `mergeSourceItemIds`(다른 품목을 이 품목으로 병합) 처리.

구매 이력·단가 추이:

`GET /items/{itemId}/purchases?from=2026-06-01&to=2026-08-31`

```json
{
  "success": true,
  "data": {
    "itemId": 601,
    "canonicalName": "우유 1L",
    "items": [
      {
        "purchaseDate": "2026-08-30",
        "evidenceId": 501,
        "supplierName": "서울우유 광주대리점",
        "quantity": 40,
        "unit": "개",
        "unitPrice": 2900,
        "amount": 116000
      }
    ],
    "priceTrend": [
      { "month": "2026-07", "avgUnitPrice": 2750 },
      { "month": "2026-08", "avgUnitPrice": 2860 }
    ]
  }
}
```

기간 집계:

`GET /businesses/{businessId}/item-purchases?from=2026-08-01&to=2026-08-31&groupBy=ITEM`

- `groupBy`: `ITEM`(품목별 합계·수량), `CATEGORY`(재료·소모품 등 분류별 합계)
- 응답은 품목별 기간 합계, 구매 횟수, 단가 변화율을 포함한다 (P1-03 완료 기준).

### 13.7 재추출 *(v1.25)*

`POST /evidences/{evidenceId}/re-extract` → `202`

```json
{
  "evidenceId": 41,
  "ocrJobId": 907,
  "extractionMode": "THOROUGH"
}
```

검토 화면에서 사장님이 「이 결과가 틀렸다」고 했을 때, 같은 증빙을 **`THOROUGH` 로 다시 읽는다.** 워커 쪽 동작과 근거는 20장 v1.17에 있다 — 타일링을 켜고, 설정돼 있으면 더 강한 모델로 바로 간다. 오독 3건 중 2건을 고쳤고 열화 이미지 품목명 exact 를 76.3 → 83.3% 로 올렸다. **전건에 쓰지 않는 이유는 비용 +52%** 이고, 사장님이 틀렸다고 지목한 건에만 쓰면 부담이 없다.

- **`ocrStatus`가 `EXTRACTED`일 때만 된다.** 그 외에는 `409 EVIDENCE_STATE_CONFLICT`.
  - **확정(`CONFIRMED`)된 증빙은 거절한다.** 재추출은 새 행을 넣고 이전 행을 `is_current = false`로 내리므로, 확정본에 그대로 하면 **사장님이 승인한 값이 조용히 사라진다.** 확정을 되돌리는 경로가 먼저 있어야 그다음이다.
  - 이미 `PROCESSING`이면 읽는 중이라 다시 걸지 않는다.
- **접수 시점에 이전 추출을 내리지 않는다.** 내리는 일은 콜백이 도착해 새 결과를 저장할 때 한다. `THOROUGH`는 실패를 감추지 않아 1차 결과로 폴백하지 않으므로(20장), 재추출이 실패하면 이전 결과가 그대로 남아 있어야 한다.
- 파일은 이미 있다. 업로드와 달리 저장소에 다시 쓰지 않고 같은 `storageKey`를 워커에 준다.
- 응답 뒤 `ocrStatus`는 `PROCESSING`이다. 화면은 업로드와 같은 방식으로 상태를 다시 조회한다.

**어느 모드로 뽑았는지가 추출 행에 남는다** *(v1.25)*. `EVIDENCE_EXTRACTION.extraction_mode` — `extractionMode`는 요청 필드라 콜백 본문에 없고 Job 파라미터에만 있는데 그 Job 은 정리 배치가 지운다. 이 값이 없으면 **「재추출이 실제로 고쳤나」를 실사용 데이터로 답할 수 없다.** 이 컬럼이 생기기 전 행은 `NULL`이며, 「모드가 없었다」가 아니라 「소급이 안 된다」는 뜻이다.
