카테고리는 서버가 관리하는 고정 목록이며, LLM 분류 결과도 이 목록 외 값은 저장하지 않는다.

> **`CARD_SETTLEMENT`은 입금이다.** 카드사가 가맹점에 주는 정산금이며 계좌 거래내역의 적요로 들어온다. 금융망의 `CREDIT_CARD_*` API는 방향이 반대인 **카드 결제·청구(출금)**이므로 섞지 않는다. 금융망에는 가맹점 매출 입금 구조가 없다 — 공통규약 1.5, `docs/예측엔진_설계노트.md` G-4·G-5.
>
> 입금 4종(`CARD_SETTLEMENT`·`PLATFORM_SETTLEMENT`·`CASH_SALES`·`TRANSFER_SALES`)이 **매출성 입금**이다. 매출 금액의 단일 출처이며, 신고서 ⑪ 매출액(14.3)·부가세 예수금(12.4)·What-if `SALES_CHANGE`(11.1)가 모두 이 4종을 기준으로 계산한다. 상품별 매출(P1-22)은 여기에 더해지지 않고 **구성비만** 제공한다.

`GET /transaction-categories` *(v1.4 추가)*

```json
{
  "success": true,
  "data": {
    "items": [
      { "code": "CARD_SETTLEMENT", "name": "카드 정산금", "direction": "DEPOSIT" },
      { "code": "RENT", "name": "임차료", "direction": "WITHDRAWAL" }
    ]
  }
}
```

- 분류 선택 UI가 목록을 서버에서 받도록 추가했다. 프론트가 23종을 하드코딩하면 카테고리가 늘어날 때마다 배포가 함께 필요해진다.
- 인증 필요. 표시 순서(`sortOrder`)로 정렬해 반환하며 비활성 항목은 제외한다.
- **카테고리는 DB 테이블 데이터다.** 추가·비활성·개명은 마이그레이션만으로 가능하지만, `code`는 규칙셋·LLM few-shot·분류 이력이 참조하는 안정 식별자이므로 바꾸지 않는다.

### 8.2 거래 목록

`GET /businesses/{businessId}/transactions?from=2026-08-01&to=2026-08-31&direction=WITHDRAWAL&classificationStatus=SUGGESTED&needsConfirmation=true&hasEvidence=false&q=우아한&page=0&size=20`

| Query | 필수 | 설명 |
| --- | --- | --- |
| `from`, `to` | N | 거래일 범위 (기본: 최근 31일) |
| `accountId` | N | 특정 계좌만 |
| `direction` | N | `DEPOSIT`, `WITHDRAWAL` |
| `category` | N | 8.1의 카테고리 |
| `classificationStatus` | N | `UNCLASSIFIED`, `SUGGESTED`, `CONFIRMED` |
| `needsConfirmation` | N | `true`면 확인 질문 대상만 |
| `hasEvidence` | N | 증빙 연결 여부 (P0-10 누락 필터) |
| `taxReviewStatus` | N | 종합소득세 검토 상태. 쉼표로 복수 지정 가능 (P0-12 검토 필터) |
| `minAmount`, `maxAmount` | N | 금액 범위 |
| `q` | N | 적요·거래처명 검색 |
| `includeDisconnected` | N | `true`면 **해제된 계좌**의 거래까지 함께 준다 (기본 `false`) |

```json
{
  "success": true,
  "data": {
    "items": [
      {
        "transactionId": 88001,
        "accountId": 21,
        "finTransactionId": 10241,
        "counterpartyAccountNo": null,
        "occurredAt": "2026-08-25T04:12:00Z",
        "description": "우아한형제들",
        "direction": "DEPOSIT",
        "amount": 850000,
        "balanceAfter": 5850000,
        "category": "PLATFORM_SETTLEMENT",
        "merchantId": 301,
        "merchantName": "배달의민족",
        "classification": {
          "status": "SUGGESTED",
          "source": "AI",
          "confidence": 0.86,
          "needsConfirmation": true,
          "reason": "적요 '우아한형제들'은 배달의민족 정산 계좌명입니다."
        },
        "evidence": {
          "linked": false,
          "evidenceIds": []
        },
        "isExcluded": false,
        "taxReview": {
          "status": "UNREVIEWED",
          "note": null,
          "reviewedAt": null
        }
      }
    ],
    "page": 0,
    "size": 20,
    "totalElements": 1,
    "totalPages": 1
  }
}
```

- `finTransactionId`는 금융망 거래고유번호이며 CSV 업로드 거래는 `null`이다. `counterpartyAccountNo`는 이체 거래의 상대 계좌번호로, 거래처 식별의 보조 정보로 사용한다.
- `classification.source`: `RULE`(규칙), `DICTIONARY`(거래처 사전), `AI`(LLM), `USER`(사용자 확정). **DB 는 이 값을 `LLM` 으로 저장한다** — 네 값 중 이것만 이름이 다르다(ERD 표기 대응).
- `needsConfirmation = true`는 신뢰도가 기준 미만이거나 신규 거래처인 경우다. 확인 질문 UX("이거 배달의민족 정산금 맞나요?")의 데이터 소스로 사용한다.
- `isExcluded = true`는 **예측·집계에서 제외**한 거래다(반복 패턴 학습·잔액 곡선 제외). 세무상 필요경비 제외 판단은 `taxReview.status`가 담당하며 두 값은 독립적이다 — 장비 구입은 예측에서 빼되 경비로 인정될 수 있고, 개인 사용 지출은 경비에서 빼되 예측에는 반영해야 한다.
- `taxReview.status`는 종합소득세 검토 상태다(기획정리본 §6.5). 값은 8.7에 정의한다.

**해제된 계좌의 거래는 기본으로 빠진다** *(v1.25)*. 연동을 끊어도 거래는 보존하지만(7.2), 보존이 "합계에 계속 기여한다"는 뜻은 아니다 — 목록에 섞여 있으면 그것을 더해 만드는 숫자가 전부 그만큼 부풀고, 그 계좌 잔액은 이미 총잔액·곡선에서 빠져 있어(`AccountBalancesService` 는 `CONNECTED` 만 센다) 앞뒤가 맞지 않는다.

- 보려면 `includeDisconnected=true` 를 보낸다. **`accountId` 로 지목해도 이 값이 필요하다** — 같은 것을 얻는 길을 둘로 두면 어느 쪽이 합계에 들어가는지가 호출자마다 갈린다. 화면의 「해제된 계좌 포함」이 이 문을 쓴다.
- **빠지는 것은 해제뿐이다.** 인증 대기·만료 계좌의 거래는 그대로 나온다 — CSV 로 직접 올린 자료가 있을 수 있고(7.4는 계좌 상태를 보지 않는다) 그것은 사용자가 넣은 것이다.
- **종합소득세 검토·신고서 초안도 기본값을 따른다**(팀 결정, 2026-09-11). 과세기간 중에 해제한 계좌의 거래는 신고 대상이지만 초안 합계에서는 빠진다 — 신고 금액을 사람이 검토할 때 이 점을 알아야 한다(P0-12 착수 시 재검토 대상).
- 예측 입력은 기준이 더 좁다. 반복 패턴 탐지는 `CONNECTED` 계좌만 읽는다(7.2, `TransactionHistoryService`). 화면에 보이는 것과 곡선이 세는 것이 다른 것은 의도다.

### 8.3 거래 수정 (사용자 확정)

`PATCH /transactions/{transactionId}`

```json
{
  "category": "PLATFORM_SETTLEMENT",
  "merchantName": "배달의민족",
  "memo": "주간 정산",
  "isExcluded": false,
  "taxReviewStatus": "PERSONAL_SUSPECTED",
  "taxReviewNote": "대표자 개인 경조사비"
}
```

- 사용자가 카테고리 또는 거래처를 수정하면 `classification.status = CONFIRMED`, `source = USER`로 바뀌고, `(거래처, 카테고리)` 매핑이 거래처 사전에 축적된다.
- 정정 이력은 `ClassificationHistory`에 저장되어 다음 LLM 분류의 few-shot 예시로 사용된다 (P1-01).
- `taxReviewStatus`를 사용자가 지정하면 `tax_reviewed_at`이 기록된다. 자동 판정값(`EVIDENCE_CONFIRMED`·`EVIDENCE_MISSING`)에는 기록하지 않는다.

### 8.4 AI 제안 수락

`POST /transactions/{transactionId}/confirm-classification`

확인 질문에서 "맞아요"를 눌렀을 때 제안된 분류를 그대로 확정한다. 본문 없이 호출하며, 변경된 거래를 반환한다. `classificationStatus`가 `SUGGESTED`가 아니면 `409 CLASSIFICATION_STATE_CONFLICT`를 반환한다.

### 8.5 LLM 분류 작업

`POST /businesses/{businessId}/classification-jobs`

**본문 없음** *(2026-09-14 정정 — 이전 판의 `transactionIds` 를 뺐다)*

- **무엇을 분류할지는 서버가 정한다.** 요청이 목록을 지목하지 않고, 워커에 보낼 때 그 시점의
  미분류 거래를 다시 조회한다(20.3 합의 ④). 목록을 요청이 들고 오면 그것은 **버튼을 누른
  순간의 사진**이라, 왕복 5분 사이에 사용자가 직접 분류했거나 계좌가 해제된 거래까지 값을
  치르고 보내게 된다. 조회 기반이면 그 셋이 자동으로 빠지고 같은 요청이 멱등해진다.
  "이 몇 건만 다시" 가 필요해지면 그때 설계한다 — 지금 그 화면은 없다(화면구성도 SC-04 의
  버튼은 「AI 분류 재실행」 하나다).
- `202 Accepted`와 `TRANSACTION_CLASSIFICATION` Job을 반환한다. 완료 시 `resultRef`: `{ "classifiedCount": 34, "needsConfirmationCount": 6 }`
- **이미 도는 분류 작업이 있으면 그 작업을 그대로 반환한다**(409 가 아니다). 버튼을 두 번
  눌러도 사용자가 보려는 것은 같은 진행률이고, 새로 넣으면 같은 거래를 두 번 분류해 값이 두 번
  나간다. 같은 사업장에 미완료 분류 작업은 하나로 유지한다.
- 한 작업이 담는 거래 수에 상한이 있다(`jango.classification.batch-size`, 기본 20). 남은
  미분류가 있으면 **반영이 끝난 뒤 다음 작업 하나를 이어 넣는다** — 동시에 도는 것은 항상
  하나이고, 진행률은 미분류 잔량으로 본다. 큰 CSV 는 목록이 조금씩 채워진다.
- 서버는 규칙 → 거래처 사전 순으로 먼저 처리하고, 남은 거래만 배치로 묶어 AI 워커에 전달한다(20.3). 프롬프트에는 업종, 확정 분류 사례(few-shot), 거래 주기 정보를 포함한다.
- 동기화·CSV 업로드 완료 시 자동 실행되므로 이 API는 수동 재실행용이다.
- **다만 그 자동 실행은 지금 꺼져 있다**(2026-09-17 · `jango.classification.auto-trigger` 기본 꺼짐). 거래가 들어올 때마다 LLM 을 부르면 시드를 넣고 빼며 시험하는 동안 그것이 그대로 토큰이 된다. **그래서 지금은 이 API 가 분류를 시작하는 유일한 문이다** — 화면의 「AI 분류 재실행」 버튼이 사실상 「분류 실행」이다.

#### 8.5.1 진행 중 분류 작업 조회

`GET /businesses/{businessId}/classification-jobs/current`

```json
{
  "success": true,
  "data": {
    "running": true,
    "job": {
      "jobId": 412,
      "jobType": "TRANSACTION_CLASSIFICATION",
      "status": "PROCESSING",
      "createdAt": "2026-09-18T04:12:07Z"
    }
  }
}
```

- **화면이 돌아왔을 때를 위한 문이다.** 분류는 브라우저와 무관하게 서버에서 돈다(워커 스레드
  → AI 워커 → 콜백 → 이어달리기). 그런데 진행 표시는 화면의 로컬 상태라, 다른 페이지에 갔다
  오면 **돌고 있는데 아무 표시도 없는** 상태가 된다. 그러면 사용자는 멈춘 줄 알고 버튼을
  다시 누른다.
- **8.5 `POST` 로 대신할 수 없다.** 그쪽은 도는 것이 있으면 그것을 돌려주지만 **없으면
  새로 만든다** — 화면에 들어올 때마다 분류가 시작되고 LLM 값이 나간다. 이 `GET` 은
  아무것도 만들지 않는다.
- **도는 것이 없어도 `200` 이다.** `{ "running": false }` 이고 `job` 은 **키 자체가 없다**.
  「분류가 안 돌고 있다」는 오류가 아니라 정상 상태다 — `404` 로 주면 화면이 「기능 없음」과
  구분하지 못한다.
- `QUEUED`·`PROCESSING` 이 「도는 중」이다. 끝난 작업(`COMPLETED`·`FAILED`)은 없는 것으로 친다.
- **`job.jobId` 로 진행률을 재지 말 것.** 한 작업이 `batch-size` 만큼만 맡고 서버가 다음
  작업을 **새 id 로** 이어 걸기 때문에, 이 id 가 `COMPLETED` 가 되어도 분류는 계속 돈다.
  이 응답이 답하는 것은 「지금 돌고 있는가」 하나뿐이고, 진행은 8.2 의 미분류 잔량으로 센다
  (`classificationStatus=UNCLASSIFIED` 의 `totalElements`).

### 8.6 거래처 사전

`GET /businesses/{businessId}/merchants?q=배달&page=0&size=20`

```json
{
  "success": true,
  "data": {
    "items": [
      {
        "merchantId": 301,
        "displayName": "배달의민족",
        "matchPatterns": ["우아한형제들", "우아한형제들(주)"],
        "defaultCategory": "PLATFORM_SETTLEMENT",
        "direction": "DEPOSIT",
        "confirmedCount": 12,
        "avgDelayDays": 1.0,
        "lastUsedAt": "2026-08-25T04:12:00Z"
      }
    ],
    "page": 0,
    "size": 20,
    "totalElements": 1,
    "totalPages": 1
  }
}
```

`PATCH /merchants/{merchantId}` — 수정 가능 필드: `displayName`, `defaultCategory`. 수정하면 이후 동일 적요 거래는 사전 단계에서 자동 분류된다. **이미 분류된 거래는 소급해 바꾸지 않는다** — 사장님이 확인해 둔 것이 말없이 뒤집히지 않게 한다.

- **`matchPatterns` 는 읽기 전용이다** *(2026-09-14 정정)*. 매칭 열쇠를 바꾸는 일이라 유일 인덱스 구조까지 함께 가야 하는데, **표기가 갈리는 거래처가 아직 관측되지 않았다**. 지금은 적요 원문 한 줄이 나가고, 보내면 `400` 이다 — 조용히 무시하면 화면은 바뀐 줄 알고 사전은 그대로다. 관측되면 별칭 배열로 넓힌다.
- `displayName` 과 매칭 열쇠는 **다른 칸이다**(`V19`). 한 칸이 둘을 겸하면 이름을 고치는 순간 매칭이 깨진다 — 적요는 여전히 법인명으로 들어오기 때문이다.
- 수정은 **사람이 한 확인으로 센다**. 모델이 담아 둔 항목(`confirmedCount = 0`)을 고치면 그 자리에서 확정이 되고 다음부터 확인을 묻지 않는다.

`avgDelayDays`는 예측 정확도 집계(P1-05)에서 계산된 거래처별 평균 정산 지연일이다. **P1-05 착수 전까지는 응답에 키 자체가 없다** *(2026-09-14)* — 0 으로 내보내면 "지연이 없다" 로 읽힌다.

### 8.7 종합소득세 검토 상태 (P0-12)

계좌에서 출금되었다는 사실만으로 필요경비 인정 여부가 확정되지 않으므로, 거래별 검토 상태를 별도로 관리한다 (기획정리본 §6.5). 이 값은 P0-12 내보내기의 `07_거래증빙_연결목록.xlsx` **검토 상태** 열의 원천이다.

| 값 | 한글 라벨 | 판정 주체 | v1 범위 |
| --- | --- | --- | --- |
| `UNREVIEWED` | 미검토 | 기본값 | ✅ |
| `EVIDENCE_CONFIRMED` | 증빙 확인 완료 | **자동** — 증빙 연결됨 | ✅ |
| `EVIDENCE_MISSING` | 증빙 누락 | **자동** — 증빙 미연결 | ✅ |
| `BUSINESS_USE_UNCLEAR` | 사업 관련성 확인 필요 | 사용자 | ✅ |
| `PERSONAL_SUSPECTED` | 개인 사용 가능성 있음 | 사용자 | ✅ |
| `DUPLICATE_SUSPECTED` | 중복 등록 가능성 있음 | 사용자 | ✅ (자동 탐지는 P1) |
| `EXPERT_REVIEW` | 세무전문가 확인 필요 | 사용자 | ✅ |
| `ASSET_REVIEW` | 자산 등록 또는 감가상각 검토 필요 | 사용자 | ⏸ 값만 예약 (화면 P2) |

- **자동 판정은 두 값뿐이다.** 증빙 연결 여부로 기계적으로 알 수 있는 `EVIDENCE_CONFIRMED`·`EVIDENCE_MISSING`만 서버가 부여한다. 나머지는 서비스가 임의로 확정하지 않는다 (SRS 1.3 제외 범위, 기획정리본 §10 "세무 판단의 자동 확정 방지").
- 사용자가 지정한 값은 자동 판정으로 덮어쓰지 않는다. 증빙이 뒤늦게 연결되어도 `EXPERT_REVIEW`는 유지된다.
- `ASSET_REVIEW`는 자산대장·감가상각 관리가 상용화 확장(기획정리본 §9)이라 값만 예약한다. 나중에 마이그레이션 없이 화면만 붙인다.

**일괄 변경**

`POST /businesses/{businessId}/tax-review/bulk`

```json
{
  "transactionIds": [88001, 88014, 88027],
  "taxReviewStatus": "EXPERT_REVIEW",
  "taxReviewNote": "세무사 확인 요청"
}
```

```json
{
  "success": true,
  "data": {
    "updatedCount": 3,
    "failedCount": 0,
    "failed": []
  }
}
```

- 동기 처리이며 `transactionIds`는 최대 200건이다. 초과 시 `400 VALIDATION_ERROR`.
- 다른 사업장의 거래가 섞여 있으면 해당 건만 `failed`에 담아 반환하고 나머지는 반영한다.
- 내보내기 직전 96건을 한 건씩 처리하게 하면 기능이 쓰이지 않으므로, 검토 화면(SC-07-7)의 기본 저장 경로는 이 엔드포인트다.
