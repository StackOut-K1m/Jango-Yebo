## 백엔드 답변 (2026-09-09)

**①~⑤·⑦ 은 권고를 그대로 채택했고 `V6__evidence_extraction.sql` 로 반영했다.** 로컬에 적용해
테이블 4개(`item`·`evidence_extraction`·`evidence_item`·`evidence_correction`)가 생기는 것을
확인했다. 부록 A 초안에서 바꾼 것은 셋뿐이다.

| | 초안 | 반영 | 왜 |
| --- | --- | --- | --- |
| 파일명 | `V4` | **`V6`** | 그 사이 V4(사업자등록번호)·V5(cadence·안전선)가 들어갔다 |
| `ITEM` | "그 테이블이 생긴 뒤에" | **같은 마이그레이션에 포함** | 한 파일 안에서는 순서만 지키면 되고, 나눠 두면 `fk_evidence_item_item` 만 나중에 붙이는 ALTER 가 남는다 |
| `ITEM` 컬럼 | (초안 없음) | `created_at`·`updated_at` 추가 | 변경되는 업무 테이블이라 엔티티가 `BaseEntity` 를 상속하고, 그것이 두 컬럼을 요구한다 (V5 가 `safety_balance_policy` 에서 같은 판단을 했다) |

**⑥ 은 백엔드가 정할 것이 아니라 그대로 남겼다.** 완료 기준(인수 조건) 변경이라 팀 판단이 필요했다 — **2026-09-11 에 「필드 강조」로 확정됐다**(아래 ⑥ 머리의 상자).
다만 스키마는 어느 쪽으로 가도 안 바뀐다 — `source_coordinates` 컬럼을 남겨 뒀으므로,
`OCR_PIPELINE` 공급자를 붙이는 날 값만 채우면 된다. **화면 설계는 지금 좌표가 항상 `null` 이라는
전제로 진행해야 한다.** 백엔드 의견은 아래에 따로 적었다.

### ⑥ 에 대한 백엔드 의견 — 「필드 강조」를 지지한다 *(2026-09-10)*

정하는 것은 팀이지만, **프론트가 화면을 만들기 전에 결론이 나야 하므로** 근거를 정리해 둔다.
AI 2번이 *"늦으면 헛일이 된다"* 고 회신한 것이 이 때문이다.

**하이라이트를 지금 만들면 기능이 아니라 오답이 된다.**

| 실측 (2026-09-08, 15장 $0.08) | |
| --- | --- |
| 좌표 중심 적중 | **33%** |
| IoU ≥ 0.5 | **9%** |
| 같은 추출의 **값** 정확도 | 99% |

세 줄을 나란히 놓는 것이 요점이다 — **값은 맞는데 위치만 틀린다.** 사용자가 보는 것은
"이 숫자가 저기서 왔다"는 주장이고, 셋 중 둘은 엉뚱한 곳을 가리킨다. 도메인 규칙 1(확정 표현
금지)이 예측에 요구하는 것과 같은 성격이다 — **근거를 보여줄 수 없으면 보여주지 않는 편이 낫다.**

**대체 신호가 이미 계약에 있고 저장도 된다.** `validation.needsReview` 로 정렬하고
`fieldConfidence` 가 낮은 필드를 강조하면 "먼저 볼 곳"이라는 목적은 달성된다. 둘 다
`header_data` 에 들어와 있어 **백엔드 추가 작업이 0** 이다.

⚠ **다만 `fieldConfidence` 를 게이트로 쓰지 않는다**(③과 같은 이유). 강조는 눈길을 끄는 것이고
게이트는 "여기만 보면 된다"는 뜻인데, 후자는 성립하지 않는다 — 임계값 0.7 이 정밀도 23%,
0.85 가 25% 인데 그 데이터의 기저 오류율이 16.7% 다.

**되돌리는 비용이 비대칭이다.** 지금 「필드 강조」로 가고 나중에 `OCR_PIPELINE` 공급자를 붙이면
하이라이트를 **얹으면** 된다(컬럼·계약 필드가 이미 있다). 반대로 지금 하이라이트를 만들면
좌표가 없는 동안 **빈 화면을 그리거나 틀린 위치를 그린다.**

**남는 것 — 원본 이미지는 보여줘야 한다.** 좌표 없이도 나란히 놓는 것은 되고, 그러려면
13.5 다운로드가 필요하다. 지금 13.1 응답에 `fileUrl` 이 없는 이유이기도 하다(구현현황 3.17).
⑥ 이 어느 쪽으로 가도 **13.5 는 필요하다.**

**⑧ 은 키 형식만 채택하고 퍼미션은 인프라에 넘긴다.**

- ⑧-1 키 형식 — 제안대로 `evidences/{businessId}/{evidenceId}.{ext}` ·
  `product-sales/{businessId}/{jobId}-{n}.{ext}`. 사업장으로 한 단계 나누는 편이 운영 중에
  찾기 쉽고 사업장 단위 용량 산정이 된다. 업로드 엔드포인트를 쓸 때 이대로 고정한다.
- ⑧-2 퍼미션 — **인프라가 default ACL 로 해결했다** *(회신 2026-09-10, 닫힘)*.
  **앱은 퍼미션을 설정하지 않는다** — `Files.copy` 를 그대로 쓰고 `PosixFilePermission` 을
  붙이지 않는다. 앱이 직접 정하면 ACL 이 준 기본값을 덮어써 워커(uid 10001, `:ro`)가 못 읽고,
  `PosixFilePermission` 은 POSIX 전용이라 Windows 로컬 개발에서 즉시 터진다.
  이 금지를 `EvidenceStorage.write` javadoc 에도 적었다 — **증상이 배포 live 첫 실행에서만
  나타나므로**(로컬은 같은 사용자, stub 은 파일 미열람) 그때 여기에 퍼미션 코드를 넣는 것이
  자연스러워 보이는데 그게 틀린 답이다.

### 남은 작업 (합의 문서 "승인 후 순서" 기준)

1번(`V6`)·3번(영속화)이 끝났고 13.1 업로드도 붙였다. 2번(stub 1회 통과)은 **워커 자리를 백엔드가
대신해** 업로드 → 파일 → Job → 콜백 → 저장까지 확인했다 — `EvidenceExtractionHandler` 가 워커를
부르는 요청 한 칸만 남았고 AI 2번에게 넘겼다. 4번(검토 화면)은 프론트 몫이고 ⑥ 결정에 달렸다.

## ① 헤더 확장 필드와 `validation` 의 저장 위치

**결정할 것.** 워커는 v1.10부터 `taxableAmount`(과세물품) · `taxFreeAmount`(면세물품) ·
`discountAmount`(할인 총액) 를 더 보낸다. ERD의 `EVIDENCE_EXTRACTION.header_data` 는 `JSONB` 라
컬럼 추가 없이 들어간다.

**권고.**

1. 워커 콜백의 `data` 를 **가공하지 않고** `header_data` 에 넣는다. 필드가 늘어도 마이그레이션이 없다.
2. `core.evidence.issued_on`(이미 있는 `DATE` 컬럼)은 `issuedDate` 로 채운다 — 증빙함 기간 필터
   (13.2 `from`/`to`)가 JSONB 를 뒤지지 않게 한다.
3. 목록 정렬·필터에 금액이 필요해지면 그때 `header_data->>'totalAmount'` 표현식 인덱스를 만든다.
   지금 컬럼으로 승격하지 않는다.

**13.2 응답 노출.** 현재 13.2 예시에는 `supplierName`·`supplierBusinessNo`·`issuedDate`·
`totalAmount`·`vatAmount`·`items[]`·`fieldConfidence` 만 있다. 검토 화면에 필요한 만큼만 늘리자는
쪽을 권한다 — **`discountAmount` 와 `validation`(`needsReview`·`reviewReasons`) 추가**. 과세·면세
금액은 화면이 쓰지 않으므로 `header_data` 에만 두고 응답에서는 뺀다.

**주의 (라벨·용어 함정).** `totalAmount` 는 **최종 결제 금액**이다. 한국 영수증에는 할인 전
`총합계` 가 따로 인쇄되는 경우가 많고(`총합계 − 할인 = 결제금액`), KORIE 공개 라벨의 `Total` 이
바로 그 할인 전 값이어서 실측 초기에 정확도가 93.5%로 잘못 측정됐다. 저장·표시·거래 매칭에 쓰는
값은 전부 `totalAmount`(결제금액)로 통일하고, 할인 전 값은 `discountAmount` 로 역산한다.

## ② `EVIDENCE_ITEM` 에 `amount`·`discount_amount` — 선택이 아니다

**현재 ERD.** 품목 금액 컬럼이 `supply_amount`(공급가액)·`vat_amount`(부가세) 두 개뿐이다.
세금계산서 서식을 기준으로 잡힌 것으로 보인다.

**문제 1 — 명세 13.2·13.3 자체가 저장할 곳 없는 필드를 주고받는다.** 워커 계약과 무관하게,
13.2 응답과 13.3 수정 요청 모두 `items[].amount` 를 쓴다. 지금 스키마로는 그 값을 넣을 컬럼이 없다.

**문제 2 — 에누리는 갈 컬럼이 아예 없다.** 워커는 행 아래 인쇄된 에누리·행사할인을
`items[].discountAmount`(양수)로 보낸다. 대응 컬럼이 없다.

**`supply_amount` 로 대신 쓸 수 없는 이유.** 소매 영수증은 **행마다 공급가액·부가세를 인쇄하지
않는다.** 부가세는 합계 구역에 한 번만 나온다(`과세물품 + 부가세 + 면세물품 = 결제금액`). 행 금액에서
역산(`amount / 1.1`)하려면 그 행이 과세인지 면세인지 알아야 하는데 영수증에 행별 표시가 없고,
**KORIE val 50장 중 26장이 면세 줄을 가진 혼합 영수증**이었다. 역산은 그 26장에서 틀린다. 또한
우리 원칙은 "인쇄된 값만 저장하고 계산은 검산에만 쓴다" 다 — 파생값을 저장하면 서버가 나중에
`Σ(amount − discountAmount) ≒ totalAmount` 검산을 다시 돌릴 수 없다.

**권고.**

| 컬럼 | 처리 | 이유 |
| --- | --- | --- |
| `amount NUMERIC` Optional | **추가** | 인쇄된 행 금액(할인 전). 13.2·13.3 이 이미 쓰는 필드 |
| `discount_amount NUMERIC` Optional | **추가** | 행 에누리(양수). 순액은 `amount − COALESCE(discount_amount, 0)` |
| `supply_amount`·`vat_amount` | **남긴다** (당장은 NULL) | 세금계산서·거래명세서는 행별 공급가액·세액이 인쇄된다. OCR 공급자를 붙여 그 값을 뽑게 되면 채운다 |

**순액 계산은 백엔드가 한다.** 워커는 인쇄값만 넘긴다. 그리고 **할인을 음수 품목 행으로 만들지
않는다** — 음수 행이 품목으로 섞이면 단가·품목 통계(P1-03 품목 가계부, 13.6)가 왜곡된다.

**측정 근거.** test 359장에서 품목 금액 정확도 97.3%, 품목 합 검산 일치 99.1%. 이 두 수치는
`amount` 와 `discountAmount` 를 따로 받는 구조에서 나온 것이다.

## ③ `needsReview` — 상태가 아니라 정렬·강조 신호

**결정할 것.** `ck_evidence_status` 에 `REVIEW` 를 추가할 것인가. **권고: 추가하지 않는다.**

명세 13.2의 `ocrStatus` 는 `QUEUED → PROCESSING → EXTRACTED(사용자 확인 대기) → CONFIRMED` 이고,
**모든 추출이 이미 `EXTRACTED` 에서 사람의 확인을 기다린다.** 즉 `needsReview` 가 "사람이 보는지"를
가르지 않는다. 가르는 것은 **무엇을 먼저 보여줄지** 다.

**근거 (test 359장, 2026-09-08).**

| | 검토율 | 검토 대상 중 실제 오류(정밀도) |
| --- | ---: | ---: |
| 결정적 검사만 (채택) | 13.9% | 18% |
| + 모델 신뢰도 0.7 | 23.4% | 23% |
| + 모델 신뢰도 0.85 | 42.1% | 25% |

이 데이터의 오류율 자체가 **16.7%** 라, 무작위로 찍어도 정밀도가 16.7%다. 어느 임계값도 이를
의미 있게 넘지 못한다. 게이트를 "여기만 보면 된다"는 뜻으로 쓰면 위험하다는 근거가 하나 더 있다 —
**회계에 영향을 주는 오류 6건(날짜 3 · 합계 3)을 결정적 검사는 0/6 잡는다.** 그럴듯한 오답 날짜는
범위 검사를 통과하고, 서로 맞아떨어지는 숫자를 잘못 읽으면 검산도 통과한다.

**그래서 역할을 나눴다** (계약 20.4 v1.13):

- `validation.needsReview` = "인쇄된 숫자들이 서로 모순된다" → 검토 화면 **정렬 상단**
- `fieldConfidence` = 필드별 자기 신뢰도 → 검토 화면 **필드 강조**

**저장.** `validation` 은 `header_data` 안에(①과 동일). 별도 컬럼·별도 상태 없음.

> *(v1.14·v1.15 추가)* `validation` 에 `vatRatioConsistent`·`itemsAligned` 와 사유 `VAT_RATIO_INCONSISTENT`·`ITEM_ROWS_MISALIGNED` 가 늘었다. `header_data` 가 JSONB 라 **스키마 영향은 없다** — ① 의 "워커 `data` 를 그대로 넣는다" 원칙을 지키면 앞으로 검사가 더 늘어도 마이그레이션이 없다. 이 검사는 금액 칸이 밀린 것을 잡는데, 합계 검산으로는 원리적으로 불가능하다(덧셈은 순열을 못 본다).

## ④ `matchedBy` 집계

**배경.** 20.5 품목 정규화는 **동기** 엔드포인트라 워커가 아무것도 저장하지 않는다. 매핑에
`matchedBy`(`RULE`/`SIMILARITY`/`LLM`/`null`)를 붙인 것은 기술스택 §6.5의 **"규칙이 90% 이상을
처리한다"** 를 실제로 셀 수 있게 하기 위해서다. 세는 주체는 백엔드다.

**권고.** `EVIDENCE_ITEM.matched_by VARCHAR(12)` 추가. 테이블이 아직 없으니 비용이 0이고,
`item_id` 와 나란히 두면 "이 매핑을 누가 확정했나"가 행에 남는다.

**대안(로그 집계)을 권하지 않는 이유.** 명세 20.1에 따라 품목명은 로그에 남기지 않으므로 로그로는
비율만 세게 되는데, 재집계·검증이 불가능하고 발표 수치로 쓰기 어렵다.

| ③ | **하이라이트를 빼고 필드 강조로 간다** | 0 | 아래 제안 |

**`fieldConfidence` 가 낮은 필드를 강조**한다. 원본 이미지는 나란히 보여주되 좌표 하이라이트는 하지
않는다." `boundingBox` 는 스키마에 그대로 두고(OCR 공급자를 붙이면 채워진다) 값은 `null` 로 나간다.

근거는 셋이다. ① 좌표가 부정확하면 사용자를 잘못된 곳으로 유도한다. ② 13.2 의 모든 추출은 어차피
`EXTRACTED`(사용자 확인 대기)를 거치므로 사람이 전체를 한 번 본다 — 하이라이트는 "먼저 볼 곳"을
알려주는 편의이고, 그 역할은 필드 강조로도 된다. ③ 필드 강조에 쓸 신호는 이미 계약에 있다
(`fieldConfidence` 는 v1.9 부터, `needsReview`·`reviewReasons` 는 v1.10 부터).

**AI 파트가 혼자 정하지 않는다.** 완료 기준은 화면 설계·데모 범위와 묶여 있어 올린다. ①을 택하면
Azure 리소스와 키가 필요하고(월 500페이지 제약·다중 페이지 앞 2장만·요청 폭주 시 403), ②를 택하면

## ⑦ 사용자 수정 이력 — 실사용 정확도를 얻는 유일한 방법

**문제.** 지금 우리 정확도 수치는 전부 **KORIE(라벨 노이즈가 있다) + 합성**이다. 제가 보고한
상호명 91.3%·부가세 90.6% 는 "미달분이 라벨 노이즈다" 라고 해석했는데, 그 해석이 맞는지 확인할
방법이 레포 안에 없다. 신뢰도가 정말 변별력이 없는지도(test 에서는 무작위와 같았다) 실사용에서는
다를 수 있다.

**있는 것.** 13.3 `PATCH /evidences/{evidenceId}/extraction` 은 사용자가 고친 값을 받아
`confirmed: true` 면 `CONFIRMED` 로 넘긴다. **즉 사용자가 이미 라벨을 만들고 있다** — 지금은
그걸 버리고 최종 값만 남긴다.

**요청.** 확인 시점에 두 가지를 남겨 달라.

| 무엇 | 어디 | 왜 |
| --- | --- | --- |
| 확인 사실 (`confirmed_at`, `confirmed_by`) | `EVIDENCE_EXTRACTION` 컬럼 2개 | **정확도의 분모**. 이게 없으면 고친 것만 남아 모든 필드가 100% 틀린 것처럼 보인다 |
| 바뀐 필드 (`field`, `before`, `after`) | `EVIDENCE_CORRECTION` 새 테이블 | 정확도의 분자 |

**가장 중요한 점 — 수정이 없어도 확인은 기록해야 한다.** 고친 것만 모으면 분모가 없어서 정확도를
낼 수 없다. 이 조건은 워커 쪽 테스트로 못 박아 뒀다
(`tests/experiments/test_analyze_corrections.py::test_logging_only_corrections_makes_accuracy_meaningless`).

**추출 행을 지우지 말 것.** `is_current = false` 로 내린 이전 추출도 남겨야 한다 — 모델·프롬프트
버전과 `validation`·`fieldConfidence` 가 그 행의 `header_data` 에 있어서, 조인만으로 "그때 게이트가
이걸 지목했나" 를 알 수 있다. 별도로 복제할 필요가 없다.

**분석기는 이미 있다.** `ai/experiments/analyze_corrections.py` 가 JSONL 한 줄 = 검토 1건을 먹고
네 가지를 낸다. 로그가 없어도 `--simulate` 로 기존 측정에서 같은 모양을 만들어 출력을 볼 수 있다.

1. **필드별 실사용 정확도** = 1 − 수정률. KORIE 수치와 대조하면 라벨 노이즈 몫이 드러난다.
2. **게이트가 맞았나** — `needsReview` 의 실제 정밀도·재현율.
3. **신뢰도에 변별력이 있나** — 수정된 필드와 안 고친 필드의 평균 신뢰도.
4. **재추출이 실제로 고쳤나** — `extractionMode=THOROUGH` 의 수정률이 낮은가 (⑥·v1.17 과 연결).

내보낼 JSONL 한 줄:

```json
{"extractionId": 1, "evidenceId": 501, "modelName": "claude-sonnet-5",
 "promptVersion": "evidence-extraction/v4", "extractionMode": "STANDARD",
 "validation": {"needsReview": false, "reviewReasons": []},
 "fieldConfidence": {"totalAmount": 0.99},
 "corrections": [{"field": "totalAmount", "before": "156000", "after": "155000"}],
 "confirmedAt": "2026-09-08T05:00:00Z"}
```

`validation`·`fieldConfidence` 는 `header_data` 에서, 나머지는 조인으로 나온다. **새로 저장할 것은
확인 시각·확인자와 수정 행뿐이다.**

**개인정보.** `before`/`after` 에 상호명·품목명이 들어간다. 사용자 자신의 증빙 데이터이고 이미
`EVIDENCE_ITEM` 에 있는 값이라 저장 자체는 새로운 노출이 아니다. 다만 **분석용으로 내보낼 때는
사업장 밖으로 값을 들고 나가지 않는다** — 필드 이름과 "바뀌었나" 만으로도 위 네 가지가 다 나온다
(분석기는 `before`/`after` 값을 쓰지 않는다).

`/opt/jango-yebo/uploads:/data/uploads` 로, `jango-ai` 가 `./uploads:/data/uploads:ro` 로 같은
디렉터리를 공유한다 — `sync-infra.sh` 의 `APP=/opt/jango-yebo` 이라 두 표기가 같은 경로다
(`infra/README.md` 에도 적혀 있다). **볼륨 합의는 필요 없다.** 두 가지만 정하면 된다.

### ⑧-1 키 형식 — 백엔드가 정하고 워커는 그대로 읽는다

워커는 키를 해석하지 않는다. `STORAGE_ROOT` 아래 상대 경로로만 보고, 다음을 거절한다
(`app/ocr/storage.py`): 절대 경로, `..` 포함, 드라이브 문자(`C:`), 저장소 밖을 가리키는 것.
파일이 없으면 **202 를 주기 전에 `400`** 으로 끝낸다 — Job 이 `PROCESSING` 에 남지 않게.

**문제: 지금 정해진 규칙이 없다.** 워커 쪽 예시·테스트에도 두 형태가 섞여 있다
(`evidences/11/501.jpg` 와 `evidences/501.jpg`). ERD 의 `EVIDENCE.storage_key`(UK, NN)가 정본이니
백엔드가 정하는 것이 맞다.

**제안.** 사업장으로 한 단계 나누면 운영 중에 사람이 찾기 쉽고 사업장 단위 정리·용량 산정이 된다.

| 용도 | 키 | 비고 |
| --- | --- | --- |
| 증빙 (20.4) | `evidences/{businessId}/{evidenceId}.{ext}` | 증빙 1건 = 파일 1개 |
| 매출 인쇄물 (20.9) | `product-sales/{businessId}/{jobId}-{n}.{ext}` | 여러 장을 한 요청에 싣는다(최대 10). `n` 은 1부터 |

`ext` 는 업로드된 원본 확장자(`jpg`·`png`). 워커는 확장자로 형식을 판단하지 않고 바이트를 읽는다.
키에 사용자 입력(원본 파일명)을 그대로 넣지 않기를 권한다 — 한글·공백·경로 문자가 섞이면
`storage_key` UK 와 URL 인코딩에서 번거로워진다. 원본 파일명은
`EVIDENCE.original_filename` 에 따로 있다.

### ⑧-2 파일 권한 — 워커 uid 10001 이 읽을 수 있어야 한다

`compose.yml` 주석에만 있고 합의 문서에는 없던 항목이다. 워커 컨테이너는 **uid 10001(worker)**
로 돌고 볼륨을 `:ro` 로 붙인다. **API 서버가 파일을 자기만 읽을 수 있게 쓰면(0600) 워커는 못
읽고 모든 추출이 `400` 이 된다.** 컨테이너가 다르니 uid 도 다르다.

정해야 할 것: 업로드 파일의 퍼미션(예: `0644`) 또는 두 컨테이너가 공유하는 gid. 파일이 아니라
디렉터리 권한도 필요하다(`0755`) — 워커가 경로를 훑어야 한다.

이건 **조용히 실패하는 종류**다. 로컬 개발(같은 사용자로 둘 다 실행)에서는 안 보이고 배포에서만
터진다. ②번 작업(stub 연동)은 파일을 읽지 않으므로 여기서도 안 걸린다 — **live 모드 첫 실행에서
처음 드러난다.**

### ⑧-3 정리 정책 (지금 정하지 않아도 되지만 남겨 둔다)

`uploads/` 는 계속 커진다. 증빙 원본은 사용자가 다시 보는 자료이니 함부로 지울 수 없고, 매출
인쇄물은 추출이 끝나면 원본을 둘 이유가 약하다. 용량 한계가 보일 때 다시 꺼낼 항목이다.

## 부록 A. `CREATE TABLE` 초안 (백엔드 소유 — 참고용)

**이 SQL을 마이그레이션 파일로 만들지 않았다.** `db/migration/` 은 백엔드 소유이고 다음 버전 번호
도 백엔드가 정할 몫이다 — **작성 시점의 다음 번호를 쓴다**(2026-09-09 현재 V1~V5 가 있으므로
V6). 위 결정이 승인되면 아래를 옮겨 쓰면 된다. `V1__p0_baseline.sql` 의
스타일(스키마 `core`, `GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMPTZ`, `fk_`/`ck_`/`uk_`/`ix_`
접두사)에 맞췄다.

```sql
CREATE TABLE core.evidence_extraction (
    id             BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    evidence_id    BIGINT      NOT NULL,
    model_name     VARCHAR(100) NOT NULL,
    model_version  VARCHAR(100),                      -- ⑤ 워커는 항상 null 을 보낸다
    prompt_version VARCHAR(100),                      -- ⑤ 재현성의 실제 키
    pipeline       VARCHAR(20) NOT NULL,
    status         VARCHAR(20) NOT NULL,
    header_data    JSONB,                             -- ① 워커 data 를 그대로. validation 포함
    confidence     NUMERIC(4, 3),
    is_current     BOOLEAN     NOT NULL DEFAULT true,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT fk_extraction_evidence FOREIGN KEY (evidence_id) REFERENCES core.evidence (id),
    -- ⑤ STUB 은 연동 검증용(명세 20.2 v1.9). 빠뜨리면 stub 모드 INSERT 가 깨진다
    CONSTRAINT ck_extraction_pipeline CHECK (pipeline IN ('OCR_PIPELINE', 'VLM', 'STUB')),
    CONSTRAINT ck_extraction_status   CHECK (status IN ('COMPLETED', 'PARTIAL'))
);

-- ERD 규정: 증빙당 현재 결과는 하나
CREATE UNIQUE INDEX uk_extraction_current ON core.evidence_extraction (evidence_id)
    WHERE is_current = true;

CREATE TABLE core.evidence_item (
    id                 BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    extraction_id      BIGINT       NOT NULL,
    item_id            BIGINT,
    raw_name           VARCHAR(255) NOT NULL,
    quantity           NUMERIC(14, 3),
    unit               VARCHAR(20),
    unit_price         NUMERIC(14, 2),
    amount             NUMERIC(14, 2),   -- ② 인쇄된 행 금액(할인 전). 13.2·13.3 이 쓰는 필드
    discount_amount    NUMERIC(14, 2),   -- ② 행 에누리(양수). 순액 = amount - COALESCE(이것, 0)
    supply_amount      NUMERIC(14, 2),   -- ② 세금계산서·거래명세서용. 소매 영수증에서는 NULL
    vat_amount         NUMERIC(14, 2),   -- ② 같음
    matched_by         VARCHAR(12),      -- ④ RULE / SIMILARITY / LLM. 미매칭은 NULL
    source_coordinates JSONB,            -- boundingBox. VLM 경로에서는 NULL (아래 참고)
    CONSTRAINT fk_evidence_item_extraction FOREIGN KEY (extraction_id)
        REFERENCES core.evidence_extraction (id) ON DELETE CASCADE,
    CONSTRAINT fk_evidence_item_item FOREIGN KEY (item_id) REFERENCES core.item (id),
    CONSTRAINT ck_evidence_item_matched_by
        CHECK (matched_by IS NULL OR matched_by IN ('RULE', 'SIMILARITY', 'LLM')),
    CONSTRAINT ck_evidence_item_discount CHECK (discount_amount IS NULL OR discount_amount >= 0)
);

CREATE INDEX ix_evidence_item_extraction ON core.evidence_item (extraction_id);
```

⑦ 수정 이력 — `EVIDENCE_EXTRACTION` 에 컬럼 둘을 더하고 테이블 하나를 만든다.

```sql
ALTER TABLE core.evidence_extraction
    ADD COLUMN confirmed_at TIMESTAMPTZ,   -- ⑦ 정확도의 분모. 수정이 없어도 채운다
    ADD COLUMN confirmed_by BIGINT REFERENCES core.users (id);

CREATE TABLE core.evidence_correction (
    id            BIGINT       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    extraction_id BIGINT       NOT NULL,
    field         VARCHAR(100) NOT NULL,  -- 계약 필드 키. 품목은 `items[3].amount`
    before_value  TEXT,                   -- 모델이 낸 값 (null 이면 모델이 못 읽음)
    after_value   TEXT,                   -- 사용자가 넣은 값 (null 이면 사용자가 지움)
    corrected_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT fk_correction_extraction FOREIGN KEY (extraction_id)
        REFERENCES core.evidence_extraction (id) ON DELETE CASCADE,
    -- 안 바뀐 것을 넣으면 분자가 부풀어 정확도가 낮게 나온다
    CONSTRAINT ck_correction_changed CHECK (before_value IS DISTINCT FROM after_value)
);

CREATE INDEX ix_correction_extraction ON core.evidence_correction (extraction_id);
```

> `core.item` 테이블도 아직 없다(ERD `ITEM`). `fk_evidence_item_item` 은 그 테이블이 생긴 뒤에
> 넣어야 한다 — 순서상 `ITEM` → `EVIDENCE_EXTRACTION` → `EVIDENCE_ITEM` 이다.

> **`boundingBox` 는 지금 비어 온다.** VLM은 좌표를 신뢰성 있게 내지 못해 의도적으로 뺐고,
> `STUB` 만 채운다. `OCR_PIPELINE` 공급자(Azure `prebuilt-receipt` 등)를 붙이면 실제 값이 들어온다.
> 검토 화면의 원본 하이라이트(13.2 문구)는 그때까지 동작하지 않는다 — 화면 설계에서 감안해야 한다.

## 부록 C. 필드 → 컬럼 매핑표

| 콜백 `data` 필드 | 저장 위치 | 비고 |
| --- | --- | --- |
| `status` | `evidence_extraction.status` | `COMPLETED` / `PARTIAL` |
| `modelName` | `evidence_extraction.model_name` | 실제로 응답한 모델 (티어링·폴백 시 그 모델) |

## 승인 후 순서

0. **팀** — ⑥(완료 기준) 판단. ③이면 추가 작업이 없고, ①·②면 좌표 공급자 작업이 붙는다.
0b. **백엔드** — ⑦ 수정 이력. 같은 마이그레이션에 함께 넣으면 나중에 `ALTER` 가 없다.
0c. **백엔드** — ⑧ 키 형식 확정(업로드 엔드포인트를 쓸 때) + 업로드 파일 퍼미션.
1. **백엔드** — ①~⑤ + ⑦ 반영해 마이그레이션 작성 (부록 A, 다음 번호는 V6). `ITEM` 이 먼저다.
2. **합동** — stub 모드로 업로드 → Job → 콜백 → 저장까지 1회 통과 (부록 B 픽스처).
3. **백엔드** — `AiResultApplier` 가 `JOB.result` 저장에서 멈추지 않고 위 두 테이블로 영속화.
   현재는 결과를 `JOB.result` JSON 에 통째로 넣고 Job 만 완료 처리한다.
4. **프론트** — 검토 화면. `needsReview` 로 정렬, `fieldConfidence` 로 필드 강조. **하이라이트는 ⑥ 결정에 달렸다** — ③이면 만들지 않는다.
