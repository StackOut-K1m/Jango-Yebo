## 7. 사업장과 계좌·거래 수집

### 7.1 사업장

`GET /businesses`

```json
{
  "success": true,
  "data": {
    "items": [
      {
        "businessId": 11,
        "name": "카페 한잔",
        "industryType": "FOOD_CAFE",
        "region": "광주 서구",
        "taxationType": "GENERAL",
        "openedAt": "2023-04-01",
        "accountCount": 2,
        "currentRiskLevel": "CAUTION"
      }
    ]
  }
}
```

`POST /businesses`

```json
{
  "name": "카페 한잔",
  "businessRegNo": "123-45-67890",
  "industryType": "FOOD_CAFE",
  "region": "광주 서구",
  "taxationType": "GENERAL",
  "openedAt": "2023-04-01",
  "annualRevenue": 88000000,
  "employeeCount": 2
}
```

- `industryType`: `FOOD_CAFE`, `FOOD_RESTAURANT`, `FOOD_BAKERY`, `FOOD_OTHER`, `RETAIL`, `SERVICE`, `OTHER` (요식업 우선, 이후 확장)
- `taxationType`: `GENERAL`(일반과세), `SIMPLIFIED`(간이과세) — 부가세 예수금(P1-11)과 세금 일정 계산에 사용한다.
- `annualRevenue`, `region`, `openedAt`, `employeeCount`는 지원 제도 매칭(P1-15)의 프로필 필터로 사용한다.
- ⚠ **예시의 8,800만원을 1억 이상으로 올리지 않는다** *(2026-09-09 정정, 이전 값 1.8억)*. 음식점업은 직전연도 수입금액 1억 5천만 이상이면 복식부기 의무라 P0-12 신고서 초안의 v1 대상 서식(간편장부소득금액계산서 · 총수입금액 및 필요경비명세서)과 어긋난다. 시연 데이터(`scripts/seed.mjs`)도 같은 값으로 맞춰져 있다.
- `PATCH /businesses/{businessId}`는 위 필드 전체를 부분 수정한다.

### 7.2 계좌 연결과 1원 인증

은행 목록: `GET /bank-codes` — 계좌 등록 화면용 공용 목록 `[{ "bankCode": "088", "bankName": "신한은행" }]`을 반환한다(금융망 은행코드 조회 동기화, 인증 불필요).

`POST /businesses/{businessId}/accounts`

```json
{
  "bankCode": "088",
  "accountNo": "110-123-456789",
  "alias": "주거래 사업용",
  "isPrimary": true
}
```

```json
{
  "success": true,
  "data": {
    "accountId": 21,
    "bankCode": "088",
    "bankName": "신한은행",
    "accountNoMasked": "110-***-***789",
    "alias": "주거래 사업용",
    "isPrimary": true,
    "status": "PENDING_VERIFICATION",
    "balance": null,
    "balanceUpdatedAt": null,
    "lastSyncedAt": null,
    "syncStatus": "NEVER"
  }
}
```

- `alias`는 **필수**다(1~100자). 다계좌를 화면에서 구분하는 유일한 이름이라 비워 둘 수 없다. 누락·공백이면 `400 VALIDATION_FAILED`이며 `detail.alias`에 사유가 담긴다.
- 등록 시 금융망으로 계좌 존재를 확인한 뒤 해당 계좌로 1원 인증 송금을 발송한다(통장 적요에 "서비스명 + 인증코드 4자리" 표기).
- **계좌번호를 금융망이 인정하지 않으면 `400 ACCOUNT_NO_INVALID`** 이다(v1.9). 존재하지 않는 계좌·형식 오류·**타인 계좌**가 모두 여기 해당하며 서로 구분되지 않는다 — 구분해 알려주면 계좌 존재 여부가 새어 나가기 때문이다. 그 밖의 금융망 호출 실패는 `502 FIN_API_FAILED`를 반환한다.
- 계좌 `status`: `PENDING_VERIFICATION`(인증 대기) → `CONNECTED`(인증 완료), 인증 시간이 지나면 `VERIFICATION_EXPIRED`. 인증 완료 전 계좌는 동기화·예측 대상에서 제외한다.
- **`syncStatus` 는 `NEVER`·`RUNNING`·`SUCCESS`·`FAILED` 넷이다** *(v1.9에서 명시)*. `status` 와 독립된 축이며 `CONNECTED` 가 된 뒤에야 움직인다. 값을 열거한 적이 없어 한 번 어긋났다 — 프론트가 `SYNCING`·`SYNCED` 로 추측했고 DB CHECK 는 `RUNNING`·`SUCCESS` 였다.
- **이미 등록된 계좌번호로 다시 등록하면 세 갈래로 갈린다** *(v1.17 신규 — 이전에는 전부 `409` 였다)*. 계좌번호 해시는 전역 유일이라 어느 사업장·어느 사용자의 것이든 한 행뿐이며, 그 행의 정체에 따라 응답이 다르다.

  | 그 행의 정체 | 응답 |
  |---|---|
  | 같은 사업장의 `DISCONNECTED` · `VERIFICATION_EXPIRED` 행 | **되살린다** — `201` + `PENDING_VERIFICATION`, 1원 재발송 |
  | 같은 사업장의 `CONNECTED` · `PENDING_VERIFICATION` 행 | `409 ACCOUNT_ALREADY_LINKED` |
  | 같은 사용자의 **다른 사업장** 행 | `409 ACCOUNT_ALREADY_LINKED` |
  | **다른 사용자**의 행 | `400 ACCOUNT_NO_INVALID` |

  마지막 줄이 `409`가 아닌 이유는 위의 타인 계좌 규칙과 같다 — "누군가 이 계좌를 등록해 두었다"를 알려주면 계좌 존재 여부가 새어 나간다.

- **되살리기는 행을 그대로 쓴다.** `accountId`가 바뀌지 않으므로 그 계좌에 매달린 거래 이력이 이어진다. 요청에 담아 보낸 `bankCode`·`alias`·`isPrimary`가 **기존 값을 덮어쓴다** — 사용자가 다시 채워 보낸 값이 최신 의사다. `lastSyncedAt`·`syncStatus`는 유지하고(거래가 그대로 있으니 "언제까지 맞는 데이터인가"가 여전히 참이다) `balance`·`balanceUpdatedAt`은 `null`로 되돌린다(시점 값이라 지금도 맞다고 말할 수 없고, 인증이 끝나면 자동 동기화가 다시 채운다).

- `PENDING_VERIFICATION` 계좌를 다시 등록하는 것은 되살리기가 아니라 `409`다. 1원이 이미 나가 있어 재발송(`POST /accounts/{accountId}/verification`)이 맡을 몫이고, **재발송 상한은 그쪽에만 있다** — 이쪽으로 열면 상한 없이 금융망을 두드릴 수 있다.
- 계좌번호 원문은 저장 시 암호화하고 응답에는 항상 마스킹해 반환한다.
- `DELETE /accounts/{accountId}`는 연동을 해제한다(`204`). 이미 수집된 거래는 보존하되 이후 동기화 대상에서 제외한다. **해제는 되돌릴 수 있다** — 같은 계좌번호로 다시 등록하면 위의 되살리기가 일어난다. 화면은 "다시 연결하려면 1원 인증을 새로 받는다"로 안내한다.
- **해제하면 `balance`·`balanceUpdatedAt`을 `null`로 되돌린다** *(v1.25)*. 되살리기와 같은 이유다 — 시점 값이라 지금도 맞다고 말할 수 없고, 해제 뒤로는 동기화가 돌지 않아 이 값만 영원히 낡는다. 남겨 두면 **연동을 끊은 계좌의 돈이 화면 총잔액에 계속 섞인다**(실제로 그랬다). 마지막 잔액은 거래의 `balance_after`에 남아 있어 되살릴 때 시작 잔액을 메울 수 있다.
- **해제는 예측 재계산을 건다** *(v1.25)*. 거래는 안 바뀌어도 곡선이 세는 집합이 바뀐다 — 걸지 않으면 저장된 곡선이 해제한 계좌의 잔액이 들어간 `currentBalance` 를 04:00 배치까지 계속 내려준다(공통규약 2.6 실행 트리거). 화면은 해제 직후 잠깐 `409 FORECAST_NOT_READY` 를 받을 수 있다 — 오류가 아니라 재계산 대기다.
- **보존은 「합계에 기여한다」는 뜻이 아니다.** 해제된 계좌는 총잔액·예측 곡선·정산 공백에서 빠지고(`AccountBalancesService`는 `CONNECTED`만 센다), 거래 목록에서도 기본으로 빠진다(8.2 `includeDisconnected`). 이력을 보려면 명시로 물어야 한다 — 세무 쪽도 같은 기본값을 쓴다(8.2 주석).

계좌 삭제:

`POST /accounts/{accountId}/purge`

```json
{ "confirm": "주거래", "purgeOrphanEvidence": false }
```

```json
{
  "success": true,
  "data": {
    "transactions": 412,
    "evidenceLinks": 37,
    "evidenceMarkedDeleted": 0,
    "settlementAllocations": 8,
    "settlementsRefreshed": 3
  }
}
```

- **해제와 다른 문이다** *(v1.26)*. 해제(`DELETE`)는 계좌 행을 남기고 거래를 보존하지만, 이쪽은 **계좌와 그 계좌의 거래·분류 이력·예정 거래·반복 패턴을 실제로 지운다. 되돌릴 수 없다.** 잘못 등록한 계좌나 시연 준비로 갈아엎는 계좌를 치울 방법이 해제뿐이었고, 해제된 계좌는 목록에 영구히 남는다.
- **같은 `DELETE`에 플래그로 얹지 않았다.** 앱은 웹보다 늦게 배포된다 — 메서드의 뜻을 바꾸면 구버전 앱이 「해제」하려고 부른 호출이 서버에서 하드 삭제가 된다. 되돌릴 수 없는 쪽으로 어긋나는 것이 최악이라 경로를 갈랐다. `200` 인 것도 이유가 있다: `204`로 두면 무엇이 얼마나 지워졌는지 돌려줄 자리가 없다.
- **`confirm`은 계좌 별칭(`alias`)이다.** 계좌번호를 묻지 않는 이유는 화면에 마스킹밖에 없고 그 마스킹이 **앞뒤 3자리씩만** 남기기 때문이다(`110-***-***789`) — 「뒤 몇 자리」가 무엇인지 사용자가 알 수 없다. 앞뒤 공백은 흘린다. 틀리면 `400 VALIDATION_FAILED`이고 **아무것도 지워지지 않는다**.
- **증빙은 지우지 않는다.** 끊는 것은 `TRANSACTION_EVIDENCE` 연결뿐이고 증빙 행·파일·추출·보정 이력은 남는다. 증빙 ↔ 거래는 N:M이라(ERD §658) 한 증빙이 **다른 계좌** 거래에도 붙어 있을 수 있어, 지우면 살아 있는 계좌의 근거가 사라진다. `purgeOrphanEvidence: true`는 *이 계좌 거래에만* 붙어 있던 증빙을 소프트 삭제(`deleted_at`)로 표시할 뿐이며, 다른 거래에 연결이 하나라도 있으면 켜도 남는다.
- **대출과 상환 회차는 남고 연결만 끊긴다.** 계좌가 사라져도 빚은 남는다 — 지우면 상환 예정 거래까지 없어져 **곡선에서 나갈 돈이 빠지고** 없는 여유를 있다고 보여준다. `LOAN.withdrawal_account_id`와 `LOAN_REPAYMENT.transaction_id`가 `null`이 되며 회차의 `status`는 그대로다(이미 갚은 것을 미납으로 되돌리지 않는다).
- **배분을 전부 잃은 정산은 `PENDING`으로 돌아간다.** `SETTLEMENT`는 사업장 것이라 남는데, 그대로 두면 `MATCHED`인데 매칭이 하나도 없는 대사가 생긴다. 불일치 알림도 함께 내린다(14.1).
- **예측 재계산을 건다.** 해제와 달리 거래가 실제로 사라졌으므로 곡선이 세는 값 자체가 바뀐다. 직후 잠깐 `409 FORECAST_NOT_READY`를 받을 수 있다 — 오류가 아니라 재계산 대기다.
- **계좌번호 해시가 풀린다.** `uk_account_number`가 비므로 같은 계좌번호를 다시 등록하면 되살리기가 아니라 **새 계좌**가 만들어진다(새 `accountId`). 해제와 갈리는 지점이다.
- **`CONNECTED` 계좌는 지울 수 없다 — `409 ACCOUNT_STATE_CONFLICT`.** 연동을 먼저 해제해야 한다. 친절이 아니라 **경합을 닫는 장치다**: 자동 반영 워커가 `auto_execute_planned = true AND status = 'CONNECTED'`로 계좌를 고르므로(9.6), 연결된 채로 지우는 동안 워커가 **금융망에 실제로 출금을 보낼 수 있다.** 우리 트랜잭션이 되감겨도 나간 돈은 돌아오지 않는다. 해제가 `auto_execute_planned`를 함께 끄므로 해제를 앞 단계로 두면 그 창이 구조적으로 닫힌다. 화면에서만 막으면 API 를 직접 부르는 쪽에는 창이 그대로 열려 있다.
  - **`DISCONNECTED`로 좁히지는 않는다.** 인증 대기(`PENDING_VERIFICATION`)·만료(`VERIFICATION_EXPIRED`) 계좌는 동기화도 자동 반영도 대상이 아니라(둘 다 `CONNECTED`를 요구한다) 막을 이유가 없다. 계좌번호를 잘못 쳐서 인증 대기에 걸린 계좌에까지 해제를 먼저 시키면 **연결된 적 없는 계좌의 연결을 끊으라는 말**이 된다.
  - 동기화 Job 은 막지 않아도 안전하다. 계좌가 사라지면 `ACCOUNT_NOT_FOUND`로 끝나고, 구간별 INSERT 는 외래키에 막혀 되감기므로 고아 거래가 남지 않는다.
- 남의 계좌는 `404 ACCOUNT_NOT_FOUND`다.

인증코드 검증:

`POST /accounts/{accountId}/verify`

```json
{
  "authCode": "8212"
}
```

- 사용자가 통장 입금 내역에서 확인한 4자리 인증코드를 검증한다. 성공 시 `status = CONNECTED`로 바뀌고 잔액 조회와 최초 거래 동기화가 자동 실행되며, 변경된 계좌를 반환한다.
- 인증코드 불일치는 `400 ACCOUNT_AUTH_CODE_MISMATCH`, 인증 시간 만료·발급 기록 없음은 `409 ACCOUNT_AUTH_EXPIRED`를 반환한다.
- 재발송: `POST /accounts/{accountId}/verification` — 새 인증코드로 1원 송금을 다시 발송하고 `status`를 `PENDING_VERIFICATION`으로 되돌린다.
- **재발송은 인증 대기·만료 계좌만 받는다** *(v1.17 명시)*. 인증이 끝난 계좌는 `409 ACCOUNT_ALREADY_LINKED`, **해제된 계좌는 `409 ACCOUNT_STATE_CONFLICT`** 이며 후자는 계좌를 다시 등록해 되살리는 것이 답이다 — 되살리는 문을 하나로 두어야 새로 입력한 `bankCode`·`alias`가 반영된다.

#### 예정 거래 자동 반영 on/off *(v1.19 신규)*

`PATCH /accounts/{accountId}/planned-execution`

```json
{ "enabled": true }
```

- 켜면 **서버가 예정일마다 이 계좌에서 실제로 출금·입금한다**(9.6). 시연 데이터가 날짜를 넘겨도 스스로 움직이게 하려는 장치이며, 대상은 우리가 만든 싸피은행 계좌다.
- **기본값은 `false` 이고 화면에 노출하지 않는다.** 켜는 주체는 시드 도구와 계좌 소유자뿐이다 — 실사용자 계좌에 켜면 자동 실행 금지 원칙(공통규약 23장)을 어긴다.
- 인증 전 계좌는 `409 ACCOUNT_NOT_VERIFIED`. **연동을 해제하거나 다시 연결하면 함께 꺼진다.**
- 응답은 계좌 객체이며 `autoExecutePlanned` 필드가 함께 나간다(7.2 목록·등록 응답도 같다).

### 7.3 금융망 거래 동기화

`POST /accounts/{accountId}/sync`

마지막 동기화 시점 이후의 거래를 SSAFY 금융망에서 가져와 저장한다.

```json
{
  "success": true,
  "data": {
    "jobId": 9002,
    "jobType": "ACCOUNT_SYNC",
    "status": "QUEUED",
    "lastSyncedAt": "2026-08-30T21:00:00Z"
  }
}
```

- `202 Accepted`. 완료 후 Job의 `resultRef`에 `{ "importedCount": 18, "duplicateCount": 0 }`을 담는다.
- 인증 완료(`CONNECTED`) 상태의 계좌만 동기화할 수 있다 (`409 ACCOUNT_NOT_VERIFIED`).
- 금융망 거래내역 조회의 거래고유번호(`transactionUniqueNo`)를 `finTransactionId`로 저장하고, 중복 판정 키는 `(계좌, finTransactionId)`를 사용한다. 금융망 조회에는 페이지네이션이 없으므로 서버가 조회 기간을 분할해 가져온다.
- 필드 매핑: 거래일자·시각(`YYYYMMDD`+`HHMMSS`, KST) → `occurredAt`(UTC), `transactionSummary`(적요) → `description`, `transactionAfterBalance` → `balanceAfter`, 이체 상대 계좌번호(`transactionAccountNo`) → `counterpartyAccountNo`.
- 동기화 완료 시 반복 패턴 재탐지와 분류 파이프라인(규칙 → 사전 → LLM)이 자동 실행된다.
- 금융망 실패 시 Job은 `FAILED`가 되고, 계좌의 `syncStatus = FAILED`와 `lastSyncedAt`(마지막 성공 시각)을 화면에 그대로 표시한다(비기능 요구사항: 가용성).

### 7.4 CSV 거래 업로드

`POST /accounts/{accountId}/transactions/import`

`multipart/form-data`로 `file`(CSV, 최대 10MB)을 전달한다. `202 Accepted`와 `TRANSACTION_IMPORT` Job을 반환한다.

CSV 컬럼 규격 (헤더 필수, 한글·영문 헤더 모두 허용):

| 컬럼 | 영문 헤더 | 필수 | 형식 |
| --- | --- | --- | --- |
| 거래일시 | `transactionAt` | Y | `YYYY-MM-DD HH:mm:ss` |
| 적요 | `description` | Y | 문자열 |
| 입금액 | `depositAmount` | Y* | 정수 (출금 행은 0 또는 빈 값) |
| 출금액 | `withdrawalAmount` | Y* | 정수 (입금 행은 0 또는 빈 값) |
| 거래후잔액 | `balanceAfter` | N | 정수 |

- 입금액·출금액 중 정확히 하나만 양수여야 한다.
- 중복 판정 키는 **`(계좌, 거래일시, 방향, 금액, 적요)`** 이며 중복 행은 건너뛰고 `duplicateCount`로 집계한다 (인수 조건: 중복 없는 귀속).
  - **v1.4에서 `방향`을 추가했다.** 같은 시각·같은 금액의 입금과 출금은 서로 다른 거래인데, 방향이 빠지면 하나로 뭉개져 한 건이 유실된다(계좌 간 이체가 한 파일에 함께 담기는 경우 실제로 발생한다).
  - 파일 내부의 중복도 같은 키로 걸러진다. DB에도 부분 유일 인덱스 `(account_id, deduplication_key)`가 걸려 있어 애플리케이션 판정이 새더라도 최종적으로 막힌다.
- 금액 셀의 천 단위 구분자(`1,200,000`)와 통화 기호(`₩`, `원`)는 제거 후 파싱한다 — 은행 내보내기 형식이 제각각이라 사용자가 파일을 손보지 않아도 되게 한다.
- 형식 오류 행이 있으면 Job을 실패시키지 않고 `resultRef.rejectedRows`에 행 번호와 사유를 담는다. 파일 자체가 규격이 아니면 `400 IMPORT_INVALID_FORMAT`을 즉시 반환한다.
