## 10. 잔액 예측과 정산 공백

### 10.1 예상 잔액 곡선 (P0-07)

`GET /businesses/{businessId}/forecast/balance?days=30`

| Query | 설명 |
| --- | --- |
| `days` | `7`, `14`, `30` 중 하나 (기본 30) |
| `accountId` | 특정 계좌만 (생략 시 사업장 전체 합산). ⚠ **P1 이다** — `FORECAST_RUN` 에 `account_id` 가 없어 계좌별 실행을 저장할 수 없다(ERD 1.3). 보내면 `400` |

- `curve`는 날짜별 예상 잔액과 그 범위이며, **동일 입력 + 동일 `modelVersion`에 대해 항상 같은 결과를 반환해야 한다**(인수 조건: 재현성). 모델 산출값은 실행 시점에 `FORECAST_RUN.basis`로 고정 저장되므로, 같은 실행을 다시 조회하면 재추론 없이 같은 값이 나온다.
- `modelVersion`은 **계산 엔진 버전과 모델 아티팩트 버전을 함께** 담는다(`engine-<x.y>/<model>-<ver>`). 모델을 쓰지 않은 실행은 `engine-1.2/none`이다. 워커가 주는 `<ver>` 에는 **학습 데이터 지문이 붙어 있다**(`0.3.0+a82bc981`) — 구조를 안 바꾸고 데이터만 바꿔 재학습하면 버전이 그대로여서 위의 재현성 보증이 조용히 깨지기 때문이다(20.11 참조). API 서버는 워커가 준 문자열을 **가공하지 않고 그대로** 붙인다.
- `expectedDeposit`·`expectedWithdrawal`은 **해당일 채널 합계**다. 대상 매장은 카드사 정산(영업일마다 소액 다건)·배달 플랫폼 정산(주 단위 묶음)·현금 입금이 섞이므로, 한 날의 입금이 여러 거래처에서 온다. 곡선이 완만한 구간은 카드 정산이, 계단처럼 뛰는 구간은 플랫폼 정산이 만든다.
- 연휴에는 카드 정산이 멈춰 `expectedDeposit`이 0이 되는 날이 연속으로 생긴다. 위 예시의 9월 25일(추석)이 그 경우다. 2026년 추석 연휴는 9/24(목)~9/26(토)이고 9/27(일)까지 이어지며, **대체공휴일은 없다**(설날·추석 연휴는 일요일이나 다른 공휴일과 겹칠 때만 적용). 정산은 9/28(월)에 4영업일분이 누적되어 재개된다.
- `riskLevel`은 2.6의 4단계 체계를 따르고 안전선(P1-08)이 설정되지 않았으면 `safetyLine: null`에 0원 기준(`GAP`)만 판정한다.
- `adjustments.type`: `HOLIDAY_SHIFT`(P1-04), `SEASONALITY`(P1-07), `VAT_DUE`(P1-11), `ACCURACY_CORRECTION`(P1-05 오차 보정), **`MODEL_RESIDUAL`**(잔여 흐름 모델)
- **`MODEL_RESIDUAL` — 잔여 현금흐름.** 반복 패턴·사용자 등록 어느 쪽으로도 잡히지 않는 흐름(현금 매출 입금, 소액 부정기 지출, 미분류 거래)을 **잔여 예측 모델**이 추정한 값이다. 정의는 `일별 실제 합계 − 예정 거래에 매칭된 합계`이므로 **`confirmedPlannedCount`·`expectedPlannedCount` 항목과 중복 계상되지 않는다.** 사용자가 반복 후보를 새로 승인하면 그만큼 잔여가 줄어든다.
- **잔여는 API 서버가 만든다.** `residual_deposit(d) = 실제 입금 합계(d) − Σ 예정 거래에 매칭된 입금(d)` (출금도 동일). 워커는 시계열만 받고 계산 규칙을 모른다(20.11). 집계 규칙 4가지와 참조 구현(`ai/app/forecast/residual.py`)은 [예측엔진 설계노트 M-1 「잔여를 누가 어떻게 만드나」](../예측엔진_설계노트.md)에 있다.
- **⚠ 매칭이 돌아야 모델을 태울 수 있다** *(2026-09-10 해소 — 최소 매처가 섰다)*. 잔여의 뺄셈 대상은 `PLANNED_TRANSACTION.matched_transaction_id` 인데 그것을 채우는 자동 매칭이 API 9.5(P1-05)라, 한동안 컬럼과 엔티티 필드만 있고 쓰는 코드가 없었다. 매칭이 비면 잔여가 「실제 거래 전부」가 되고 곡선이 `시작잔액 + Σ예정 + Σ실제` 가 되어 **예정 거래를 두 번 센다** — 「뺄셈이라 이중 계상이 구조적으로 불가능하다」는 설명은 매칭이 돌 때만 참이다. **9.5 의 네 조건(방향·계좌·날짜·금액)만 줄인 최소 매처를 P0 로 올려 이 전제를 세웠고**, 그 위에서 모델을 켰다. 이 순서가 뒤집히면 곡선이 위로 발산해 공백을 아예 못 잡는다.
- **`basis.residual.judgmentAlpha` 는 워커가 준 값을 그대로 적는다.** 곡선 판정용 대표값을 만들 때 쓴 보수성이다 — `잔여입금 = q50 + α·(q10 − q50)`, `잔여출금 = q50 + α·(q90 − q50)` (20.11). **α 없이는 곡선을 재현할 수 없다** — 같은 `modelVersion` 과 같은 입력이어도 α 가 다르면 부족일이 달라지므로, 위 재현성 보증(동일 입력 + 동일 `modelVersion` → 동일 결과)이 α 를 같이 고정해야 성립한다. **통계 폴백 경로에도 같은 α 를 적용한다** — 두 경로에 다른 α 를 쓰면 채택 비교가 무의미해진다.
- **α 는 API 서버가 임의로 정하면 안 된다.** 「공백 경보니까 안전하게」라며 하한 쪽으로 올리는 것이 자연스러운 선택인데, 그러면 **모델을 채택한 근거가 사라진다** — 운영 구간에서 채택 게이트는 α=0.00 에서만 통과하고 0.05 면 유의차가 없어진다 (근거표는 20.11). 값을 바꾸려면 채택 판정을 다시 돌려야 한다.
- `basis.residual.source`: `MODEL`(모델 적용) · `BASELINE`(통계 폴백) · `NONE`(미적용). `applied: false`이면 잔여를 0으로 두고 곡선을 산출한 것이며, 사유가 `warnings`에 담긴다 — 과거 데이터 **30일** 미만 *(2026-09-09 에 90 → 30)*, 워커 오류·타임아웃, 사용자 토글 OFF 세 가지다.
- 과거 데이터가 **30~180일**이면 잔여를 반영하되 `confidence`를 한 단계 낮춘다 *(2026-09-10 정정 — 이 줄만 90 으로 남아 있었다. 바로 윗줄·20.11·설계노트·SRS·화면구성도는 모두 30 이다. 90 을 그대로 구현하면 **기록이 30~60일인 지금 계좌 대부분에서 강등이 통째로 누락된다**)*. **모델이 실패해도 곡선은 반드시 산출된다.**
- 데이터가 부족하면 범위를 넓히고 `confidence: "LOW"`와 `warnings`로 표시한다 (P0-07 예외 처리).
- **`confidence` 산정 공식은 공통규약 23장에 있다** *(2026-09-10 확정)*. DB 는 일별 `NUMERIC(5,4)` 를 저장하고 이 응답은 조회한 `days` 창의 평균을 네 등급으로 환산한 값이다 — **창마다 다시 계산하므로 7일 조회가 30일 조회보다 높게 나올 수 있다.**
- **실행은 항상 30일이고 `days` 는 조회에서 자른다.** `ix_fr_latest` 가 `days` 를 구분하지 않아 기간별로 실행을 따로 저장하면 "최신"이 엉뚱한 실행을 가리킨다. 곡선의 첫날은 `baseTime` 의 **다음 날**이다(위 예시가 8/31 → 9/1). **기준일 당일자 예정 거래는 그 첫날 점에 합산한다** *(2026-09-11 추가 — `engine-1.1`)*. 시작 잔액은 이미 일어난 거래만 담으므로 여기서까지 빼면 곡선 **전 구간**이 그 금액만큼 높아지고 공백 경보가 울리지 않는다. 딥이 하루 늦게 찍히는 대신 레벨이 맞는다.
- **최신 `COMPLETED` 실행이 없으면 계산하지 않고 알린다** — 연결된 계좌가 없으면 `422 FORECAST_INSUFFICIENT_DATA`, 계좌는 있는데 실행만 없으면 재계산을 예약하고 `409 FORECAST_NOT_READY`. 조회 API 는 읽기만 한다(공통규약 2.6 캐시 전략).
- ⚠ **`adjustments.type` 에 `HOLIDAY_AMOUNT_SCALE` 이 없다.** 설계노트 G-1 이 「연휴 다음 영업일에 며칠분이 몰리는 금액 배율」을 날짜 보정과 분리해 추가하기로 했는데 아직 반영 전이다. **P1-04 착수 시 함께 넣는다** — 지금 구현은 6종만 다룬다.

#### 수동 새로고침 (명세 밖 임시)

`POST /businesses/{businessId}/forecast/refresh` → `202`

- **명세에 없는 임시 엔드포인트다** *(2026-09-10 신설)*. 재계산은 원래 트리거(공통규약 2.6)가 걸지만, 화면에 「지금 다시 계산」 버튼이 필요하고 위 `409 FORECAST_NOT_READY` 에서 벗어날 진입점도 있어야 한다. 반복 패턴 탐지(`POST .../recurring-patterns/detect`)와 같은 성격이다.
- 실제 계산은 서버가 **5초 디바운스 뒤 사업장 락 아래에서** 돌린다(공통규약 2.6). 즉시 곡선이 바뀌지 않으므로 클라이언트는 잠시 뒤 10.1 을 다시 부른다.
- 연타해도 실행은 한 번이다 — `forecast:dirty:{businessId}` 플래그가 합쳐 준다.

### 10.2 정산 공백 (P0-08)

`GET /businesses/{businessId}/forecast/cash-gaps?days=30`

```json
  "data": {
    "baseTime": "2026-08-31T02:00:00Z",
    "items": [
      {

```

- 최초 부족 예상일, 최대 부족 금액, 지속 기간, 회복 예상일, 주요 원인을 모두 포함한다 (P0-08 완료 기준).
- `items`는 예측 기간 내 공백 구간을 **모두** 반환한다. 위 예시는 급여 출금(9/14)과 추석 연휴 정산 정지(9/26~9/27) 두 건이며, 원인 유형이 다르므로 대응 제안도 달라진다.
- 메시지는 확정 표현을 쓰지 않는다: "부족합니다" ✕ → "현재 데이터 기준 부족할 가능성이 있습니다" ○. 문구 생성은 클라이언트가 하되 서버 응답의 `riskLevel`·범위 필드를 근거로 한다.
- **공백은 `expectedBalance < 0` 으로 판정한다** *(2026-09-10 명시)*. `balanceMin` 이 아니다 — 하한선으로 판정하는 것은 판정 보수성 `α = 1` 을 쓰는 것과 같고, 그러면 **모델을 채택한 근거가 사라진다**(10.1 의 α 규약, 20.11 근거표). `maxShortfallAmount` 도 `expectedBalance` 기준이며, 하한 기준 부족액은 알림 문구의 범위 상단("약 42만~80만 원")에 쓴다.
- **`cashGapId` 는 이 공백으로 만들어진 `ALERT.id` 다**(ERD 1.3). 공백 구간 자체는 저장하지 않는 파생값이라 안정적인 자기 id 가 없다. 같은 시작일의 공백은 알림이 갱신되며 id 가 유지되고, 공백이 사라지면 그 알림이 `RESOLVED` 로 내려간다.
- **`days` 로 자른 창 안에서 구간을 계산한다.** 창 끝까지 잔액이 음수면 `expectedRecoveryDate` 는 키가 빠지고 `durationDays` 는 창 안 일수다 — `basis.referenceCurveDays` 가 그 창을 알려 준다.

- 집계된 오차는 다음 예측의 날짜 보정치와 금액 범위 폭에 자동 반영되며(`adjustments.type = ACCURACY_CORRECTION`), 보정 적용 내용을 `appliedCorrection`으로 표시한다.
- **위 `modelComparison` 숫자는 합성 데이터 실측값이다** (과거 30일~1년 구간, 사업장 200곳). 짝지은 부트스트랩으로 `+0.016 [+0.008, +0.024]` — 유의하지만 **차이는 작다.** **`activeVariant` 는 실행마다 컨텍스트 길이로 정한다** — 30일 미만은 모델 미적용(워커가 `422`), **30일~1년은 `MODEL`**, 1년 이상은 `BASELINE` 이다. `FORECAST_RUN` 단위 값이라 새 필드 없이 표현된다. **그리고 판정 보수성 `judgmentAlpha` = 0.00 이 전제다** — α 를 0.05 로 올리면 같은 구간에서 차이가 `+0.006 [−0.003, +0.013]` 으로 유의성을 잃고, 0.10 이면 모델이 유의하게 나빠진다 (근거표는 20.11). **채택 게이트는 이 구간에서만 통과한다** — 과거 1년 이상 구간에서는 모델이 통계를 넘지 못하므로(−0.006, 구간이 0 을 포함) 그쪽 실행은 `activeVariant` 가 `BASELINE` 로 남는다. 실제 통장 데이터로 재측정하기 전까지 이 숫자를 절대 성능으로 인용하지 않는다. 근거는 [`예측엔진_설계노트.md`](../예측엔진_설계노트.md) M-3 「실측 결과」다.
- **`modelComparison`은 채택 근거를 그대로 노출한다.** 비교 지표는 모델 손실이 아니라 **다운스트림 지표**(`gapF1` 정산 공백 발생 F1, `firstShortfallDateErrorDays` 최초 부족일 오차)다. 모델이 베이스라인을 넘지 못하면 `activeVariant`가 `BASELINE`이 되고 예측은 통계 경로로 돈다. 평가 표본이 부족하면 `modelComparison: null`이다.
- `variant` 값: `BASELINE`(통계) · `MODEL`(잔여 흐름 모델) · `MODEL_CORRECTION`(지연·금액 보정 모델까지 적용). 셋 중 무엇이 도는지는 `GET /forecast/balance`의 `modelVersion`과 일치한다.
- 채널에 따라 보정 성격이 다르다. **카드 정산은 영업일 달력으로 입금일이 결정**되므로 `avgDelayDays`가 0에 수렴하고 보정은 금액 축(요일 편차)에서 일어난다. **플랫폼 정산은 마감 기준이 달라** 날짜 보정이 주가 된다.

### 10.5 (결번)

원자재 설정(`PUT /businesses/{businessId}/ingredients`)·시세 조회(`GET /market-indicators`)·영향 분석(`GET /businesses/{businessId}/forecast/material-impact`)이 이 절에 있었다. **P1-06 원자재 가격 지표가 SRS v1.10 에서 범위 제외(결번)되어 세 엔드포인트를 모두 삭제했다.** 절 번호는 다른 문서가 10.6·10.7 을 가리키고 있어 그대로 비워 둔다.

재료비 변화 시뮬레이션도 **함께 빠졌다**(11.1 `MATERIAL_COST_CHANGE`, API v1.28). 시세 없이 `rate` 만으로는 무엇에 곱하는지가 정의되지 않았고, 패턴으로 안 잡힌 재료비가 잔여 축에 섞여 골라낼 수 없었다. 매출 쪽 시뮬레이션은 `PRODUCT_SALES_CHANGE`(P1-22 구성비 연동)가 맡는다.

### 10.7 예측 옵션

`GET /businesses/{businessId}/forecast-settings`
`PATCH /businesses/{businessId}/forecast-settings`

```json
{
  "applySeasonality": true,
  "applyVatReserve": true,
  "applyResidualModel": true,
  "peakMonths": [7, 8, 12],
  "offMonths": [2]
}
```

- 계절성 반영은 사용자가 토글할 수 있으며(P1-07 완료 기준), 잔액 곡선 응답의 `appliedOptions`로 현재 상태를 확인한다.
- **`applyResidualModel`** — 잔여 현금흐름 모델 반영 여부(기본 `true`). `false`로 두면 예측이 예정 거래와 통계 보정만으로 돌고, `basis.residual.applied`가 `false`, `modelVersion`이 `engine-<x.y>/none`이 된다. **끈 상태에서도 곡선과 부족일은 정상 산출된다**(인수 조건). 이 토글이 곧 모델 반영 전후를 비교하는 수단이다.
- 토글을 바꾸면 다음 예측 실행부터 적용된다. 이미 저장된 `FORECAST_RUN`은 실행 당시의 `appliedOptions`를 그대로 유지한다.
- `peakMonths`/`offMonths`는 사용자가 수동 입력하는 성수기·비수기이며 계절성 계수에 병합된다.
- **저장 위치는 `FORECAST_SETTING` 테이블이다**(ERD 1.3 — 2026-09-10 신설). 사업장당 한 행이고 행이 없으면 위 기본값(`applyResidualModel`만 `true`)으로 응답한다. `FORECAST_RUN.applied_options` 는 **실행 당시 값의 사본**이라 설정의 원본이 될 수 없다.
- P0 범위에서 실제로 곡선을 바꾸는 것은 **`applyResidualModel` 하나뿐이다.** 나머지 둘은 P1-07·11 기능이 없어 저장은 되지만 `appliedOptions` 에는 항상 `false` 로 나간다.
- **`applyMaterialIndex` 는 삭제했다.** P1-06 원자재 가격 지표가 범위에서 빠졌다(SRS v1.10). DB 컬럼도 `V20` 으로 함께 지웠다.
