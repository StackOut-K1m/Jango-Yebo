## 배경 — 왜 하이브리드인가

**v1은 ML을 전면 배제했다. v2에서 조건부 도입으로 바꾼다.** 판단을 바꾼 근거는 새로 확인한 사실 하나다 — **v1의 반박은 "우리 데이터로 학습하는 모델"에만 적용된다.**

### v1의 반박은 폐기하지 않는다

| 조건 | 확인 결과 |
| --- | --- |
| 학습 데이터 | SSAFY 금융망은 **API만 제공, 데이터셋 없음** |
| 대체 수단 | 합성 데이터 — 생성 규칙 `R`로 만든 데이터에서 모델이 배울 수 있는 정보의 상한이 `R`이다. `R`을 코드로 쓰는 것보다 나은 결과가 나올 수 없다(순환논법) |
| 관측 가능 범위 | CSV·금융망 모두 은행 거래내역(`거래일시`·`적요`·`입금액`·`출금액`·`거래후잔액`). **일별 매출 데이터 없음** — POS API 연동을 하지 않는다(SRS 1.3). P1-22가 받는 판매 데이터는 기간(월) 단위 구성비라 일별 학습 표본이 되지 않는다 |

이 표는 유효하다. **학습을 하는 모델에는 그대로 적용되며**, 그래서 M-2(XGBoost)는 이 제약을 안고 들어간다(M-2 「한계」 참조).

### zero-shot 으로 순환논법을 피하려 했고, 실측에서 실패했다

> **2026-09-08 개정.** 아래 논거는 v2 에서 M-1 을 zero-shot 으로 고른 이유였다. **실측이 이 논거를 뒤집었으므로 원문과 결과를 함께 남긴다.** 근거는 M-3 「실측 결과」다.

**당시 논거** — 시계열 파운데이션 모델(TimesFM·Chronos 계열)은 추론 시 학습을 하지 않는다. 사전학습 가중치를 고정한 채 쓰고 우리 데이터는 컨텍스트로만 들어가므로, 정보가 `R` 밖에서 온다. 학습 단계가 없어 일정 리스크도 거의 없다.

| | 정보의 출처 | 순환논법 |
| --- | --- | --- |
| 우리 시드로 학습하는 모델 | 우리 생성 규칙 `R` | **성립** — 정보 상한이 `R` |
| zero-shot 파운데이션 모델 | 사전학습이 가져온 외부 시계열 | 불성립 — `R` 밖의 정보가 들어온다 |

**실측** — zero-shot 은 통계 베이스라인보다 **유의하게 나빴다.**

| | 공백 발생 F1 | 통계 대비 (짝지은 부트스트랩 95%) |
| --- | --- | --- |
| 통계 베이스라인 (요일 중앙값) | 0.692 | — |
| Chronos zero-shot | **0.600** | **−0.092 [−0.105, −0.080]** 유의하게 나쁨 |
| 같은 계열 fine-tune (48M) | 0.687 | −0.006 [−0.013, +0.001] 판정 보류 |

사전학습이 가져온 사전분포가 **일별 잔여 현금흐름으로 전이되지 않았다.** 잔여는 예정 거래를 뺀 나머지라서 일반 시계열과 성질이 다르다 — 0 이 많고, 요일 리듬 외의 자기상관이 약하다.

**그래서 순환논법 회피 수단이 사라졌다.** 채택한 `residual-gru` 는 우리 생성 규칙 `R` 로 만든 데이터로 학습하므로, 위 표의 **첫 줄이 M-1 에도 그대로 적용된다.** 숨기지 않고 다음 두 가지로 경계를 그었다.

- **상한을 같이 재서 `R` 을 되짚었는지 확인한다.** 요일별 참값을 직접 보는 부정 팔(모수 오라클, ±60일 중심창 요일 평균)이 0.733 이다. `residual-gru` 는 0.687 로 **그 상한에 못 미친다** — 생성 규칙을 외운 것이 아니라는 뜻이다. 만약 0.733 에 붙었다면 그것이 곧 순환논법의 증거였다.
- **주장의 범위를 좁힌다.** 우리가 말할 수 있는 것은 「같은 데이터에서 통계 베이스라인보다 낫다」까지다. **「실제 소상공인 통장에서 이만큼 맞춘다」로 확장하지 않는다.** 실제 통장 데이터를 얻기 전까지 절대 성능을 인용하지 않는다.

### 곡선에 이미 비어 있던 칸

예측 입력은 `CONFIRMED` 패턴에서 생성된 `PlannedTransaction`뿐이다(API 9.1). 즉 **패턴으로 잡히지 않는 흐름이 곡선에서 0으로 취급된다** — 현금 매출 입금, 소액 부정기 지출, 미분류 거래. 명세 어디에도 이 축을 다루는 규칙이 없다.

모델의 자리를 새로 만드는 것이 아니라 **이미 비어 있던 칸을 채운다.** 이것이 M-1이다.

### 3층 구조 — Layer 2를 두 축으로 나눈다

```
Layer 3   What-if        원장 스냅샷에 결정론적 변환 → Layer 1 재실행 (모델 재추론 없음)
               ↑
Layer 2-A 원장(ledger)   항목별 { 예정일, 금액 min/expected/max, confidence }
                         ← 통계 보정 · XGBoost 분위수 회귀 (M-2)
Layer 2-B 잔여 흐름       일별 { 잔여 입금·출금 q10/q50/q90 }
                         ← 잔여 예측 모델 residual-gru (M-1) · v2 신설
               ↑
Layer 1   회계 항등식     잔액 = 시작잔액 + Σ입금 − Σ지출 (날짜별 누적) — 영구 결정론
```

**Layer 1과 Layer 3은 손대지 않는다.** v1이 "ML을 도입하더라도 Layer 2만 교체되고 나머지는 불변"이라고 예고한 그 지점을 채우는 변경이다.

**매출 레이어는 여전히 두지 않는다.** Layer 2-B가 예측하는 것은 매출이 아니라 **원장이 설명하지 못한 나머지**다. 정의가 뺄셈이라(M-1) 매출을 모델링하지 않으며, 원장 항목이 늘면 잔여는 자동으로 줄어든다. 매출 변동은 v1 그대로 `SEASONAL_FACTOR.multiplier` 계수로 흡수한다.

**P1-22 상품별 매출과의 관계** — P1-22는 기간(월) 단위 **구성비**를 만들며 이 원칙을 깨지 않는다.

| | 들어가는가 | 이유 |
| --- | --- | --- |
| Layer 2-A 원장 | **아니오** | 판매를 입금으로 바꾸려면 채널 구성비·정산 주기·수수료율이 필요하다. 월 구성비로는 일별 입금 시점을 만들 수 없다 |
| Layer 2-B 잔여 | **아니오** | 잔여는 계좌 거래내역의 뺄셈으로만 정의된다. 판매 데이터가 들어오면 정의가 무너진다 |
| Layer 3 What-if | **예** | `PRODUCT_SALES_CHANGE`(API 11.1)가 구성비로 총매출 **배율 하나**를 만들어 기존 입금 패턴에 곱한다. 원장을 건드리지 않는 결정론적 변환이라 Layer 3의 정의 안이다 |
| 모델 학습·컨텍스트 표본 | **아니오** | M-1의 입력은 잔여 시계열, M-2의 입력은 정산 매칭 이력이다. 판매 데이터는 어느 쪽에도 넣지 않는다 |

즉 판매 데이터는 **예측을 만들지 않고 예측을 흔드는 데만** 쓴다. 이 구분을 흐리면 매출 레이어가 뒷문으로 들어온다.

**G-3은 v1의 「중」에서 「높음」으로 올린다** — M-2의 교차 사업장 풀링이 `MERCHANT_MASTER` 없이는 성립하지 않기 때문이다.

## M-1. Layer 2-B 잔여 흐름 축 (신설)

### 문제

예측 곡선에 들어가는 것은 `PLANNED_TRANSACTION`뿐이다(API 9.1·10.1 `basis`). 그래서 **패턴으로 잡히지 않는 현금흐름이 곡선에서 0으로 취급된다.**

| 빠지는 흐름 | 예 |
| --- | --- |
| 현금 매출 입금 | 사장님이 현금 매출을 주 1~2회 몰아서 입금 |
| 소액 부정기 지출 | 소모품·잡비·수리비 — 주기가 없어 패턴 탐지에 안 걸린다 |
| 미분류 거래 | 규칙·사전·LLM 어디서도 카테고리가 확정되지 않은 건 |

곡선이 체계적으로 낙관(입금 누락) 또는 비관(지출 누락)으로 치우친다. 어느 쪽이든 **공백 판정일이 밀린다.**

### 판정

**Layer 2-B를 신설하고 잔여 예측 모델로 채운다.** (v2 는 zero-shot 파운데이션 모델을 전제했다. 실측 후 자체 학습 모델 `residual-gru` 로 바뀌었다 — M-3 참조.)

```
residual_deposit(d)    = 실제 입금 합계(d) − Σ 예정 거래에 매칭된 입금(d)
residual_withdrawal(d) = 실제 출금 합계(d) − Σ 예정 거래에 매칭된 출금(d)
```

매칭은 P1-05의 가중 점수 매칭 결과(`PLANNED_TRANSACTION` ↔ `TRANSACTION`)를 그대로 쓴다. **정의가 뺄셈이므로 이중 계상이 구조적으로 불가능하다** — 원장이 설명한 만큼은 잔여에서 이미 빠져 있다.

| | 내용 |
| --- | --- |
| 입력 | 과거 일별 잔여 시계열 2개(입금·출금). 컨텍스트 **30~365일**(`features.MIN_HISTORY`~`LOOKBACK`. 30일 미만은 워커가 422 로 거절한다) |
| 출력 | horizon 30일 × 분위수 `q10 / q50 / q90` |
| 반영 | `DAILY_BALANCE_FORECAST.residual_deposit`·`residual_withdrawal`(q50), 곡선 `balance_min/max` 폭에 q10·q90 합산 |
| 제외 | `TRANSACTION.is_excluded = true`(예측에서 제외) 거래는 실제 합계 집계에서 뺀다 — 장비 구입 등 일회성 |

### 재계산 규칙 — 캐시하지 않는다

사용자가 새 패턴을 승인하면 **과거 잔여 시계열이 소급해서 바뀐다**(매칭 항목이 늘어 잔여가 준다). 잔여 시계열은 예측 실행 시점에 매번 새로 집계한다. 캐시하면 패턴 승인 직후 이중 계상이 생긴다.

### 잔여를 누가 어떻게 만드나 — BE 계약 (S15P21C105-65 · 2026-09-10)

**API 서버가 만든다.** 매칭 결과가 DB 에 있고, 워커는 계산 규칙을 모른 채 시계열만 받는다(20.11).

참조 구현이 있다 — `ai/app/forecast/residual.py` (`aggregate_residual`, 테스트 3건). Java 로 옮길 때 지켜야 할 규칙은 넷이다.

| 규칙 | 왜 |
| --- | --- |
| `TRANSACTION.is_excluded = true` 는 **실제 합계에서 아예 뺀다** | 장비 구입 같은 일회성이라 예측 대상이 아니다. 잔여로도 넘기지 않는다. 세무 판단(`tax_review_status`)과는 독립이다 |
| `PLANNED_TRANSACTION.matched_transaction_id` 가 가리키는 거래를 뺀다 | 예정 거래가 이미 설명한 몫이다. 부분 UK(`uk_pt_matched`)가 1:1 을 보장하므로 한 거래가 두 예정에 붙지 않는다 |
| **거래가 없는 날도 0 으로 채운다** | 배열에서 빠뜨리면 요일별 통계의 표본 수가 틀어진다. 「비어 있음」이 아니라 「0」이다 |
| 금액은 `BigDecimal` 로 다루고 **워커에 보낼 때만** 숫자로 바꾼다 | `double` 로 합치면 워커의 값과 갈린다 |

#### ⚠ 전제 — 매칭이 없으면 곡선이 두 배가 된다

**2026-09-10 확인: `matched_transaction_id` 를 채우는 코드가 없다.** 컬럼과 엔티티 필드는 있지만 쓰는 곳이 `PlannedTransactionDtos` 의 읽기뿐이고, 매칭 클래스 자체가 없다. 자동 매칭은 **API 9.5 = P1-05** 로 정의돼 있다.

**P0-07(예상 잔액)이 P1 기능에 의존하고 있다.** 우선순위가 뒤집혀 있고, 그대로 두면 이렇게 된다.

```
매칭 없음  →  잔여 = 실제 거래 전부
           →  곡선 = 시작잔액 + Σ예정거래 + Σ잔여
           →  예정거래가 두 번 세어진다
```

「뺄셈이라 이중 계상이 **구조적으로** 불가능하다」는 이 노트의 문장은 **매칭이 돌 때만** 참이다. 뺄 대상이 비면 뺄셈은 아무것도 빼지 않는다.

크기는 실측으로 안다 — 탐지가 0% 일 때 공백 F1 이 **0.687 → 0.029** 로 떨어진다(M-3 「탐지 재현율이 성능을 지배한다」). 그건 예정거래가 **잔여로 옮겨간** 경우이고 합계는 보존된다. **이중 계상은 그보다 나쁘다** — 곡선이 위로 발산해 공백을 아예 못 잡는다.

#### 그때까지 무엇을 하나

두 갈래 중 하나를 골라야 한다. **셋째 길(매칭 없이 잔여를 「실제 전부」로 두고 모델을 태우는 것)은 안 된다.**

1. **최소 매처를 P0 로 올린다.** 9.5 의 자동 매칭 규칙을 줄여서 — 같은 `flow_type`, 예정일 ±N일, 금액이 `[amount_min, amount_max]` 안. 거래처 유사도는 나중에. 매칭되면 `status = MATCHED` · `matched_transaction_id` · `matched_date_diff_days` 를 채운다
2. **모델을 태우지 않는다.** `basis.residual.applied = false` · `source = NONE` 으로 두고 곡선은 예정거래만으로 낸다. **계약에 이미 있는 상태**이고 틀린 숫자를 내지 않는다. 대신 공백 F1 이 바닥(0.457)에 머문다

> **결정 (2026-09-10) — 2 로 시작해서 1 을 붙인다.** 곡선·저장·조회 API 를 `source = NONE` 으로 먼저 세우고, 그다음 최소 매처를 넣고, 잔여 모델은 마지막에 켠다. 2 는 **틀린 숫자를 내지 않는 상태이면서 프론트가 붙을 표면을 먼저 만들고**, 「모델이 실패해도 곡선은 반드시 산출된다」는 인수 조건이 그 순서를 이미 요구한다. 부분 UK(`uk_pt_matched`)가 1:1 을 강제하므로 1 을 나중에 붙여도 데이터가 어긋나지 않는다. 최소 매처의 규칙과 허용폭 `N` 은 [API 9.5](api/09_반복_예정거래.md) 에 표로 적었다.

> **완료 (2026-09-10) — 세 단계가 다 섰다.** 곡선(`S15P21C105-132`) → 최소 매처(`-136`) → 잔여 모델·통계 폴백(`-137`) 순으로 들어갔고, 서버 기본값이 `residual-mode: MODEL` 이다. 실제 경로는 폴백 사슬이 정한다 — 워커가 없거나 응답이 검증을 통과하지 못하면 통계로, 표본이 30일 미만이면 미적용으로 내려간다. **어느 갈래로 가든 곡선은 나온다.** BE 쪽 상태는 [구현현황 §3.21](api/99_구현현황.md) 에 있다.

#### `activeVariant` 는 구간 분기를 표현할 수 있다

`modelComparison.activeVariant` 는 `FORECAST_RUN` 단위 값이라 **실행마다 컨텍스트 길이로 정하면 된다.** 새 필드가 필요 없다.

| 워커에 넣은 컨텍스트 | `activeVariant` | 근거 |
| --- | --- | --- |
| 30일 미만 | — (모델 미적용) | 워커가 `422` 로 거절한다 |
| **30 ~ 364일** | **`MODEL`** | 채택 게이트가 통과하는 유일한 구간 (`+0.0162 [+0.0080, +0.0244]`) |
| **365일** (창 상한) | `BASELINE` | **게이트의 F1 조건을 못 넘었다** — `−0.006 [−0.012, +0.001]`, **유의차 없음** |

> ⚠ **「통계가 낫다」가 아니다** (2026-09-10 정정). 이 칸에 원래 「그 구간은 통계가 낫다」로
> 적혀 있었는데, 신뢰구간이 0 을 포함하므로 **두 경로를 구분할 수 없다**는 뜻이다. 게다가
> **최초 부족일 오차는 모델이 오히려 낫다**(통계 9.10일 → 모델 8.99일). 그런데도 `BASELINE`
> 인 이유는 게이트가 `F1 > 베이스라인 AND 최초오차 ≤ 베이스라인` 둘 다를 요구하고 **첫
> 조건을 못 넘었기** 때문이다 — 「통계를 써야 한다」가 아니라 **「모델을 쓸 근거가 없다」**다.
> 이 프로젝트에서 여러 번 지켜 온 규칙이라 여기서도 지킨다.

> ⚠ **「1년 이상」이 아니라 「365일 정확히」다** (2026-09-10 정정). 나누는 축은 **사업장 기록의
> 나이가 아니라 워커에 넣은 일수**다. `LOOKBACK` 이 365 이고 BE 의 잔여 집계 창도 365라
> **운영에서 컨텍스트가 365를 넘는 일은 없다.** 그래서 `historyDays == 365` 하나가 아래
> 표의 「1~2년」 구간이고, **첫 거래일을 따로 조회할 이유가 없다** — 기록이 3년이든 10년이든
> 워커가 보는 것은 마지막 365일이다.
>
> 이 정정 전에는 밴드 라벨이 「1~2년」이라 **「기록 1년 이상 사업장은 전부 `BASELINE`」**
> 으로 읽혔다. 그렇게 구현하면 오래된 사업장이 통째로 모델을 못 쓰게 되는데, 실측이 말하는
> 것은 그게 아니다.

그리고 **두 경로에 같은 α(0.00)를 적용한다.** 다른 α 를 쓰면 `variants` 표의 비교가 무의미해진다(위 「게이트는 판정 보수성 α 에 딸려 있다」).

#### 공백 기준선은 계약에 못박지 않는다

α 와 헷갈리기 쉬운 값이 하나 더 있다 — **잔액이 얼마 아래로 가면 「공백」인가.** 이쪽은 `SAFETY_BALANCE_POLICY.amount` 로 **사용자가 정하고, 계약이 값을 강제할 이유가 없다.** 기준선을 시작 잔액의 0~75% 로 옮겨 가며 재도 **다섯 자리 전부에서 모델이 통계를 유의하게 이긴다**(위 「공백 기준선은 사용자가 정한다」).

**α 와 정반대다.** α 는 0.00 에서만 채택이 성립해 응답에 실어 보내야 하지만, 기준선은 사용자가 어디에 두든 M-1 의 근거가 유지된다. **워커는 기준선을 알 필요도 없다** — 분위수를 그대로 주고, 「선 아래냐」 판정은 API 서버(Layer 1)가 사용자 값으로 한다.

### 표본 부족 처리

| 과거 데이터 | 처리 |
| --- | --- |
| **30일 미만** | **모델 미적용.** 잔여 = 0으로 두고 `warnings`에 사유 표시 |
| **30~180일** | 적용하되 `confidence` 한 단계 강등 |

> **2026-09-09 개정 — 하한을 90 → 30 으로 내렸다.** 실측(합성 데이터, 창 9,600개) — 30~89일 구간에서 **잔여 0 은 공백 F1 0.457 · 최초 부족일 오차 19.4일**, **모델은 0.676 · 9.28일**이다. 통계도 0.652 로 멀쩡히 나온다. 90 은 「근거 없는 숫자를 내느니 모른다고 하자」는 원칙에서 나온 값인데, **원칙은 맞고 값이 틀렸다.**
>
> 그리고 90 은 모델만이 아니라 **통계까지 같이 막았다** — 둘 다 못 쓰고 0.457 로 떨어진다. 워커 하한(`features.MIN_HISTORY`)이 이미 30 이라 **두 값이 하나로 합쳐졌다.** 싸피 금융망 계좌는 기록이 30~60일이라 **서비스가 실제로 도는 구간이 바로 여기다.**
| 180일 이상 | 정상 적용 |

### 근거

- Layer 1의 항등식은 그대로다. 잔여는 **입금·출금 합계에 더해지는 항**일 뿐 계산 구조를 바꾸지 않는다

## M-2. Layer 2-A 지연·금액 보정 — XGBoost 분위수 회귀 (조건부)

### 문제

v1의 통계 보정은 **패턴별 `matched_date_diff_days` 중앙값**과 **과거 입금액 분위수**다(부록). G-3이 지적하듯 표본이 사업장당 3~5건이라 중앙값도 신뢰할 수 없고, G-1이 지적한 **지연–금액 상관**은 두 축을 독립 집계하면 원리적으로 잡히지 않는다.

### 판정

두 타깃을 **한 모델의 다중 분위수 출력**으로 낸다. XGBoost `reg:quantileerror`(다중 분위수 동시 학습).

| 타깃 | 정의 | 출력 |
| --- | --- | --- |
| 지연일 | `실제 입금일 − 예정일` | q10 / q50 / q90 → `expected_date` 보정과 날짜 범위 |
| 금액 배율 | `실제 금액 ÷ 예정 금액` | q10 / q50 / q90 → `amount_min / expected / max` |

**피처** — `merchant_master_id`(G-3), 요일, 연휴 인접 거리(±3일), 직전 회차 지연일, 회차 간격, 금액 밴드, `industry_type`, 거래처 표본 수.

한 모델이 두 축을 함께 보므로 **G-1의 「지연–금액 결합」과 「연휴 인접 표본군 분리」가 피처로 흡수된다.** `HOLIDAY_AMOUNT_SCALE`은 모델 미적용 구간의 베이스라인으로 남는다.

### 한계 — 순환논법이 그대로 남는다

M-1과 달리 **M-2는 우리 시드로 학습한다.** 배경 절의 반박이 적용된다. 두 가지로 방어한다.

| 방어 | 내용 |
| --- | --- |
| **blind split** | 시드 생성기를 모델 담당자가 아닌 팀원이 작성하고 생성 규칙을 공개하지 않는다. 평가는 시드 기간 마지막 4~6주 hold-out |
| **표현의 정확성** | 발표·문서에서 "정확도가 좋아졌다"고 쓰지 않는다. **"합성 벤치마크에서 베이스라인 대비 개선"**으로만 표기한다 |

blind split을 확보하지 못하면 두 번째 방어만 남는다. 그 경우 **M-2를 시연 화면에 노출하지 않고** 내부 실험으로만 남긴다.

### 학습·배포

| 단계 | 내용 |
| --- | --- |
| 학습 | **오프라인.** 시드로 만든 과거 매칭 이력에서 학습해 아티팩트(`.ubj`)를 만든다 |
| 배포 | 아티팩트를 AI 워커 이미지에 포함. 런타임은 **추론만** |
| 재학습 | 실제 매칭 데이터가 쌓인 뒤 수동 트리거. 자동 재학습은 하지 않는다 |

이 구조가 **P1-05 의존성을 끊는다.** 도입 순서상 P1-05는 13단계인데, 학습을 오프라인으로 빼면 워커 착수(6단계) 직후에 M-2를 얹을 수 있다.

### 반영 위치

- API 20.12 — `POST /internal/v1/ai/settlement-delay`
- API 10.1 `adjustments.type` — `ACCURACY_CORRECTION`에 모델 산출 여부 표기
- ERD `MERCHANT_MASTER` (G-3) — **M-2의 전제**

## M-3. 모델 선정 — 2종 비교와 채택 게이트

### 판정

**후보 2종 + 통계 베이스라인의 3자 비교로 정한다.** 컨설팅이 OCR/VLM에 요구한 「2개 이상 모델 비교」와 같은 형식이며, `EVIDENCE_EXTRACTION`이 `model_name`·`model_version`을 남기듯 예측도 `FORECAST_RUN.model_version`에 남긴다.

**v2 의 후보** — TimesFM 계열(약 200M) 1순위, Chronos-Bolt 계열(약 48M) 2순위, 통계 베이스라인이 하한선. 이 노트는 후보와 절차만 고정하고 모델을 확정하지 않았다.

### 실측 결과 (2026-09-08) — **`residual-gru` 로 확정**

합성 데이터 사업장 200곳. **채점은 시간 hold-out 창 9,600개**에서 했다(학습에 쓴 창은 따로 30,600개). 공백 창 30.0% · 학습 데이터 지문 `a82bc981`.

**표본을 부풀려 읽지 않도록 두 가지를 밝힌다.**

- 창 간격이 7일이라 **정답이 창끼리 23/30 겹친다.** 9,600개가 독립 표본 9,600개가 아니다 — 겹치지 않는 30일 뭉치로 환산하면 **2,200개 규모**다.

| **30일~1년** | **+0.016** [+0.008, +0.024] 유의 | 9.27 → **9.14일 (개선)** | **통과** |
| 365일 (창 상한) | **−0.006** [−0.012, +0.001] 판정 보류 | 9.10 → 8.99일 (개선) | **미통과** — F1 이 통계보다 낮다 |

**게이트 판정 — 「컨텍스트 30~364일」 구간에서만 통과한다.** 게이트는 `F1 > 베이스라인 AND 최초오차 ≤ 베이스라인` 이고, 세 구간 중 이 한 곳만 두 조건을 함께 만족한다. **전체 창을 한 덩어리로 채점하면 미채택이다** — 5년치 합성 데이터에서는 대부분의 창이 컨텍스트 상한(365일)까지 차 있고, 그 구간에서 통계가 이미 강하다. 아래 세 가지를 함께 읽어야 판정이 뒤집히지 않는다.

- **컨텍스트가 상한(365일)까지 차면 모델이 통계를 넘지 못한다** (−0.006, 구간이 0 을 포함). **세 구간 이름은 「기록의 나이」가 아니라 「워커에 넣은 일수」다** — 평가 `X` 폭이 365라 「1~2년」을 요청해도 365일만 들어갔다. 통계가 이미 0.692 로 요일 축 상한(0.733)의 상당 부분을 먹는다. **모델의 값은 표본이 적을 때 나온다.**
- **과거 30~89일 구간이 2026-09-09 에 열렸다** — `baseline.MIN_SAMPLE_DAYS` 를 90 → 30 으로 내려 **워커 하한과 같은 값이 됐다.** 그 구간 실측은 모델 **0.676** · 통계 0.652 · 잔여 0 **0.457** 이고, 모델이 통계를 `+0.024 [+0.015, +0.033]` 로 **유의하게** 넘는다 — 90일 이상(+0.005 판정 보류)보다 차이가 크다. **모델의 값어치가 대부분 여기서 나온다.**
- **파라미터를 늘려도 얻는 것이 없었다.** 48M fine-tune 과 88K `residual-gru` 가 전체 구간 **0.6867 로 소수점 넷째 자리까지 같다** (통계 0.6923 대비 둘 다 −0.006, 구간이 0 을 포함). 병목은 용량이 아니라 **데이터에 실제로 들어 있는 신호**다. 그래서 200M TimesFM 을 넣을 근거가 없다.
- **LightGBM 분위수가 근소하게 낫다** (전체 0.697 · 30일~1년 0.682). 다만 전체 구간에서도 통계 대비 `+0.005 [−0.000, +0.010]` 로 **판정 보류**이고, 워커 계약이 GRU 아티팩트를 전제하므로 배포하지 않았다. 뒤집을 만한 차이가 아니다.
- 닫은 방향: 채널 분해(−0.0011), 부족확률 분류 헤드(게이트 미달), 사업장 수 증설(학습곡선이 50곳부터 평평), zero-shot(−0.092).

### 게이트

v1의 원칙을 그대로 승계한다 — **베이스라인 없이 정교화하지 않는다.**

1. 통계 베이스라인을 먼저 구현하고 다운스트림 지표를 측정한다
2. 모델이 **다운스트림 지표에서** 베이스라인을 넘지 못하면 채택하지 않는다. pinball loss만 좋은 것은 채택 사유가 아니다
3. 채택하더라도 베이스라인 경로는 **폴백으로 남긴다**(아래 「폴백」)

#### 게이트는 판정 보수성 α 에 딸려 있다 (2026-09-09 실측 · 3번 파트)

워커는 `q10/q50/q90` 을 그대로 준다. 곡선을 만들어 「0 아래냐」를 판정하는 것은
API 서버(Layer 1)이고, **그 판정을 어느 분위수로 하느냐가 α 다.**

```
잔여입금(d) = q50(d) + α · (q10(d) − q50(d))      적게 들어온다고 본다
잔여출금(d) = q50(d) + α · (q90(d) − q50(d))      많이 나간다고 본다
```

α 는 모델만의 값이 아니다. **모델 경로와 통계 폴백 경로에 똑같이 적용된다.** 그래서
물어야 할 것은 「모델의 최적 α」가 아니라 **「그 α 에서도 모델이 통계를 이기는가」**다.
운영 구간(과거 30일~1년, `residual-gru` − 통계 베이스라인, 짝지은 부트스트랩) —

| α | 공백 F1 차이 [95% CI] | 게이트 |
| ---: | --- | --- |
| **0.00** | **+0.0162 [+0.0080, +0.0244]** 유의 | **통과** |
| 0.05 | +0.0055 [−0.0027, +0.0131] 유의차 없음 | 탈락 |
| 0.10 | −0.0096 [−0.0169, −0.0027] 유의하게 나쁨 | 탈락 |

**즉 α = 0.00 은 계약의 선택 사항이 아니라 이 채택 판정의 전제다.** API 20.11 이
응답에 `judgmentAlpha` 를 실어 보내는 이유가 이것이다 — 문서에만 적으면 재학습했을 때
값이 가중치와 어긋난다. α 는 모델 상수가 아니라 **데이터에 딸린 값**이고, 옛 데이터에서
정한 0.10 을 새 데이터에 그대로 썼다가 공백 F1 이 0.687 → 0.612 로 깎인 적이 있다.

α 를 올리는 것은 **정밀도를 팔아 경보를 앞당기는 거래**다 — 모델 기준 0.00 → 0.05 에서
최초 부족일 오차가 9.14 → 7.63일(−1.51일 [−1.73, −1.28])이고 정밀도가 0.708 → 0.637 로
떨어진다. 양쪽 다 유의하다. 제품이 그 거래를 원하면 **게이트를 다시 돌려야 하고, 지금
숫자로는 그때 쓸 것은 통계 경로다.**

*표본 하한과 묶여 있다.* 과거 7~30일 구간은 α=0.00 이면 게이트를 떨어지고
0.05·0.10 이면 통과한다. 지금은 하한이 30일이라 그 구간이 호출되지 않지만
(`features.MIN_HISTORY`), **하한을 내리면 α 도 같이 다시 정해야 한다.**

재현: `private/현재/forecast-lab/audit/alpha_gate.py` (창 9,600개 · 데이터 `a82bc981`).

#### 공백 기준선은 사용자가 정한다 — 판정이 거기에는 안 흔들린다 (2026-09-10 실측)

그런데 제품에서 그 선은 **사장님이 정한다** — `core.safety_balance_policy` 가 P0-08 로
들어와 있다(`V5`). 0원까지 가서야 알려주면 늦고 「50만원 아래면 알려줘」가 쓸모 있다.

확인해야 했다. 사업장마다 규모가 달라 절대 금액으로는 비교가 안 되어 **창의 시작 잔액에

7.63일 vs 7.54일, 0.09일 차이다. 첫째 조건(F1)은 통과한다.

않지만, **채택 근거 +0.016 은 이 칸이 만든 것**이라고 읽어야 정확하다.

**「잔여가 클수록 모델이 낫다」는 관계는 없다.** 0.45 이상에서 유의하지 않고, 통계와
모델이 **같이** 무너진다(0.567 → 0.436). 잔여가 커지면 예측 불가능한 몫이 느는 것이지
모델이 그것을 잡아내는 것이 아니다. 전체 길이로 재면 같은 칸이 **−0.013 으로 유의하게
나쁘다** — 컨텍스트가 길면 통계가 더 이득을 본다.

> **이것이 「재학습해야 하나」에 대한 답이다.** 시연 CSV 한 곳에서 모델이 통계에 졌을 때
> 「학습 분포 밖이라 재학습이 필요하다」가 자연스러운 결론으로 보였다(그 가게는 잔여 입금이
> 71%의 날에 있고 학습 데이터 200곳의 최대가 41.6%다). **재학습은 싸지 않다** — 지문이
> 바뀌어 채택 게이트와 α 를 처음부터 다시 돌려야 하고 쌓아둔 기록이 비교 불가능해진다.
> 위 표는 **잔여가 커도 모델이 더 이기지는 않는다**고 말하고, 게다가 `BUSINESS_DAILY`를
> 넣고 나면 **그 가게의 잔여 몫은 0.000 이다** — 맞힐 것이 남지 않는다. **재학습이 아니라
> 탐지(G-2)를 고치는 것이 답이었다.**

## 공통 — 재현성 · 폴백 · 서버 예산

### 재현성 — `basis` 스냅샷으로 구조적으로 보장한다

SRS 13장 인수 조건이 "7/14/30일 잔액과 부족일이 **동일한 입력에 대해 재현된다**"를 요구한다. 모델 추론은 CPU 스레드 수만 바뀌어도 부동소수점 합산 순서가 달라져 비트 단위 동일을 보장하지 못한다.

**해법 — 추론 결과를 `FORECAST_RUN.basis`에 스냅샷으로 남긴다.** `basis`는 이미 "실행 시점 불변 스냅샷" 용도로 설계돼 있다(ERD `FORECAST_RUN`). 잔여 분위수와 보정 계수를 여기 기록하면 같은 `FORECAST_RUN`의 재조회는 항상 같은 값이고, **재현성이 저장 구조에서 보장된다.**

- 인수 조건 문구는 "동일 입력 **+ 동일 모델 버전**에 대해 재현된다"로 개정한다(SRS 13장)
- `FORECAST_RUN.model_version`은 **계산 엔진 버전 + 모델 아티팩트 버전**을 함께 담는다 (예: `engine-1.2/residual-gru-0.3.0+a82bc981`). 아티팩트 버전에 **학습 데이터 지문**이 붙는 이유는 위 인수 조건 때문이다 — 구조를 안 바꾸고 데이터만 바꿔 재학습하면 버전이 그대로여서 **재현성 보증이 조용히 깨진다**
- Layer 1·3은 여전히 순수 함수다. 모델 출력은 **인자로 주입**되고 함수 안에서 추론을 호출하지 않는다

## G-1. 지연 보정 — 날짜만 정의되고 금액이 비어 있다

### 문제

`HOLIDAY_SHIFT`(P1-04)와 `ACCURACY_CORRECTION`(P1-05)은 모두 **`expected_date`만 이동**시킨다. `amount_expected`를 어떻게 다루는지가 어디에도 없다.

지연은 소멸이 아니라 이연이므로, 날짜만 옮기면 다음 세 가지가 누락된다.

| 누락 | 내용 |
| --- | --- |
| **연휴 전후 금액 변동** | 연휴 직후 회차는 커버 구간이 길거나 연휴 매출이 반영돼 평소와 금액이 다르다. 배달 업종은 증가, 오피스 상권은 감소 |
| **지연–금액 결합** | `matched_date_diff_days`와 `matched_amount_diff`를 **독립 집계하면 "밀린 회차는 금액도 크다"는 상관을 놓친다** |
| **다건 병합 규칙** | 연휴로 여러 회차가 한 영업일에 몰릴 때 건수를 유지할지 1건으로 합칠지 미정의 |

> **주의 — "예측 창 내 총액 보존 제약"은 걸지 않는다.** 창 경계를 넘어간 정산(9/28 → 10/2)은 해당 월의 **정당한 감소**이므로, 총액을 억지로 보존하면 오히려 곡선이 왜곡된다. 보정 대상은 총액이 아니라 **회차별 금액 배율**이다.

### 판정

날짜 보정과 금액 보정을 **별개 조정 항목**으로 정의한다.

| 조정 | 대상 | 산출 |
| --- | --- | --- |
| `HOLIDAY_SHIFT` (기존) | `expected_date` | 영업일 달력 기반 결정론 |
| `HOLIDAY_AMOUNT_SCALE` (신규) | `amount_min/expected/max` | 연휴 직후 회차의 과거 금액 배율 중앙값 |

통계 집계 시 **연휴 인접 회차를 별도 표본군으로 분리**한다. 전체 평균에 섞으면 배율이 1에 수렴해 보정이 무력화된다.

> **M-2와의 관계 (v2)** — XGBoost 분위수 회귀를 채택하면 연휴 인접 거리가 **피처**가 되므로 표본군 분리와 지연–금액 결합이 모델 안에서 처리된다. `HOLIDAY_AMOUNT_SCALE`은 **모델 미적용 구간(표본 부족·폴백)의 베이스라인**으로 남는다. 둘 중 하나만 고르는 것이 아니라 계층이 다르다.

### 근거

- 정산 공백 판정은 "특정 시점에 돈이 없는가"이고, 이연은 **정확히 그 시점을 결정하는 요소**다. 금액을 고정한 채 날짜만 옮기면 지연 구간을 과대·회복 구간을 과소 추정해 오탐 알림이 발생한다
- API 10.2가 `firstShortfallDate`·`maxShortfallAmount`·`durationDays`·`expectedRecoveryDate`를 모두 요구하므로, 회복 시점의 금액 정확도가 응답 4개 필드에 직접 영향한다

### 반영 위치

- API 10.1 `adjustments.type` — `HOLIDAY_AMOUNT_SCALE` 추가
- `FORECAST_RUN.basis.adjustments` — 배율과 근거 표본 수 기록
- P1-05 정확도 집계 — 연휴 인접 표본군 분리

## G-2. `BUSINESS_DAILY` cadence — 카드 정산을 표현할 수 없다

### 문제

API 9.2의 `cycle.type`은 `WEEKLY`(요일 반복) · `MONTHLY`(일자 반복) · `INTERVAL`(N일 간격) 3종이다. 카드 정산은 **영업일마다 발생**하는데 어느 것으로도 맞지 않는다.

| 우회안 | 결과 |
| --- | --- |
| `INTERVAL = 1` | 주말·공휴일에도 입금 예측 — 곡선에 없는 입금이 찍힌다 |
| `INTERVAL = 1` + `NEXT_BUSINESS_DAY` | 토·일 예정분이 월요일로 이월돼 **한 날에 3건**. 실제는 영업일당 1건이고 금액만 요일마다 다르므로 건수가 부풀려진다 |
| `WEEKLY` 5개(월~금) | 카드사 4곳이면 패턴 20개. 사용자가 승인·관리할 수 없다 |

**실질 위험은 탐지 단계다.** API 9.1에 따르면 예측 입력은 `CONFIRMED` 패턴에서 생성된 `PlannedTransaction`뿐이다. 카드 정산이 저신뢰 후보로 잡히거나 요일별로 쪼개지면 사용자가 승인하지 않고, 그러면 **카드 입금이 잔액 곡선에서 통째로 빠진다.**

> **G-4와 혼동 주의.** 금융망 카드 API(G-4)는 카드 **소지자 지출** 측이라 여기서 말하는 카드 정산 **입금**과 무관하다. 실사용에서 카드사 정산금은 은행 계좌 거래내역에 입금으로 찍혀 CSV·계좌 동기화 경로로 들어온다. 따라서 이 갭은 시연 환경에서는 드러나지 않고 실사용에서만 드러난다.

### 판정

`cadence_type`에 **`BUSINESS_DAILY`**를 추가한다.

- 날짜: `BUSINESS_CALENDAR_DAY.day_type = 영업일`인 날에만 인스턴스 생성. 연휴 길이만큼 자동 스킵되므로 **별도 지연 보정이 필요 없다**
- 금액: **요일별로 다르다.** 주말 매출분이 D+2로 유입돼 주 초 회차가 크다 — 실측에서 월요일이 나머지의 3배다. **담을 자리를 아래 「금액 축」에서 다시 정한다** (v1이 지목한 `SEASONAL_FACTOR`로는 표현되지 않는다)
- 카드사별로 패턴을 분리한다. D+2/D+3이 다르고 가맹점 수수료율도 달라 순액 비율이 다르다. 적요(`신한카드`·`KB국민카드`)로 `COUNTERPARTY` 사전에서 자연히 분리된다

### 근거

- 카드 지연은 확률적이지 않고 **영업일 달력에서 결정론적으로 계산**된다. 따라서 통계 지연 보정(G-1·G-3)은 주로 플랫폼 정산에 필요하고 카드는 달력 계산으로 끝난다 — `matched_date_diff_days`가 0에 수렴한다
- ~~`SEASONAL_FACTOR`가 이미 "**요일**·월·시즌 예측 계수"로 정의돼 있어 금액 축은 스키마 변경 없이 처리된다~~ — **철회 (2026-09-10).** 아래 「금액 축」 참조
- `BUSINESS_CALENDAR_DAY`가 이미 존재하므로 구현 비용은 cadence 분기 하나다

### 실측 — 이득의 크기 (2026-09-09 · 3번 파트)

판정은 v1부터 있었지만 **얼마나 이득인지는 재본 적이 없었다.** 「P0-03 탐지에 착수하기 전에 이걸 닫아야 한다」는 요청이 나와, 팀원이 만든 시연용 거래 CSV(카페 1곳 · 2026-04-01~09-27 · 180일)로 쟀다.

> 위 G-4 주석은 이 갭이 "시연 환경에서는 드러나지 않는다"고 적었는데, **시연용 CSV에서는 드러났다.** 같은 주석이 지목한 두 유입 경로(CSV·계좌 동기화) 중 하나다.

**카드 정산이 입금의 절반을 넘는다.**

| 항목 | 값 |
| --- | --- |
| 적요 `신한카드` 건수 | 124건 — **월~금에만 있고 토·일은 0건** |
| 입금 총액 대비 | **58.5%** (22,775,800 / 38,925,200원) |
| 요일별 median | 월 385,750 · 화 128,500 · 수 134,800 · 목 126,000 · 금 118,600원 |

토·일이 0건이므로 우회안 `INTERVAL = 1`은 **실제로 없는 입금을 주말에 찍는다** — 위 표의 예상이 그대로 확인된다. 월요일이 나머지의 3배인 것은 판정이 적어 둔 「주말 매출분이 D+2로 유입돼 주 초 회차가 크다」의 실측이고, 그래서 금액 축을 `SEASONAL_FACTOR` 요일 계수로 두는 것도 맞다.

**곡선 오차가 85% 줄어든다.**

| | 헛경보 | 곡선 평균오차 |
| --- | ---: | ---: |
| 지금 — 카드 정산이 잔여로 간다 | 0 / 8창 | **1,895,833원** |
| `BUSINESS_DAILY`가 있다면 | 0 / 8창 | **279,163원** (−85%) |

지금이 나쁜 이유는 **M-1 모델이 잔여 입금을 거의 0으로 예측**하기 때문이다 — 학습 데이터의 잔여 입금 66%가 실제로 0이라 중앙값 0이 맞고, **매 영업일 들어오는 카드 정산은 그 분포에 아예 없다.** 예정거래로 빠지지 않으면 곡선이 카드 입금만큼 통째로 내려앉는다.

> *2026-09-10 두 번째 정정 — 이 표는 하루 사이에 두 번 바뀌었다.* 처음 `6,637,118 → 4,684,823 (−29%)`, 위상 버그를 고쳐 `5,557,987 → 3,620,674 (−35%)`, 그리고 **주기 오분류 버그 둘**(아래 「구현 함정」)을 고쳐 지금 값이 됐다. **비교 방식도 바꿨다** — 예전에는 카드를 손으로 흉내 내 얹었는데, 탐지기가 `BUSINESS_DAILY`를 직접 만들게 된 뒤로는 그게 **이중 계상**이 된다. 지금은 탐지 가설 하나만 껐다 켠다.
>
> **헛경보가 사라진 것이 이 정정의 핵심이다.** 예전 8/8은 cadence 부재가 아니라 **내 투영기가 월 1회 청구를 「매주」로 잡아 30일에 4번씩 빼던 것**이 만든 값이었다. 그것을 고치니 양쪽 다 0/8이다. **cadence 부재만으로는 헛경보가 나지 않는다** — 카드가 잔여로 가면 곡선이 낮아지지만 이 계좌는 잔액 여유가 커서 0을 안 넘는다. 이득은 곡선 오차 한 축으로만 말해야 한다. 카드 정산 58.5%는 세 번 모두 그대로다.

**한계 — 이 숫자로 말할 수 없는 것**

- **실제 공백이 한 창에도 없다** (계좌 일별 종료잔액 최저 823,100원). 그래서 공백 F1과 최초 부족일 오차는 못 쟀고, 읽을 수 있는 것은 곡선 오차와 헛경보뿐이다. 헛경보 8→6도 창 8개 위의 2건이라 신뢰구간을 낼 표본이 아니다
- 사업장 1곳 · 180일 · 창 8개다 (과거 90일을 요구하고 7일 간격으로 잘랐다)
- **헛경보로는 아무것도 말할 수 없다** — 양쪽 다 0/8이다. 이 계좌가 잔액 여유가 커서 곡선이 낮아져도 0을 안 넘는다
- 영업일 판정을 **공휴일까지 보고** 했다(`월~금 AND 공휴일 아님`). 판정의 `BUSINESS_CALENDAR_DAY` 연동과 같은 규칙이다

재현: `private/현재/forecast-lab/audit/business_daily.py` — 실험 코드는 레포 밖이다.

### 금액 축 — `SEASONAL_FACTOR`로는 표현되지 않는다 (2026-09-10 · V5 작성자 판단)

v1은 「`SEASONAL_FACTOR`가 이미 요일 계수라 스키마 변경이 없다」고 적었다. **ERD의 컬럼을 다시 읽으니 그렇지 않다.**

| 왜 안 되나 | 근거 |
| --- | --- |
| **요일 칸이 없다** | 컬럼이 `business_id`·`factor_type`·`effective_from`/`to`·`multiplier`·`model_version`·`confirmed`뿐이다. `effective_from`~`to`는 **그 안의 모든 요일을 함께 덮는다** — 「월요일만 ×3」을 적을 자리가 없다 |
| **사업장 단위다** | 패턴이 아니라 사업장에 붙는다. PG가 둘이면(신한·KB) 요일 모양이 달라도 갈라낼 수 없다 |

`RECURRING_PATTERN` 쪽도 `expected_amount_min`/`max` 두 칸이라 점 하나다. 요일 간 3배 차이를 이 범위로 덮으면 **범위가 너무 넓어져 제약 구실을 못 한다.**

**얼마짜리인가 — 1.5배 · 133,797원.** 같은 백테스트에서 금액만 바꿔 쟀다.

| 금액 표현 | 곡선 평균오차 |
| --- | ---: |
| 요일별 (지금 실험실 구현) | **279,163원** |
| 단일 median (`amount_min`/`max`만 있는 세상) | 412,960원 |

재현: `private/현재/forecast-lab/audit/weekday_axis.py`.

**반영됨 (2026-09-11 · MR !76).** 제안대로 `RECURRING_PATTERN`에 nullable JSONB 한 칸이 들어갔다(`V10`). `BUSINESS_DAILY`일 때만 채우고 나머지 cadence는 `null`이며, `null`이면 기존 `expected_amount_min`/`max` 경로로 그대로 떨어진다.

- **패턴 단위라 PG가 둘이어도 갈라진다** (`SEASONAL_FACTOR`가 못 하는 것)
- nullable 컬럼 추가는 `backend-architecture.md` §5의 **허용** 목록에 있다 — 롤백이 깨지지 않는다
- `SEASONAL_FACTOR`는 원래 자리(P1-07 계절성 — 월·시즌 배율)에 그대로 둔다. **성격이 다르다** — 이쪽은 사업장 전체에 걸리는 배율이고, 요일별 정산액은 패턴 하나의 금액이다

**모양이 제안과 다르다 — 스칼라가 아니라 분위수 셋이다.** 제안은 `{"1":385750, ...}` 였는데 구현은 이렇다.

```json
{"1": {"lo": 342600, "mid": 394300, "hi": 437600},
 "2": {"lo": 114300, "mid": 132800, "hi": 146200}}
```

중앙값 하나만 담으면 **범위를 여전히 통짜 `min`/`max`에서 가져와야 한다.** 그러면 밴드는 안 좁아지고 중앙선만 고쳐진다 — 문제의 절반만 푼다. `lo`/`hi`는 **q10/q90**이다. 최소·최대로 잡으면 이상치 한 건이 그 요일 폭을 혼자 만든다(화요일 582,100원 한 건이 폭 47만원).

표본이 한 요일이라도 6건(`MIN_WEEKDAY_SAMPLES`) 미만이면 **전체를 `null`로 둔다.** 3~4건으로 뽑은 q10/q90은 사실상 최소·최대라 폭을 좁히려는 목적을 잃고, 일부 요일만 채우면 같은 패턴 안에서 기준이 갈린다.

**실측 효과** (하노식당 · 신한카드 124건 · 2026-04-01~09-23).

| | 통짜 min/max | 요일별 |
| --- | ---: | ---: |
| 하루 폭 | 471,500원 | 28,600~95,000원 |
| 30일(영업일 20) 누적 폭 | 9,430,000원 | **867,000원** (−91%) |
| 중앙선 | 346,350원 고정 | 월 394,300 · 화~금 119,500~134,700 |

`(min+max)/2 = 346,350`을 모든 날에 쓰면 월요일엔 5만원 모자라고 화~금엔 **2.7배 과대**하다.

⚠ **위 −91%는 화면 밴드가 아니라 「이 패턴이 밴드에 보태는 몫」이다.** 곡선 밴드는
`Σ예정 폭 + Σ잔여 q10~q90`인데, 실측에서 30일 밴드 32,874,488원 중 **예정 전체가
2,048,200원(6%)이고 나머지 94%가 잔여**다. 예정 거래가 하나도 없는 날(2026-09-12)에도
밴드가 558,435원이다 — 전부 모델이 낸 잔여 폭이다.

**그래서 이 변경으로 화면 밴드가 눈에 띄게 좁아지지는 않는다.** 같은 데이터로 재면
예정 몫이 10,611,400 → 2,048,200 이라 전체 밴드가 약 20% 줄어드는 정도다. 이 항목의
값어치는 **중앙선**에 있다 — 월요일마다 5만원씩 어긋나던 것이 없어진다. 밴드를 실제로
좁히려면 잔여 쪽(M-3 판정 보수성 α, 모델 자체)을 건드려야 한다.

**후속 — 신뢰도도 같은 범위로 재야 한다** (S15P21C105-143). 예정 거래는 요일별로 만들면서 `RecurringPatternDetector.score()`의 금액 안정성은 통짜 `min`/`max`로 재고 있었다. 같은 패턴을 두 잣대로 본 셈이다.

| | 통짜 | 요일별 |
| --- | ---: | ---: |
| 금액 안정성 | 0.595 (5.26배) | 0.894 (1.25~1.29배) |
| 신한카드 패턴 신뢰도 | 0.5849 | 0.8793 |
| 곡선 일별 신뢰도 평균 | 0.5972 | 0.6554 |
| 화면 배지 | 낮음 | **보통** |

`MEDIUM` 경계가 0.60이라 **0.003 차이로 낮음**에 걸려 있었다. 남은 강등 한 축은 데이터 문제다 — 과거가 164일이라 180일 미만 강등(×0.85)에 걸린다(`ConfidencePolicy.DEGRADED_HISTORY_DAYS`).

### 구현 함정 셋 — 둘은 밟았고 하나는 앞에 있다 (2026-09-10)

`BUSINESS_DAILY`를 넣고도 곡선이 쳐져서 파 보니 **cadence와 무관한 버그 둘**이 있었다(①②). 그것을 고치고 BE 코드를 읽다가 **아직 아무도 안 밟은 것 하나**를 더 찾았다(③). 탐지·투영을 구현하는 쪽에서 같은 것을 밟을 수 있어 적어 둔다.

**① `WEEKLY`는 요일뿐 아니라 간격도 봐야 한다.** 공휴일 밀림을 견디려 요일 허용폭을 ±3일로 두면 **7일 중 4일을 덮는다.** 그래서 간격이 14일이든 30일이든 「매주」로 통과했다 — 월 1회 청구(한전·가스·KT)가 30일 예측에 **4번씩** 찍혔다. 관측일 간격의 중앙값이 6~8일인지 보는 한 줄이 격주·월간을 갈라낸다. (`기능별_기술스택_선정.md` §4.3이 경고한 바로 그 함정이다.)

**② 주기당 발생 횟수는 n−1로 센다.** n번 관측되면 그 사이 간격은 **n−1개**다. `len(days)`로 세면 한전 5회/121일이 「월 1.26회」가 되어 상한에 걸리고 **정답인 `MONTHLY`가 후보에서 걸러진다.** n−1로 세면 1.01이다.

둘을 고치자 30일 투영 순증감이 **−3,817,400 → +311,300원**(실제 −52,800원)이 됐고, 시험 데이터 탐지 **정밀도가 72.0% → 74.7%**로 올랐다(재현율 100% 유지).

**③ `BUSINESS_DAILY` 투영은 공휴일을 건너뛰어야 한다** *(2026-09-10 제기 · **2026-09-13 반영**)*. 들어온 탐지기(`BusinessDaily.tryMatch`)는 **주말만 본다** — `isWeekend` 뿐이고 공휴일 개념이 없다. **탐지에서는 문제가 안 된다**: 커버리지 분모가 6%p쯤 부풀 뿐 0.6 위를 유지한다. **투영에서 갈린다** — 판정이 「`BUSINESS_CALENDAR_DAY.day_type = 영업일`인 날에만 인스턴스 생성」이라고 적었지만, 그 연동을 빼먹고 `월~금`으로만 짜면 **빨간날에 없는 입금을 만든다.**

같은 CSV의 신한카드(월 385,750 · 화~금 118,600~134,800)로 재면:

| 30일 창 | 공휴일까지 봄 | 주말만 봄 | 없는 입금 |
| --- | ---: | ---: | ---: |
| 설날이 낀 창 | 3,188,850원 | 3,837,900원 | **+649,050원** |
| 추석이 낀 창 | 3,456,000원 | 3,819,200원 | **+363,200원** |
| 어린이날이 낀 창 | 3,446,100원 | 3,574,600원 | +128,500원 |

**설날 창의 649,050원은 이 사업장 곡선 전체 오차(279,163원)의 두 배가 넘는다.** 2026년 평일 공휴일이 9일이므로 연 **1,385,350원**이 없는 입금으로 잡힌다. 곡선이 위로 뜨면 **공백을 못 잡는다** — 미탐 쪽이라 대가가 크다(위 M-3).

⚠ **P0-04 예정일 계산에서 `BUSINESS_CALENDAR_DAY` 연동을 빼먹지 않는 것**이 이 항목의 전부다.

**반영됨** (`BusinessCalendar` · `S15P21C105-156`). 별도 테이블 대신 **상수 달력**을 뒀다 — `BUSINESS_CALENDAR_DAY` 는 사업장마다 다른 영업일까지 담는 테이블인데, 지금 필요한 것은 관공서 공휴일 하나뿐이라 그것부터 넣었다. `BUSINESS_DAILY` 는 공휴일에 **회차 자체를 만들지 않고**, 나머지 주기는 저장만 되고 안 쓰이던 `holidayRule` 로 앞뒤 영업일에 붙인다.

**이월은 아직 안 한다.** 실제로는 공휴일 매출이 다음 영업일 정산에 얹히는데, 그러려면 **그날 가게가 열었는지**를 알아야 한다 — 명절에 닫는 가게와 여는 가게가 다르고 백엔드는 그 정보가 없다. 그래서 위 표의 「없는 입금」은 사라지지만, 다음 영업일이 그만큼 커지는 것은 아직 반영되지 않는다. 그건 `BUSINESS_CALENDAR_DAY` 가 실제로 필요해지는 자리다.

목록이 **세 곳**(시드 생성기 · 워커 · 백엔드)에 있어 테스트로 묶어 뒀다. 실제로 워커에 대체공휴일 둘(3/2 · 5/25)이 빠져 있었고 그 비교에서 찾았다. 실험실은 `공휴일 아님 AND 월~금`으로 정의해 두었다 (`ai/app/forecast/patterns.py:_is_settle_day`).

**판정은 바뀌지 않는다. 순서가 정해진다.** P0-03 반복 거래 탐지에 착수하기 **전에** cadence를 열어야 한다. 안 열면 입금의 58.5%가 탐지 대상에서 구조적으로 빠지고, **탐지 재현율이 모델보다 예측 성능을 지배하므로**(M-3 「모델보다 탐지 재현율이 성능을 지배한다」) 그 손실은 모델 쪽에서 메울 수 없다.

**그러므로 지금 만들 필요가 없다.** 만들어도 위 「금액 축」이 필요로 하는 것을 못 한다 — 요일 칸이 없고 사업장 단위다. `SEASONAL_FACTOR` 는 원래 자리(P1-07 계절성 — 월·시즌 배율)에 그대로 두고, **요일별 정산액은 다른 칸으로 받는다.**

**`holiday_rule` 함정은 알고 미뤄 뒀다.** 탐지기가 모든 패턴에 `NEXT_BUSINESS_DAY` 를 넣지만(`RecurringPattern.java`) **그 값을 날짜에 적용하는 코드가 아직 없다.** 구현현황 §3.15 가 그렇게 적어 두었다 — 「`holidayRule` 을 저장하고 응답에 실어 보내지만 날짜를 옮기지는 않는다」. **P1-04(영업일 보정)에서 켤 때가 위험한 순간이다** — `BUSINESS_DAILY` 는 이미 주말을 건너뛰므로, 그 위에 이월 규칙을 또 걸면 연휴 예정분이 다음 영업일로 몰려 **한 날에 여러 건**이 된다. 위 우회안 표의 두 번째 실패가 그대로 재현되는 자리다. 그때 `BUSINESS_DAILY` 는 `NONE` 으로 두어야 한다.

## G-3. `MERCHANT_MASTER` — 교차 사업장 통계가 불가능하다

### 문제

`COUNTERPARTY`는 `business_id` FK를 가진 **사업장별** 거래처 사전이다. "배달의민족"이 사업장 수만큼 별개 행으로 존재하고, 이들을 묶는 전역 키가 없다.

ERD는 거래처별 평균 지연일을 `PLANNED_TRANSACTION` 매칭 결과에서 집계한다고 정의하는데, 조인 키가 사업장 안에 갇혀 있어 **표본이 사업장당 3~5건**에 그친다. 이 표본으로는 중앙값도 신뢰할 수 없다.

### 판정

전역 `MERCHANT_MASTER` 테이블을 도입하고 `COUNTERPARTY.merchant_master_id` FK로 연결한다.

- 플랫폼(배민·쿠팡이츠·요기요), 카드사, PG는 목록이 유한하므로 **시드 데이터로 선적재** 가능
- 매칭되지 않는 로컬 거래처는 `merchant_master_id = null`로 두고 사업장 내 통계만 사용
- 통계 산출 시 `merchant_sample_count`를 함께 노출해 표본 부족을 신뢰도에 반영한다

### 근거

- 배민 정산 주기는 사업장이 달라도 동일하다. **교차 사업장 집계가 통계 보정의 유일한 성립 근거**다
- 이것이 없으면 G-1의 연휴 배율도 사업장당 표본 1~2건이라 산출 자체가 불가능하다
- API 10.4 `byMerchant` 응답이 이미 `sampleCount`·`avgDelayDays`·`appliedCorrection` 구조라 전역 집계로 바꿔도 응답 스키마는 그대로다

### 반영 위치

- ERD — `MERCHANT_MASTER` 신규, `COUNTERPARTY.merchant_master_id` 추가
- API 10.4 `byMerchant` — 표본 출처(전역/사업장) 구분 필드 검토

## G-4. 금융망 카드 API — 출금 축은 예측이 아니라 확정 데이터다

### 확인 결과

`SSAFY_교육용_금융망_API_Inferface_예제.xlsx`의 `CREDIT_CARD_01~13`을 확인했다. **가맹점 매출 입금이 아니라 카드 소지자(지출) 측 API다.**

| API | 실제 내용 |
| --- | --- |
| `createMerchant` (CC_02) | 가맹점 마스터 데이터 등록 — 결제 **대상** 목록을 만드는 관리자 기능 |
| `createCreditCardTransaction` (CC_09) | 사용자가 가맹점에서 **결제**(지출). 예제 `merchantName: 코스트코 / paymentBalance: 500000` |
| `inquireCreditCardTransactionList` (CC_10) | 카드 결제 내역 + **`estimatedBalance`(청구예정금액)** |
| `inquireBillingStatements` (CC_12) | 청구서 — 주 단위 발행, 지정일 자동 출금 |
| `updateWithdrawalAccount` (CC_13) | 결제 출금계좌·결제일 변경 |

**따라서 카드 매출을 예측 입금 축에 넣을 수는 없다.** 우리 사용자는 가맹점이 아니라 카드를 쓰는 쪽이다.

### 판정 — 출금 축을 3층으로 정의한다

CC_12의 청구 규칙이 명시적이다: *"월~일(일주일) 카드 거래 내역을 반영하여 차주 월요일 7:30 발행, 설정한 출금날짜 16:00에 출금 연결계좌에서 자동 출금."*

| 층 | 근거 | `PlannedTransaction` |
| --- | --- | --- |
| **확정** | 청구서 발행 + `billStatementsStatus = 미결제` + 출금일 지정 | `CONFIRMED`, `amount_min = expected = max` |
| **예정** | `estimatedBalance`(미발행분) — 차주 월요일 발행이 확정 | `EXPECTED`, 금액 확정 · 날짜 계산 |
| **추정** | 아직 발생하지 않은 카드 지출 | 과거 주간 평균 (유일한 통계 구간) |

앞 두 층은 **통계 보정 대상이 아니다.** API가 사실을 알려주므로 G-1·G-3의 보정 로직을 적용하지 않는다.

### 부수 효과

- **What-if 연동** — CC_13이 결제일 변경을 제공하므로 `EXPENSE_DATE_SHIFT` 시나리오가 실행 가능한 조언이 된다. 단 설계 원칙 4(자동 실행 금지)에 따라 서비스는 시뮬레이션만 하고 실행은 사용자가 한다
- **시연 데이터** — CC_09로 카드 결제를 직접 생성할 수 있어 지출 축 시연 데이터는 API로 확보된다. 입금(정산) 축은 **DD_09 계좌 입금**을 쓴다(G-5)
- **분류 부하 감소** — CC_10이 `categoryName`·`merchantName`을 이미 제공하므로 카드 거래는 LLM 분류 대상이 아니다. 분류 파이프라인은 계좌 적요 기반 거래에 집중한다

### 반영 위치

- ERD `PLANNED_TRANSACTION.source_type` — `CARD_BILLING` 추가 검토 (현행 `USER`·`PATTERN`·`TAX`·`LOAN`)
- API 7.3 금융망 동기화 — 카드 결제 내역·청구서 수집 경로 추가
- API 10.1 `basis.summary` — 확정/예정/추정 건수 구분

## G-5. 입금 축 시연 데이터 — `DEMAND_DEPOSIT_09`를 쓴다

### 확인 결과 — 카드에는 가맹점 입금 구조가 없다

먼저 확정한다. `CREDIT_CARD_*`에는 **가맹점이 돈을 받는 흐름이 존재하지 않는다.**

| 근거 | 내용 |
| --- | --- |
| `createMerchant`(CC_02) 요청 필드 | `categoryId` + `merchantName` **뿐**. 계좌번호 없음 |
| 동 API 헤더 비고 | `userKey 제외` — 특정 사용자에 귀속되지 않는 **전역 마스터 데이터** |
| 워크북 전체 검색 | `매출` 0건 · `settlement` 0건 · 가맹점 입금 0건 |

가맹점은 소유자도 계좌도 없는 **결제 대상 라벨**이다. 카드 결제는 단방향 지출로만 모델링돼 있다.

### 정산 구조는 `VIRTUAL_ACCOUNT_*`에 있다 (참고)

| API | 핵심 필드 |
| --- | --- |
| `createVirtualAccount` (VA_01) | `mainAccountNo`(본인 소유 연결 계좌) · `autoTransfer`(입금 후 자동이체, 기본 `true`) · `expiryDate` |
| `inquireVirtualAccountDeposits` (VA_04) | `depositAmount` · `depositedAt` · `settledAt` · `transferred` |
| `settleVirtualAccount` (VA_07) | `settledAmount` · `pendingAmount` · `settledAt` |

`autoTransfer = false`로 발급하면 입금이 **보류금**으로 적립되고, `settleVirtualAccount` 호출 시점에 연결 계좌로 넘어온다. 카드·플랫폼 정산과 구조가 같다.

```
고객 입금(매출 발생)  →  보류금 적립          [depositedAt]
        … D+n …
정산 실행             →  연결 계좌 입금        [settledAt, settledAmount]
```

### 카드 결제와 가상계좌는 연결되어 있지 않다

`createCreditCardTransaction`(CC_09)은 `merchantId`를 대상으로 하고, 응답에 계좌 이동 정보가 없다. 가상계좌는 `virtualAccountNo`로 **계좌 이체·입금**을 받는 별개 구조다. **"카드 결제하면 가상계좌로 자동 입금"되는 흐름은 존재하지 않는다.** 카드 결제는 어디로도 돈이 가지 않는 단방향 기록이다.

### 판정 — 기본 경로는 `DEMAND_DEPOSIT_09`

`updateDemandDepositAccountDeposit`(DD_09)이 가장 직접적이다.

| 파라미터 | 용도 |
| --- | --- |
| `accountNo` | 사업자 본계좌 |
| `transactionBalance` | 입금 금액 |
| `transactionSummary` | **입금계좌요약 = 적요.** `"배달의민족"`·`"신한카드 정산"` 지정 |

우리 파이프라인(패턴 탐지·규칙→사전→LLM 분류)의 입력이 **계좌 거래내역의 적요**이므로, 적요를 직접 지정할 수 있는 DD_09가 목적에 맞는다. 정산 지연 시연도 입금 호출 날짜를 늦추면 그만이다.

| 경로 | 단계 | 용도 |
| --- | --- | --- |
| **DD_09 계좌 입금** | 1회 호출 | **기본** — 패턴 탐지·분류·예측 곡선 시연 전부 |
| 가상계좌 정산 | 발급 → 이체 → D+n → `settle`, 4단계 | **P0-11 정산 대사 한정** |
| CC_09 카드 결제 | — | 매출 시연 **불가**(계좌 무변동). 지출·청구서 시연용 |

**가상계좌를 기본 경로로 쓰지 않는 이유** — 가상계좌가 추가로 주는 것은 `depositedAt`/`settledAt` 관측인데, 이는 우리가 생성한 값이라 이미 아는 정보다. 4단계 + 30일 만료 + 주문당 1계좌라는 비용에 비해 실익이 없다. 다만 **보류 입금 여러 건 vs 정산 1건** 구조는 P0-11 정산 대사 화면의 실제 데이터가 되므로 그 용도로는 유지한다.

### 여전히 학습 데이터가 아니다

어느 경로든 **우리가 생성하는 데이터**다. **M-2(XGBoost)에는 순환논법이 그대로 적용되며**, 그래서 M-2가 조건부이고 blind split과 표현 제약을 붙였다.

> **2026-09-08 정정.** 원래 이 자리에 「M-1(zero-shot)은 이 경로로 학습하지 않으므로 영향받지 않는다」가 있었다. **채택된 M-1(`residual-gru`)은 우리 데이터로 학습하므로 그 면제가 사라졌다.** 대신 상한(모수 오라클 0.733)을 같이 재서 생성 규칙을 되짚지 않았음을 확인하고, 주장 범위를 「같은 데이터에서 통계보다 낫다」로 좁혔다 — 위 「zero-shot …」 절 참조.

가상계좌를 쓰면 `settledAt − depositedAt`으로 절대 지연을 관측할 수 있으나, 이는 **시연 환경 한정**이다. 실사용에서 소상공인이 카드사·배달 플랫폼 정산을 가상계좌로 받지 않으므로, G-1의 잔차 타깃(`matched_date_diff_days`)을 그대로 유지한다. 시연 환경의 관측 가능성을 실사용 가정으로 옮기면 안 된다.

### 한계 (가상계좌 사용 시)

| # | 내용 | 영향 |
| --- | --- | --- |
| 1 | `expiryDate`가 발급일로부터 **30일 이내** | 장기 운영 불가 |
| 2 | **주문 1건당 1계좌**, `settleVirtualAccount`가 `virtualAccountId` 1개만 수신 | N건 정산 = N번 호출 = 연결 계좌에 소액 N건 |
| 3 | 정산 실행이 수동 API 호출 | 정산 배치를 직접 시뮬레이션해야 한다 |

한계 2는 **곡선에는 영향이 없다** — `DAILY_BALANCE_FORECAST.expected_deposit`이 일별 합계다. 영향받는 것은 패턴 탐지(건수 증가)와 거래 목록 UI다.

### 반영 위치

- 시연 데이터 생성 스크립트 — DD_09 반복 호출(적요·금액·날짜 지정)
- P0-11 정산 대사 — 보류 입금 합계(`depositAmount`) vs 정산액(`settledAmount`)이 대사 데이터 원천
- G-2 패턴 탐지 — 소액 다건 정산이 후보 탐지에 미치는 영향 확인 필요

## 부록 — 보정 대상과 담당 층 정리

매출은 보정 대상이 아니다. 일별로 관측하지 않기 때문이다(P1-22의 월 구성비는 여기 들어오지 않는다 — 배경 절).

**Layer 2-A 원장 — 정산 입금의 세 축**

| 축 | 베이스라인(통계) | M-2 채택 시 | 근거 컬럼 |
| --- | --- | --- | --- |
| 날짜 편차 | 패턴별 `matched_date_diff_days` 중앙값 (카드는 달력 계산으로 대체) | 지연일 분위수 회귀 | `PLANNED_TRANSACTION` |
| 금액 분포 | 패턴별 과거 입금액 분위수(q10/q50/q90) | 금액 배율 분위수 회귀 | `RECURRING_PATTERN.expected_amount_min/max` |
| 이연 결합 | 연휴 인접 표본군의 금액 배율 (G-1) | 연휴 인접 거리 피처로 흡수 | `SEASONAL_FACTOR.multiplier` |

**Layer 2-B 잔여 — 축 하나**

| 축 | 베이스라인(통계) | M-1 채택 시 | 근거 컬럼 |
| --- | --- | --- | --- |
| 잔여 흐름 | seasonal naive + 요일 median | `residual-gru` 분위수 | `DAILY_BALANCE_FORECAST.residual_*` |

**베이스라인 없이 정교화하지 않는다.** 통계 열이 곧 게이트의 기준선이자 폴백 경로다. 어떤 보정을 추가하든 — 통계든 모델이든 — **베이스라인 대비 개선**을 다운스트림 지표(공백 발생 F1, 최초 부족일 오차)로 확인한 뒤 채택한다(M-3).
