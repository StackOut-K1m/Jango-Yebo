# 지원사업 공고 수집기 (P1-15)

기업마당 공식 API 로 공고를 받아 백엔드에 밀어 넣는다. 명세 20.8.

```bash
npm run collect:programs -- --limit 20 --dry-run        # 적재 없이 모양만 확인
npm run collect:programs -- --region 광주               # 광주·전국 공고만, 상한 200
npm run collect:programs -- --max-structure 50          # 구조화를 50건으로 제한
npm run collect:programs                                 # 전량 (상한 200 은 그대로)
```

| 옵션 | 기본 | 무엇 |
| --- | --- | --- |
| `--max-structure N` | **200** | 한 번에 **새 본문을 받아** 구조화를 걸 상한. 넘는 것은 다음 실행. ⚠ **비용 상한이 아니다** — 아래 참조 |
| `--region <키워드>` | 없음 | 그 지역과 「전국」 공고만. 나머지는 뒤로 미룬다 |
| `--limit N` | 전량 | 목록 API 에서 받을 건수 |
| `--dry-run` | — | 적재하지 않고 첫 건 모양만 |

## 비용이 어디서 나는가

**수집 자체는 공짜다.** 돈은 구조화(20.6 LLM 호출)에서만 나가고, **`2단계 — 구조화큐 N` 의 N 이 곧 비용**이다.

| 모델 | 공고당 | 전체 1,526건 | +Batch(50%) |
| --- | ---: | ---: | ---: |
| Opus 5 | $0.033 | $50 | $25 |
| Sonnet 5 | $0.013 | $20 | $10 |
| Haiku 4.5 | $0.0066 | $10 | $5 |

원문 중앙값 **1,346자**(12건 실측) 기준 상한값이다. 단가는 기술스택 8장 표(2026-06-24 스냅샷).

> ⚠ **2026-09-17 정정 — 이제 실제로 돈이 나간다.**
>
> 여기 오래 「지금은 $0 이다」라고 적혀 있었다. `build_structurer` 가 `live` 에서도
> `StubStructurer` 를 돌려주던 때의 이야기이고, **티켓 94(2026-09-16)에서 `ClaudeStructurer`
> 가 붙었다.** 그 문장을 믿고 `--max-structure` 를 올리면 **바로 과금된다.**
>
> 서버 cron 을 붙인 뒤 실측: 200건을 큐에 넣어 **50건 성공 · 150건 실패**(레이트리밋),
> 성공분만 과금됐다. 남은 1,376건을 다 채우면 약 **$9** 다.

`AI_PIPELINE_MODE=live` 면 구조화 한 건마다 Anthropic 호출이 나간다. `stub` 이면 $0 이고
응답의 `pipeline` 이 `STUB` 으로 온다 — **금액을 말하기 전에 그 필드를 먼저 확인해라.**

비용이 나가는 것을 전제로 아래 셋을 넣어 뒀다.

1. **상한**(`--max-structure`, 기본 200) — `npm run collect:programs` 한 줄이 1,526건어치를 한 번에 쓰는 사고를 막는다. **`0` 은 「구조화하지 않는다」**로, 목록·제목·기관·기간만 $0 로 받는다 *(2026-09-17 수정 — 전에는 `Number(...) || 200` 이라 **0 을 주면 200 이 됐다.** 「돈 안 쓰고 받아 보자」는 시도가 정확히 반대 결과를 냈다)*
2. **마감 임박순** — 예산이 중간에 끊겨도 쓸모 있는 것부터 채워진다. 기간 없는 공고(1,526건 중 916건이 「예산 소진시까지」·「상시」)는 내일 읽어도 그대로 있다
3. **지역 좁히기**(`--region`) — 광주·전국은 572건(37%)이다. **버리는 게 아니라 뒤로 미루는 것**이고, 행은 원문 없이 남아 나중에 받아 온다

상한에 걸려 남은 것은 **다음 실행에서 이어 받는다.** 서버가 `needBody` 로 계속 알려 주므로 수집기가 어디까지 했는지 기억할 필요가 없다.

> ⚠ **`--max-structure` 는 비용 상한이 아니다** *(2026-09-17 실측으로 드러났다)*
>
> 여기 오래 그렇게 적혀 있었는데 **거짓이다.** 이 값은 **2단계(새 본문을 받는 것)에만** 걸린다.
>
> 1단계는 **목록 전량을 보내고**(`collect.mjs` 의 `items.map(forIngest)`), 서버는 그중
> **본문을 이미 가졌는데 구조화가 안 된 것**을 상한·지역과 무관하게 큐에 건다
> (`SupportProgramIngestService` — `needsStructuring = changed || !isStructured()`).
> 대개 **지난 실행의 실패분**이다.
>
> ```
> --region 광주 --max-structure 40 으로 1회 실행 (2026-09-17)
>
>   1단계 — 구조화큐 129 · 본문필요 1375      ← 재투입. 상한·지역 안 걸림
>   2단계 — 본문 40건 전달 · 구조화큐 40       ← 여기만 상한이 걸린다
>   합계 169건 · 성공 98 · 실패 71(429) · 약 $0.65   (예상 $0.26 의 2.5배)
> ```
>
> **다만 무한정 늘지는 않는다.** 재투입 대상은 본문을 가진 것뿐이고 본문은 2단계에서만
> 붙으므로 풀이 하루 최대 상한만큼만 커진다. 성공분은 빠지므로 **며칠이면 마른다** —
> 위 실측 뒤 남은 실패 71건은 이틀이면 소진된다.
>
> 그래도 **그 돈은 좁히려던 지역 밖 공고에 쓰인다.**
>
> 제대로 고치려면 **적재(20.8)가 상한을 알아야 한다.** 1단계가 아무것도 큐에 걸지 않고
> `needStructuring`(본문 있고 구조화 안 됨)을 돌려주면, 수집기가 `needBody` 와 합쳐
> **지역 필터와 상한을 걸어** 요청할 수 있다. 계약 개정이 필요해 마감 뒤 과제로 두었고
> **S15P21C105-243** 에 적어 뒀다.

## 무엇을 하나

**2단계로 돈다. 상세 페이지는 꼭 필요한 것만 받는다.**

```
1) 목록 API   GET bizinfoApi.do                       1,526건 · 호출 1회
2) 1단계 적재 POST .../support-programs:batch         본문 없이 목록만
              ← 서버가 needBody 로 「본문이 필요한 것」을 알려 준다
3) 상세 페이지 GET .../selectSIIA200Detail             needBody 에 있는 것만
4) 2단계 적재 POST .../support-programs:batch         본문을 실어 다시
              → 서버가 구조화 Job 을 건다
```

**이 구조가 아니면 매일 1,526번 남의 서버를 두드린다.** 0.7초 간격이면 18분이다. 기업마당이 주는 `updtPnttm`(수정일자)이 안 바뀌었으면 서버가 본문을 다시 달라고 하지 않으므로, 평소에는 바뀐 몇 건만 받는다.

**출처가 고치면 갖고 있던 본문은 낡은 것으로 본다.** 그걸로 구조화하면 옛 조건이 새 공고의 자격으로 저장된다 — 연장·정정된 공고에서 바로 일어나는 일이다.

## 왜 상세 페이지까지 가나

**목록 API 의 `description` 은 사업개요 한두 문장이다.** 원문이 아니다 (2026-09-15 공식 응답 예시로 확인).

요약을 원문인 척 모델에 보내면 **모델은 본문을 다 봤다고 여기고 `uncertainConditions` 를 비워 돌려준다.** 사장님은 자격이 있다고 읽고 서류를 준비한 뒤 기관에서 거절당한다 — 이 기능의 안전장치를 정확히 무력화하는 방식이다.

본문을 못 받으면 **비워서 보낸다.** 서버가 구조화를 걸지 않고 행만 남기며, 그 공고는 검색에서 빠진다. 요약으로 때우지 않는다.

## 크롤링 정책

**수집 대상 네 곳 중 세 곳은 `robots.txt` 가 크롤링을 금지한다** (공통규약 23장, 2026-09-15 조사).

| 사이트 | robots.txt | 여기서 |
| --- | --- | --- |
| 중소벤처24 · 소진공 | `Disallow: /` | **안 긁는다** |
| K-Startup | 공고 목록 경로 차단 | **안 긁는다** |
| 기업마당 | 공고 경로 허용 | 상세 페이지만 |

기업마당도 목록은 **공식 API** 로 받고, HTML 은 상세 본문 하나만 가져온다. 요청 간격 0.7초를 두고 `User-Agent` 에 연락처를 밝힌다.

소진공은 공고 전용 API 가 없지만 **그 공고가 기업마당에 실린다.** K-Startup·중소벤처24 는 확장 단계에 공공데이터포털 API 로 붙인다.

## 설정

**개발 기계는 `backend/.env`** 에서 읽는다 (`scripts/fin-account.mjs` 와 같은 규칙 — 시크릿을 인자로 받지 않는다). 다른 파일을 쓰려면 `COLLECTOR_ENV_FILE` 로 경로를 준다.

| 키 | 무엇 |
| --- | --- |
| `BIZINFO_API_KEY` | [기업마당 사용신청](https://www.bizinfo.go.kr/apiDetail.do?id=bizinfoApi) → 이메일로 발급. 로그인 불필요 |
| `AI_SERVICE_TOKEN` | 적재 경로 인증. 이미 있는 값이다 |
| `COLLECTOR_API_BASE_URL` | 기본 `http://localhost:8080` |

**서버에는 `backend/.env` 가 없다.** 저장소 미러에 시크릿이 안 들어가고 실값은 `~/app/secrets/` 에만 있다. 그래서 **수집기 전용 파일을 새로 만들지 않고 `jango-api.env` 를 그대로 가리킨다** — `AI_SERVICE_TOKEN` 이 이미 거기 있어서다(2026-09-16 확인).

따로 두면 그 토큰이 **두 벌**이 되고, 한쪽만 교체되면 수집기가 **조용히 401 을 받는다.** 컨테이너가 안 읽는 변수가 둘 느는 쪽이 낫다고 봤다. 서버에 더할 것은 둘뿐이다.

```
BIZINFO_API_KEY=...
COLLECTOR_API_BASE_URL=http://localhost:8080
```

## ⚠ 한 번에 많이 넣으면 대부분 실패한다 (2026-09-17 실측)

`--max-structure 200` 으로 돌렸더니 **50건 성공 · 150건 실패**였다.

```
PROGRAM_STRUCTURING  COMPLETED    50
PROGRAM_STRUCTURING  FAILED      150   (attempt_count=1)
app.nlp.router - 공고 구조화 실패 stage=model: 요청 한도를 초과했습니다.
```

**원인은 동시성이다.** 백엔드는 잡을 집어 워커에 넘기고, 워커는 `202` 를 즉시 돌려준 뒤
`BackgroundTasks` 에서 처리한다. **워커 쪽에 동시 실행 상한이 없어** 200건이 한꺼번에
Anthropic 으로 몰린다.

**워커는 429 를 `retryable=True` 로 표시하지만 아무도 그 값을 안 본다.** 백엔드의
`JobSweeper` 는 *멈춰 있는*(`PROCESSING` 이 `stallTimeout` 초과) 잡만 되살리고
**`FAILED` 는 되살리지 않는다.** 그래서 `attempt_count` 가 1에서 멈춘다.

다만 **영영 잃지는 않는다** — 적재 쪽이 `!isStructured()` 면 다시 큐에 걸므로
(`SupportProgramIngestService`) 다음 수집에서 재시도된다. 같은 상한에 또 걸릴 뿐이다.

**당장의 우회는 `--max-structure` 를 낮추는 것**이고, 제대로 된 해결은 워커에 동시 실행
상한(세마포어)과 429 백오프를 넣는 것이다.

## 화면 개발용 샘플 — 수집기를 안 돌려도 된다

**프론트가 화면을 만들려고 이 수집기를 띄울 필요는 없다.** 기업마당 API 키·백엔드·
Postgres·AI 워커가 다 있어야 하고, 구조화는 공고당 약 $0.0066 씩 **실제로 돈이 나간다.**

`seed-sample.sql` 은 **Postgres 만 있으면 된다.**

```bash
docker exec -i jango-pg-local psql -U jango -d jango   -f - < tools/support-program-collector/seed-sample.sql
```

**LLM 호출 0회 · $0.** 여러 번 돌려도 안전하다(`uk_sp_source` upsert).

들어가는 것은 둘이다.

| | |
| --- | --- |
| **실데이터 3건** (`source_name = 'BIZINFO'`) | 2026-09-17 수집 + Haiku 구조화 결과 **그대로**. 셋 다 지급 시기가 비어 있는데 **그게 실측상 대부분의 경우다**(32건 중 1건만 적는다) |
| **합성 fixture 8건** (`source_name = 'SAMPLE'`) | 실데이터에 없는 경우를 채운다 — 전국·전 업종, 지급 시기 있음, 제출 서류 있음, 확인 필요 없음, 마감 임박, 마감됨, 금리 있는 융자, **구조화 안 된 것** |

`SAMPLE` 은 **실데이터가 아니다.** 기관명에 「샘플」을 붙여 화면에 실수로 떠도 바로
보이게 했다. **시연에 쓰지 마라.**

> ⚠ **Flyway 마이그레이션으로 옮기지 마라.** 운영 DB 에 샘플 공고가 들어가면
> **사장님에게 가짜 지원금이 보인다.** 손으로 부르는 파일로 둔 이유가 그것이다.

합성분만 지울 때:

```sql
DELETE FROM core.support_program WHERE source_name = 'SAMPLE';
```

## 알려진 함정

### 공식 문서와 실제 응답이 다르다 (2026-09-15 실호출 확인)

문서의 JSON 예시는 유효한 JSON 이 아니었는데(값에 따옴표가 없다), **실제 응답은 멀쩡한 JSON 이다.** 대신 구조와 필드가 다르다.

| | 문서 | 실제 |
| --- | --- | --- |
| 구조 | `jsonArray` 가 `item[]` 을 품은 객체 | **`jsonArray` 자체가 배열** |
| 식별자·제목·링크 | `seq` · `title` · `link` | **`pblancId` · `pblancNm` · `pblancUrl`** |
| 요약 | `description` (`<div>`) | **`bsnsSumryCn` (`<p>`)** |
| 신청기간 | `reqstDt` = `20220727 ~ 20220930` | **`reqstBeginEndDe` = `2026-09-14 ~ 2026-09-20`** |
| 해시태그 | `hashTags` | **`hashtags`** (소문자) |
| 문서에 없던 것 | — | `updtPnttm`(수정일자) · `pldirSportRealmMlsfcCodeNm`(중분류) |

문서 계열 이름은 **하나도 오지 않는다.** 수집기는 양쪽을 다 받지만 실제 이름을 먼저 본다. 전체 건수는 `totCnt` 로 온다 (2026-09-15 기준 **1,526건**).

### 출처가 주는 값은 모델에게 다시 뽑게 하지 않는다

- **`updtPnttm`(수정일자)** → `SUPPORT_PROGRAM.source_updated_at` (V25). 변경 감지의 근거
- **`reqstBeginEndDe`(신청기간)** → `application_start_date`/`end_date`. **구조화가 이 값을 덮지 않는다** — 출처가 적어 둔 것이 정본이고, 원문에서 다시 뽑게 하면 틀릴 자리를 하나 더 만드는 셈이다
- **`bsnsSumryCn`(사업개요)** → `raw_summary` (V24). 17.2 상세 화면의 요약

신청기간 형식이 둘이다 — 문서는 `20220727 ~ 20220930`, 실제는 `2026-09-14 ~ 2026-09-20`. 둘 다 받는다. **비어 있는 것도 정상이다**(상시모집).

수정일자는 **한국시간으로 읽는다.** 응답에 표준시 표시가 없어 UTC 로 읽으면 9시간이 밀리고, 그러면 안 바뀐 공고를 매일 다시 받는다.

**상세 본문을 자르는 지점이 중요하다.** 페이지 아래에 「이 공고를 열람한 사용자가 함께 본 공고」 블록이 있어서, 안 자르면 **다른 공고의 제목과 신청기간이 원문에 섞인다.** 모델은 그것을 이 공고의 내용으로 읽는다.

**지역 해시태그에 「광주」가 없다.** 기업마당은 전남과 광주를 「전남광주」 한 태그로 묶는다. 검색 쪽(17.1)이 지역을 가장 넓은 한 토막으로 줄여 이걸 흡수한다.

**`reqstDt` 는 `"20220727 ~ 20220930"` 문자열 한 덩어리이고 선택 항목이다.** 상시모집 공고는 비어서 온다.

03:00 인 이유는 공통규약 23장이 정한 값이고, 기업마당이 밤사이 갱신한 것을 아침 첫 화면이
보게 하려는 것이다. **예측 일배치(04:00)보다 앞에 둔다** — 공고가 먼저 들어와야 그날의
맞춤 추천(17.3)이 새 공고를 포함한다.

### 어디에 붙이나

**`tools/support-program-collector/run-daily.sh`** 를 crontab 이 부르면 된다.

```cron
PATH=/usr/local/bin:/usr/bin:/bin

0 3 * * * COLLECTOR_ENV_FILE=/opt/jango-yebo/secrets/jango-api.env           <미러>/tools/support-program-collector/run-daily.sh
```

**`infra/` 는 건드리지 않았다.** 배포 반영(`sync-infra.sh` 복사 목록)과 서버 crontab 등록은
인프라 담당 몫이다 — 여기 있는 것은 수집기를 감싸는 얇은 껍데기다.

> ⚠ **서버에 넘길 때 두 가지가 필요하다.**
>
> 1. **미러에 `tools/support-program-collector/` 가 내려와야 한다.** 지금 `sync-infra.sh` 는
>    `infra/` 만 갱신해서 수집기가 서버에 없거나 낡아 있다
> 2. **`~/app/secrets/jango-api.env` 에 두 줄** — `BIZINFO_API_KEY` 와
>    `COLLECTOR_API_BASE_URL`. 저장소 미러에는 시크릿이 없다

컨테이너로 두지 않은 이유는 **수집기의 npm 의존성이 0**(node 내장 모듈만 쓴다)이라 이미지를
하나 더 만들 값이 없어서다.

래퍼가 하는 일은 셋이다.

| | 왜 |
| --- | --- |
| **겹침 방지** (`flock`) | 첫 수집은 상세 페이지를 0.7초 간격으로 훑어 18분이 걸릴 수 있다. 겹치면 남의 서버를 두 배로 두드리고 구조화가 두 번 걸려 돈이 나간다 |
| **로그** | 시각을 붙여 `collect-programs.log` 에 남긴다 |
| **조용한 실패를 시끄럽게** | 아래 |

### 「0건」을 실패로 바꾼다

**이 수집기의 주된 고장 방식은 예외가 아니라 「0건」이다.** 인증키가 만료되거나 기업마당이
응답 형식을 바꾸면 목록이 빈 배열로 와서 `목록 0건` 을 찍고 **정상 종료한다** — 2026-09-15
에 실제로 겪었다(문서의 필드 이름이 실제 응답과 달랐다). 그대로 두면 아무도 모르는 채
공고가 며칠씩 안 들어온다.

래퍼가 그 경우 **1 로 끝낸다.** cron 메일이든 모니터링이든 거기에 걸면 된다.

`flock` 이 없을 때도 마찬가지다 — 겹침을 막을 수 없으면 **돌리지 않고 1 로 끝낸다.**
(초안에서는 이걸 「이미 돌고 있다」와 구분하지 않아 매일 조용히 건너뛸 뻔했고, 테스트가
잡았다.)

⚠ **cron 의 `PATH` 는 보통 `/usr/bin:/bin` 뿐이다.** `which node` 가 그 밖이면
(nvm·`/usr/local/bin`) cron 에서만 「node: command not found」로 매일 실패한다 —
crontab 위에 `PATH=` 한 줄을 깔면 된다.
